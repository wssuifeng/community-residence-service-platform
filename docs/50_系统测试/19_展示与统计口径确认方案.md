# 展示、统计与看房权限：现状、已修和待确认方案

> 本文只讨论当前需要核对的问题，不汇总全项目待办。测试仍在50步骤7/8；统计含义的调整须经用户确认，不能用测试通过替代规则裁决。

## 1. 服务人员看工单提交人：不再推测称谓和居住身份

**现状**：WorkOrderVO提供residentName，但没有性别，也没有与该工单明确关联的唯一居住关系。原前端`staffPlaceholder.ts`按工单ID取模生成“先生/女士”和“业主/租客/家属”。同一个居民不同工单可能被显示成不同性别和身份。

**本轮修复**：工作台、列表、详情共用`staffResidentPresentation.ts`；显示后端真实姓名，缺名显示“居民”，头像取姓名首字。旁边中性“居民”表示提交人角色，**不表示租客/业主关系**。不新增性别字段、不解析姓名、不向服务人员开放全居民资料接口。

**建议**：保持这个最小设计即可，无需决定额外性别模型。如果以后确实需要显示居住关系，应先让工单明确绑定服务房屋/关系，再由后端输出对应关系；居民可能有多条关系，不能直接任选其一。本轮不实施新关联模型。

## 2. 改派与趋势：先让当前看板真实，再确定事件统计

**实际有两套逻辑，不应混称一个问题**：

- 前端工作台的四条小曲线和25%/-40%/33%/50%原来是MOCK固定值，与任何接口无关；“今日完成”读取COMPLETED列表的total，没有日期条件。
- 后端`GET /statistics/staff/trend`确实存在，前端工作台未接它。它按“本人曾被派过”的工单集合聚合，日期用工单created_at；TO_CONFIRM/COMPLETED/CLOSED均算完成。改派给别人后，旧人员也可能计入新人员完成的工单。不是前端硬编码，也不等于当前派单权限。

**本轮最小修复**：删除MOCK曲线和百分比，不把任意趋势接口硬接进四张含义不同的卡片；显示“趋势待明确”。真实COMPLETED卡片更名“已完成（未关闭）”，不再冒称今日。待接单/处理中/紧急待接单继续取后端列表total，环图标为工单进度，不冒称今日进度。

### 推荐口径（待你确认，尚未实施）

| 区域 | 归属与日期 | 改派效果 |
|---|---|---|
| 当前待接单／处理中／紧急待接单 | 按**最新有效派单人**及当前状态，和本人工作列表同源 | 旧人员立即移出，新人员立即移入 |
| 今日提交结果 | 按处理时间线中提交处理结果的实际操作者与操作日期；不是工单创建日期，也不是居民确认日期 | 只归实际提交结果者；之后改派不抹掉真实动作 |
| 近7日派入量 | 派单记录的接收人员与派单发生日期；每次真实改派是新派入事件 | 旧人员保留真实历史派入，新人员有新派入；标签明确“派入次数”，不能叫去重工单数 |
| 当前负荷趋势／增长百分比 | 若没有逐日快照，就暂不展示，不用当前状态反推过去负荷 | 不造历史负荷；此类快照本轮不新增 |

**为什么推荐**：把“现在负责什么”和“过去做过什么”分开，可解释改派，不把别人完成的工单归给旧人员，也不把重派次数冒充工单数。现有staffTrend字段结构、TO_CONFIRM算完成的口径和前端卡片含义均需设计修订后再变；本轮只补现行行为单测以暴露差异，不据此认可现行统计定义。

**备选（更小）**：仅改后端staffTrend为最新派单归属，仍按created_at归日。工程小，但显示的是“现在名下按创建日分布”，不是服务业绩趋势；若采用，必须改标题，不能继续叫当天完成。

**需要你确认的只有这一项**：是否采纳上述“当前负荷按最新派单，历史动作按实际操作人/发生日，暂无快照就不展示负荷趋势”的口径？

## 3. 评价列表：失败与空态必须可区分

**现状**：列表请求失败只弹消息，空records继续渲染“暂无评价”；跟进详情请求失败被当成0条，误列待跟进；统计失败也呈现“暂无评价”。

**本轮修复**：

- 列表失败显示固定错误区及“重新加载”，不渲染空态；成功且零条才显示暂无评价。
- 统计失败独立显示“评价统计加载失败／重试统计”，不伪造数量为零。
- 跟进读取失败不归零、不显示发起跟进按钮；显示“跟进状态加载失败／重试跟进状态”，工作台失败显示错误区，不误分组。
- 保持现有评价分值、满意度、跟进权限和接口，不新增业务字段。只补UI状态和异常处理。

**后续建议**：数据量增长时由后端提供跟进状态过滤，取代当前最多20页不满意评价加逐条读跟进；这是后续设计项，本轮不擅自扩接口。当前真实空态、失败、原地重试、跟进失败分别由组件单测与隔离浏览器验证，证据见08。

## 4. 看房登记完成：冻结设计的权限口径冲突（补充现场）

**现有设计和代码**：UI设计中的`/staff/viewings`路由表及按钮权限表明确“看房登记完成：STAFF，限被分配人”。接口设计§9.12.2.5和运行Controller则仅允许ADMIN/SUPER_ADMIN；界面上“登记完成”实际返回403。页面同时展示“标记违约”，但接口设计§9.12.2.7仅允许管理员。本轮真实点击复现；没有擅自修改后端权限或冻结的30包。

**推荐方案**：服务人员只对分配给本人的RESERVED看房预约登记完成；服务层再次检查assigned_staff_id及角色，其他服务人员、居民、游客均拒绝；管理员仍按社区范围登记完成。**违约及账号冻结仍由管理端处置**，服务人员页移除违约处置按钮，保留沟通入口。这样带看执行和管理处置职责分开，不把STAFF扩成社区管理员，不给取消/确认权限。

**备选**：所有登记均只允许管理端；服务人员页取消完成/违约按钮，显示“请联系管理员登记”。改动小，但需修订冻结UI设计，服务人员不能直接登记自己带看的结果。

**需你确认**：是否采用推荐方案——“被分配人员可登记完成，违约由管理员处理”？确认后先按纪律对齐30接口/UI设计并留决策，再修权限和按钮，不能只改Controller角色白名单。当前仅完成冲突定位与现行拒绝回归，不将这条跨端带看完成链判通过。
