# 四段房屋业务编号与居民导入：批准设计

> 仅处理用户2026-10-14提出的编号与填表问题。用户2026-10-14确认并修订：四段强制、查看业务编号、不支持数据导出。实际执行及确认记录只写50中控。

## 1. 修正前的问题

修正前房屋已有`house_number`，如101；自增的`house.id`是内部关联主键，两者不是一回事。社区只有名称，楼栋/单元只有名称，没有独立的业务编号属性。旧居民CSV让用户填写社区ID和房屋ID；下载的“位置与ID对照”不是居民数据导出，也不能直接当作预填模板。当前没有居民导出接口。

依据：Community/Building/Unit/House实体、ResidentService.parseResidentRow、ResidentImportDialog、30数据库§3.1与50/18。

## 2. 已批准规则

**保留所有数据库主键，增加独立位置编号；不重编号或删除已有业务数据。**

| 数据 | 编号规则 |
|---|---|
| 社区编号 | 系统内唯一、可读的业务编号，不把数据库ID当作永久业务规则 |
| 楼栋号 | 同社区内唯一，独立于展示名称；如“1号楼”的楼栋号为1 |
| 单元号 | 同楼栋内唯一，独立于展示名称；如“1单元”的单元号为1 |
| 房屋号 | 继续使用同单元内唯一的house_number，如101，不用house.id代替 |
| 完整房屋编号 | 社区编号-楼栋号-单元号-房屋号，例如5-1-1-101 |

编号分段按文本保存，保留前导零；每段不能为空；前三级不能含分隔符，不能靠截取任意名称猜位置。按分段的自然顺序排序，不按房屋主键排序。已有数据只新增编号，不改变名称或主键：社区首次按既有记录顺序分配独立编号；楼栋/单元名称为标准数字且本父级不重复时保留该数字，否则分别分配B/U前缀编号。非标准名称不会截取猜数字。管理员可核对修改本级编号。

**房屋业务编号强制四段。** `5-1-101`三段无效，即使只有一个单元也不能省略。

位置编号变化后内部主键不变，历史关系和租约仍关联同一房屋；修改走原操作留痕入口。导入前以当前查看表为准；不存在的编号逐行拒绝，不按三段、名称近似或主键猜测。房号原含“-”或“%”时，该段分别显示为%2D/%25，复制完整编号仍精确对应原房号。

不采用两种替代方式：继续填自增ID只改善排序，未解决可读性；把组合编号替换数据库主键会破坏现有外键与租住历史。

## 3. 用户怎么操作

1. 管理端进入「居民管理 → 批量导入」，选择操作社区，点击“查看结构业务编号”。
2. 表格显示社区、楼栋、单元编号和完整四段房屋编号，按结构自然排序；不再下载ID对照，不提供数据导出。
3. 下载空白/合成账号示例导入模板，复制所需房屋编号；同一户多人使用相同完整编号，分别填写账号资料。
4. 常用填写项仅姓名、手机号、关系类型、入住日期；证件、用户名、邮箱、备注选填。上传后精确解析唯一房屋和社区，执行权限及关系校验。

推荐新版机器表头：`房屋编号,姓名,手机号,证件号,用户名,邮箱,关系类型,入住日期,备注`。位置说明用模板说明页/表格展示，不加入需要手填的ID列。仅建账号可不填房屋编号，使用上传窗口选定的社区作为操作范围；注册账号本身仍不等于居住关系。

用户填写的文件里仅有房屋编号、居民输入全部留空的行明确计为未填写，不建账号也不当成失败；半填居民信息的行仍按规则失败，不能静默跳过。

旧四列、旧十列CSV继续兼容，不让用户已有文件突然失效。逻辑编号不可解析/不存在/有歧义时逐行失败；同住行遵循20的有效主关系规则，不绕过待签约或未付首期保护。

## 4. 查看结构业务编号，不支持数据导出

原查看ID功能改为查看社区、楼栋、单元业务编号和完整房屋业务编号；按结构自然排序读齐所有分页，不显示内部主键作为用户填写依据。移除“下载房屋位置与ID对照”，不新增居民台账导出、房屋数据导出或.xlsx导出。仅保留空白/合成示例的导入模板下载，不输出现有居民个人资料。

## 5. 验证重点

保留主键和历史；多单元歧义明确失败；有前导零的编号不丢失；全分页与排序正确；跨社区拒绝；旧文件兼容；同户多人不重复建账号或租约；编号对照与筛选范围一致；界面没有数据导出入口。
