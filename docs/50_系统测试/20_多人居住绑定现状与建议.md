# 一户多人：现有绑定方式与建议

## 现在实际是什么

**没有“一个主账号挂多个附属账号”的模型。** 每个人都是独立居民账号，房屋信息通过居住关系关联，不直接存在账号表中。

| 数据 | 当前内容 |
|---|---|
| resident | 用户名、姓名、手机号、证件、邮箱、账号状态等，不存父账号ID或房屋归属 |
| residence_relation | resident_id、community_id、house_id、relation_type（OWNER/TENANT/FAMILY）、入住/迁出日期、is_primary、lease_id等 |
| is_primary | 关系标记，不是“此账号属于某个主账号”的外键；现有直录入口写1 |
| 租客关系 | 租赁协议确认且首期支付成功后建立正式关系，并关联租约 |

注册只建立账号；管理员代建/CSV可选同时直录具体关系；未录关系的账号没有在住信息。表结构能保存不同居民指向同一房屋，但**当前服务规则不允许向已入住房屋直接补另一名住户**：直录仅限空置房，同时检查在住关系及待处理申请/租约。入住申请审批也不能绕过已有占用。故已入住租客的家属不是当前“创建一个FAMILY账号就能自动绑定”的功能。

事实来源：`ResidenceRelationService.adminCreate`、`ResidenceApplicationService`、`ResidenceRelation`及30接口§9.2.4.5。管理员/服务人员账号由超级管理员创建，居民账号由注册、管理员代建或CSV导入创建。

## 建议怎么做（本批不实施，待你确认）

**继续使用“独立账号＋同一房屋的多条居住关系”，不另造附属账号和密码共享。**

1. 在现有居住关系详情增加“登记同住人员”；当前社区管理员选择已存在居民，或代建账号后继续登记。
2. 同住关系用FAMILY，关联该房屋当前主关系；主关系必须仍有效、双方社区范围一致。同住成员不生成第二份承租租约，也不继承租金/押金/支付义务。
3. 每个成员独立登录和接收本人通知，账号不是由主住户控制的子账号。迁出单人只结束本人关系；主关系迁出时，列出仍在住成员供管理员一起核对，不隐式留下占用或删除账号。

推荐先只做管理员审核登记，不开放居民随意拉人入住。待明确FAMILY是否作为所有共同居住人的统一标签，以及主关系结束时的确认方式后，再单独修订30并实施。**本批修复不把这个建议当成已经存在的能力。**
