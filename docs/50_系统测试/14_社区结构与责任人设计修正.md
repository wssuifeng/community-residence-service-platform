# 社区结构与责任人设计修正

> 日期：2026-10-11。用户已批准实施的功能设计；执行与验证状态以本阶段中控为准。
> 仅包含：所属楼栋楼层边界、户型替代房间数、社区责任人账号绑定。

## 1. 楼层：以每栋楼的属性为边界

### 1.1 数据含义

- `building.floors`：**这一栋楼实际有多少层**，由管理方录入和修改。
- `house.floor`：该房屋所在楼层。
- 房屋经所属单元关联楼栋；校验使用这栋楼当前的 `floors`，不得使用系统统一的楼层上限。

规则只有：

```text
楼栋层数：正整数，不设置99层、200层等固定业务上限。
房屋楼层：1 <= house.floor <= 所属楼栋的 building.floors。
```

整数类型的可表示范围不是建筑层数的业务限制；1000层可以正常登记。

### 1.2 操作规则

| 操作 | 设计 |
|---|---|
| 新建、编辑楼栋 | 可填写1000等层数，不再使用固定200层校验。 |
| 新建、编辑房屋 | 从所属单元查询实际楼栋，以楼栋当前层数校验；超层拒绝保存。 |
| 在已有楼栋下批量建房 | 起止楼层均须落在该楼栋的层数内；预览、执行与单建使用同一规则。 |
| 生成新楼栋及其房屋 | 明确每栋楼的总层数，再在该范围内生成房屋；生成房屋的范围不反向扩充已有楼栋属性。 |
| 增加楼栋层数 | 修改保存后，才允许在新增楼层录入房屋。 |
| 减少楼栋层数 | 若有未删除房屋位于新上限之外，拒绝修改，并提示最高楼层和处理指引；先处理这些房屋，再降低层数。 |

前端楼栋层数输入不设固定业务最大值；房屋楼层输入的最大值随所属楼栋变化。界面提示示例：**“该楼栋共6层，可录入楼层为1～6层。”**

所有后端写入口共用楼栋边界校验。建房与修改楼栋层数对同一楼栋串行处理，避免并发降低层数后写入超层房屋；不能仅靠前端限制。

批量接口已有的单次房屋数量限制用于控制请求规模，**不是楼栋层数限制**：1000层楼栋可分批录入，不能因此被拒绝登记。逐行批量建房保留现有部分成功规则，超层行失败且不写入；范围式生成在预览与执行前拒绝不合法的楼层计划。

### 1.3 行为示例

| 楼栋属性与操作 | 结果 |
|---|---|
| 楼栋6层，创建第6层房屋 | 允许。 |
| 楼栋6层，创建第9层房屋 | 拒绝；不能在不存在的楼层录入房屋。 |
| 先将该楼栋改为9层，再创建第9层房屋 | 允许。 |
| 楼栋1000层，创建第1000层房屋 | 允许。 |
| 楼栋1000层，创建第1001层房屋 | 拒绝；须先修改该楼栋层数。 |

历史超层测试数据按用户授权清理，不为异常旧数据增加兼容逻辑。本文只规定清理边界，不在文档编写时执行删除。

## 2. 户型：删除房间数，只保留布局描述

### 2.1 数据调整

| 属性 | 设计 |
|---|---|
| `house.room_count` / `roomCount` | **删除**：数据库、后端实体、请求/返回字段、前端类型和表单一并移除，不是只隐藏输入框。 |
| `house.layout` | 保留为真实房屋的户型描述，例如“三室一厅一卫”；沿用现有字符串字段。 |
| `housing.layout` | 挂牌户型必须与关联房屋的 `house.layout` 一致，不作为独立可编辑属性。 |

不将“室、厅、卫”合并成一个房间数，不解析描述反推数值，也不新增卧室数、客厅数、卫生间数等拆分属性。

实施采用新增数据库迁移移除旧列，不修改已经执行的历史迁移。原房间数不转换为户型；户型仍以管理方录入的真实描述为准。

### 2.2 单建与批量生成

- 单建、编辑房屋仅填写“户型”，删除“房间数”输入。
- 所有结构生成、建单元带建房、批量建房入口统一提供“本批户型”。
- 该批实际生成的每套房屋使用表单填写的同一户型，不根据房号、楼层或旧房间数猜测。
- 生成预览显示本批户型，提交结果与预览一致。
- 挂牌时读取真实房屋户型；房屋户型变更时同步关联挂牌的户型，展示与户型筛选保持一致。既有挂牌不留另一份可自行修改的户型。
- 户型为空时显示“未填写”，不得伪造描述；保留现有字段非必填口径，不引入额外资料录入要求。

### 2.3 社区结构卡片多选配置

复用现有卡片多选与框选，增加“配置户型”操作：

1. 选中多套房屋后，右键已选卡片，操作范围保持为当前选中的房屋。
2. 右键未选卡片时，仅将该卡片作为操作对象，避免误改原选区。
3. 菜单显示“配置所选N套房屋户型”；选中操作条也提供同一入口。
4. 弹窗显示选中数量、房屋范围、现有户型以及“新户型”。原值不同则显示“多个不同户型”。
5. 确认后，仅修改明确选中的房屋及其关联挂牌；取消弹窗不写入。
6. 保存前校验全部选中房屋的权限和存在性；一项不合法则本次户型修改整体拒绝，不产生只改了一部分却提示全部成功的结果。
7. 切换社区、楼栋或筛选范围时沿用现有清空选区规则，不修改不可见的旧选区。

## 3. 社区责任人：绑定管理员账号

### 3.1 数据模型

社区新增：

| 数据库字段 | 接口字段 | 含义 |
|---|---|---|
| `responsible_admin_id` | `responsibleAdminId` | 责任人的系统账号ID，关联 `sys_user.id`。 |

- 责任人就是社区联系人，不再维护一份独立、可手填的联系人资料。
- 社区返回的联系人姓名、电话从绑定账号实时读取；修改账号姓名或电话后，社区展示随之变化。
- 责任人选择沿用原联系人非必填口径：未设置时保存空值并显示“未设置”。非空ID必须通过下述校验，不能接受悬空或错误角色账号。
- 现有自由文本姓名、电话不再作为数据来源，也不根据同名或手机号自动猜测绑定账号。

### 3.2 绑定校验

服务端必须确认：

```text
responsibleAdminId非空时：账号存在，并且 role == ADMIN。
```

| 选择对象 | 结果 |
|---|---|
| 已绑定本社区的管理员 | 可选，优先展示。 |
| 系统内其他社区或尚未绑定社区的管理员 | 可选。 |
| 超级管理员（SUPER_ADMIN） | 拒绝。 |
| 服务人员（STAFF）、居民账号、不存在的账号 | 拒绝。 |

候选查询、提交保存均执行角色校验，不能只在前端筛选。社区创建、编辑沿用原权限规则；**选择责任人不自动建立管理员与社区的权限绑定**。

### 3.3 管理交互

- 社区表单使用可搜索的“社区责任人”账号选择框，删除手填联系人姓名、电话的入口。
- 候选分为“已绑定本社区”与“其他管理员”（候选结果尚未覆盖的当前值单独作为“当前责任人”回显，不猜测权限绑定），本社区候选优先；选项显示姓名及必要的区分信息。
- 选中后显示账号姓名和联系电话，只读，不在社区表单修改账号资料。
- 专用候选查询只返回责任人选择所需信息，不为此向普通管理员开放完整系统用户管理。
- 社区列表、详情显示同一账号的实时姓名和联系电话；不维护两套联系人信息。

## 4. 本次设计变更摘要

| 对象 | 变更 |
|---|---|
| 楼栋 | 去掉固定层数业务上限；每栋楼的 `floors` 成为自身房屋的真实楼层边界。 |
| 房屋 | 删除房间数；所有写入口按所属楼栋校验楼层，保留真实户型描述。 |
| 批量结构及卡片 | 使用表单户型生成房屋；多选右键配置户型并同步挂牌。 |
| 社区 | 新增责任人账号ID，服务端校验ADMIN角色，联系人资料随账号同步。 |

用户已于2026-10-11批准实施，相关需求、数据库、接口和UI设计已定向对齐。本文定义功能契约；测试证据见08§3.77，执行状态只以本阶段中控为准。

## 5. 完整功能闭环与实施契约

| 功能入口 | 请求与业务处理 | 页面结果 |
|---|---|---|
| 社区新建/编辑 | POST communities、PUT communities/{id}提交responsibleAdminId；非空校验ADMIN；null实际解除引用 | 返回账号派生姓名/电话，联系人不独立编辑 |
| 搜索责任人 | GET communities/responsible-admins按communityId/page/size/keyword查询，限管理员；本社区绑定者优先 | 保留当前选中值，旧搜索结果不覆盖新搜索；只读联系电话 |
| 楼栋维护 | POST/PUT buildings，层数为正整数；编辑降层锁楼栋并锁定读现有最高房屋 | 超层冲突明确提示，不静默删除房屋 |
| 单屋维护 | POST/PUT houses按所属单元定位真实楼栋并加锁校验 | 不出现房间数；创建和编辑都能录户型，编辑同步挂牌 |
| 结构生成/批量建房 | 结构生成载荷包含layout；已有楼栋的范围先预检，后端逐行楼层检查 | 显示生成户型与逐行失败；不存在楼层不能落库 |
| 卡片多选户型 | PATCH houses/layout提交明确houseIds/layout，全选区鉴权、加锁并原子更新两表 | 成功回传数量，逐个刷新受影响单元，失败不关闭/不显示成功 |

数据迁移为V31：移除house.room_count，community新增responsible_admin_id外键，并移除旧联系人文本列；Entity中的联系人名称保留为不映射数据库的派生展示属性。接口不存在roomCount输入/输出；null引用必须显式写入，不能被ORM的跳过null策略吞掉。全部实现仍挂靠既有C1，挂牌同步属C1/C12关联一致性，不另起功能域。


### 5.1 可直接操作的完整流程

**社区结构维护**：管理端「社区管理 → 社区结构」选择社区 → 创建/编辑楼栋总层数 → 创建单元 → 单建或批量建房。前端根据目标楼栋更新楼层输入上限；后端不信任前端表单，从单元归属查询当前楼栋并锁定校验。降层与建房共用父楼栋锁，防止两个同时操作留下虚空层。批量建房延续逐行结果，一条超层不写入，其他有效行正常生成；一次结构链生成保留既有数量门槛，不将数量门槛解释为层数上限。

**户型维护与挂牌联动**：单屋创建/编辑录入真实户型；结构生成填写本批户型，预览与实际房屋均使用它。卡片Ctrl/Cmd多选或框选 → 右键已选卡片/操作条「配置户型」→ 查看数量、范围和旧户型差异 → 填新户型或留空清除 → 保存。服务端先校验完整选区，再统一锁定、同事务更新房屋及关联挂牌；任一非法ID拒绝整批。保存失败保留弹窗与输入，不发成功刷新；成功返回不同房屋的数量，依次刷新所有受影响单元。挂牌单建、批量挂牌也锁定房屋并使用最新户型，不用锁前快照制造第二个户型来源。

**责任人维护**：超管创建社区，超管/绑定社区管理员编辑社区 → 搜索ADMIN账号 → 本社区已绑定者优先，也能选其他ADMIN → 只读查看电话 → 保存账号ID。未设置或清空时显示未设置，null明确落库。修改管理员账号姓名/电话后，下一次社区读取直接派生新资料。账号仍被引用为责任人时不能改为非ADMIN；先更换或解除责任人。选择跨社区账号不会把管理权限自动带过来，管理范围仍由既有权限绑定维护。

### 5.2 请求、响应与失败态

| 写操作 | 输入/成功结果 | 失败时的系统行为 |
|---|---|---|
| 楼栋维护 | floors为正整数，返回保存后的楼栋 | 超层降层拒绝，楼栋属性不变；不自动删房 |
| 单屋维护 | unitId/floor/layout等既有字段；不接受或返回roomCount | 超出所属楼栋范围拒绝；单屋更新与挂牌同步同事务 |
| 批量建房 | 每行floor/layout，返回逐行成功/失败明细 | 无效行不入库，不把部分成功提示成全部成功 |
| 多选户型 | `{houseIds:[...],layout:"三室一厅一卫"}`，返回修改房屋数 | 空选区、过长户型、不存在或越权房屋拒绝整批；取消不调用写接口 |
| 社区责任人 | responsibleAdminId为有效ADMIN ID或null，返回ID与派生contactPerson/contactPhone | 不存在/非ADMIN拒绝；加载候选失败可重新搜索，旧响应不覆盖新搜索或已关闭的表单 |

责任人候选分页最多100条/页，远程关键字搜索可继续查找；当前已选择但不在本页的责任人保留回显。候选只暴露选择所需的账号ID、姓名、电话和绑定标识，不返回密码/角色管理接口。新增专用接口不改变既有管理员创建权限：系统管理员/服务人员账号由超级管理员通过系统用户管理创建。

### 5.3 数据迁移与可复验判据

- V31新增责任人外键，删除旧联系人文本列及房间数列，不改已执行迁移；不按同名/同电话猜测责任人，不把旧房间数转换成户型。
- 旧异常测试房屋按用户授权先备份、再定向清理关联测试记录；正常社区/楼栋/单元/房屋和账号不整体清空。此清理不是租约状态业务流转，也不发渠道交易指令。
- 验证判据：6层拒绝9层；先改9层后成功；1000层可登记/1001层拒绝；并发建房和降层不遗留超层数据；批量户型失败不部分写入/清空同步；ADMIN角色与范围校验、资料同步及真实解绑；真实右键多选→保存→房屋和挂牌一致，1024/768下页面不横向溢出。
- 本批只覆盖以上三个功能闭环；不包含居民批量居住关系、入住申请生命周期、图片上传或交易恢复。
