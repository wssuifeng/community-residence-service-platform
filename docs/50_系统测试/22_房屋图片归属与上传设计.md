# 房屋图片归属与上传设计

## 修正前现状（保留问题依据）

- 当前图片字段是 `housing.images`，归属于挂牌；`house` 没有图片字段或图片关联表。
- 管理端卡片读取后端挂牌图片，**没有图片时使用前端占位图片（housing-placeholder.png）**。这不是已配置的实拍图；批量挂牌也没有生成真实图片。当前挂牌编辑回显/保存已有图片字符串，但缺少完整上传管理交互。
- 同一实体房屋换挂牌时，图片可能重复维护或不一致。因此建议按你提出的方向，把图片管理落在房屋，不落在挂牌。

代码依据：`House`、`Housing.images`、`HousingService.applyDto`、`HousesWithHousingView`；不以示意图代替真实图片配置。

## 推荐设计：房屋相册，挂牌只读取

采用独立 `house_image` 表，而不是再给挂牌加一份副本。

| 属性 | 含义 |
|---|---|
| id / house_id | 图片记录与真实房屋引用，内部主键不改变 |
| storage_key | 服务器生成的存储引用，前端不能提交任意公网URL |
| kind | 实拍图 / 户型平面图；不从户型描述推算房间数 |
| caption / sort_order | 简短说明及顺序；第一张实拍图作为封面，只有平面图时使用第一张 |
| uploaded_by / created_at | 上传人及时间，便于管理留痕 |

列表采用封面缩略图与懒加载，详情才读取大图；上传需验证真实图片内容、尺寸和大小，不仅判断文件扩展名。

最多10张，沿用已有图片上传校验：JPG/JPEG/PNG/GIF，每张不超过5MB；不在此轮偷偷增加WEBP等未经后端支持的类型。

### 管理端交互

1. 社区结构的单屋操作及“房屋与房源”卡片都提供 **管理房屋图片**，打开同一个相册弹窗。相册不是多选房屋属性的一部分，避免误把同一照片批量附给不同房屋。
2. 从本地选择文件上传；缩略图展示上传中/失败/成功。上传失败可重试，不能把本地预览误报为已保存。
3. 每张可选择类型、写说明、调整顺序、设置封面、删除；设置封面即将选中的实拍图置于实拍图首位，无实拍图时按平面图顺序取封面。删除须确认，无URL输入框。
4. 已保存图片刷新后仍在。无图明确显示 **尚未上传房屋图片**，占位图只能作为空态，不伪装房屋实拍。

### 保存与权限

- 使用房屋专属上传接口，例如 `POST /houses/{id}/images`（本轮源码已实现，正常库尚未升级），上传与该房屋关联一起完成；顺序/说明单独更新，不依赖整份房屋表单覆盖。
- 仅超管和管辖该社区的管理员可写；后端核对房屋归属、文件类型/大小和存储位置，不能挪用其他业务附件。
- 公开挂牌仅返回本房屋相册；居民私有租约上下文仍按参与者与租约来源权限读取。房屋相册变更不修改协议正文、租期或居住关系。
- 图片记录解除关联与文件清理分开，存在其他有效引用的文件不能误删。新增功能不借机清空现有资料。

## 历史图片迁移

先只读列出每个房屋的旧挂牌图片。相同文件去重；来源不明或多挂牌图片冲突的房屋列出待核对，不按“最新挂牌”猜测。未经确认不删除旧字段或图片；过渡读路径只允许一处后端适配，前端不混合两套来源。确认迁移后再决定旧字段退役。

## 实施结果（2026-10-15 bu）
V39、HouseImageService与受权限保护的专属接口、两处共用HouseImageDialog已落地。公开/管理分页相册按页批量读取，不新增逐行相册查询；实拍优先封面，删除仅解除关联。基础回归覆盖跨社区、10张上限、完整顺序防偷图/重复、切房请求竞态、初次打开与错误空态。

正常库只读盘点：15条挂牌、旧images非空0条、对应房屋0套；因此没有需要猜测归属的旧图，不执行旧图迁移，不删除旧字段。证据见evidence/bu-implementation-20261015/database-readonly-inventory.json。正常库仍V38，真实上传/多分辨率用户复验须在升级服务后进行；本轮未声称浏览器验证通过。

补充交叉入口核对：旧管理房源列表/详情同样复用HouseImageDialog，去除URL输入和旧images副本写入。游客首页/列表/详情、居民列表/详情/申请、旧管理列表/详情共8入口统一明确“尚未上传房屋图片”空态，不再使用示例实拍。新增源码守卫防止旧兜底和URL入口回归；未声称已在浏览器执行视觉验证。
