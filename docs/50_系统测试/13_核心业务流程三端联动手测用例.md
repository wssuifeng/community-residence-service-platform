# 核心业务流程三端联动手测用例（E1~E13 + E10b）

> **本文件是什么**：**跨端交替操作**的完整业务闭环手测用例集——一条业务从居民端发起，
> 经管理端审核 / 派单、服务人员端执行，再回到居民端确认，**验的是「编码是否符合 30 系统设计」**。
> **与 `12_用户手测清单.md` 的分工（先读这条再决定用哪个）**：**单点核对用 12 号**
> （U-01~U-34，逐条验某个页面 / 某个接口 / 某条规则按设计做对了没有）；
> **完整闭环用 13 号**（本文件，跨端交替操作的端到端链路）。
>
> **阶段职责边界（2026-09-21 用户裁决，必须遵守）**：本文件**只判「编码是否符合 30 系统设计」**
> （**设计符合性**——设计写「已到期不得支付首期」，就验它是否真的拒绝；设计写「越权 100% 拒绝」，
> 就验是否真被拒）。**「功能是否满足 20 需求 / 好不好用」由 `60_评估验收` 判定，
> 不在本文件作为通过 / 不通过判据**；执行中观察到需求满足性 / 体验类现象，
> **只记录**并标注「**需求满足性 → 60 评估验收**」，**不判通过与否**。
>
> **执行中若发现「文档如此写、实现非如此」** → 按 `docs/50_系统测试/08_缺陷跟踪与回归.md`
> 登记 **DEF**（附端点 / 状态 / 错误码 / 日志），并在本文 **§1.3 记录表**填「**不通过 + 缺陷号**」。
>
> **权威依据（纪律 8）**：`docs/20_需求分析/需求规格说明.md`（端到端流程 **E1~E12 + E10b**；
> 当前 **v1.12**，需求 **R1~R75**）+ `docs/30_系统设计/接口设计.md`（**v1.7**）+
> `docs/30_系统设计/UI设计.md`（**v1.5**）+ `docs/30_系统设计/架构设计.md` §6（六大状态机）。
> **状态名 / 错误码 / 端点路径一律以 20 / 30 包当前版本为准**；不确定处标「**待核**」，不猜。

### CF-E1 社区初始化与结构配置（E1 · C1）

**流程目标**：超管从零搭建一个社区的四级结构（社区 → 楼栋 → 单元 → 房屋）与公共资源，
并核对结构在居民端 / 游客端的可见性；**验结构链的创建、批量生成、删除保护与留痕是否符合设计**。
**涉及端与角色**：超管 `superadmin`（全局级：建 / 停用 / 级联删除社区）+ 社区管理员 `admin1`（绑定社区内的结构与资源维护）。

| # | 端 · 账号 | 操作 | 预期 |
|---|-----------|------|------|
| 1 | 管理端 · `superadmin` | 「社区管理」→ 新建社区：填名称、地址、联系方式、简介 → 保存 | 社区创建成功并出现在列表（状态「运营中」）；写操作日志；**社区新建 / 停用 / 删除仅超管可执行** |
| 2 | 管理端 · `admin1` | 用 `admin1` 尝试**新建 / 停用 / 删除社区**（全局级动作） | **100% 被拒**（全局级仅超管）并**记录越权日志**；列表不出现删除入口 |
| 3 | 管理端 · `superadmin` | 在该社区下新建楼栋（编号、名称、层数、备注） | 楼栋创建成功、挂在社区下；被下级或业务数据引用的楼栋**禁止删除**（仅可停用），返回明确错误 |
| 4 | 管理端 · `admin1` | 在**绑定社区**下新建单元（楼栋下） | 单元创建成功；被引用的单元禁止删除（仅可停用） |
| 5 | 管理端 · `admin1` | 在单元下新建房屋：房号、面积、户型、朝向；状态**初始为空置** | 房屋创建成功、初始状态「**空置**」（`VACANT`）；**同一单元内房号唯一**（重复房号被拒）；房屋状态变更留记录（操作人 / 时间 / 原因） |
| 6 | 管理端 · `admin1` | 「社区管理」→ 用**结构链一次性批量生成**（楼栋 → 单元 → 房屋），先 `dryRun` 预览再正式生成 | 预览与实际生成条数一致；批量生成后楼栋 / 单元 / 房屋三层按命名规则正确落地、无孤儿节点；一次成多栋 / 多单元 / 多房号 |
| 7 | 管理端 · `admin1` | 对新建房屋尝试**删除**（或对含下级节点的楼栋 / 单元删除） | **已被下级节点或业务数据引用的楼栋 / 单元 / 房屋禁止物理删除**，仅可停用；返回明确错误且**数据不变** |
| 8 | 管理端 · `admin1` | 配置**公共资源**（名称、类型、位置、容量、介绍）并配置**是否开放预约**与可预约时段 | 资源创建成功；可预约时段可配置；**存在未完成预约的资源 / 时段禁止删除**；时段重叠被拒（`TIMESLOT_CONFLICT(5107)`） |
| 9 | 管理端 · `superadmin` | 另建一个测试社区走**级联删除**（二次确认） | 社区及其下级结构（楼栋 / 单元 / 房屋 / 公共资源 / 房源）与关联业务数据一并删除；**无孤儿残留**；删除全量留痕 |
| 10 | 居民端 · `resident1` + 游客端（隐身窗口 D） | 打开居民端「租住与房源 → 房源信息」与游客端 `/guest` 房源列表，按社区 / 楼栋 / 单元 / 状态筛选 | 新建社区的结构与房源按**全社区开放**口径可见、筛选结果准确；**未配置开放的私有数据对无关系账号一律拒绝** |
| 11 | 管理端 · `superadmin` | 「系统 → 操作日志」核对上述创建 / 变更 / 删除动作 | 关键数据变更**均写入操作日志**（操作人 / 时间 / 对象 / 内容），日志**仅追加不可修改** |

**通过判据**：社区四级结构可建、可批量生成、可停用，**被引用的楼栋 / 单元 / 房屋 / 资源禁止物理删除**；
社区级联删除后**无孤儿记录**；公共资源与可预约时段 CRUD 与冲突校验符合设计；
全局级动作仅超管可执行（社区管理员 100% 被拒并留痕）；创建 / 变更 / 删除全程留痕。

**跨端衔接点**：管理端建好的结构与房源 → **居民端 / 游客端房源列表立即可见**（全社区开放 + 社区筛选）；
房屋状态（空置 / 已入住）是 **CF-E2 / CF-E3-A / CF-E3-C / CF-E3-F** 的联动观察点；
公共资源与时段是 **CF-E7** 的起手数据。

### CF-E2 居民注册 · 入住申请审核 · 搬出归档（E2 · C2）

**流程目标**：居民自助注册（或管理员代建 / CSV 批量导入）→ 提交入住申请 → 管理端审核通过 / 驳回
→ 建立居住关系、开放居民端功能 → 期末搬出登记 → 关系终止归档；覆盖入住申请 **4 态**
（`PENDING` 待审核 / `APPROVED` 已通过 / `REJECTED` 已驳回 / **`WITHDRAWN` 已撤回**）。
**涉及端与角色**：居民（`resident1`，自助注册 + 提交申请 + 撤回）+ 社区管理员 `admin1`（代建 / 导入 + 审核 + 搬出登记）+ 超管 `superadmin`（注册方式全局开关）。

| # | 端 · 账号 | 操作 | 预期 |
|---|-----------|------|------|
| 1 | 管理端 · `superadmin` | 「系统 / 全局配置」查看**注册方式全局开关**（管理员代建 / 自助注册，两者可独立开关） | 开关仅超管可操作；**社区管理员访问全局配置 100% 被拒并记录**；关闭自助注册后前端注册入口隐藏、注册接口返回明确拒绝（`REGISTRATION_DISABLED(5204)`） |
| 2 | 居民端（隐身窗口 B） | 打开注册页注册新居民账号（姓名 / 手机号 / 密码等）→ 用新账号登录 | 注册成功、可登录并进入 `/resident/home`；**未建立居住关系时私有功能不可用** |
| 3 | 管理端 · `admin1` | 「居民」→ **代建居民**（填姓名、联系方式、证件号等）→ 记录弹出的初始密码 → 用该密码在新窗口登录验证 | 代建账号可登录；初始密码符合设计；操作入日志 |
| 4 | 管理端 · `admin1` | 「居民」→ **批量导入**：下载 CSV 模板 → 改成 3 行（2 行合法 + 1 行故意重复手机号）→ 上传 | **部分成功语义**：逐行结果反馈，`2 成功 1 失败` 且失败行**标明失败原因**；成功行生效 |
| 5 | 居民端 · 新账号 | 「租住与房源 → 房源信息」选一处**空置**房屋 → 「申请租住 / 入住申请」：填关系类型（产权人 / 承租人 / 共同居住人等）、居住起止、备注 → 提交 | 提交成功、状态「**待审核**」（`PENDING`）；**房屋非空置时被拒**（`HOUSE_NOT_VACANT(5205)`）；**同一居民同一房屋已有待审核申请时被拒**（`APPLICATION_PENDING_EXISTS(5206)`） |
| 6 | 管理端 · `admin1` | 「租住与房源 → **入住申请**」（Hub 默认 Tab）查看该申请（申请人 / 身份 / 目标房屋 / 申请时间 / 状态 / 操作） | 待审申请可见；历史行（已通过 / 已驳回 / 已撤回）在历史筛选中可见 |
| 7 | 居民端 · 新账号 | 对该**待审核**申请点「**撤回申请**」→ 二次确认 | 状态 → **`WITHDRAWN` 已撤回**；管理端同一行的状态同步为「已撤回」；**对已通过 / 已驳回的申请再撤回被拒**（`APPLICATION_NOT_WITHDRAWABLE(5605)`） |
| 8 | 管理端 · `admin1` | 另起一条待审申请 → 审核**驳回**（理由必填） | 状态 → **`REJECTED` 已驳回**、驳回理由可见、申请人收到通知；**已审核的申请再次审核被拒**（`APPLICATION_ALREADY_REVIEWED(5202)`） |
| 9 | 管理端 · `admin1` | 再起一条待审申请 → 审核**通过**（按设计填租期起止 / 月租 / 押金） | 状态 → **`APPROVED` 已通过**；**建立居住关系**（按设计联动租约：本文件 CF-E3-A 起手，审核通过落**待签约**租约，**房屋不置已入住**） |
| 10 | 管理端 · `admin1` | 「居民 → 居住关系」页选该居民 → 查看居住关系行 | 出现「居民｜房屋｜入住日期｜-｜**居住中**｜搬出登记」；居住关系台账**按房屋查当前与历史居住人员**、**按居民查全部居住历史**双向一致 |
| 11 | 居民端 · 该居民 | 用已通过审核的账号登录，打开原私有功能 | 居住关系生效后**居民端业务功能入口开放**（待办 / 报修 / 反馈 / 预约等可用） |
| 12 | 管理端 · `admin1` | 对该居住关系点「**搬出登记**」（填搬出日期与原因）→ 提交 | 居住关系**终止并记搬出时间**、状态不再为「居住中」；历史关系仍可查；**该居民失去对应房屋的居民端功能入口** |
| 13 | 管理端 · `admin1` | 对**非在住**居住关系再办搬出 | 被拒（`RELATION_NOT_ACTIVE(5207)`「居住关系不在住，不可办理迁出」）；全流程写操作日志 |

**通过判据**：入住申请 **4 态**（待审核 / 已通过 / 已驳回 / **已撤回**）流转可达且只有设计允许的流转成功；
注册方式开关（全局级）生效且社区管理员越权被拒；代建与 CSV 批量导入**部分成功语义**正确；
审核通过 → 居住关系建立 → 居民端功能开放三者联动一致；搬出登记终止关系并记搬出时间、历史保留；
非法流转与越权 **100% 被拒**并留痕。

**跨端衔接点**：居民提交申请 → **管理端「入住申请」待办 + 通知**；
管理端审核通过 → **居民端申请状态 + 待签约租约 + 自动建租约群聊**（接 **CF-E3-A**，详见 §4 速查表第 1~2 行）；
**入住申请行的会话入口按真关联 `conversationId` 渲染**（本轮新增交互）：**有群**才出现「进入租约会话」；**无群不出现该入口**（另有「咨询社区管理员」居民侧直通会话兜底，与租约会话不是同一入口，见 **CF-E3-B** 第 11 步）；
**申请行「查看我的租约」按 `residence_application.lease_id`（V26 强关联）深链**，`lease_id` 为 NULL 时给中性兜底「暂无关联租约」+ 去租约列表，**不出错指死链**；
搬出归档是 **CF-E3-F** 的终态口径。

> **备注（观察项）**：社区开启 `auto_approve_residence`（R62 补）时，提交入住申请即由系统自动审批、
> 无需人工审核——此路径的覆盖情况按 `50_系统测试/_中控.md` 批次 e 口径记录；
> 「审核体验 / 提示文案是否好用」属 **需求满足性 → 60 评估验收**，本文件只记录现象。

### CF-E3-A 租住申请与审核通过（→ 待签约）（E3 段 A · C3 · R66）

**流程目标**：居民提交租住申请 → 管理端审核通过 → 租约落「**待签约**（`TO_SIGN`）」
——**审核通过 ≠ 租约生效，房屋不置已入住**。
**涉及端与角色**：居民（提交申请 + 待审核阶段可撤回）+ 社区管理员 `admin1`（审核通过 / 驳回）。

| # | 端 · 账号 | 操作 | 预期 |
|---|-----------|------|------|
| 1 | 居民端 · 居民账号 | 「租住与房源 → 房源信息」选一处**空置**房屋 → 「**申请租住**」：填关系类型与备注 → 提交 | 提交成功、状态「**待审核**」（`PENDING`）；申请可在居民端「入住申请」列表看到；**待审核阶段可撤回** |
| 2 | 居民端 · 同上 | （附验）对待审核申请点「撤回」 | 状态 → **`WITHDRAWN` 已撤回**、**不产生租约**、房屋状态不变；对已通过 / 已驳回的申请再撤回被拒（`APPLICATION_NOT_WITHDRAWABLE(5605)`） |
| 3 | 管理端 · `admin1` | 「租住与房源 → 入住申请」找到该申请 → 点「**通过**」→ 按设计填**租约起止 / 月租 / 押金** → 确认通过 | 申请状态 → **`APPROVED` 已通过**；toast 提示审批通过（「已创建居住关系与租住记录」口径）；**同事务生成租约** |
| 4 | 管理端 · `admin1` | 「租住与房源 → 租约管理」切到「**待签约**」分组，查看该租约行 | 租约状态 = **「待签约」（`TO_SIGN`）**——**不是「已生效」**；**承租确认 = 「待确认」**；协议 = 「未发起协议」；租期 / 月租 / 押金与第 3 步填写值一致 |
| 5 | 管理端 · `admin1` | 「社区管理」/「租住与房源 → 房源管理」核对目标房屋状态 | 房屋仍为「**空置**」——**审核通过后房屋不置已入住**（设计硬口径，DEF-070 断言口径） |
| 6 | 居民端 · 该居民 | 「租住与房源 → 我的租约」查看租约卡片 | 卡片显示「**待签约**」+「**确认承租**」入口；租期 / 月租 / 押金与登记值一致（金额取种子实际值即可做等值断言） |
| 7 | 管理端 · `admin1` | 驳回分支：另取一条待审申请点「**驳回**」（理由必填） | 状态 → **`REJECTED` 已驳回**、理由可见、申请人收到通知；**不产生租约** |
| 8 | 管理端 · `admin1` | 越权 / 边界：对**非绑定社区**的申请执行审核 | 被拒或无数据（社区级数据权限过滤）；越权记录入日志 |

**通过判据**：审核通过后租约状态为 **`TO_SIGN` 待签约**（**不是 `ACTIVE`**）且**房屋不置已入住**；
申请 4 态流转与撤回口径正确（撤回不产生租约，非法撤回 5605）；驳回不动租约、须填理由；
审核通过 → 建立居住关系（同 **CF-E2** 第 9~10 步）+ 自动建租约群聊（接 **CF-E3-B**）；
数据级权限（社区级）在审核动作上生效。

**跨端衔接点**：居民提交申请 → **管理端「入住申请」待办 + 通知**；
管理端审核通过 → **居民端出现「待签约」租约卡片 + 「确认承租」入口**，同时**自动建 `LEASE_GROUP` 租约群聊**（接 CF-E3-B）。

### CF-E3-B 租约群聊与看房 / 带看分配（E3 · C3/C11/C12 · R59 / R63 / R68 / R69）

**流程目标**：租住申请**审核通过**时自动创建 `LEASE_GROUP` 租约群聊；
群内可发起**看房预约**（复用 R54/R55/R60 契约与冲突校验），管理端**分配带看人**后带看人入群并形成带看沟通会话。
**涉及端与角色**：居民（群内发起看房预约与沟通）+ 社区管理员 `admin1`（分配带看人）+ 服务人员 `staff1` / `staff2`（带看人）。

| # | 端 · 账号 | 操作 | 预期 |
|---|-----------|------|------|
| 1 | 管理端 · `admin1` | 审核通过一条租住申请后，打开「**消息会话**」列表 | 出现「**租约沟通·<房屋位置>**｜租约群聊｜进行中」；`conversation.type=LEASE_GROUP`、`related_id=租约 ID`、`status=ACTIVE` |
| 2 | 管理端 · `admin1` | 打开该会话详情 / 消息列表 | 群聊**立即可见、可打开、可发送**；默认参与者 = **申请居民 + 该社区全部启用状态的社区管理员**（R68 口径）；页面不展示成员名单时以成员接口口径核对 |

### CF-E3-C 承租确认 → 协议发起 → 协议确认 → 租约生效（E3 · C3 · R64 / R66 / R67 / DEF-077 / DEF-078）

**流程目标**：居民**确认承租**（管理方不可代确认）→ 管理方**发起租赁协议**（模板 + `{{变量}}` 渲染**快照**）
→ **管理端确认 + 居民端确认（不重复采集同意）** → 协议 `SIGNED`、租约 **`ACTIVE`**、房屋置**已入住**（`OCCUPIED`）。
**涉及端与角色**：居民（确认承租 + 协议文本确认）+ 社区管理员 `admin1` / `admin2`（发起协议 + 管理方确认）。

> **本轮口径（2026-09-22 用户裁决，先读这条）**：
> ① **承约前置 = 本人 + 待签约（`TO_SIGN`）**——**看房预约与租约群聊是「沟通手段」，不是承约门槛**，
> 不得把「需先完成看房」「需先有群聊」当作承约前置；
> ② `LEASE_TENANCY_VIEWING_REQUIRED(5607)` / `LEASE_TENANCY_CONVERSATION_REQUIRED(5608)`
> **保留定义、当前无任何调用点**——**不得**把 5607 / 5608 写作承约被拒的预期错误码；
> ③ **同意只采集一次**：居民「同意承租」＝**唯一一次**同意采集；
> 其后**管理端确认 + 居民端确认 → 协议直接推进**，**居民不再为同一同意二次点击**
> （原「承约 + 协议确认」两次采集已判定为**重复确认缺陷**，本轮已修，DEF-078 去重）。

> **同一方重复确认不覆盖首次留痕**；**非参与者查看 / 确认协议 100% 拒绝并记录**；
> 撤回后再发起须不被未完成协议阻塞（见第 14 步）。

**通过判据**：
① **承约不依赖看房 / 群聊**：承约前置**仅「本人 + `TO_SIGN`」**；**无 5607 / 5608 调用点**（该两码**保留定义、不构成承约被拒理由**）；
② **同意只采集一次**：居民「确认承租」＝**唯一一次同意采集**，随后**管理端确认 + 居民端确认即推进协议**，**居民不再二次点击确认同意**（DEF-078 去重，留痕不覆盖首次值）；
③ **未确认承租时管理端发起协议被明确拒绝（5601）**；**承租确认是协议发起的前置**、**管理方不可代确认**（越权 100% 拒绝并留痕）、重复确认幂等不覆盖首次留痕；
④ 协议正文 = **发起时租约数据的快照**（不随模板后续修改变化）；单方确认 → `PARTIAL` 而**租约不生效**；
⑤ **双方确认齐 → 协议 `SIGNED`，同事务租约 `TO_SIGN` → `ACTIVE` 已生效 + 房态 `OCCUPIED`「已入住」**；
⑥ **租约详情失败态分层**：**主数据失败 → 阻断式错误态**（非空白页）；**变更历史失败 → fail-soft**（主体可用、仅该区块降级）；
⑦ 撤回仅限未完成协议且租约签约状态回落；全流程在租约变更历史留痕（`CREATE` / `STATUS` / `AGREEMENT`）。

**跨端衔接点**：居民确认承租 → **管理端「发起协议」入口解锁** + 管理方收到「居民已确认承租」通知（§4 速查表第 4 行）；
双方协议确认齐 → **租约「生效」+ 房屋「已入住」+ 群聊系统消息（有群时）**（速查表第 5 行）；
租约生效后居民端出现「**待支付首期费用**」入口（接 **CF-E3-D**）；
租约群的**会话入口**按 `lease_record.conversation_id` **真关联**渲染（见 **CF-E3-B** 第 11 步）。

### CF-E3-D 首期费用在线支付（E3 · C3 · R71，复用 R61 契约）

**流程目标**：租约**正式生效**后，居民在「我的租约」支付**首期费用（首月租金 + 押金）**：
金额**服务端计算**、支付宝电脑网站 / 微信 Native **双渠道凭据门控**、
**后端主动查单 + 前端轮询**替代异步回调；**首期支付与签约解耦**——不因未付首期阻止租约生效。
**涉及端与角色**：居民（`resident1` 起手支付 / `resident5` 已付清收口）+ 管理端（管理员口径通知与支付记录核对）。

| # | 端 · 账号 | 操作 | 预期 |
|---|-----------|------|------|
| 1 | 居民端 · `resident1` | 「租住与房源 → 我的租约」查看**已生效且未付首期**的租约卡片 | 卡片有「**待支付首期费用**」入口（`resident1` ZL0001 口径）；租约状态仍为「在租」；**本轮新增交互**：**任何状态的租约卡都有可见支付入口**——可支付时**可点**，已结清 / 止期已过 / 终态时**置禁用并显示原因**，**不再整块消失** |
| 2 | 居民端 · `resident1` | 点「支付首期费用」→ 弹窗第一步：核对金额构成与渠道卡片 | **首期费用 = 月租 + 押金**（服务端计算，客户端传金额被忽略 / 拒绝）；金额构成分别列出「首月租金」与「押金」；**押金不提供独立支付入口**——押金与首月租金由**首期付费一次收取**，其生命周期在**退租**环节由押金退还收口（接 **CF-E3-F**）；渠道卡片按**凭据门控**展示：已配置渠道可用、未配置渠道**置灰并标「未配置」**（不报错不阻断） |
| 3 | 居民端 · `resident1` | 选渠道 → 「去支付」 | 生成支付单：`payment_type=FIRST`、`months=1`、状态 `PENDING`；支付宝返回 `alipayForm`（新窗口跳转收银台）/ 微信返回 `qrCode`（Native 扫码）；**本轮不真实付款也可继续核对**；**渠道未配置时发起应预期 `PAYMENT_CHANNEL_DISABLED(5901)`**（而非失败） |
| 4 | 居民端 · `resident1` | 关闭弹窗（不付款）→ **重新打开**该入口 | **幂等续接**：**不停在「选渠道」，续接既有 `PENDING` 单直达支付步**，并提示「已续接您此前未支付的首期支付单，渠道以该单为准」；**同单号、不重复创建**；`CLOSED`（已关闭）允许重新发起新单 |
| 5 | 居民端 · `resident1` | 完成沙箱支付 → 观察「完成支付后本页自动确认结果」提示 | **后端主动查单 + 前端轮询**落账（本地无公网回调，以轮询替代 notify）；查单返回后支付单状态回写；也可点「我已完成支付」立即查询 |
| 6 | 居民端 · `resident1` | 支付成功后复核租约卡片与支付记录 | **支付成功不改动租约 `status`、不改动 `end_date`**——**首期支付与签约解耦**（未付首期也不阻止租约生效）；「支付记录 / 租约明细」出现该单且**类型标签为「首期」**；**首期与续期同表不同类型（`FIRST` / `RENEWAL`）互不混淆** |
| 7 | 居民端 · `resident1` | 再次对**同一租约**发起首期支付 | **仅存在 `PENDING` 单时幂等续接原单**（不重复创建）；**已存在 `SUCCESS` 单时返回 `PAYMENT_ALREADY_EXISTS(5904)`**（首期只收一次） |
| 8 | 居民端 · **`resident5`** | 「我的租约」打开**租约 6（首期已付）** | **收口断言（本轮口径修正）**：卡片显示「**首期已支付 ¥7,600**·<时间>」；**支付入口仍然渲染，但为禁用态并给出原因**（如「首期已结清…」）——**任何状态的租约卡都有可见入口（可点 或 禁用 + 原因），不再整块消失**；因此 **5904 在 UI 上不可达**（仅为客户端状态陈旧时的兜底分支），UI 侧以「**入口常显但禁用**」为设计符合性判据 |
| 9 | 管理端 · `admin1` | 核对支付记录与通知落点 | 管理端可查续约 / 支付记录（限绑定社区）；居民支付成功产生的通知**为管理员口径**，**不得串到居民身份空间**（与 **CF-E11** 的 `owner_type` 收口一致） |
| 10 | 边界核查 | 支付渠道环境变量未配置时的整体口径 | `GET /api/v1/payment/channels` 返回对应渠道 `enabled=false`（不报错）；涉及支付的流程按 **5901** 预期核对，**不记为失败** |

**通过判据**：首期金额 = **月租 + 押金**且由服务端计算（篡改被忽略 / 拒绝）；
`payment_type=FIRST`、`months=1`；**同租约同类型仅一单进行中且 `PENDING` 单可反复续接**，
`SUCCESS` 后再发起 **5904**；**渠道凭据门控**（未配置 **5901**、不报错不阻断）；
**主动查单 + 前端轮询**可落账；**支付成功不改动租约状态与止期**（签约解耦）；
**租约卡支付入口常显（本轮口径修正）**：**任何状态都有可见入口**（**可点** 或 **禁用 + 显示原因**），
**不再整块消失**；**已付清租约入口常显但禁用**（`resident5` 收口）；
**押金 / 租金不做独立支付**——随**首期付费**一次收取，`deposit_status` 随之联动（**押金为 0 的租约不置已缴**），
其生命周期在**退租**环节由押金退还收口（接 **CF-E3-F**）；通知**不串身份空间**。

**跨端衔接点**：居民支付成功 → **管理端管理员口径通知（不得串到居民）**（§4 速查表第 6 行）；
支付记录是 **CF-E9** 看板与 **CF-E3-F/E3-G** 时间线（R73）的数据源；
首期与续期共用同一套支付契约与渠道门控（接 **CF-E3-E**）。

> **⚠️ 待核（不要猜）**：任务下达时提到「`PARTIAL` / `SIGNED` 口径（**仅全额付清才 `SIGNED`**）」。
> 据本仓库现有权威材料：**支付单状态（`lease_payment.status`）为 `PENDING` / `SUCCESS` / `CLOSED` 三态**
> （V15 迁移注释 + §9.13.2 / §9.19.12），**`PARTIAL` / `SIGNED` 是协议状态与租约 `agreement_status` 的取值**
> （§9.17）。因此**第 6~8 步的「付清 / 部分」口径以 `30_系统设计/接口设计.md` 当前版本（v1.6）与实现为准**：
> 实现若存在首期部分支付口径，按实现核对并回填本节；**在核对清楚前不写「仅全额付清才 `SIGNED`」的断言**。

### CF-E3-E 续期支付与租期延展（E3 · C3 · R61）

**流程目标**：居民对已生效租约发起**续约申请** → 生成续约支付单（`payment_type=RENEWAL`，`months` 可选）
→ 在线支付（同 R61 双渠道）→ 支付成功后**自动延展租期并通知**；未支付 / 失败**不延展**。
**涉及端与角色**：居民（发起续约 + 支付）+ 社区管理员 `admin1`（续约与支付记录核查）。

| # | 端 · 账号 | 操作 | 预期 |
|---|-----------|------|------|
| 1 | 居民端 · `resident1` | 「租住与房源 → 我的租约」对**已生效**租约点「**续租**」→ 选月数（`@Min(1)` ~ `@Max(36)`）与支付渠道 → 提交 | 生成续约支付单：`payment_type=RENEWAL`、`months=所选月数`、状态 `PENDING`；**金额 = 月租 × 月数，服务端计算**（客户端传金额无效）；**仅本人且 `status=ACTIVE` 的租约可发起**，否则 403 / 状态非法 |
| 2 | 居民端 · `resident1` | 核对金额与渠道卡片 | 金额与实际选值一致；渠道按凭据门控展示（未配置则置灰「未配置」）；**渠道未配置时下单预期 5901**；渠道下单失败时支付单关闭并返回 `PAYMENT_CREATE_FAILED(5902)` |
| 3 | 居民端 · `resident1` | 幂等核查：对**同一租约再次发起续约**（前单仍 `PENDING`） | **同租约存在 `PENDING` 支付单时直接返回该单**（重新获取渠道凭据），**不重复创建**；同单号续接与 CF-E3-D 同口径 |
| 4 | 居民端 · `resident1` | 完成沙箱支付 → 观察轮询落账 | 主动查单 + 前端轮询回写支付单状态；金额与渠道金额不一致时 `PAYMENT_AMOUNT_MISMATCH(5903)` |
| 5 | 居民端 · `resident1` | 支付成功后复核租约卡片与支付记录 | **租期自动延展**：止期按 `months` 精确后移、**延展准确**；「支付记录 / 租约明细」出现该单且**类型标签为「续期」**（与首期区分）；**双方（居民与管理方口径）收到通知** |
| 6 | 居民端 · `resident1` | 未支付 / 支付失败分支核查（关闭支付单或让支付失败后查看租约） | **未支付 / 支付失败不延展租期**（止期不变）；支付单状态为 `CLOSED` 等设计允许的终态；可重新发起新单 |
| 7 | 管理端 · `admin1` | 「租住与房源 → 租约管理」/ 租约详情查看续约与支付记录 | 管理端**可查续约与支付记录**（限绑定社区）；留痕与居民端一致（支付单号 / 渠道 / 金额 / 时间） |
| 8 | 居民端 · `resident4` | 越权 / 边界：对**已到期**租约发起续租（租约 5 口径） | **允许发起**——**5606 只拦首期，不拦续期**（续期是延续租期的正当动作）；与 **CF-E3-G** 第 5 步同口径 |

**通过判据**：续约单为 `payment_type=RENEWAL`、金额 = 月租 × 月数（服务端计算、篡改拒绝）；
`PENDING` 单幂等续接不重复创建；**支付成功才延展租期且延展准确**、双方收到通知；
**未支付 / 失败不延展**；居民仅可续约本人租约（越权 100% 拒绝）；管理端可查续约与支付记录；
**已到期不拦续期**（只拦首期，与 5606 口径一致）。

**跨端衔接点**：居民续期支付成功 → **管理端租约止期与支付记录同步变化** + 通知（§4 速查表第 6 行同口径）；
续期单与首期单在**同一支付记录 / 租约明细时间线**中按类型区分（接 **CF-E3-F** 第 6 步的 R73 时间线）。

### CF-E3-F 自助退租 → 审核 → 押金退还 → 搬出归档（R70/R72/R73）· **可执行**

**流程目标**：居民发起退租申请 → 管理端审核 → 押金按原渠道退还 → 租约已搬出 → 已归档（群聊关闭）。
**涉及端与角色**：居民（`resident1`，退租申请 + 押金与时间线可见性）+ 社区管理员（`admin1`，审核 + 发起押金退还 + 归档）。
**起手数据（种子已含，按此选单）**：
- **`resident1` 的租约 4＝`MOVED_OUT` 且押金 `PAID`、有历史成功首期支付单（金额 7600 = 月租 3800 + 押金 3800）** → **第 4~6 步用它起手**（满足"已搬出 + 押金已缴"的退还前置）；
- ⚠️ **反例数据**：`resident4` 的租约 5（**已到期**）与 `resident5` 的租约 6（**已付首期**）**均为 `ACTIVE` ⇒ 不满足退还前置**，只可用于"**状态不允许退还（5703）**"的反例；
- 第 1~3 步若要跑完整退租，用一条 `ACTIVE` 租约新发起（审核通过后即成为上表可退还的 `MOVED_OUT` 单）。

| # | 端 · 账号 | 操作（点什么 / 填什么） | 预期（状态 + 页面 + 错误码/留痕） |
|---|-----------|----------------------|--------------------------------|
| 1 | 居民端 · `resident1` | 「我的租约」对**已生效**租约点「申请退租」→ 填搬出日期 + 原因 → 提交 | 提交成功、状态「待审核」；**同一租约重复发起被拒**（**5603** `MOVE_OUT_APPLICATION_PENDING`）；非 `ACTIVE` 租约发起被拒（**5602**） |
| 2 | 管理端 · `admin1` | 「租住与房源 → 退租申请」找到该申请 → 审核**通过**（可选房源回收：在架 / 下架） | **联动一致**：租约 → **已搬出（`MOVED_OUT`）**、居住关系终止并记搬出时间、房屋置空置、房源状态按选择回收、**租约群聊关闭**（发消息被拒 **5604**）、居民收到通知；写变更历史（`STATUS`）；**此时押金状态应仍为 `PAID`**（退还需单独发起，见第 4 步） |
| 3 | 管理端 · `admin1` | 另取一条退租申请做**驳回**（理由必填） | 状态驳回、租约**保持已生效**、理由可见、居民收到通知 |
| 4 | 管理端 · `admin1` | **押金退还（可执行）**：「租住与房源 → 退租申请 / 租约详情」打开**租约 4** → 查看**押金状态（应为「已缴 `PAID`」）** → 点「**发起押金退还**」→ 弹窗内**金额默认全额、可改但须 ≤ 实缴押金**、**渠道只读＝原支付渠道（不可切换）** → 填 `remark`（如 `退租结算，押金原路退还`）→ 确认 | 退款记录 `PENDING` → 渠道成功 → `SUCCESS`；押金状态 **`PAID → REFUNDING → REFUNDED`**；记录含**渠道退款单号 / 金额 / 时间**；**错误码**：非 `PAID` 发起 → **5703**；**超实缴 → 5704**（报文含「可退 X 元」）；**跨渠道（渠道与实缴不一致）→ 5705**；**同一 `outRequestNo` 重复提交 → 幂等返回既有记录**（内容不一致时 **5706**）；**失败**：状态**回落 `PAID`** 且**失败原因常驻可见**，**重试须换新 `outRequestNo`**；`remark` 经 **`lease_change_log`（`changeType=DEPOSIT_REFUND`）**留痕并在时间线渲染 |
| 5 | 居民端 · `resident1` | 「我的租约」→ 租约 4 → 查看**押金状态**与**退还记录** | 显示押金徽标五态（未缴 / 已缴 / 退还中 / 已退还 / 已抵扣）+ **退还流水明细**：金额、渠道、状态、**失败原因**（失败时有）、时间、渠道退款单号；**仅本人租约可见**（越权 100% 拒绝） |
| 6 | 居民端 · `resident1` | 打开该租约的**租约明细时间线** | **状态流转 + 支付流水 + 退款流水三源合并为同一条时间线**、时间倒序；支付条目含**金额构成拆分（月租 / 押金）**、**覆盖租期区间**、业务单号、渠道流水号、创建与完成时间；退款条目含渠道退款单号与结果；`remark` 渲染为条目说明 |
| 7 | 管理端 · `admin1` | 对已搬出租约做**归档** | 租约 → **已归档**（终态，不可修改）；群聊保持关闭；历史可查 |

**通过判据**：退租通过后**租约 / 居住关系 / 房屋 / 房源 / 群聊**五者联动一致；驳回不动租约状态；
**押金退还金额 ≤ 实缴押金且原渠道原路退回（渠道只读）**，全流程留痕；**幂等键 `out_request_no` 生效**（同号不重复退款）；归档后不可修改。
**跨端衔接点**：居民申请 → 管理端待办；管理端审核通过 → 居民端租约「已搬出」+ 群聊关闭；**管理端发起退还 → 居民端押金状态与退还流水、时间线同步变化**；驳回/失败 → 居民端状态与原因可见。

**执行前置与边界（本段现已可执行）**：
- **押金前后端均已交付上线**：数据库 **V22**（`lease_record.deposit_status` + 索引、新表 `lease_deposit_refund`）、接口 **§9.20.1 / §9.20.2**（错误码 **5703~5706**）、前端交付（**押金徽标五态 / 退还记录含失败原因 / 租约明细时间线 / 发起押金退还弹窗**）；
- **平台边界（不得据此判失败）**：平台**不托管押金资金、不计息、不垫付**，仅做**状态记录 + 渠道原路退款**；库内**不得出现押金资金账户 / 余额 / 计息字段**（定义 v1.6 §3 核查项）；
- **`OFFSET`（已抵扣）当前无发起入口**：设计未定义抵扣发起端点，本轮**不产生该状态**——第 5 步对「已抵扣」**仅核对其枚举与徽标展示口径**（若种子无该状态数据，如实记为「无数据可验」，**不写"待实现"**）；
- **渠道未配置时**：`GET /payment/channels` 显示对应渠道 `enabled=false` → 发起退还应预期 **5901**（渠道未配置），而非失败。

### CF-E3-G 到期与已到期口径（含 DEF-069 收口）

**流程目标**：验证"即将到期 / 已到期"是**日期自动判定标注**（非状态流转），以及已到期租约的**首期支付入口收口**。
**涉及端与角色**：居民 + 社区管理员；定时任务（`LeaseStatusTask` 01:00 / `LeaseExpiryReminderTask` 01:30）。

| # | 端 · 账号 | 操作 | 预期 |
|---|-----------|------|------|

**流程目标**：从房源挂牌起，走完「看房（**可选**）→ 入住申请 → 审核通过（→ 待签约）→ 承约 → 协议 → 生效 → 首期 → 续租 → 退租 → 押金退还 → 归档」全链路，

**本节统一通过判据（设计符合性）**：
① 全链路状态**逐节点可达**：租住 **6 态**（含 **`TO_SIGN`**）、入住申请 **4 态**（含 **`WITHDRAWN`**）、看房预约 **5 态**（工单 / 资源预约 / 反馈状态机不在本节）；
② **看房预约与租约群聊是「沟通手段」**：第 2 步的看房与第 4 步自动建的群聊**不是第 5 步承约的前置**——**跳过第 2 步、无群聊时全链仍可走通**；
③ **同意只采集一次**：第 5 步＝唯一一次同意采集，第 7 步**只是协议文本确认**，**不是第二次同意采集**；
④ **协议 `SIGNED` → 同事务租约 `ACTIVE` + 房态 `OCCUPIED`**；**单方确认（`PARTIAL`）不生效**；
⑤ **首期费用含押金、不做独立支付**；押金 `deposit_status` 随首期收取与退租退还闭环（`UNPAID → PAID → REFUNDING → REFUNDED`，失败回落 `PAID`）；
⑥ **入住申请 ↔ 租约强关联（V26）**：申请行按 `residence_application.lease_id` 深链；**`lease_id` 为 NULL 时不回退弱关联猜测**（页面给中性兜底「暂无关联租约」+ 去租约列表入口，**不出错指的死链**）；
⑦ **居民端会话入口按真关联 `conversationId` 渲染**（**有群才出现**租约会话入口；**无群不出现**；**不按 `houseId` 反查**）；
⑧ 全链各步**通知收件人**符合设计（申请人 / 该社区绑定管理员 / 居民本人 / 被派服务人员，按 **`owner_type` 身份空间**收口，**不串号**）。
⑨ **全链每一步只判设计符合性**；观察到的「入口好不好找 / 文案清不清楚」类现象**只记录**，归 **60 评估验收**。

**本轮修正要点（2026-09-22，入住链路缺陷修复）**：
1. **承约前置简化**——承约前置**仅「本人 + 待签约 `TO_SIGN`」**；**看房预约与租约群聊是沟通手段、不是门槛**（`5607` / `5608` **保留定义、当前无任何调用点**）；
2. **同意只采集一次**——居民「同意承租」为**唯一一次**同意采集，协议阶段**居民不再二次点击同意**（**DEF-078** 去重：管理方确认时引用承约留痕回填居民侧）；
3. **入住申请 ↔ 租约强关联（V26）**——新增 `residence_application.lease_id`，由审批通过内核**同一事务**回写；**`lease_id` 为 NULL 时不回退弱关联猜测**（修掉「同房屋多租约指错」）；
4. **居民端会话入口按真关联**——租约卡 / 入住申请行按 **`conversationId`** 渲染，**不再靠 `houseId` 反查**（无群不出现租约会话入口）；
5. **租约详情失败态分层**——**主数据失败 → 阻断式错误态**（不再空白页）；**变更历史失败 → fail-soft**（页面仍可用，仅该区块降级并提示原因）；
6. **服务人员端列表真动作**——`staff/WorkOrderListView.vue` 的接单 / 处理入口**真调** `accept` / `process`、跳详情 **`?action=complete`**，**按钮文案与动作一致**；
7. **租约卡支付入口常显**——**任何状态都有可见入口**（可点，或**禁用 + 显示原因**），**不再整块消失**；**押金 / 租金不做独立支付**——随**首期付费**收取，其生命周期在**退租**（押金原路退还）时结束。

## 6. 核心业务链路连续性只读观察项（2026-09-27，未实施）

> 本节不新增 CF 用例，也不改变设计符合性结论。执行时把现象写在对应 CF 行备注；
> 「需求满足性 / 易用性」只记录并转 60 评估验收；只有文档设计与实现不一致才登记 DEF。

### 6.1 租住闭环连续性

1. **申请到租约的强关联**：管理端审核通过后，居民端申请行、租约卡、租约详情和租约会话是否始终指向同一个 `leaseId` / `conversationId`；同一房屋存在多条租约时不得靠猜测反查。
2. **承租确认到协议入口**：居民确认承租后，管理端对应租约是否立即解锁「发起协议」；管理端不能代替居民完成承租确认；刷新或重新登录后状态仍一致。
3. **协议确认到生效**：协议发起、居民/管理方确认、`SIGNED`、租约 `ACTIVE`、房屋已入住是否按设计顺序发生；避免出现重复确认、跳级生效或局部成功局部失败后页面误导。
4. **首期费用支付可恢复**：首期入口是否持续显示正确状态；支付宝页面关闭、支付单 `PENDING` / `CLOSED` / `SUCCESS` 后重新进入，是否能续接、重试或明确告知不可操作原因。
5. **退租到押金退还再到归档**：退租申请、审核、房态、居住关系、押金状态、退款流水、租约时间线和群聊关闭是否跨端同步；部分退款失败时不得误显示为已全部退还。
6. **通知与深链**：租约、退租、押金、协议相关通知点击后是否落到正确租约/申请；不同身份空间不会串收，也不会出现通知成功但页面找不到目标对象。

### 6.2 工单闭环连续性

1. **受理前后群聊边界**：未受理工单不应提前出现临时群聊；管理端受理后才建立 `WORK_ORDER_GROUP`，居民、受理管理员和服务人员看到的会话状态应一致。
2. **派单与服务人员入群**：派单后服务人员待办、通知、群成员和工单详情是否同时更新；改派、重复派单、刷新后不得出现旧人员仍可操作的假状态。
3. **按钮与状态机一致**：居民、服务人员、管理员各端每个状态下可执行按钮是否与 30 系统设计一致，尤其是接单、开始处理、提交结果、居民确认、管理员终审与退回。
4. **终审与会话回收**：管理员终审结束后工单关闭、群聊只读、历史可查、发送消息被拒的结果是否一致；评价入口不得指向已不可评价的状态。
5. **失败恢复与通知收件人**：网络失败、刷新失败、重复点击、通知延迟时，页面是否给出当前状态和重试入口；通知对象必须是正确的居民、服务人员或管理方，不能只依赖相同数字 ID 猜测身份空间。
