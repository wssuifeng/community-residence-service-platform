# 功能用例 · C4 服务申请与工单管理

> 依据：01_测试需求分析.md §3.4（TR-C4-01~09）、需求规格 R17~R23 + E4、
> 接口设计 9.4（实现口径以后端 WorkOrderController/WorkOrderService 为准，
> 状态常量 WorkOrderStatus）。编号规则：TC-C4-NNN；每条至少覆盖一个 TR；
> 执行结果列由步骤 7 回填。
>
> 种子账号（Flyway V3/V6/V7）：superadmin/Admin@123456（超管）、
> admin1/Admin123456（社区管理员，绑定社区 1）、staff1/Staff123456（服务人员）、
> resident1/Resident123456（居民，已入住社区 1）；社区 1 已有 V7 种子
> 服务类别 7 类（室内维修/公共设施报修/公共区域卫生/水电管道/电梯楼道/
> 安全安全隐患上报/其他，均为启用状态）。
> 工单状态 10 态（架构设计 §6.1）：PENDING 待受理 / TO_ASSIGN 待派单 /
> ASSIGNED 已派单 / ACCEPTED 已接单 / IN_PROGRESS 处理中 / TO_CONFIRM 待确认 /
> COMPLETED 已完成 / CLOSED 已关闭 / REJECTED 已驳回 / CANCELLED 已取消。
>
> **实现口径说明（影响用例预期，见文末口径疑点）**：
> - 「受理（→待派单）」无独立端点：PENDING 可直达派单/驳回/取消，
>   PENDING→TO_ASSIGN 流转在实现中无触发入口；
> - 「不满意退回处理中」（R22）后端无对应端点，用例按需求原文保留；
> - 附件上传/删除的访问口径为「工单读权限」（居民限提交人 / 服务人员限
>   被派单人 / 管理员放行），BE-ISSUE-10 修复口径。

### TC-C4-001 创建服务类别（正常）
- 关联：TR-C4-01　类型：功能　优先级：P2
- 前置：admin1 已登录；社区 1 存在（V6 种子）。
- 数据：name=「绿化养护」，description=「公共绿化带养护」，
  communityId=1，sortOrder=8，parentId=null，isActive=1。
- 步骤：
  1. admin1 调用 POST /api/v1/service-categories 提交上述数据；
  2. 调用 GET /api/v1/communities/1/service-categories 查看社区类别树。
- 预期：
  1. 返回 code=200，类别创建成功，id 非空，isActive=1；
  2. 类别树中出现「绿化养护」，且不破坏既有 7 类的 sortOrder 排序。

### TC-C4-002 服务类别更新与停用
- 关联：TR-C4-01　类型：功能　优先级：P2
- 前置：admin1 已登录；TC-C4-001 创建的「绿化养护」类别存在。
- 数据：更新请求 name=「绿化养护」，isActive=0（停用）；
  另准备二级类别：parentId=「室内维修」类 id，name=「灯具维修」。
- 步骤：
  1. admin1 调用 PUT /api/v1/service-categories/{id} 将「绿化养护」置为停用；
  2. resident1 登录，进入居民端工单提交页，加载类别树；
  3. admin1 创建子类别「灯具维修」（parentId=室内维修）；
  4. admin1 对「室内维修」类提交 parentId=「灯具维修」id 的创建请求（三级）。
- 预期：
  1. 更新成功，类别 isActive=0；
  2. 居民提交选项中不再出现已停用的「绿化养护」（R17 验收：停用类别不再
     出现在提交选项；树接口/前端过滤任一口径均须满足——若树接口仍返回
     停用类别且前端未过滤，记缺陷）；
  3. 二级类别创建成功，挂入「室内维修」之下；
  4. 三级类别创建被拒（仅支持二级分类，INVALID_PARAM 400）。

### TC-C4-003 服务类别删除保护
- 关联：TR-C4-01　类型：异常　优先级：P2
- 前置：admin1 已登录；存在被工单引用的类别（「室内维修」）与含子类别的
  类别（「室内维修」下有「灯具维修」）。
- 数据：无新增。
- 步骤：
  1. admin1 调用 DELETE /api/v1/service-categories/{灯具维修 id}（无引用）；
  2. admin1 调用 DELETE /api/v1/service-categories/{含子类别的类别 id}；
  3. admin1 调用 DELETE /api/v1/service-categories/{被工单引用的类别 id}。
- 预期：
  1. 无引用类别删除成功；
  2. 含子类别删除被拒（DATA_EXISTS 5002，提示存在子类别），类别数据不变；
  3. 被工单引用删除被拒（DATA_EXISTS 5002，提示已被工单引用），
     类别与既有工单数据均不变。

### TC-C4-005 工单提交参数校验与停用类别拒绝
- 关联：TR-C4-02　类型：异常　优先级：P1
- 前置：resident1 已登录；存在已停用类别（TC-C4-002 停用的「绿化养护」）。
- 数据：四组请求——A：title 为空；B：content 为空；C：categoryId 指向停用
  类别；D：contactPhone=「12345」（不合法手机号）。
- 步骤：
  1. resident1 依次用 A、B、D 请求体调用 POST /api/v1/work-orders；
  2. resident1 用 C 请求体（停用类别）调用 POST /api/v1/work-orders。
- 预期：
  1. 三组均被参数校验拒绝（400，@NotBlank/@Pattern 生效），不生成工单；
  2. 停用类别提交被业务拒绝（5003，提示服务类别不存在或已停用），
     不生成工单（R17 判据后端兜底）。

### TC-C4-006 工单提交权限否定（游客/服务人员/管理员）
- 关联：TR-C4-02　类型：权限　优先级：P0
- 前置：staff1、admin1 已登录；另备未登录游客会话。
- 数据：合法工单请求体（同 TC-C4-004）。
- 步骤：
  1. 游客（无 Authorization 头）调用 POST /api/v1/work-orders；
  2. staff1 登录态调用 POST /api/v1/work-orders；
  3. admin1 登录态调用 POST /api/v1/work-orders。
- 预期：
  1. 游客请求被拒（401），不生成工单；
  2. 服务人员请求被拒（403，接口仅 RESIDENT），不生成工单；
  3. 社区管理员请求被拒（403），不生成工单；
  4. 三次拒绝均有对应拒绝留痕可检索（安全/操作日志）。

### TC-C4-007 受理分支与状态机口径（PENDING 可达分支）
- 关联：TR-C4-03　类型：功能　优先级：P1
- 前置：admin1、resident1 已登录；存在 1 张 PENDING 工单（TC-C4-004 产物）。
- 数据：无新增。
- 步骤：
  1. admin1 查看工单详情确认 status=PENDING；
  2. admin1 对该工单执行派单（PATCH /{id}/assign，assigneeId=staff1）；
  3. 查询工单详情与时间线。
- 预期：
  1. 状态为待受理；
  2. 派单成功，状态流转 PENDING→ASSIGNED（实现口径：受理与派单合并，
     PENDING 可直接派单；PENDING→TO_ASSIGN 待派单中间态无独立触发入口，
     记口径疑点，不阻断）；
  3. 时间线含 SUBMIT 与 ASSIGN 两条记录（操作人/时间/备注齐全）。
     R19 验收「已驳回仅可自待受理流转、已取消仅可自待受理/待派单流转」
     按实现口径为：驳回自 PENDING/TO_ASSIGN，取消自 PENDING/TO_ASSIGN/
     ASSIGNED/ACCEPTED——见 TC-C4-011 非法流转矩阵。

### TC-C4-008 驳回须填理由（PENDING → REJECTED）
- 关联：TR-C4-03　类型：功能　优先级：P1
- 前置：admin1 已登录；resident1 在线（可查通知）；存在 PENDING 工单。
- 数据：reason=「不属于社区维修范围」；空 reason 一组。
- 步骤：
  1. admin1 调用 PATCH /api/v1/work-orders/{id}/reject，reason 为空；
  2. admin1 带理由调用 reject；
  3. resident1 查询通知列表与工单详情；
  4. admin1 再次对该工单调用 reject（已 REJECTED）。
- 预期：
  1. 空理由被参数校验拒绝（@NotBlank，400），状态不变；
  2. 驳回成功，status=REJECTED，时间线新增 REJECT 记录（含理由）；
  3. resident1 收到工单被拒绝通知（R48），详情 status=REJECTED；
  4. 已驳回再驳回被拒（5302 工单状态流转非法），状态仍为 REJECTED，
     不新增处理记录（非法流转不产生处理记录，架构设计 §6.1）。

### TC-C4-009 居民受理前取消（仅 PENDING/TO_ASSIGN/ASSIGNED/ACCEPTED）
- 关联：TR-C4-03　类型：功能　优先级：P1
- 前置：resident1 已登录；依次准备 PENDING、ASSIGNED、TO_CONFIRM、
  COMPLETED 状态工单各 1 张（后两张经 TC-C4-016/018 流程或手工造数）。
- 数据：cancelReason=「问题已自行解决」。
- 步骤：
  1. resident1 对 PENDING 工单调用 PATCH /api/v1/work-orders/{id}/cancel；
  2. 对 ASSIGNED 工单重复取消操作；
  3. 对 TO_CONFIRM 工单调用 cancel；
  4. 对 COMPLETED 工单调用 cancel。
- 预期：
  1. PENDING 取消成功，status=CANCELLED，时间线新增 CANCEL 记录；
  2. ASSIGNED 取消成功（实现口径：已派单/已接单仍可取消并通知服务人员；
     需求原文为「受理前取消」限待受理/待派单——实现放宽，记口径疑点）；
  3. TO_CONFIRM 取消被拒（5302），状态不变、不产生处理记录；
  4. COMPLETED 取消被拒（5302），状态不变。
- 备注：R19 验收「已取消仅可自待受理/待派单流转」的否定侧由
  TC-C4-011 矩阵覆盖（CANCELLED 为终态，任何动作拒绝）。

### TC-C4-010 派单对象须为启用状态服务人员
- 关联：TR-C4-04　类型：异常　优先级：P1
- 前置：admin1 已登录；存在 PENDING 工单。
- 数据：依赖：05 测试环境与数据 · 停用（FROZEN）状态的 STAFF 账号
  staff2；另备 resident1 的用户 id（非服务人员）。
- 步骤：
  1. admin1 调用 PATCH /api/v1/work-orders/{id}/assign，
     assigneeId=resident1 的用户 id；
  2. admin1 调用 assign，assigneeId=staff2（停用账号）；
  3. admin1 调用 assign，assigneeId=staff1（启用账号）。
- 预期：
  1. 非服务人员账号派单被拒（5003 服务人员不存在），工单状态不变；
  2. 停用账号派单被拒（5201 账号已冻结），工单状态不变（R20 验收）；
  3. 启用账号派单成功，status=ASSIGNED，写入派单关系
     （work_order_assignment），staff1 与居民各收到一条通知。

### TC-C4-011 工单状态机非法流转否定矩阵
- 关联：TR-C4-03、TR-C4-06　类型：异常　优先级：P0
- 前置：按合法路径准备 10 态工单各 1 张：PENDING（新提交）、
  TO_ASSIGN（依赖：05 测试环境与数据 · SQL 直插或后门造数，实现无触发
  入口）、ASSIGNED/ACCEPTED/IN_PROGRESS/TO_CONFIRM/COMPLETED/
  CLOSED/REJECTED/CANCELLED（经正常流转产生）。
- 数据：非法动作集合（当前状态 → 尝试动作）：
  REJECTED→reject/assign/cancel；CANCELLED→assign/accept/cancel；
  ASSIGNED→accept（正常）后再次 accept；ASSIGNED→reject；
  ACCEPTED→assign；IN_PROGRESS→cancel/reject；
  TO_CONFIRM→cancel/reject/assign；COMPLETED→assign/confirm/cancel；
  CLOSED→assign/reject/confirm/close。
- 步骤：
  1. 按矩阵逐格以对应角色（动作归属角色）调用相应 PATCH 端点；
  2. 每次调用后查询工单详情与时间线。
- 预期：
  1. 全部非法动作被业务拒绝（5302 工单状态流转非法或 403），
     返回明确错误信息（含当前状态提示）；
  2. 工单状态不变，时间线不新增处理记录（非法流转不产生处理记录）；
  3. 「已驳回再受理/再驳回」「非待确认发起确认」等 R19/R22 关键否定
     场景全部命中拒绝分支，无一漏网（状态机完整性 P0）。

### TC-C4-012 接单与处理权限（仅被派单人）
- 关联：TR-C4-04　类型：权限　优先级：P1
- 前置：staff1 已登录；存在 ASSIGNED 给 staff1 的工单。
- 数据：依赖：05 测试环境与数据 · 第二名启用 STAFF 账号 staff3。
- 步骤：
  1. staff3 调用 PATCH /api/v1/work-orders/{id}/accept；
  2. staff1 调用 accept（remark=「已确认，将尽快处理」）；
  3. staff3 调用 PATCH /api/v1/work-orders/{id}/process；
  4. staff1 再次调用 accept。
- 预期：
  1. 非被派单人接单被拒（403，仅被派单的服务人员可操作）；
  2. staff1 接单成功，status=ACCEPTED，写接单时间，居民收到通知；
  3. 非被派单人开始处理被拒（403），状态不变；
  4. 接单后其他人（含本人）不可再接：再次 accept 被拒（5302，
     仅 ASSIGNED 可接单）——R20「接单后其他人不可再接」判定。

### TC-C4-013 处理与结果提交（文字必填 + 多图可选）
- 关联：TR-C4-05　类型：功能　优先级：P1
- 前置：staff1 已登录；工单经 accept 后处于 ACCEPTED。
- 数据：处理结果 solution=「已更换水龙头阀芯，问题解决」；
  现场照片 2 张（jpg ≤5MB）；空 solution 一组。
- 步骤：
  1. staff1 调用 PATCH /api/v1/work-orders/{id}/process（开始处理）；
  2. staff1 调用 PATCH /api/v1/work-orders/{id}/complete，solution 为空；
  3. staff1 带 solution 调用 complete；
  4. staff1 上传 2 张现场照片（POST /api/v1/work-orders/{id}/attachments）；
  5. resident1 查询工单详情与附件列表。
- 预期：
  1. 状态 ACCEPTED→IN_PROGRESS，时间线新增 PROCESS 记录；
  2. 空结果被参数校验拒绝（@NotBlank，400），状态仍 IN_PROGRESS；
  3. 提交成功，状态 IN_PROGRESS→TO_CONFIRM（待居民确认），
     时间线新增 COMPLETE 记录（含处理结果文字）；
  4. 被派单服务人员上传附件成功（BE-ISSUE-10 修复口径）；
  5. 居民端详情可见状态待确认、处理结果与全部附件（提交图 + 现场图），
     并收到「工单已处理完成，请确认」通知（R21 验收：流转后居民端可见）。

### TC-C4-015 不满意退回处理中（R22，仅自待确认 + 须原因）
- 关联：TR-C4-06　类型：功能　优先级：P1
- 前置：resident1 已登录；存在 TO_CONFIRM 工单。
- 数据：退回原因=「漏水仍未解决，水压异常」。
- 步骤：
  1. resident1 在居民端工单详情页对 TO_CONFIRM 工单发起「不满意退回」；
  2. 若界面无入口，探测后端是否存在 TO_CONFIRM→IN_PROGRESS 的退回端点。
- 预期：
  1. 退回成功：状态 TO_CONFIRM→处理中，退回须填写原因且记录在时间线
     （R22 验收：退回仅可自待确认发起且须填原因）；
  2. **当前实现无退回端点（WorkOrderService 无 TO_CONFIRM→IN_PROGRESS
     流转入口），预期本用例执行失败并记缺陷**——用例按需求原文保留，
     结果以步骤 7 实测为准（见文末口径疑点 1）。
  3. 否定侧：非 TO_CONFIRM 状态（如 IN_PROGRESS/COMPLETED）发起退回须
     被拒（并入 TC-C4-011 矩阵断言）。

### TC-C4-016 管理员关闭工单与关闭留痕
- 关联：TR-C4-06　类型：功能　优先级：P1
- 前置：admin1 已登录；存在 COMPLETED（已确认）工单。
- 数据：closeRemark=「工单关闭，归档」。
- 步骤：
  1. admin1 调用 PATCH /api/v1/work-orders/{id}/close；
  2. 查询时间线；
  3. admin1 对 COMPLETED 但未评价的工单发起关闭（经管理端界面操作），
     观察是否存在「未评价先行提示」；
  4. 对 CLOSED 工单再次调用 close。
