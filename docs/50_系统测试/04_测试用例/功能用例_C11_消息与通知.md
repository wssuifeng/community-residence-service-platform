# 功能用例 · C11 消息与通知中心

> 依据：01_测试需求分析.md §3.11（TR-C11-01~05）、需求规格 R48~R51 + E11、接口设计 9.11、架构设计 §4/§4b。
> 编号规则：TC-C11-NNN；每条至少覆盖一个 TR；执行结果列由步骤 7 回填。
> 口径说明：①WebSocket 通道：/ws 端点（SockJS + STOMP），CONNECT 帧认证，订阅 /user/queue/notifications，载荷 {type:"NOTIFICATION", data:{...}} 包裹；反馈会话另订阅 /topic/feedback/{id}（归 C6 文件，本文件仅涉通知通道）；②unread / pull 后端返回**纯数组**（决策日志 2026-09-09 契约口径，非接口设计文档旧示例的包裹结构）；③在线推送 ≤3s 计时测量（抽样 ≥10 次）与断线重连、降级归「非功能与专项用例」TR-SP-04，本文件 TR-C11-02 仅覆盖在线推送功能性送达；④渠道分级验证深度按 Q6 裁决：勾选触发留痕 + 未勾选不触发（否定）+ 非管理员越权操作渠道勾选被拒。
> 种子数据：resident1/Resident123456、staff1/Staff123456、admin1/Admin123456（绑定种子社区）、superadmin/Admin@123456。
> 可溯源断言要素（每条事件通知通用）：通知记录含操作时间（createdAt）与来源事件（sourceType + sourceId），可回查到源业务单据。

### TC-C11-001 工单流转通知逐事件断言
- 关联：TR-C11-01　类型：统计核对　优先级：P1
- 前置：resident1、staff1、admin1 账号可用；可现场走通工单主流程（E4 前段）；三方通知中心初始状态已知。
- 数据：一张工单走完：派单（→已派单）、处理完成（→待确认）、居民确认（→已完成）三个通知触发点。
- 步骤：
  1. resident1 提交工单 → admin1 受理 → admin1 派单给 staff1；
  2. staff1 接单 → 处理 → 提交处理结果（→待确认）；
  3. resident1 确认（→已完成）；
  4. 分别登录三方调用 GET /api/v1/notifications 查看通知列表，逐条核对标题/内容/来源。
- 预期：
  1. 派单触发双向通知：staff1 收到「新工单派发」、resident1 收到「工单已派单」，内容含工单号与处理人姓名；
  2. 处理完成触发 resident1「工单已处理完成，请确认」；
  3. 居民确认触发 staff1「居民已确认工单」；
  4. 每条通知的 sourceType=WORK_ORDER、sourceId=该工单 id、createdAt 与操作时间吻合，「通知记录操作时间与来源事件，可溯源」（R48 验收标准）——凭 sourceId 回查工单详情一致。

### TC-C11-002 审核结果通知——入住申请通过/驳回
- 关联：TR-C11-01　类型：统计核对　优先级：P1
- 前置：存在两个自助注册测试账号各提交一条入住申请（一条待通过、一条待驳回）；admin1 可审核。
- 数据：依赖：05 测试环境与数据 · 两个自助注册+已提交入住申请的测试账号（或复用 C2 用例账号）。
- 步骤：
  1. admin1 通过第一条入住申请；
  2. admin1 驳回第二条（填理由）；
  3. 两个申请人分别登录查看通知列表与通知详情。
- 预期：
  1. 通过方收到入住申请通过通知（含建立的居住关系信息或申请编号）；
  2. 驳回方收到驳回通知（含驳回理由）；
  3. 两条通知 sourceType 标识申请来源、sourceId 可回查对应申请单，操作时间与审核时间一致；
  4. R48 清单「审核结果（入住）」事件覆盖确认。

### TC-C11-003 审核结果通知——资源预约确认/拒绝与违约处置
- 关联：TR-C11-01　类型：统计核对　优先级：P1
- 前置：resident1 名下有两条待审核预约 + 一条可标记违约的已预约预约；admin1 可操作（数据可复用 C7 文件 TC-C7-008/012 产物，本条仅断言通知侧）。
- 数据：拒绝理由=「时段冲突」；违约理由=「未到场」。
- 步骤：
  1. admin1 确认预约 1、拒绝预约 2；
  2. admin1 对已预约预约标记违约；
  3. resident1 登录查看通知列表，逐条核对。
- 预期：
  1. 收到「预约已确认」通知（含预约日期）；
  2. 收到「预约未通过」通知（含拒绝理由）；
  3. 收到「预约违约处置」通知（含违约理由）；
  4. 三条通知 sourceType=RESOURCE_RESERVATION、sourceId 分别指向对应预约单，可溯源回查（R48 清单「审核结果（预约）」+「违约处置」两事件覆盖）。

### TC-C11-004 租期到期提醒通知
- 关联：TR-C11-01　类型：统计核对　优先级：P1
- 前置：存在止期落在提醒窗口内（前 N 天，N 按配置）的已生效租约；租期判定与到期提醒定时任务已执行（跨日长跑归 TR-SP-03，本条验证通知产物）。
- 数据：依赖：05 测试环境与数据 · 止期落在提醒窗口内的已生效租约（可复用 C3 用例造数；定时任务触发依赖 01:30 任务执行或测试环境手动触发口径，见 03 计划）。
- 步骤：
  1. 任务执行后，租约承租居民登录查看通知列表；
  2. 绑定社区管理员（admin1）登录查看通知列表；
  3. 核对通知内容与租约信息。
- 预期：
  1. 承租居民收到租期到期提醒通知（含止期与剩余天数口径的内容）；
  2. 管理员同步收到该租约的到期提醒（R15：向居民与管理员触发）；
  3. 同一租约同一状态仅一条（去重口径，重复执行任务不重复通知）；
  4. 通知来源可溯源到该租约记录（R48 清单「租期到期」事件覆盖）。

### TC-C11-005 公告广播通知
- 关联：TR-C11-01　类型：统计核对　优先级：P1
- 前置：admin1 已登录；居民端测试账号在公告目标范围内；公告支持定向（社区/楼栋）。
- 数据：公告标题=「停水通知」；范围=种子社区；生效时间=立即。
- 步骤：
  1. admin1 发布公告（范围限绑定社区）；
  2. 目标范围内的居民账号登录查看通知列表；
  3. 核对通知与公告的关联字段。
- 预期：
  1. 「公告广播」事件产生对应通知（R48 原文清单项）：目标用户收到公告发布通知，覆盖无遗漏（范围内用户均可见）；
  2. 通知内容含公告标题，来源可溯源到该公告（sourceType/sourceId 或等价关联字段回查公告一致）；
  3. 范围外用户不收到该通知（定向口径；若实现为列表内公告可见而无声通知，按执行口径记录并在 08 缺陷跟踪挂「R48 公告广播事件通知缺失/降级」议题）。

- 步骤：

  2. 居民追问触发处理管理员的新消息通知；

### TC-C11-007 通知事件覆盖清单汇总核对（覆盖无遗漏）
- 关联：TR-C11-01　类型：统计核对　优先级：P1
- 前置：TC-C11-001~006 执行完毕（或等价事件数据就位）；superadmin 已登录。
- 数据：R48 事件清单——①工单流转；②审核结果（入住/搬出/租住/预约/看房）；③租期到期；④公告广播；⑤反馈会话新消息；⑥违约处置。
- 步骤：
  1. 汇总 TC-C11-001~006 的通知断言结果，按清单逐项勾销；
  2. 对清单中未在前序用例覆盖的事件（搬出审核、租住审核、看房预约确认），分别执行对应业务操作并核对通知；
  3. 统计每事件的「产生通知 + 可溯源」双要素通过情况。
- 预期：
  1. 「以上每个事件均产生对应通知，覆盖无遗漏」（R48 验收标准）：清单六类事件均有对应通知产生；
  2. 每类事件的通知均含操作时间与来源事件且可回查源单据；
  3. 任一事件缺失通知或不可溯源，记缺陷并挂 08 缺陷跟踪（预期疑点：看房预约确认、搬出/租住审核、公告广播的通知触达以执行结果为准）。

### TC-C11-008 在线实时推送送达（WS 通知通道）
- 关联：TR-C11-02　类型：性能　优先级：P0
- 前置：resident1 已登录且前端 WebSocket 已连接（订阅 /user/queue/notifications）；admin1 可触发面向 resident1 的事件。
- 数据：触发事件=预约确认（或工单派单）；计时口径=业务操作完成时刻 → 前端通知渲染时刻。
- 步骤：
  1. resident1 保持在线，确认 WS 连接与订阅就绪；
  2. admin1 执行预约确认操作；
  3. 观察 resident1 前端通知铃铛/列表是否实时收到推送（不出现在轮询周期后才可见的延迟假象）；
  4. 核对推送载荷结构。
- 预期：
  1. 推送经 /user/queue/notifications 到达，载荷为 {type:"NOTIFICATION", data:{...}} 包裹结构，data 含 id/seq/title/content/sourceType/sourceId；
  2. 在线状态下通知实时到达（功能性送达；≤3s 计时抽样 ≥10 次归 TR-SP-04 统一测量，本条不合格即已构成缺陷）；
  3. 推送内容与库中通知记录一致（seq 匹配）。

### TC-C11-009 上线补拉：离线期间通知不丢失
- 关联：TR-C11-03　类型：异常与边界　优先级：P0
- 前置：resident1 记录当前最新通知 seq（lastSeq）后登出/断开 WS；admin1 可连续触发多个事件。
- 数据：离线期间产生 ≥3 条不同事件通知（如：预约确认、工单派单、反馈回复）。
- 步骤：
  1. resident1 登出（或断开网络模拟离线），记录离线前最新 seq；
  2. 离线期间由 admin1/staff1 触发 ≥3 个面向 resident1 的通知事件；
  3. resident1 重新登录（前端建立连接时主动补拉，调用 GET /api/v1/notifications/pull?lastSeq={seq}）；
  4. 核对补拉结果与库内记录（SQL 直查 notification 表该用户 seq > lastSeq 的记录）。
- 预期：
  1. pull 返回**纯数组**（契约口径），包含离线期间产生的全部通知，按 seq 升序；
  2. 「登录/重连时按通知序号增量拉取离线期间通知，不丢失」（R50 原文）：补拉条数与 SQL 直查 100% 一致，无遗漏、无重复；
  3. 响应含最新 seq 游标（latestSeq 口径或以数组末元素 seq 为准，按实现契约），供下次补拉使用；
  4. 离线通知在列表页同样全部可见。

### TC-C11-010 补拉游标边界与纯数组契约
- 关联：TR-C11-03　类型：异常与边界　优先级：P0
- 前置：resident1 已登录，名下有多条历史通知；另一账号的通知数据作隔离对照。
- 数据：lastSeq=0（全量）；lastSeq=当前最新 seq（空结果）；lastSeq=中间值（增量）。
- 步骤：
  1. 调用 GET /api/v1/notifications/pull?lastSeq=0；
  2. 取返回末条 seq 作为 lastSeq 再次调用；
  3. 取中间某条 seq 调用（增量）；
  4. 用另一账号的通知 id/seq 构造越界对照（数据隔离）。
- 预期：
  1. lastSeq=0 返回该用户全部通知（纯数组，仅本人数据）；
  2. lastSeq=最新 seq 时返回空数组（无重复推送）；
  3. 中间游标仅返回 seq 更大的通知，边界不重叠不遗漏（等于 lastSeq 的不返回）；
  4. 任何游标下均不出现他人通知（recipient 级隔离）。

### TC-C11-011 未读通知列表准确
- 关联：TR-C11-04　类型：功能　优先级：P2
- 前置：resident1 名下有已读与未读通知混合；可继续产生新通知。
- 数据：初始未读数已知；新增 1 条通知。
- 步骤：
  1. 调用 GET /api/v1/notifications/unread；
  2. 触发一条新通知后再次调用；
  3. 将其中一条标记已读后再次调用；
  4. SQL 直查：SELECT COUNT(*) FROM notification WHERE user_id={id} AND is_read=0。
- 预期：
  1. 返回纯数组，仅含未读通知，按 seq 倒序；
  2. 新通知产生后未读列表即时含新条目；
  3. 标记已读后该条从未读列表消失；
  4. 「已读/未读状态准确」（R51 验收标准）：未读条数与 SQL 直查一致；若未读数超 50，仅返回最新 50 条（接口契约上限口径）。

### TC-C11-012 标记已读与全部已读（含越权与幂等）
- 关联：TR-C11-04　类型：功能　优先级：P2
- 前置：resident1 名下有若干未读通知；居民 B 名下有未读通知。
- 数据：依赖：05 测试环境与数据 · 居民 B 账号（可复用其他文件的第二居民账号）。
- 步骤：
  1. resident1 调用 PATCH /api/v1/notifications/{id}/read 标记本人一条未读通知；
  2. 对同一条再次调用（幂等对照）；
  3. resident1 取居民 B 的通知 id 调用标记已读（越权对照）；
  4. resident1 调用 PATCH /api/v1/notifications/read-all 全部已读；
  5. SQL 直查核对 is_read 状态。
- 预期：
  1. 本人通知标记成功，is_read=1；
  2. 重复标记不报错（幂等），状态保持已读；
  3. 标记他人通知被拒绝（仅通知接收人可标记，403），B 的通知保持未读；
  4. 全部已读后未读数为 0，返回本次标记条数；
  5. 已读/未读状态与库内一致，「已读/未读状态准确」（R51）。

### TC-C11-013 渠道分级：勾选模拟通道触发留痕可查
- 关联：TR-C11-04　类型：功能　优先级：P2
- 前置：admin1 已登录；渠道分级配置入口可用（公告/通知发布时的渠道勾选，站内必达 + 短信/微信服务号模拟通道）；notification_channel_log 表可 SQL 直查。
- 数据：发布信息时勾选「短信 + 微信服务号」模拟渠道（站内默认必达）。
- 步骤：
  1. admin1 发布信息（如公告）并勾选短信、微信服务号渠道；
  2. 等待通知生成后 SQL 直查：SELECT * FROM notification_channel_log WHERE notification_id IN (本次通知 id)；
  3. 核对留痕记录字段。
- 预期：
  1. 「勾选的模拟通道触发留痕可查」（R51 验收标准）：notification_channel_log 产生对应渠道（SMS/微信）发送记录；
  2. 每条留痕含通知 id、渠道、发送状态（SUCCESS/FAILED）、发送时间；
  3. 站内渠道（WEBSOCKET）记录与站外模拟渠道记录均留痕，站内必达不受勾选影响。

### TC-C11-014 渠道分级：未勾选渠道不触发（否定场景）
- 关联：TR-C11-04　类型：异常与边界　优先级：P2
- 前置：同 TC-C11-013；渠道勾选默认状态已知。
- 数据：发布信息时不勾选任何模拟渠道（仅站内）。
- 步骤：
  1. admin1 发布信息且不勾选短信/微信渠道；
  2. SQL 直查 notification_channel_log 中本次通知的记录；
  3. 核对通知本身仍正常送达。
- 预期：
  1. 「未勾选不触发」（Q6 裁决否定场景）：notification_channel_log 无本次通知的 SMS/微信渠道记录；
  2. 站内通知照常生成与送达（未勾选站外渠道不影响站内必达）；
  3. 勾选/未勾选两态的留痕差异清晰可辨。

### TC-C11-015 非管理员越权操作渠道勾选被拒（Q6 裁决）
- 关联：TR-C11-04　类型：权限　优先级：P2
- 前置：resident1、staff1 已登录可用；渠道勾选配置为管理员侧操作（R51/定义 §2 C11：管理员按信息重要性勾选广播渠道）。
- 数据：越权请求——居民/服务人员调用渠道勾选配置接口（或携带渠道勾选参数的发布类请求）。
- 步骤：
  1. resident1 尝试调用渠道勾选/渠道配置相关接口；
  2. staff1 重复步骤 1；
  3. 检查操作日志是否记录越权尝试。
- 预期：
  1. 两次越权请求均被拒绝（403/权限不足，非业务放行）；
  2. 渠道配置保持管理员原值不变；
  3. 越权尝试留有日志（越权 100% 拒绝并记录的通用口径，具体日志断言口径与 TR-SP-02 一致）。

### TC-C11-016 通知列表分页过滤与数据隔离
- 关联：TR-C11-01　类型：统计核对　优先级：P1
- 前置：resident1 名下有多条不同来源（WORK_ORDER/RESERVATION/FEEDBACK）、不同已读状态的通知；其他账号通知作对照。
- 数据：过滤条件——isRead=false；sourceType=WORK_ORDER；分页 page=1/size=10。

### TC-C11-017 E11 全流程：事件→通知→推送/入库→补拉→已读→渠道留痕
- 关联：TR-C11-05　类型：功能　优先级：P1

- 步骤：
  1. resident1 在线，admin1 确认其预约 → 观察 WS 实时推送到达；
