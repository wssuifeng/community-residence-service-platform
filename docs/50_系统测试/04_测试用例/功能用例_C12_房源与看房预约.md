# 功能用例 · C12 房源展示与看房预约

> 依据：01_测试需求分析.md §3.12（TR-C12-01~08）、需求规格 R52~R57 + E12/E10a、
> 接口设计 9.12。系统定义 v1.2 C12 判据；架构设计 §6.4 看房预约状态机。
> 编号规则：TC-C12-NNN；每条至少覆盖一个 TR；执行结果列由步骤 7 回填。
> 实现口径（以代码与迁移脚本为准，与接口设计 9.12 原稿的差异已在用例内标注）：
> - 房源创建 DTO（CreateHousingDTO）：houseId/title 必填，monthlyRent 必填非负，
>   description≤2000 可选，images 为逗号分隔 URL 串；标题≤200（接口设计写 100，以实现为准）；
>   户型/朝向在 house 表（V4 加 layout/orientation 列），房源关联房屋间接携带；
> - 房源状态：AVAILABLE/RESERVED/RENTED/OFFLINE；公开列表与详情按状态过滤
>   （已出租/下线对游客不可见——HousingController 注释口径）；
> - 房源列表筛选参数：communityId/status/minRent/maxRent/keyword（无独立
>   户型/租售类型参数——R53 的户型/租售筛选经 keyword 或前端组合实现，用例按
>   实现口径设计并留口径疑点，见文末）；
> - 删除保护：存在 TO_CONFIRM/RESERVED 预约时不可删（错误码 5801 口径），物理删除；
> - 看房时段：housing_timeslot 为周循环模板（day_of_week + start/end + is_available），
>   available-slots 接口按日期范围展开 + 占用计数，maxBookings 固定 1（实现注释口径）；
> - 预约创建：居民取令牌身份（user_id）；游客必填 visitor_name + contact_phone；
>   时段须完整落入某可用模板（半重叠/跨界拒绝）；同房源同日期同起止时间
>   在 TO_CONFIRM/RESERVED 状态下仅一条（冲突检测）；预约日期受
>   viewing.max_days_ahead（默认 14 天）约束；
> - 状态机（代码 validateTransition 权威）：TO_CONFIRM→{RESERVED, CANCELLED}；
>   RESERVED→{COMPLETED, CANCELLED, VIOLATED}；其余流转全部 5802 口径拒绝；
> - 确认/完成/违约仅管理端（ADMIN+，checkCommunityAccess 数据级）；取消居民限本人
>   （user_id 比对）；违约登记写 violation_record（VIEWING_NO_SHOW，居民预约），
>   游客无账号不计——接口设计 9.12.2.7 的「违约次数累计/超限自动冻结/手机号黑名单」
>   当前实现为「记录违约」，处置粒度口径疑点见文末；
> - 通知：接口设计 9.12.2 原稿的「通知社区管理员/通知访客」在 housing 模块代码
>   未见直调 NotificationService——确认/取消通知以 C11 事件覆盖（TR-C11-01）归口径，
>   本文件仅按 R55「确认/取消均通知对方」断言，执行时若未达标记缺陷。
> 种子数据（Flyway V6）：阳光花园社区在架房源「阳光花园 1 号楼 102 室 · 三室两厅」
> （house_id=102，月租 4500，AVAILABLE），周循环时段模板：每天 09:00-12:00 与 14:00-18:00。

### TC-C12-001 房源创建-正向与必填完整性校验
- 关联：TR-C12-01　类型：功能　优先级：P1
- 前置：admin1 已登录；阳光花园社区下有空置房屋可用（house.layout='2室1厅1卫'，V4 字段）。
- 数据：依赖：05 测试环境与数据 · 空置房屋 H-T1（带 layout/orientation 字段值）。
- 步骤：
  1. POST /api/v1/housings 提交完整合法房源（houseId=H-T1、标题、描述、月租 3500、押金、图片 URL）。
  2. GET /api/v1/housings/{id} 查详情，核对全部字段与关联房屋地址回显。
  3. POST /api/v1/housings 缺 title（空串）。
  4. POST /api/v1/housings 缺 houseId、缺 monthlyRent 各一次。
  5. POST /api/v1/housings monthlyRent=-100。
  6. POST /api/v1/housings description 超 2000 字。
- 预期：
  1. 创建成功，初始状态 AVAILABLE，viewCount=0。
  2. 字段一致（含社区名/房屋位置回显）——地址、面积、租金信息真实准确完整（R52 真实性自查清单口径：关联真实房屋）。
  3. 校验拒绝（title @NotBlank）。
  4. 均校验拒绝（@NotNull）。
  5. 校验拒绝（非负约束）。
  6. 校验拒绝（@Size max 2000）——完整性必填校验生效。

### TC-C12-002 房源唯一性约束-同一房屋重复上架拒绝
- 关联：TR-C12-01　类型：异常　优先级：P1
- 前置：admin1 已登录；H-T1 已存在关联的在架房源（TC-C12-001 产物）。
- 数据：houseId=H-T1 的第二条创建请求。
- 步骤：
  1. POST /api/v1/housings 再次以 houseId=H-T1 创建房源。
  2. 将 H-T1 现有房源状态改为 OFFLINE 后再次创建。
  3. 恢复：删除步骤 2 新建房源、原房源改回 AVAILABLE。
- 预期：
  1. 创建被拒（同一房屋仅允许一条在架房源——HousingService 口径「同一房屋仅允许一条非下线房源」）。
  2. 下线后可重新创建（下线视同释放，按实现口径断言）。
  3. 环境恢复原状。

### TC-C12-003 房源编辑/状态流转/删除保护
- 关联：TR-C12-01　类型：功能　优先级：P1
- 前置：admin1 已登录；测试房源 F1（AVAILABLE，无预约）；F2（有一条约在 TO_CONFIRM 的预约）。
- 数据：依赖：05 测试环境与数据 · 房源 F2 + 一条 TO_CONFIRM 预约（或现场经 TC-C12-012 链路创建）。
- 步骤：
  1. PUT /api/v1/housings/{F1} 修改月租 3500→3800 与描述。
  2. PATCH /api/v1/housings/{F1}/status，body {status:"OFFLINE", remark:"测试下架"}。
  3. 游客调用 GET /api/v1/housings/{F1} 详情与 GET /api/v1/housings?status=AVAILABLE 列表。
  4. PATCH /api/v1/housings/{F1}/status 恢复 AVAILABLE。
  5. DELETE /api/v1/housings/{F2}（存在未完成预约）。
  6. 将 F2 预约取消（或登记完成）后再 DELETE /api/v1/housings/{F2}。
- 预期：
  1. 编辑成功，修改后字段一致。
  2. 状态流转成功。
  3. OFFLINE 后详情不可见（404/明确不可见口径）、列表不含 F1——下架后前台不可见。
  4. 恢复成功。
  5. 删除被拒（5801 口径：存在未完成看房预约）。
  6. 无未完成预约后删除成功——删除保护边界成立。

  2. 仅返回租金区间内房源（边界值 3000/5000 含端点，按实现断言）。

### TC-C12-006 房源浏览量统计-浏览计数与回写
- 关联：TR-C12-02　类型：统计核对　优先级：P1
- 前置：种子房源在架；浏览计数为「Redis INCR + 每 5 分钟定时回写」双段口径
  （架构设计 §5：housing:view:{id} 计数 → view_count 累加，回写成功删 key）。
- 数据：记录种子房源当前 view_count 基线 V0（SQL 直查）。
- 步骤：
  1. 游客与居民各调用 POST /api/v1/housings/{id}/view 若干次（共 5 次）。
  2. 立即 SQL 查 view_count（回写周期内，可能仍为 V0——记录即时值）。
  3. 等待浏览回写定时任务执行（≤5 分钟，TR-SP-03 口径）。
  4. 再次 SQL 查 view_count。
  5. 超管查运营看板房源浏览量指标（联动 TR-C9-02）。
- 预期：
  1. 5 次调用均返回成功（游客/居民均可浏览）。
  2. 即时值 ≤V0+5（回写前 Redis 承接，允许未落库）。
  3. 任务已执行（sys_task_log 有 ViewCountSyncTask 类执行记录）。
  4. view_count = V0+5——5 次浏览全部计入、无丢失。
  5. 看板浏览量与明细一致——浏览量计入统计（R53/R57）。

  3. 更新生效。
  4. 第二条模板创建成功。

### TC-C12-008 available-slots 接口-按日期范围展开与占用计数（BE-ISSUE-5 回归）
- 关联：TR-C12-03　类型：功能　优先级：P1
- 前置：种子房源（周模板：每天 09:00-12:00、14:00-18:00）；BE-ISSUE-5 修复后该接口须正常返回。
- 数据：startDate=下周一起 7 天，endDate=下周日。
- 步骤：
  1. 游客 GET /api/v1/housings/{种子房源id}/available-slots?startDate={下周一}&endDate={下周日}。
  2. 核对返回时段：每天 2 条（09:00-12:00、14:00-18:00），共 14 条，升序排列。
  3. 核对每条 status 与 currentBookings 基线（无预约时 0）。
  4. 创建一条下周三 09:00-12:00 的预约（TO_CONFIRM），再次调用本接口。
  5. 只传 startDate 不传 endDate（可选参数边界）。
- 预期：
  1. 200 返回时段数组（BE-ISSUE-5 回归通过：接口可用、无 500）。
  2. 14 条、日期+开始时间升序、时间与模板一致。
  3. 全部 AVAILABLE、currentBookings=0。
  4. 下周三 09:00-12:00 的 currentBookings=1（或该时段不再可约——按「maxBookings=1、
     占用即满」实现口径断言 status=FULL/不可约），其余时段不变。
  5. 不报错，返回范围按实现口径（单日或默认区间）——可选参数不引发异常。

### TC-C12-009 时段外预约拒绝并提示可预约范围
- 关联：TR-C12-03　类型：异常　优先级：P1
- 前置：种子房源周模板 09:00-12:00/14:00-18:00；居民 resident1 已登录。
- 数据：下周三为示例日期 D。
- 步骤：
  1. resident1 POST /api/v1/viewing-appointments：D 13:00-14:00（落在模板间隙）。
  2. resident1 提交 D 08:30-12:00（起点早于模板）。
  3. resident1 提交 D 09:00-13:00（跨界两个模板区间）。
  4. resident1 提交 endTime 早于 startTime（09:00-08:00）。
  5. 对某有预约的时段模板尝试 DELETE /api/v1/housing-timeslots/{id}（对照：配置侧删除保护）。
- 预期：
  1. 拒绝（INVALID_PARAM 口径「所选时间不在房源可预约时段内」）。
  2. 拒绝（未完整落入模板）。
  3. 拒绝（跨界即半重叠，须完整覆盖口径）。
  4. 拒绝（结束时间必须晚于开始时间）。
  5. 删除被拒（5803 口径有预约时不可删）——四步拒绝均提示可预约范围或明确业务错误（时段外请求被拒，R54）。

### TC-C12-010 预约日期边界-过早/超期/过期日期拒绝
- 关联：TR-C12-03　类型：异常　优先级：P1
- 前置：种子房源在架；resident1 已登录；viewing.max_days_ahead 默认 14 天。
- 数据：以当前日期为基准：昨天、今天、第 14 天、第 15 天。
- 步骤：
  1. 提交 appointmentDate=昨天 09:00-12:00。
  2. 提交 appointmentDate=今天（当日预约，时段尚未过）。
  3. 提交 appointmentDate=第 14 天 09:00-12:00。
  4. 提交 appointmentDate=第 15 天 09:00-12:00。
- 预期：
  1. 拒绝（过去日期不可约）。
  2. 当日可约或按实现口径拒绝（记录实际行为）。
  3. 14 天内成功（边界含端点——若实现为「不超过 14 天」则第 14 天可约）。
  4. 拒绝（超 viewing.max_days_ahead 窗口）——提前天数约束生效。

### TC-C12-011 看房预约正向流转-待确认→已预约→已完成（居民链路）
- 关联：TR-C12-04　类型：功能　优先级：P0
- 前置：resident1 已登录；种子房源在架；下周四 D 09:00-12:00 空闲。
- 数据：resident1 令牌；日期 D。
- 步骤：
  1. resident1 POST /api/v1/viewing-appointments：{housingId, appointmentDate:D, startTime:09:00, endTime:12:00, contactPhone, remark}。
  2. 查询 GET /api/v1/viewing-appointments/{id}，核对状态与字段（visitorName 回显居民真名）。
  3. admin1 调用 PATCH /api/v1/viewing-appointments/{id}/confirm，body {remark:"预约确认"}。
  4. PATCH /api/v1/viewing-appointments/{id}/complete，body {remark:"看房完成"}。
  5. 全程后查操作日志/流转记录。
- 预期：
  1. 创建成功，状态 TO_CONFIRM，user_id 绑定 resident1（居民链路）。
  2. 状态 TO_CONFIRM，字段一致。
  3. 确认成功，状态 RESERVED。
  4. 完成成功，状态 COMPLETED——「待确认→已预约→已完成」主干全可达。
  5. 每次流转有留痕记录（操作人/时间/备注，R55「全状态流转留痕」）。

### TC-C12-012 看房预约取消流转-两源状态可取消 + 通知
- 关联：TR-C12-04　类型：功能　优先级：P0
- 前置：resident1 已登录；准备两条独立预约：A（TO_CONFIRM）、B（CONFIRMED/RESERVED）。
- 数据：日期 D1/D2 不同时段，避免冲突检测互扰。
- 步骤：
  1. resident1 对 A 调用 PATCH /api/v1/viewing-appointments/{A}/cancel，body {reason:"临时有事"}。
  2. admin1 对 B 确认后，resident1 对 B 调用 /cancel。
  3. 核对 A、B 状态均为 CANCELLED，reason 记入 remark。
  4. 取消后核对 available-slots 中该时段恢复可约（占用释放口径）。
  5. 通知断言：预约创建（新预约通知管理方）与取消（通知对方）后，admin1 与
  resident1 各自查通知列表（GET /api/v1/notifications）。
- 预期：
  1. TO_CONFIRM→CANCELLED 成功。
  2. RESERVED→CANCELLED 成功——两源状态均可取消。
  3. 状态与取消原因留痕一致。
  4. 时段占用释放（可再次被预约）。
  5. 确认/取消均通知对方（R55 口径；若实现未挂通知事件，记缺陷并归 C11 事件清单核对）。

### TC-C12-013 非法流转拒绝-状态机否定矩阵
- 关联：TR-C12-04　类型：异常　优先级：P0
- 前置：构造三个不同状态的预约：P1=TO_CONFIRM、P2=RESERVED、P3=COMPLETED、
  P4=VIOLATED、P5=CANCELLED（后三者可经前置操作或 SQL 造数达成终态）。
- 数据：依赖：05 测试环境与数据 · 终态预约 P3/P4/P5（SQL 直插或链路构造）。
- 步骤：
  1. 对 P1（TO_CONFIRM）调用 complete 与 violate（跳态）。
  2. 对 P2（RESERVED）调用 confirm（重复确认）。
  3. 对 P3（COMPLETED）调用 confirm/complete/cancel/violate 全部四操作。
  4. 对 P4（VIOLATED）、P5（CANCELLED）各调用 confirm 与 cancel。
  5. 核对每个拒绝后预约状态未变化。
- 预期：

  2. 拒绝（RESERVED 不可再确认）。
  3. 全部拒绝（终态不可流转）。
  4. 全部拒绝（VIOLATED/CANCELLED 为终态）。
  5. 状态零变化——非法流转 100% 拒绝且不留半成品数据。
