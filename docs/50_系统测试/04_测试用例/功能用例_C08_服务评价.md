# 功能用例 · C8 服务评价管理

> 依据：01_测试需求分析.md §3.8（TR-C8-01~04）、需求规格 R37~R39 + E8、接口设计 9.8。
> 编号规则：TC-C8-NNN；每条至少覆盖一个 TR；执行结果列由步骤 7 回填。
> 口径说明：可评价状态为工单「已完成/已关闭」（COMPLETED/CLOSED，R22 联动：已完成的工单在关闭前保持可评价）；评分 1~5 星整数；「≤2 星」= rating ∈ {1,2}（量化口径与 20 包一致）；不满意评价 = isSatisfied=false。
> 种子数据：resident1/Resident123456（已入住）、staff1/Staff123456、admin1/Admin123456、superadmin/Admin@123456；V7 种子服务类别 7 类。
> 统计核对方法：SQL 直查 MySQL（Flyway 迁移注释为状态枚举权威）比对接口返回，脚本以 03 计划/05 测试环境与数据为准。

### TC-C8-001 已完成工单首次评价成功
- 关联：TR-C8-01　类型：功能　优先级：P1
- 前置：resident1 名下存在一条已完成（COMPLETED）工单（E4 流程产物或预置）；resident1 已登录。
- 数据：rating=5；content=「维修及时，态度好」；tags=「及时,专业」；isSatisfied=true。
- 步骤：
  1. 调用 POST /api/v1/work-orders/{orderId}/evaluation 提交评价；
  2. 调用 GET /api/v1/work-orders/{orderId}/evaluation 查询该工单评价；
  3. 服务人员（被派单 staff）登录查看是否收到评价相关触达（如实现）。
- 预期：
  1. 提交返回 code=200，评价落库（评分、文字评语、是否满意）；
  2. 查询返回的评价与提交内容一致，关联工单号正确；
  3. 「居民对已完成工单评价一次（满意度等级 1~5 星 + 文字评语）」（R37 原文）满足。

### TC-C8-002 重复评价被拒（一单一评）
- 关联：TR-C8-01　类型：异常与边界　优先级：P1
- 前置：TC-C8-001 已完成（该工单已有一条评价）。
- 数据：同工单第二次评价请求，rating=4、content=「补充评价」。
- 步骤：
  1. resident1 对同一工单再次调用 POST /api/v1/work-orders/{orderId}/evaluation；
  2. SQL 直查库：SELECT COUNT(*) FROM work_order_evaluation WHERE work_order_id={orderId}。
- 预期：
  1. 第二次提交被拒绝（评价重复类业务错误码，非 500）；
  2. 「每工单仅一次评价，重复提交被拒绝」（R37 验收标准）；
  3. 库中该工单评价记录仍仅 1 条。

### TC-C8-003 非可评价状态工单不可评价
- 关联：TR-C8-01　类型：异常与边界　优先级：P1
- 前置：resident1 名下分别存在待受理（PENDING）、处理中（IN_PROGRESS）、待确认（TO_CONFIRM）状态的工单各一条。
- 数据：三组请求分别对三个工单提交评价（rating=5）。
- 步骤：
  1. 对待受理工单调用 POST /api/v1/work-orders/{id}/evaluation；
  2. 对处理中工单重复调用；
  3. 对待确认工单重复调用；
  4. SQL 直查库确认三工单均无评价记录。
- 预期：
  1. 三次请求全部被拒绝（评价不允许类业务错误码）；
  2. 「非已完成状态不可评价」（TR-C8-01 要点，R37 口径）；
  3. 库中未产生任何评价记录。

### TC-C8-004 非提交人评价被拒
- 关联：TR-C8-01　类型：权限　优先级：P1
- 前置：resident1 名下存在一条已完成且未评价的工单；另一已入住测试居民账号 B。
- 数据：依赖：05 测试环境与数据 · 第二个已入住测试居民账号 B（或复用 C7 冲突用例账号）。
- 步骤：
  1. 居民 B 调用 POST /api/v1/work-orders/{orderId}/evaluation 尝试评价 resident1 的工单；
  2. 居民 B 调用 GET /api/v1/work-orders/{orderId}/evaluation 查询该工单评价（对照）。
- 预期：
  1. B 的评价提交被拒绝（403：仅工单提交人可评价）；
  2. 评价查询按工单访问权限口径执行（拥有工单访问权限可查、不可评）；
  3. 该工单仍处于未评价状态，可由 resident1 正常评价。

### TC-C8-005 星级边界：0/6 拒绝，1/5 放行
- 关联：TR-C8-01　类型：异常与边界　优先级：P1
- 前置：resident1 名下有两条已完成未评价工单（工单甲、乙）。
- 数据：rating=0（低于下界）、rating=6（高于上界）、rating=1（下界）、rating=5（上界）。
- 步骤：
  1. 对工单甲分别以 rating=0、rating=6 提交评价；
  2. 对工单甲以 rating=1 提交（isSatisfied=false）；
  3. 对工单乙以 rating=5 提交（isSatisfied=true）。
- 预期：
  1. rating=0 与 rating=6 均被参数校验拒绝（@Min(1)/@Max(5) 口径）；
  2. 边界值 1 与 5 均提交成功，「满意度等级 1~5 星」（R37 量化原文）；
  3. rating=1 的评价标记为不满意（进入不满意跟进清单，衔接 TC-C8-006）。

### TC-C8-006 ≤2 星评价触发管理员跟进闭环
- 关联：TR-C8-02　类型：功能　优先级：P1
- 前置：一条 rating=1 或 rating=2 的不满意评价已存在（TC-C8-005 产物）；admin1 已登录。
- 数据：rating=2、content=「处理拖沓，未彻底解决」、isSatisfied=false；跟进内容=「已电话回访居民，安排复检并补修」。
- 步骤：
  1. admin1 调用 GET /api/v1/evaluations/unsatisfied 查看不满意评价列表；
  2. admin1 调用 POST /api/v1/evaluations/{evaluationId}/followup 添加跟进（跟进内容）；
  3. 调用 GET /api/v1/evaluations/{evaluationId}/followups 查询跟进记录；
  4. 再次对照：一条 rating=5 的满意评价（TC-C8-005 产物）是否出现在不满意列表。
- 预期：
  1. 不满意评价（≤2 星/isSatisfied=false）出现在不满意跟进列表，未跟进前处于待跟进状态；
  2. 「≤2 星评价触发管理员跟进」（R38 原文）：跟进提交成功，记录处理人与时间；
  3. 「处理结果记录在案」（R38）：跟进记录列表含跟进内容、跟进人、跟进时间，留痕可查；
  4. 满意评价不出现在不满意列表（触发范围准确，不误伤）。

### TC-C8-007 满意评价不可跟进（否定场景）
- 关联：TR-C8-02　类型：异常与边界　优先级：P1
- 前置：一条 rating=5 的满意评价存在（TC-C8-005 产物）。
- 数据：跟进内容=「例行回访」。
- 步骤：
  1. admin1 对满意评价调用 POST /api/v1/evaluations/{evaluationId}/followup。
- 预期：
  1. 请求被拒绝（仅不满意评价需要跟进）；
  2. 库中该满意评价无跟进记录，跟进机制仅由不满意评价触发。

### TC-C8-008 跟进闭环判定：未跟进不关闭、已跟进可关闭
- 关联：TR-C8-02　类型：功能　优先级：P1
- 前置：两条不满意评价（A 未跟进、B 已跟进，B 可复用 TC-C8-006 产物）。
- 数据：依赖：05 测试环境与数据 · 预置一条未跟进的不满意评价 A（rating=1）。
- 步骤：
  1. admin1 查询不满意评价列表，按是否已跟进区分 A/B；
  2. 对 A 补充跟进记录后再次查询列表；
  3. 对 B 追加第二条跟进记录（多次跟进留痕）。
- 预期：
  1. A 在未跟进时处于待跟进（跟进流程未关闭），B 已有跟进记录视为已处理；
  2. A 补跟进后进入已处理口径，「不满意评价均有跟进记录后才可关闭跟进流程」（R38 验收标准）；
  3. B 的多次跟进全量留痕（跟进记录列表按时间升序完整呈现，不被覆盖）。

### TC-C8-009 评价统计聚合与明细一致（核对方法：SQL 直查 vs 接口）
- 关联：TR-C8-03　类型：统计核对　优先级：P2
- 前置：admin1 已登录；库内评价数据覆盖 ≥3 个数据场景——场景①：种子基线；场景②：单社区新增若干条不同星级评价（前序用例产物）；场景③：另一社区的评价数据（隔离对照）。
- 数据：抽样方法——对每一统计指标（总数/平均分/满意率/分档分布）在 3 个场景下分别取数核对（01 §4：每指标抽样 ≥3 数据场景）。
- 步骤：
  1. 调用 GET /api/v1/statistics/evaluations?communityId={id} 获取评价统计（总数、平均分、满意率、评分分档）；
  2. SQL 直查库：SELECT COUNT(*), AVG(rating), SUM(is_satisfied=1)/COUNT(*) FROM work_order_evaluation WHERE community_id={id}；
  3. SQL 直查分档：SELECT rating, COUNT(*) FROM work_order_evaluation WHERE community_id={id} GROUP BY rating；
  4. 切换社区/全局（超管不传 communityId）重复步骤 1~3，覆盖其余场景。
- 预期：
  1. 每场景下接口的 total/averageRating/satisfiedRate 与 SQL 直查结果 100% 相符（平均分按实现舍入口径四舍五入 1 位小数比对）；
  2. ratingDistribution 各档计数与 SQL 分组结果逐档一致；
  3. 「聚合数值与评价明细一致」（R39 验收标准）：抽样 100% 相符，任一不符记缺陷。

### TC-C8-010 按服务人员与服务类别聚合满意度（R39 双维度）
- 关联：TR-C8-03　类型：统计核对　优先级：P2
- 前置：库内存在 ≥2 名服务人员被派单并完成、且收到不同星级评价的工单；类别覆盖 ≥2 类（V7 种子类别）；admin1 已登录。
- 数据：依赖：05 测试环境与数据 · 造数覆盖「服务人员 × 服务类别 × 星级」组合（SQL 直插或经 E4 流程产生，方法见 05 文档）。
- 步骤：
  1. 调用评价统计/看板评价相关接口，获取按服务人员、按服务类别的满意度聚合；
  2. SQL 直查：按工单表关联派单（work_order_assignment）与类别，分组计算各服务人员/各类别的评价数与平均分；
  3. 逐维度比对接口聚合值与 SQL 明细值。
- 预期：
  1. 「按服务人员、服务类别聚合满意度」（R39 原文）两个维度均能输出聚合结果（若接口缺失任一维度，记缺陷并挂 08 缺陷跟踪）；
  2. 每一服务人员、每一类别的聚合评价数与平均分与 SQL 明细 100% 相符；
  3. 无评价的服务人员/类别不出现在聚合结果或计数为 0，口径一致。

### TC-C8-011 E8 全流程：完成→评价→跟进→计入统计
- 关联：TR-C8-04　类型：功能　优先级：P1
- 前置：resident1、staff1、admin1 账号可用；E4 前段（提交→受理→派单→处理→居民确认→已完成）可现场执行或已具备已完成工单。
- 数据：主路径 rating=5；分支路径 rating=2（不满意，触发跟进）。
- 步骤：
  1. 居民确认工单 → 已完成；
  2. 主路径：居民提交 5 星评价；
  3. 分支路径：另选已完成工单提交 2 星评价 → 管理员在不满意列表跟进并记录结果；
  4. 调用评价统计接口，核对两条新评价均已计入总数/分档/满意率。
- 预期：
  1. 仅已完成工单可评价，两条评价分别落库；
  2. 「（≤2 星）管理员跟进 → 记录」（E8 数据流）：2 星评价出现在不满意列表、跟进记录在案；
  3. 「计入统计（R39/R40）」（E8 数据流）：统计接口的总数 +2，分档 5 星 +1、2 星 +1，满意率按新样本重新计算且与 SQL 直查一致；
  4. 全流程各步留痕（评价/跟进操作日志可查）。
