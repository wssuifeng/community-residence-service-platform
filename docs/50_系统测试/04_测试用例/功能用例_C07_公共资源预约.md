# 功能用例 · C7 公共资源预约管理

> 依据：01_测试需求分析.md §3.7（TR-C7-01~06）、需求规格 R32~R36 + E7、接口设计 9.7、架构设计 §6.3（资源预约 6 态状态机）。
> 编号规则：TC-C7-NNN；每条至少覆盖一个 TR；执行结果列由步骤 7 回填。
> 口径说明：并发冲突专项（N 路并发提交）在「非功能与专项用例」文件的 TR-SP-01 设计，本文件仅覆盖单线程的时段外拒绝、冲突拒绝与首尾相接/半重叠边界，不重复设计。
> 状态枚举（权威口径：Flyway 迁移脚本注释 + 架构设计 §6.3）：PENDING 待审核 / RESERVED 已预约 / COMPLETED 已完成 / REJECTED 已拒绝 / CANCELLED 已取消 / VIOLATED 已违约。
> 种子数据：V6 健身房（GYM，容量 10）时段模板为周一至周五 09:00-12:00、14:00-18:00；居民 resident1/Resident123456（已入住）、社区管理员 admin1/Admin123456、超管 superadmin/Admin@123456。

### TC-C7-001 时段内预约申请正常提交
- 关联：TR-C7-01　类型：功能　优先级：P1
- 前置：后端 8080 / 前端 5173 已启动；居民 resident1 已登录且居住关系有效（已入住）；种子健身房资源与周一至周五时段模板存在。
- 数据：资源=健身房（V6 种子）；reserveDate=下一个工作日（周一至周五，避开周末）；startTime=09:00、endTime=10:00（完全落在 09:00-12:00 模板内）；purpose=晨练；contactPhone=13800000001。
- 步骤：
  1. 居民端进入「资源预约」页，选择健身房与目标日期；
  2. 调用 GET /api/v1/resources/{resourceId}/available-slots?startDate=…&endDate=… 查看可约时段；
  3. 调用 POST /api/v1/resource-reservations 提交预约（resourceId/reserveDate/startTime/endTime/purpose/contactPhone）；
  4. 调用 GET /api/v1/resource-reservations/{id} 查询该预约详情。
- 预期：
  1. 可约时段列表按日期+开始时间升序返回，目标日期含 09:00-12:00、14:00-18:00 两个 AVAILABLE 时段及容量/占用计数；
  2. 提交返回 code=200，预约落库且状态为「待审核」（PENDING）；
  3. 详情返回的资源、日期、时段、用途、联系电话与提交一致；
  4. 「时段须落在该资源可预约时段配置内」满足时提交后状态「待审核」（R32 验收标准）。

### TC-C7-002 时段外预约请求被拒并提示可预约范围
- 关联：TR-C7-01　类型：异常与边界　优先级：P1
- 前置：同 TC-C7-001；已获取健身房时段模板（周一至周五 09:00-12:00、14:00-18:00）。
- 数据：三组非法请求——A：startTime=08:00、endTime=09:00（早于模板）；B：startTime=11:00、endTime=14:00（跨越 12:00-14:00 模板间隙）；C：reserveDate=下一个周六或周日（无可约模板）。
- 步骤：
  1. 以请求 A 调用 POST /api/v1/resource-reservations；
  2. 以请求 B 重复提交；
  3. 以请求 C 重复提交；
  4. 每次失败后调用 available-slots 核对系统返回的可用时段信息。
- 预期：
  1. 请求 A 被拒绝（业务错误，非 500），提示时间不在资源可预约时段内；
  2. 请求 B 被拒绝（跨模板间隙视为时段外）；
  3. 请求 C 被拒绝（非开放日无模板）；
  4. 「时段外请求被拒绝并提示；提交后状态『待审核』」——仅时段内请求进入待审核，三组请求均未产生预约记录（R32 验收标准；时段外提交不入状态机，架构 §6.3 口径）。

### TC-C7-003 起止时间非法与必填校验
- 关联：TR-C7-01　类型：异常与边界　优先级：P1
- 前置：同 TC-C7-001。
- 数据：endTime 早于 startTime（如 10:00-09:00）；endTime 等于 startTime（09:00-09:00）；缺少 resourceId 或 reserveDate。
- 步骤：
  1. 提交 endTime < startTime 的预约；
  2. 提交 endTime = startTime 的预约；
  3. 分别缺省 resourceId、reserveDate 提交。
- 预期：
  1. 步骤 1、2 返回参数校验错误，提示结束时间必须晚于开始时间；
  2. 步骤 3 返回 @NotNull 校验错误（400 类业务错误码）；
  3. 三种请求均未产生预约记录。

### TC-C7-004 同一居民同资源同日重复预约被拒（单线程）
- 关联：TR-C7-02　类型：异常与边界　优先级：P0
- 前置：resident1 已对健身房在某工作日成功提交一条「待审核/已预约」状态的预约（可复用 TC-C7-001 产物）。
- 数据：同居民、同资源、同日期、另一时段（如 14:00-15:00）。
- 步骤：
  1. resident1 对同一资源同一日期再次调用 POST /api/v1/resource-reservations（不同时段）；
  2. resident1 改约另一日期提交，验证仅同日受限。
- 预期：
  1. 第一次重复提交被拒绝，提示同一天已预约该资源，不可重复预约；
  2. 另一日期的预约正常受理（状态待审核）；
  3. 库中该居民该资源该日期的有效预约（待审核/已预约）仅 1 条。

### TC-C7-005 容量满的同时段预约被拒（单线程冲突拒绝）
- 关联：TR-C7-02　类型：异常与边界　优先级：P0
- 前置：容量 1 的测试资源（如「会议室」）及时段模板已由管理员配置；两个测试居民账号 A、B 均已入住该社区。
- 数据：依赖：05 测试环境与数据 · 新建容量=1 的公共资源与时段模板 + 第二个已入住测试居民账号 B（resident1 可作 A）。
- 步骤：
  1. 居民 A 对容量 1 资源提交某日 09:00-10:00 预约并经管理员确认（已预约）；
  2. 调用 available-slots 查看该时段状态；
  3. 居民 B 对同资源同日同时段（09:00-10:00）提交预约。
- 预期：
  1. 步骤 2 中该时段占用计数达容量上限，状态标记为 FULL；
  2. 居民 B 的提交被拒绝（预约冲突类错误码），提示该时段预约已满；
  3. 「同一资源同一时段的重叠预约 100% 拦截」——单线程场景下库中该时段有效预约数不超过容量（R33；并发场景归 TR-SP-01）。

### TC-C7-006 半重叠时段预约拦截（单线程边界）
- 关联：TR-C7-02　类型：异常与边界　优先级：P0
- 前置：同 TC-C7-005（容量 1 资源）；居民 A 已成功预约某日 09:00-10:00（已预约状态）。
- 数据：居民 B 请求同资源同日 09:30-10:30（与 A 的时段半重叠）；对照组：同资源同日 10:30-11:00（不重叠，落在模板内）。
- 步骤：
  1. 居民 B 提交 09:30-10:30 预约；
  2. 居民 B 提交对照请求 10:30-11:00。
- 预期：
  1. 半重叠请求被拒绝（R33：重叠预约 100% 拦截；若实现按起止时刻精确匹配计数而放行半重叠，记缺陷）；
  2. 对照请求（与既有预约无时间重叠）正常受理为待审核；
  3. 库中无与 A 时段重叠的有效预约。

### TC-C7-007 首尾相接时段预约放行（单线程边界）
- 关联：TR-C7-02　类型：异常与边界　优先级：P0
- 前置：容量 1 资源（同 TC-C7-005）；居民 A 已预约某日 09:00-10:00；居民 B 账号可用。
- 数据：居民 B 请求同资源同日 10:00-11:00（与 A 预约首尾相接、不重叠）。
- 步骤：
  1. 居民 B 提交 10:00-11:00 预约；
  2. 管理员确认 B 的预约；
  3. 查询该资源当日预约列表。
- 预期：
  1. 首尾相接（结束时刻=下一预约开始时刻，区间不重叠）请求正常受理，不被误判为冲突；
  2. 确认成功，B 预约状态为已预约；
  3. 当日两条预约（A 09:00-10:00、B 10:00-11:00）并存且均有效。

### TC-C7-008 审核通过与拒绝流转及通知（R34）
- 关联：TR-C7-03　类型：功能　优先级：P1
- 前置：存在两条居民提交的待审核预约（PENDING）；管理员 admin1 已登录（绑定该社区）。
- 数据：预约 1（正常用途）；预约 2（用途可疑/时段冲突），拒绝理由=「时段安排冲突，请改约」。
- 步骤：
  1. 管理员调用 PATCH /api/v1/resource-reservations/{id1}/confirm 审核通过预约 1；
  2. 管理员调用 PATCH /api/v1/resource-reservations/{id2}/reject，不填 reason 提交；
  3. 补填 reason 后重新提交拒绝；
  4. 居民端登录被预约居民账号，查看通知中心与本人预约列表。
- 预期：
  1. 预约 1 状态流转「待审核→已预约」，确认操作留痕（操作日志可见）；
  2. 缺省 reason 的拒绝请求被参数校验拒绝（拒绝须填理由）；
  3. 预约 2 状态流转「待审核→已拒绝」，理由留存于预约记录；
  4. 「拒绝/取消通知对方」——两位居民均收到对应站内通知（确认通知/未通过通知，含日期与理由），通知可溯源到预约单；
  5. 全状态流转留痕：两次流转均可在操作日志检索到（操作人/时间/对象）。

### TC-C7-009 用户取消预约（待审核/已预约两态）与容量释放
- 关联：TR-C7-03　类型：功能　优先级：P1
- 前置：居民 A 名下有一条待审核预约（PENDING）、一条已预约预约（RESERVED，容量 1 资源，占用计数已 +1）；居民 B 账号可用。
- 数据：取消理由=「临时有事」。
- 步骤：
  1. 居民 A 调用 PATCH /api/v1/resource-reservations/{id}/cancel 取消待审核预约；
  2. 居民 A 取消已预约预约（RESERVED）；
  3. 居民 B 对容量 1 资源同日同时段提交预约；
  4. 居民 B 尝试取消居民 A 名下另一条预约（越权对照）。
- 预期：
  1. 待审核预约流转「待审核→已取消」，理由留存；
  2. 已预约预约流转「已预约→已取消」，同时段占用计数释放；
  3. 释放后居民 B 可成功预约该时段（容量回位）；
  4. 「用户可取消（→已取消）」仅限本人：居民 B 取消他人预约被拒绝（403），A 的预约状态不变；
  5. 取消操作通知社区管理员（R34：取消通知对方），管理员通知中心可见且可溯源。

### TC-C7-010 非法状态流转拒绝
- 关联：TR-C7-03　类型：异常与边界　优先级：P1
- 前置：构造覆盖 6 态的预约记录各一条：待审核/已预约/已完成/已拒绝/已取消/已违约。
- 数据：依赖：05 测试环境与数据 · 预置或通过操作产生 6 种状态的预约各一条（已完成/已违约可由 TC-C7-011/012 产物复用）。
- 步骤：
  1. 对已拒绝预约调用 confirm（已拒绝→已预约）；
  2. 对已取消预约调用 reject（已取消→已拒绝）；
  3. 对已完成预约调用 cancel（已完成→已取消）；
  4. 对待审核预约调用 violate（待审核→已违约，跳过已预约）；
  5. 对已违约预约调用 complete（已违约→已完成）。
- 预期：
  1. 步骤 1~5 全部返回状态流转非法错误（明确错误码与提示，如「预约状态不允许从 X 流转到 Y」）；
  2. 各预约状态保持不变，库中无非法流转痕迹；
  3. 合法流转全集（待审核→已预约/已拒绝/已取消；已预约→已完成/已取消/已违约）与架构 §6.3 状态机一致。

### TC-C7-011 预约到期登记已完成
- 关联：TR-C7-04　类型：功能　优先级：P1
- 前置：某居民存在一条已预约（RESERVED）且使用日期已过的预约；admin1 已登录。
- 数据：remark=「活动正常结束」。
- 步骤：
  1. 管理员调用 PATCH /api/v1/resource-reservations/{id}/complete 登记完成；
  2. 查询该预约状态与操作日志。
- 预期：
  1. 状态流转「已预约→已完成」；
  2. 完成登记留痕（操作人/时间/备注可查）；
  3. 该时段占用计数释放（available-slots 复核容量回位）。

### TC-C7-012 违约登记与违约记录可查
- 关联：TR-C7-04　类型：功能　优先级：P1
- 前置：居民 A 有一条已预约（RESERVED）预约；admin1 已登录；A 当前无违约记录。
- 数据：违约理由=「未按时到场，资源浪费」。
- 步骤：
  1. 管理员调用 PATCH /api/v1/resource-reservations/{id}/violate 标记违约；
  2. 调用 GET /api/v1/residents/{residentId}/violations 查询 A 的违约记录；
  3. 居民 A 登录查看通知中心。
- 预期：
  1. 状态流转「已预约→已违约」；
  2. 违约记录列表含该条记录（违约类型 RESERVATION_NO_SHOW、关联预约、处置说明、处理人、时间），「违约处置记录可查」（R35 验收标准）；
  3. 居民 A 收到违约处置站内通知，可溯源到该预约单；
  4. 未达违约上限（默认 3 次）时 A 的账号状态不变（仍 ACTIVE，可正常登录与预约）。

### TC-C7-013 违约超限自动冻结与限制生效
- 关联：TR-C7-04　类型：异常与边界　优先级：P1
- 前置：测试居民 A 已有 2 条违约记录（violation_record）；一条可标记违约的已预约预约；全局配置 violation 上限为默认 3 次。
- 数据：依赖：05 测试环境与数据 · 为测试居民 A 预置 2 条历史违约记录（SQL 直插 violation_record 或复用前两轮执行产物）。
- 步骤：
  1. 管理员对 A 的第三条预约执行 violate；
  2. 查询 A 的违约记录总数与账号状态（库内直查 resident.status）；
  3. A 重新登录系统；
  4. A 尝试提交新的资源预约。
- 预期：
  1. 第三次违约登记后违约计数达上限，A 的账号状态自动变更为 FROZEN（冻结），处置留痕（日志可见冻结原因与阈值）；
  2. 「被处置账号受相应限制」（R35 验收标准）：A 登录被拒或仅保留受限功能（冻结账号拒登口径），新预约提交被拒绝；
  3. 违约处置通知送达 A（或其登录前入库待补拉）；
  4. 违约记录列表 3 条齐全，处置全程留痕可查。

### TC-C7-014 预约记录查询与组合检索（R36）
- 关联：TR-C7-05　类型：统计核对　优先级：P2
- 前置：库内已有多社区、多资源、多状态的预约数据（种子 + 前序用例产物）；resident1 与 admin1 分别登录。
- 数据：组合条件——资源=健身房、状态=已预约、日期范围=本周；对照样本：另一社区的一条预约。
- 步骤：
  1. resident1 调用 GET /api/v1/resource-reservations 查询本人记录（分页）；
  2. resident1 尝试翻看他人预约详情（越权对照，取另一居民的预约 id 调 GET /{id}）；
  3. admin1 以 resourceId+status+startDate+endDate 组合检索；
  4. SQL 直查库：SELECT id,user_id,resource_id,reserve_date,status FROM resource_reservation 按同样条件统计，与接口结果比对。
- 预期：
  1. 居民端仅返回本人预约（含状态），分页与排序正常；
  2. resident1 查看他人预约被拒绝（数据级权限：限本人）；
  3. 管理员组合检索结果准确：仅含绑定社区内、满足全部条件的记录，「检索条件组合可用」；
  4. 「查询结果与预约数据一致」（R36 验收标准）：接口 records 的 total 与 SQL 直查计数 100% 相符，逐条核对无多漏。

### TC-C7-015 E7 全流程：预约→审核→使用→登记/违约→处置留痕
- 关联：TR-C7-06　类型：功能　优先级：P1
- 前置：独立测试居民账号（避免污染其他用例数据）；admin1、superadmin 可用；容量 1 测试资源已配置。
- 数据：主路径预约（正常使用）+ 分支路径预约（违约）；违约上限保持默认 3 次。
- 步骤：
  1. 居民选资源/日期/时段 → available-slots 确认可约 → 提交预约（待审核）；
  2. 管理员审核通过 → 居民收到确认通知（已预约）；
  3. 到期使用后管理员登记已完成；
  4. 同一居民再次预约另一时段 → 管理员标记违约 → 查询违约记录与通知；
  5. 全流程结束后核对操作日志：每步流转（提交/确认/完成/违约）均有留痕。
- 预期：
