# 功能用例 · C1 社区基础信息管理

> 依据：01_测试需求分析.md §3.1（TR-C1-01~11）、需求规格 R1~R6 + E1、接口设计 9.1、架构设计 §6。
> 编号规则：TC-C1-NNN；每条至少覆盖一个 TR；执行结果列由步骤 7 回填。
> 通用约定：
> - 种子账号（Flyway V3/V6）：超管 `superadmin / Admin@123456`、社区管理员 `admin1 / Admin123456`（绑定社区「阳光花园社区」）、居民 `resident1 / Resident123456`、服务人员 `staff1 / Staff123456`；
> - 种子数据（V6）：社区「阳光花园社区」（1 号楼 / 1 单元 / 101 已入住·residence_relation 关联 resident1 / 102、201 空置；健身房资源与时段）；
> - 「操作日志断言」统一指 sys_operation_log 有对应记录（操作人/时间/对象/内容），验证方式：超管调 `GET /api/v1/operation-logs` 或库内直查；
> - 房屋状态枚举以迁移脚本注释与实现常量为准（VACANT 空置 / OCCUPIED 已入住 / RESERVED 预留 / MAINTENANCE 维护中，HouseStatusConstant）；
>   R4 文档表述为五状态（自住/出租/空置/维修中/停用），与实现存在口径差异，见文件末尾「口径疑点」；
> - 需要第二个社区/管理员的数据一律标注「依赖：05 测试环境与数据」。

### TC-C1-001 超管新建社区成功
- 关联：TR-C1-01　类型：功能　优先级：P1
- 前置：superadmin 已登录（V3 种子）
- 数据：无额外（用种子数据）
- 步骤：
  1. superadmin 调 `POST /api/v1/communities`，请求体含名称（如「测试社区A」）、地址、联系电话（固话或手机号格式）、联系人、简介；
  2. 校验响应 data：id、name、address、contactPhone、contactPerson、description 与请求一致；
  3. 调 `GET /api/v1/communities/{新id}` 查询详情确认落库；
  4. 超管查 `GET /api/v1/operation-logs`，过滤本次创建操作。
- 预期：
  1. 返回 code=200，社区创建成功；
  2. 响应字段逐一相等，status 初始为 ACTIVE，createdAt/updatedAt 非空；
  3. 详情查询返回相同数据；
  4. sys_operation_log 存在本社区创建记录（操作人 superadmin、对象 COMMUNITY）。

### TC-C1-002 新建社区非法参数拒绝（空值/格式/上限边界）

- 前置：superadmin 已登录
- 数据：无额外（用种子数据）
- 步骤：
  1. name 传空字符串（或仅空格）提交；
  2. name 传 101 个字符提交；
  3. contactPhone 传 `12345`（不匹配固话/手机号格式）提交；
  4. description 传 1001 个字符提交；
  5. name 传恰好 100 字符、description 恰好 1000 字符提交。
- 预期：
  1~4. 均返回参数校验错误（拒绝创建，提示指向对应字段），community 表无新增行；
  5. 边界值恰好通过，创建成功（用后清理）。

### TC-C1-003 超管停用社区成功且停用状态可过滤
- 关联：TR-C1-01　类型：功能　优先级：P1
- 前置：superadmin 已登录；存在一个可废弃的测试社区（TC-C1-001 建立的社区A）
- 数据：依赖：05 测试环境与数据 · 可废弃社区A（由 TC-C1-001 产物或环境脚本创建）
- 步骤：
  1. superadmin 调 `PATCH /api/v1/communities/{社区A}/status`，body `{"status":"INACTIVE"}`；
  2. 调 `GET /api/v1/communities?status=INACTIVE` 过滤查询；
  3. 调 `GET /api/v1/communities?status=ACTIVE` 过滤查询；
  4. 查操作日志。
- 预期：
  1. code=200，状态更新成功；
  2. 结果包含社区A，status=INACTIVE；
  3. 结果不含社区A（正常社区仍在）；
  4. sys_operation_log 有状态变更记录。

### TC-C1-015 房屋状态变更与状态历史留痕可查
- 关联：TR-C1-07　类型：功能　优先级：P1
- 前置：admin1 已登录；存在测试房屋（状态 VACANT，如 TC-C1-014 步骤 1 建的房屋，删除前执行本用例）

- 步骤：

  2. 调 `GET /api/v1/houses/{id}` 确认当前状态；
  3. 再次调 `PATCH /api/v1/houses/{id}/status`，body `{"status":"VACANT","remark":"检修完成"}`；
  4. 调 `GET /api/v1/houses/{id}/status-history` 查状态变更历史；
  5. 遍历实现内全部状态枚举值（VACANT/OCCUPIED/RESERVED/MAINTENANCE）逐一变更（数据恢复为 VACANT）。
- 预期：
  1. code=200，状态更新成功；
  2. status=MAINTENANCE；
  3. 状态回到 VACANT；
  4. 历史含两条记录，每条含 oldStatus/newStatus（VACANT→MAINTENANCE、MAINTENANCE→VACANT）、remark（原因）、operatorId/operatorName（操作人）、createdAt（时间），按时间倒序（R4「变更留记录（操作人/时间/原因）」）；
  5. 各枚举状态均可设置成功且各自留痕。
