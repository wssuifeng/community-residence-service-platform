# 功能用例 · C9 社区运营统计

> 依据：01_测试需求分析.md §3.9（TR-C9-01~04）、需求规格 R40~R42 + E9、接口设计 9.9、UI 设计 §4.3.9（16 卡片 + 4 图表）。
> 编号规则：TC-C9-NNN；每条至少覆盖一个 TR；执行结果列由步骤 7 回填。
> 口径说明：R40 指标全集 = 房屋状态分布、居民与入住/搬出量、工单量/完成率/处理时长、服务人员工作量、满意度、公共资源预约量、房源浏览与带看量；看板卡片清单以 UI 设计 §4.3.9（4 行 × 4 列 = 16 卡片）为准；权限矩阵否定用例（居民/服务人员/游客访问统计接口）归 TR-SP-02 权限矩阵专项，本文件不重复。
> 统计一致性核对方法：SQL 直查 MySQL 明细（Flyway 迁移注释为状态枚举权威）vs 看板/统计接口返回，每指标抽样 ≥3 数据场景（01 §4 口径），脚本以 03 计划/05 测试环境与数据为准。
> 种子数据：admin1/Admin123456（绑定种子社区）、superadmin/Admin@123456、resident1/Resident123456、staff1/Staff123456；V6 种子含公告/房源/看房时段/健身房资源与时段。

### TC-C9-001 运营看板 16 卡片指标逐一断言（R40 覆盖）
- 关联：TR-C9-01　类型：功能　优先级：P1
- 前置：admin1 已登录；种子社区数据齐备（V1~V7 迁移 + 前序用例业务数据）。
- 数据：16 卡片清单（UI 设计 §4.3.9）——第一行（社区运营）：总社区数+活跃社区数、总楼栋数+总房屋数、总居民数+入住率、租住记录数+即将到期数；第二行（工单服务）：工单总数+待处理数、工单完成率+平均处理时长、服务人员数+平均工单数、评价总数+满意度；第三行（资源预约）：资源总数+开放预约数、预约总数+预约完成率、违约次数+违约率、资源使用率+热门资源；第四行（房源看房）：房源总数+在线房源数、看房预约数+预约完成率、房源浏览量+热门房源、看房转化率。
- 步骤：
  1. 管理端打开「运营看板」（/admin/statistics/dashboard），等待加载完成；
  2. 调用 GET /api/v1/statistics/dashboard 获取看板数据；
  3. 逐卡片核对页面渲染数值与接口返回字段一一对应；
  4. 对照 R40 指标全集，逐项勾销（房屋状态分布→房屋状态卡片/图表、居民与入住搬出量、工单量/完成率/处理时长、服务人员工作量、满意度、公共资源预约量、房源浏览与带看量）。
- 预期：
  1. 看板渲染 16 个统计卡片，无缺卡、无空白、无 NaN/undefined；
  2. 每个卡片数值均来自接口返回字段（页面与接口数值一致）；
  3. 「看板覆盖以上全部指标」（R40 验收标准）：R40 枚举的每一项指标均能在看板定位到对应卡片/图表，任一缺失记缺陷；
  4. 数值均为非负整数/合法百分比格式。

### TC-C9-002 社区筛选：超管全局/单社区，社区管理员限绑定社区
- 关联：TR-C9-01　类型：功能　优先级：P1
- 前置：superadmin 与 admin1 分别可用；系统内存在 ≥2 个社区且数据量不同（种子社区 + 另一社区）。
- 数据：依赖：05 测试环境与数据 · 第二个社区及其业务数据（楼栋/房屋/工单若干，SQL 直插或接口造数）。
- 步骤：
  1. superadmin 调用 GET /api/v1/statistics/dashboard（不传 communityId）获取全局数据；
  2. superadmin 分别传两个社区的 communityId 获取单社区数据；
  3. admin1 打开看板（其绑定社区），观察社区筛选控件；
  4. 比对：全局数值 = 两社区数值之和（可加和指标）。
- 预期：
  1. 超管不传社区时返回全系统聚合数据；
  2. 超管按社区筛选时数据仅含该社区；
  3. 社区管理员的社区筛选自动限定为绑定社区（无越权选项，或选其他社区被拒/无效）；
  4. 「支持按社区与时间范围筛选」（R40 验收标准）社区维度生效，全局与分社区数值自洽。

### TC-C9-003 时间范围筛选：今日/本周/本月/自定义
- 关联：TR-C9-01　类型：功能　优先级：P1
- 前置：admin1 已登录；库内工单/预约/评价数据的 created_at 分布在今日、本周早些、本月上月、自定义区间外四种位置（种子 + 造数）。
- 数据：依赖：05 测试环境与数据 · 造数使业务数据时间分布覆盖四种筛选区间（SQL 直插时注意 created_at 设置）。
- 步骤：
  1. 看板分别切换时间范围「今日/本周/本月」；
  2. 切换「自定义」选择一个只含部分数据的区间；
  3. 每次切换后核对统计卡片与图表数据是否联动刷新；
  4. SQL 直查同一区间内工单创建数，与工单卡片核对一处抽样。
- 预期：
  1. 四种时间范围均可选择且查询成功；
  2. 「筛选条件变化自动刷新统计数据与图表」（UI 设计交互口径）：卡片与图表数值随筛选变化；
  3. 自定义区间外数据不计入（区间内计数与 SQL 直查一致）；
  4. 时间维度与社区维度可组合筛选，结果同时满足两个条件。

### TC-C9-004 空数据社区空态展示
- 关联：TR-C9-01　类型：异常与边界　优先级：P1
- 前置：superadmin 已登录；存在一个无任何业务数据的社区（仅建了社区记录，无楼栋/工单/预约/评价）。
- 数据：依赖：05 测试环境与数据 · 空数据社区（超管新建社区，不添加任何下级与业务数据）。
- 步骤：
  1. superadmin 打开看板并切换到空数据社区；
  2. 观察全部 16 卡片与 4 图表的展示；
  3. 调用 GET /api/v1/statistics/dashboard?communityId={空社区id} 核对接口返回。
- 预期：
  1. 接口返回成功（code=200），各计数字段为 0、比率为 0.0、分布为空对象，不抛错不返回 500；
  2. 页面各卡片显示 0/空态样式，图表显示空坐标系（不渲染报错、不出 NaN）；
  3. 空态不影响其他社区筛选（切回种子社区数值正常）。

### TC-C9-005 一致性核对 A：工单量/完成率/处理时长
- 关联：TR-C9-02　类型：统计核对　优先级：P1
- 前置：admin1 已登录；工单数据覆盖 ≥3 场景——①种子基线；②新增若干工单（含已完成/关闭/处理中/待受理混合，前序用例产物）；③跨社区隔离（另一社区工单不计入本社区）。
- 数据：抽样方法——工单总量、完成率、处理时长三项指标各在 3 个场景下取数；完成率口径=已完成+已关闭 / 总数；处理时长按工单处理记录时间线（提交→确认完成）计算。
- 步骤：
  1. 调用 GET /api/v1/statistics/dashboard（及 /statistics/work-orders 若适用）获取工单卡片数值；
  2. SQL 直查：SELECT status, COUNT(*) FROM work_order WHERE community_id={id} GROUP BY status；
  3. SQL 直查处理时长：按 work_order_process 时间线抽取已完成工单的提交至完成耗时取均值；
  4. 在场景②新增数据、场景③切换社区后分别重复步骤 1~3。
- 预期：
  1. 工单总数与 SQL 总计 100% 相符；
  2. 待处理/处理中/已完成各状态计数与 SQL 分组一致，完成率按口径复算一致；
  3. 平均处理时长与明细计算值一致（舍入口径按实现保留位数比对）；
  4. 「报表数值与库内明细抽样核对 100% 相符」（R41 验收标准）：3 场景 × 3 指标全部通过，任一不符记缺陷。

### TC-C9-006 一致性核对 B：房屋状态分布与入住率
- 关联：TR-C9-02　类型：统计核对　优先级：P1
- 前置：admin1 已登录；房屋数据覆盖 ≥3 场景——①种子基线；②变更若干房屋状态（自住/出租/空置/维修中/停用混合）；③空数据社区（0 房屋）。
- 数据：五状态枚举（OCCUPIED 自住类占用/RENTED 出租/VACANT 空置/MAINTENANCE 维修中/DISABLED 停用，以 Flyway 注释为准）；入住率口径=已占用房屋数/总房屋数。
- 步骤：
  1. 调用看板接口获取房屋状态分布（卡片/图表数据）；
  2. SQL 直查：SELECT status, COUNT(*) FROM house WHERE community_id={id} GROUP BY status；
  3. 场景②执行房屋状态变更后再取数；场景③切换到空数据社区取数；
  4. 复算入住率与接口值比对。
- 预期：
  1. 五种状态的分布计数与 SQL 分组逐项一致（无数据的状态计 0 或不出现，口径稳定）；
  2. 各状态计数之和 = 总房屋数；
  3. 入住率与「已占用/总数」复算值一致；
  4. 3 场景抽样 100% 相符（R41）。

### TC-C9-007 一致性核对 C：预约量/违约数、满意度、房源浏览与带看量
- 关联：TR-C9-02　类型：统计核对　优先级：P1
- 前置：admin1 已登录；数据覆盖 ≥3 场景——①种子基线；②前序 C7/C8/C12 用例产生的新增预约/违约/评价/浏览/带看数据；③跨社区隔离对照。
- 数据：预约量口径=全部状态预约记录数；违约数=VIOLATED 状态预约数；满意度=满意评价数/评价总数；房源浏览量/带看量来自 C12 模块（浏览记录/看房预约完成数）。
- 步骤：
  1. 调用看板接口获取预约、评价、房源看房相关卡片数值；
  2. SQL 直查：SELECT COUNT(*) FROM resource_reservation WHERE community_id={id}；SELECT COUNT(*) FROM resource_reservation WHERE community_id={id} AND status='VIOLATED'；
  3. SQL 直查满意度：SELECT SUM(is_satisfied=1), COUNT(*) FROM work_order_evaluation WHERE community_id={id}；
  4. SQL 直查房源浏览/带看明细（housing 浏览记录与 viewing_appointment 完成记录），与卡片比对；
  5. 场景②③分别重复取数比对。
- 预期：
  1. 预约总数、违约次数与 SQL 直查一致；
  2. 满意度百分比与明细复算一致（舍入按实现口径）；
  3. 房源浏览量、带看量与明细一致（联动 TR-C12-07 口径）；
  4. 每指标 3 场景抽样 100% 相符（R41：抽样核对用例全部相符）。

### TC-C9-008 一致性核对 D：居民/租住卡片（总居民、活跃租住、即将到期 30 天窗口）
- 关联：TR-C9-02　类型：统计核对　优先级：P1
- 前置：admin1 已登录；租住数据覆盖 ≥3 场景——①种子基线；②新增止期分别落在 30 天窗口内/外/当天的租约（TR-C3-02 同源数据，可复用）；③已搬出/归档租约不计入活跃数。
- 数据：依赖：05 测试环境与数据 · 构造止期=今天+N 天（N<30 / N>30 / N=30 边界）的已生效租约。
- 步骤：
  1. 调用看板接口获取总居民数、租住记录数、即将到期数卡片数值；
  2. SQL 直查：SELECT COUNT(*) FROM resident；SELECT COUNT(*) FROM lease_record WHERE community_id={id} AND status='ACTIVE'；SELECT COUNT(*) FROM lease_record WHERE community_id={id} AND status='ACTIVE' AND end_date BETWEEN CURDATE() AND CURDATE()+INTERVAL 30 DAY；
  3. 场景②③分别重复比对。
- 预期：
  1. 总居民数与 SQL 一致；
  2. 活跃租住数仅计 ACTIVE 状态（已搬出/已归档不计入）；
  3. 即将到期数与 30 天窗口 SQL（含边界日）一致；
  4. 3 场景抽样 100% 相符（R41）。

### TC-C9-011 E9 全流程（答辩演示口径）：选范围→聚合→渲染→逐项核对
- 关联：TR-C9-04　类型：统计核对　优先级：P1
- 前置：superadmin 已登录；两个社区（种子社区 + 数据社区）具备差异化数据；本条为演示级综合核对，复用 TC-C9-005~008 的 SQL 核对方法。
- 数据：演示场景——社区=种子社区、时间范围=本月；核对指标抽样——工单总量、房屋状态分布、预约总数、满意度、房源浏览量（每项即一个抽样场景，凑满每指标 ≥3 场景时与其余核对用例合并统计）。
- 步骤：
  1. superadmin 登录 → 打开运营看板 → 选择社区与时间范围（本月）；
  2. 等待聚合查询与图表渲染完成（记录加载耗时，仅观察非判据）；
  3. 逐项记录看板指标值（工单/房屋/预约/满意度/浏览量）；
  4. SQL 直查明细逐项复算比对；
  5. 切换到另一社区重复步骤 3~4。
- 预期：
  1. 「选择社区/时间范围 → 后端聚合查询 → 图表渲染 → 逐项与明细核对一致」（E9 数据流）全链路贯通；
  2. 两个社区的逐项核对均 100% 相符（R41 验收标准：抽样核对用例全部相符）；
  3. 看板在演示口径下无报错、无空白卡片、无图表渲染失败。
