# 功能用例 · C3 租住管理

> 依据：01_测试需求分析.md §3.3（TR-C3-01~05）、需求规格 R13~R16 + E3、接口设计 9.3、架构设计 §6.2（租住状态机）。
> 编号规则：TC-C3-NNN；每条至少覆盖一个 TR；执行结果列由步骤 7 回填。
> 通用约定：
> - 种子账号（Flyway V3/V6）：超管 `superadmin / Admin@123456`、社区管理员 `admin1 / Admin123456`（绑定「阳光花园社区」）、居民 `resident1 / Resident123456`（房屋 101，有 ACTIVE 租住记录 2026-01-01~2027-12-31）；
> - 租住状态机（架构设计 §6.2，权威）：待审核(PENDING)→已生效(ACTIVE)→已搬出(MOVED_OUT)→已归档(ARCHIVED)，待审核→已驳回(REJECTED) 终态；
>   **「即将到期(EXPIRING)/已到期(EXPIRED)」为查询期日期判定标注（expiryFlag），不是状态值、不写库、非人工流转**；
> - 到期提醒天数 N 的配置键：sys_config `lease.reminder_days_before_expire`（V2 种子默认 30）；涉及修改的用例执行后**必须恢复默认 30**；
> - 「操作日志断言」统一指 sys_operation_log 有对应记录（超管调 `GET /api/v1/operation-logs` 或库内直查）；
> - 需要特定止期租约的用例（TR-C3-02/03）依赖 05 数据脚本构造（SQL 直插或接口造数），不虚构种子数据。

### TC-C3-001 租住登记成功 → 待审核且关联正确
- 关联：TR-C3-01　类型：功能　优先级：P1
- 前置：admin1 已登录；存在承租人（resident1 或 05 账号池居民）与目标房屋（有居住关系或空置房）
- 数据：依赖：05 测试环境与数据 · 测试租客与目标房屋（05 账号池 + 社区房屋）
- 步骤：
  1. admin1 调 `POST /api/v1/leases`（residentId=承租人、houseId=目标房屋、租期起止、租金/押金、备注）；
  2. 校验响应 data：tenantName、houseLocation（楼栋+单元+房号）、起止日期、租金、status；
  3. 调 `GET /api/v1/leases/{id}` 查详情；
  4. 查操作日志。
- 预期：
  1. 创建成功，status=PENDING（待审核，R13「经审核流转」前的初始态）；
  2. 承租人姓名、房屋位置、租期、租金与请求一致，租约与房屋、居民关联正确（R13 验收标准）；
  3. 详情查询一致；
  4. 登记操作有日志记录。

  1. 提交 endDate 早于等于 startDate 的登记（起 2026-10-01 / 止 2026-09-30）；
  2. 提交 endDate=startDate 同日的登记（临界值）；
  3. 提交 residentId=999999（不存在）的登记；
  4. 提交 houseId=999999（不存在）的登记；
  5. admin1 对社区B 的房屋提交登记（数据级权限对照）。
- 预期：
  1. 明确拒绝（租期结束日期必须晚于开始日期）；
  2. 同上被拒（同日不满足「晚于」），lease_record 无新增行；
  3. 返回 404（租客不存在）；
  4. 返回 404（房屋不存在）；
  5. 被拒（403/数据级权限校验），社区B 无新增租约。

### TC-C3-004 租期状态自动判定三类场景（EXPIRING/EXPIRED/无标注）
- 关联：TR-C3-02　类型：功能　优先级：P0
- 前置：admin1 已登录；三条 ACTIVE 租约止期分别落在窗口内/外/已过（以默认 N=30 构造）
- 数据：依赖：05 测试环境与数据 · 到期判定数据集（三条 ACTIVE 租约：止期=今日+5 天、止期=今日+60 天、止期=今日-1 天，SQL 直插或接口造数）
- 步骤：
  1. 分别调 `GET /api/v1/leases/{三条租约id}` 查详情，核对 expiryFlag 字段；
  2. 库内直查 lease_record.status，核对三条记录状态值；
  3. 修改系统日期不可行时以数据口径覆盖临界日（见 TC-C3-005），本条记录判定输出。
- 预期：
  1. 止期=今日+5 天 → expiryFlag=EXPIRING（即将到期：止期前 N 天内）；止期=今日+60 天 → expiryFlag 为空（窗口外不标注）；止期=今日-1 天 → expiryFlag=EXPIRED（已到期：止期已过）——判定结果与「止期 + 当前日期 + N」规则完全一致，无需人工干预（R14 验收标准）；
  2. 三条 status 均仍为 ACTIVE（非人工流转、不写状态，R14/术语表口径）；
  3. 判定记录入执行记录供 RTM 回溯。

### TC-C3-005 判定边界：止期=今天、止期=今天+N 临界 + N 修改与 N=0
- 关联：TR-C3-02　类型：异常与边界　优先级：P0
- 前置：superadmin、admin1 已登录；临界止期租约由 05 数据脚本构造
- 数据：依赖：05 测试环境与数据 · 临界日期租约数据集（止期=今天、止期=今天+30 的 ACTIVE 租约各一条）
- 步骤：
  1. 以默认 N=30 调 `GET /api/v1/leases/{止期=今天}`，核对 expiryFlag；
  2. 调 `GET /api/v1/leases/{止期=今天+30}`，核对 expiryFlag（窗口上界临界）；
  3. 超管 `PUT /api/v1/configs/lease.reminder_days_before_expire` 置 0，调 `GET /api/v1/leases?status=ACTIVE` 列表核对各租约 expiryFlag 变化（N=0 边界）；
  4. 将 N 改为 7，核对接近日止期（如今日+5）的租约标注仍为 EXPIRING、远止期（今日+60）不标注（修改 N 边界）；
  5. **恢复 N=30**。
- 预期：
  1. 止期=今天 → EXPIRING（仍在「前 N 天内」含当天；若实现判为 EXPIRED 以执行记录留痕并按 §6.2 口径裁决）；
  2. 止期=今天+30（恰为 N 上界）→ EXPIRING（含边界日）；
  3. N=0 时窗口收窄，仅止期当日（或已过）租约被标注，其余无标注（N 可配边界生效）；
  4. N=7 后标注范围与「止期 ≤ 今天+7」一致，判定随配置即时变化；
  5. 配置恢复默认 30（强制检查项）。
  （注：实现层查询期 expiryFlag 窗口当前硬编码 30 天、不读 sys_config——见文末口径疑点 1；步骤 3/4 若因该差异失败，按疑点裁决处理并记缺陷。）

### TC-C3-006 到期判定不改库：非状态流转口径回归

### TC-C3-007 即将到期列表接口与 days 参数一致性
- 关联：TR-C3-02　类型：功能　优先级：P0
- 前置：admin1 已登录；不同止期的 ACTIVE 租约若干（含 PENDING/MOVED_OUT 对照租约）
- 数据：依赖：05 测试环境与数据 · 同 TC-C3-004 数据集 + 非 ACTIVE 状态对照租约各一条
- 步骤：
  1. 调 `GET /api/v1/leases/expiring`（默认 days=30）；
  2. 调 `GET /api/v1/leases/expiring?days=7`；
  3. 调 `GET /api/v1/leases/expiring?days=0`；
  4. 将三次结果与 SQL `status='ACTIVE' AND end_date BETWEEN today AND today+days` 直查比对，并核对排序。
- 预期：
  1. 返回止期落在未来 30 天内的 ACTIVE 租约，按到期日期升序；
  2. 窗口收窄为 7 天，远止期租约不出现；
  3. days=0 时仅含止期为当日的租约（边界）；
  4. 三次结果与规则 SQL 100% 一致；PENDING/MOVED_OUT 对照租约均不出现在任何一次结果中。

### TC-C3-011 搬出→归档流转全留痕（已生效→已搬出→已归档）
- 关联：TR-C3-04　类型：功能　优先级：P1
- 前置：admin1 已登录；存在 ACTIVE 租约（专用测试租约，勿用种子租约）
- 数据：依赖：05 测试环境与数据 · ACTIVE 测试租约（05 数据集或 TC-C3-003 产物）
- 步骤：
  1. admin1 调 `PATCH /api/v1/leases/{id}/status`，body `{"status":"MOVED_OUT","remark":"租约到期搬出"}`；
  2. 调 `GET /api/v1/leases/{id}` 核对状态与备注；
  3. 调 `PATCH /api/v1/leases/{id}/status`，body `{"status":"ARCHIVED"}`；
  4. 调 `GET /api/v1/leases?status=ARCHIVED` 按状态过滤查询；
  5. 查操作日志核对两次流转。
- 预期：
  1. 流转成功（已生效→已搬出，合法流转）；
  2. status=MOVED_OUT，remark 留痕（R16「全状态流转留痕」）；
  3. 流转成功（已搬出→已归档，租住状态机可达，系统定义 C3 判据）；
  4. 归档列表包含该租约，历史可查；
  5. 两次流转均有 sys_operation_log 记录（操作人/时间/对象/内容）。

### TC-C3-012 归档后不可修改
- 关联：TR-C3-04　类型：异常与边界　优先级：P1
- 前置：TC-C3-011 产物的 ARCHIVED 租约存在
- 数据：依赖：05 测试环境与数据 · 同 TC-C3-011（已归档租约）
- 步骤：
  1. admin1 调 `PUT /api/v1/leases/{id}` 修改租金/备注；
  2. admin1 调 `PATCH /api/v1/leases/{id}/status` 尝试流转 `{"status":"ACTIVE"}`；
  3. admin1 调 `POST /api/v1/leases/{id}/renew` 尝试续租；
  4. 调 `GET /api/v1/leases/{id}` 核对数据。
- 预期：

  3. 续租被拒（仅 ACTIVE 可续）；
  4. 租约数据与归档时一致，无任何变化。

### TC-C3-013 终态与驳回流转非法拒绝（REJECTED 终态 + 状态回跳）
- 关联：TR-C3-04　类型：异常与边界　优先级：P1
- 前置：存在 REJECTED 租约（待审核→已驳回）与 MOVED_OUT 租约各一条
- 数据：依赖：05 测试环境与数据 · REJECTED 与 MOVED_OUT 状态租约（05 数据集或 TC-C3-011 中间态产物）
- 步骤：
  1. admin1 对 REJECTED 租约调 `PATCH /api/v1/leases/{id}/status` 提交 `{"status":"ACTIVE"}`；
  2. 对 REJECTED 租约尝试直接 `{"status":"ARCHIVED"}`；
  3. 对 MOVED_OUT 租约尝试流转 `{"status":"ACTIVE"}`（状态回跳）；
  4. 提交 `PATCH` 目标状态等于当前状态（如 ACTIVE→ACTIVE，幂等对照）。
- 预期：
  1. 明确拒绝（REJECTED 为终态，无合法出边）；
  2. 明确拒绝（不可跳级归档）；
  3. 明确拒绝（状态机不允许回退，架构设计 §6.2 全流转对照）；
  4. 同状态提交为幂等成功/无变化（不产生流转记录副作用），数据不变。

### TC-C3-015 居民数据级权限：租住记录仅本人/管理员限本社区
