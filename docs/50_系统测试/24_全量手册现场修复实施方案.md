# 全量手册现场修复实施方案

仅本轮现场修正；工程结果逐项回写07/08，任务状态只在中控。交易继续暂停，房屋图片22与起租日23不在本轮实施。

## 已核对的根因与边界

1. 工单取本人关系仅前5条，且类别空集合无空态；类别树和所属社区必须准确核对，按有效关系取社区，加载失败/未配置不留空白，不硬塞不存在类别。
2. 公告列表/详情固定前端示意图片，没有对应可编辑字段。补公告images保存和上传回显，未设置不渲染图，不给已有公告自动加图。
3. 当前只有36h登录，无续期接口；任意旧请求401会清掉当前新会话。新增认证会话续期（非交易），保留同一jti/原签发时间/权限代次，延长exp；登出拉黑该会话族36h，撤权继续立即拒绝。前台可见页面接近到期时续期，不以后台轮询无限续命；过期/撤销不可复活。
4. 反馈管理页把整份附件放在最初居民消息中；居民附件在侧栏，后续附件不是任何消息，两端也未按消息推送。复用聊天基础组件（文本、图片、时间、空态、输入/上传/错误）和统一图片存储服务；反馈、租约/工单/看房会话保留原业务权限/WS主题，只作适配。上传图片原子生成图片消息，消息不可伪装成普通附件或任意URL。
5. 匿名反馈toVO直接查询真实姓名。服务端对详情/列表/消息/推送统一匿名化居民显示身份，内部真实ID只用于鉴权，不在匿名响应中公开；管理员自己的身份不匿名。
6. 月历额度分母累加半小时时段容量，分子却只数预约记录。分子改后端每段currentBookings之和；预约条数另标，某段满不代表整天全部满。
7. 后端待办汇总仅超管/社区管理员，计数应用原有数据级权限；菜单/租住Hub子Tab按键渲染红点，零/加载失败不伪造待办。

## 实施与验证顺序

- 类别、匿名、额度先补回归单测，修实际根因；不更改用户已经录入的类别或关系。
- 公告images与消息图片关联由一份增量迁移实现，旧公告空图、旧消息TEXT兼容；独立图片上传服务验证真实类型和5MB边界。
- auth/renew单独验证失效/冻结/撤权/登出与相同会话旧新令牌；前端验证单飞续期、401不误删新会话和退出不复活。
- ChatMessageList/ChatComposer作为共用底座；FeedbackChat适配反馈、ConversationChat和AppointmentChat复用底座，业务菜单按需传入。现有协议快照消息与关闭态保持。
- 先专用隔离数据库/端口运行权限及双端图片消息/匿名回归，通过后正常库备份、部署、只读核对。任何正常数据数量差异先定位，不以回填覆盖。
- 后端全量单测、前端全量单测/类型/build；记录真实浏览器与中间失败，不预填用户复验通过，不推进60/70。


## 补充核对

- 当前正常社区6实际服务类别总数0、启用数0；接口并非拉错。修复须补初始化入口与空态，不伪造类别选项。类别定义沿用V7默认目录，已有类别的社区不覆盖、不复活停用项。
- 匿名选择旧实现根本未落库，无法恢复过去每条真实选择。本轮新提交准确保存；历史NULL选择采用保守匿名显示，不按标题推断，不公开住户ID/姓名。
- JWT续期为本项目的有效会话延长机制，不声称实现OAuth Refresh Token。协议消息与业务授权不统一成无权限聊天接口。
- 官方依据：RFC 7519 §4.1.4/4.1.6/4.1.7（https://www.rfc-editor.org/rfc/rfc7519）；Vue官方Composables及Lifecycle（https://vuejs.org/guide/reusability/composables.html、https://vuejs.org/api/composition-api-lifecycle）；Spring Security JWT认证/授权（https://docs.spring.io/spring-security/reference/servlet/oauth2/resource-server/jwt.html）。只参考令牌语义与生命周期/授权原则，沿用本项目既有JWT过滤器和数据级权限，不替换框架。


## 本轮实现结果与兼容边界

- V37仅新增真实公告图字段、匿名选择及图片消息关联，V38只补完全空类别目录；当前55业务表。已有类别、原工单和正常居住链不覆盖。
- 三类聊天适配器共用前端引擎/消息列表/输入框及后端图片服务；历史消息表和业务接口保留，未把业务权限合并为一个通用无授权接口。反馈历史附件两端单独呈现，不转换为猜测的消息。
- 新匿名选择准确落库；历史NULL无法还原原选择，保守显示匿名；真实居民ID保留内部鉴权，但不输出匿名身份。已发布公告须撤回后编辑，更新空图片真实写NULL，创建表单始终清空旧图片。
- 续期只在有效前台会话进入12h窗口触发，延36h；退到后台不靠轮询续命。实际浏览器测试只调整客户端到期窗口，用真实JWT调用服务器，不宣称等36h耐久。
- 管理待办由当前权限内真实状态汇总：工单/反馈/公共预约/入住申请/退租申请/待确认看房/待审核或需发协议的租约；待付款不算管理员任务。红点零值隐藏，读取失败不编造数字。
- 工程与中间失败真实结果见07/08及evidence/bq-manual-fixes-20261015；20/30冻结正文未直接改写，必要上游同步需获得确认，不声称已完成新契约的冻结包同步验收。

撤回公告显示编辑入口，不直接显示发布按钮；编辑保存回草稿后才允许发布，与后端DRAFT发布门禁一致。


## 2026-10-15用户澄清：超管删除与共用聊天的边界

- 用户明确删除社区是主动测试操作，不是误删，不需要恢复。保留历史审计事实，但不再保留数据恢复待办；不为此恢复旧全库。
- 超管应能在充分警示后删除社区，而不是前轮新增的“存在有效关系/租约即一律不准”。拟修正为：第一次展示社区名/业务编号及房屋、有效住户/成员、进行中租约、申请、工单和资金记录数量；第二次输入社区业务编号并明确勾选“了解关联业务数据将被级联清除”；预览版本变化则重新确认。保留仅超管、事务、审计与账号本体不删除等约束。不自动恢复、不伪造退款、不调用渠道。正式实现仍需对齐获准上游契约，本轮只纠正口径，代码硬拦截尚未撤销。
- 已交付共用层是`useChatChannel`（加载/发送/图片/订阅/轮询/去重/切换隔离/关闭态）、`ChatMessageList`（文字/图片/时间/预览/业务卡片槽）、`ChatComposer`（文字输入/直接选图/扩展功能槽）和`ChatImageService`（真实图片上传及关联）。
- 租约/工单/主要看房群使用`ConversationChat`同一适配器；反馈用`FeedbackChat`，旧看房入口用`AppointmentChat`适配共用层。保留各域鉴权、主题和历史消息表，**不是后端已全部合成一张通用消息表**。图片引用统一在`chat_message_image`按消息空间区分，避免相同数字ID串图。
