# 前后端项目结构与归属规则

2026-10-18 · 后端层级按用户明确方案；前端结构供审阅 · 本文不代表已经迁移

本轮使用`codebase-design`评估职责与依赖，使用`vue-best-practices`核查前端组织。前置评估见[35](35_三端与公共模块架构评估.md)，整理难点与实施批次见[37](37_架构优化实施计划.md)。目标是方便按端定位完整业务模块、明确共享能力归属；目录调整本身不保证性能提升或缺陷减少。

## 1. 结构是否可行，有哪些问题

**可以采用。** 后端按“端 → 业务模块 → Controller/Service/Mapper”组织；前端采用相同的前两级，第三级按前端职责组织。核心业务在多个端之间共享，因此三端与公共部分的代码量不必接近。

| 需要控制的问题 | 在本项目中的影响 | 归属规则 |
|---|---|---|
| 同一规则出现多份 | 工单、租约、房源占用、居住关系被多个端共同操作，分端后若复制服务会再次漂移 | 共用状态流转、实体、通用持久化唯一维护在公共业务模块；各端维护确有差异的操作组织、查询和呈现 |
| 公共目录职责模糊 | 通知、会话、上传、安全和租约等共用能力较多，全部平铺会让公共部分难维护 | 公共目录第二级仍分具体业务/技术模块；工单规则归workorder，认证归auth/security，不能泛化成巨大公共Service或utils |
| 一条业务链需要跨目录查看 | 排查一次工单处理需要看居民提交、管理派单、服务人员处理与公共规则 | 接受按端定位带来的取舍，使用相同业务模块名、中文用途和迁移索引；不为追求目录整齐拆散一段完整规则 |
| 强制凑齐所有层 | 每个入口都增加一层转发Service、重复Mapper或空组件，会增加维护成本 | 分层是职责约束，目录按实际代码建立；共用实体保留一份，只有端专属查询才设端Mapper；纯前端展示逻辑也不必进全局Store |
| 包名被误当权限或状态隔离 | 原后端还依赖角色、社区范围、本人/参与者检查；前端登录、通知和聊天状态跨页面共享 | 包名只表示归属；保留鉴权、身份空间、同一共享Store及会话缓存，不能按三端另建独立认证/聊天状态 |
| 公共部分反向依赖端 | 当前共享会话功能直接引用居民预约页面，机械搬家会保留这个问题 | 公共不导入任何端；端特有的操作通过端内组合或显式参数/插槽接入；路由汇总由入口装配 |
| 迁移影响不止import | 后端类/Bean、Mapper语句和测试引用，前端动态页面导入、别名、样式资源及测试定位都需要同步 | 先列完整归属清单，分批迁移并检查兼容；保留API、路由、权限、业务行为及既有懒加载 |

本轮是静态结构评估，没有运行性能测试，也没有将上述风险全部认定为现场缺陷。已核实的前端依赖实例是[ConversationBusinessActions](../../frontend/src/components/conversation/ConversationBusinessActions.vue#L5)直接导入居民`HousingReservationView`。可复用预约表单应与路由页面分开归属，或由端内传入业务操作；不能只通过改路径消除表面引用。

目录是可选归属位置，不要求为每个示例模块立即创建独立Controller或空目录。多端完全相同的消息中心、会话等契约仍可由公共Controller承载；同一HTTP方法＋路径只有一个处理方法。业务模块按Controller→Service→Mapper分层，技术模块按其用途组织。端内Service可调用公共业务Service；Controller不直连Mapper。数据库实体与同一套公共写规则不在三端重复定义。

## 3. 前端：沿用端与模块，三级按页面职责

当前管理页面已按业务子目录归组，居民/服务人员页面多在各自目录平铺；API、类型和数据逻辑又分别集中在顶层目录。采用以下结构，可以把一次功能修改涉及的前端文件放得更近。

├── App.vue                           # 应用根容器
├── router.ts                         # 全站路由装配，汇总各端与公共路由
├── admin/                            # 管理端
│   ├── routes.ts                     # 组合本端业务路由
│   ├── layout/                       # 后台外壳、侧栏与端内导航
│   ├── community/                    # 社区结构、房屋编辑与房屋相册

前端第三级使用`views/components/composables/api/types`，确有跨页面共享状态时增加`store`，纯业务计算/格式化按模块用途放置；测试靠近被测模块，原全站契约测试及测试初始化仍作为测试支撑管理，不为了四个业务分组强行塞入生产公共目录。没有专用接口就直接用公共业务API，表单临时状态不要求变成Store。业务模块名尽量与后端一致；`system`、`workbench`等实际页面组合可按前端职责保留，不追求机械一一对应。

`common/public`承接现有游客页面，`common/auth`承接登录注册，不新增游客一级包。根入口文件负责创建并装配应用，根`router.ts`可以汇总三端和公共路由；公共路由工具不导入各端页面。此处是应用装配与共享能力的职责区分，避免一边要求common不依赖端，一边把全站路由汇总放进common。

登录、退出时的通知初始化/清理由当前[user Store](../../frontend/src/store/user.ts#L20)协调，当前[路由入口](../../frontend/src/router/index.ts#L20)集中汇总三端与游客页面。迁移时应保留这些生命周期行为，将需要连接多个模块的装配放在明确入口或协调位置；不能简单搬成认证状态与通知状态互相导入，也不能创建三套登录/通知/聊天状态来实现目录分离。

## 4. 两端共同遵守的维护规则

- 端可以使用公共能力；三端之间不直接导入；公共部分不反向导入端。公共业务模块之间按既有协作需要确定单向依赖，不能仅因都在common就任意互相引用。
- 后端权限仍由原安全机制与业务归属检查执行；前端角色显示仍依据后端事实和会话状态。迁移不改变用户身份、有效居住关系或付款义务。
- 后端实体/共用写规则，前端登录状态/消息中心状态/会话引擎和业务类型，各自明确唯一归属。仅被一个端使用的组件不自动提升为公共；真正共用时再提取。
- 英文包名和文件名保留，本文用中文说明用途。迁移后补模块级README或package-info的用途和依赖说明即可，不给每层添加重复文档。
- 先迁移清单，后分批调整。包扫描、Bean名、Mapper/SQL、引用、懒加载、资源与测试均纳入核对；保持原URL、路由名称、请求响应、权限、事务/锁/幂等、已读/草稿和业务行为。
- 后端与前端分别提交、分别验证。后端编译/启动映射与受影响接口，前端类型检查/构建与受影响页面/组件；行为改动另开批次，人工仅复验实际受影响的链路。

## 5. 本轮结论与边界

后端四个一级分组与三级层级已由用户明确；前端采用相同前两级、使用前端职责作为第三级，是本轮推荐方案。结构优化的第一收益是定位、归属与协作，性能/缺陷改善需由后续具体改动及证据证明。

本轮只核查源码、评估风险和整理中文目录说明，未移动业务文件、修改冻结30、启停服务或操作数据库/交易，也没有新增一轮手测。后续难点与迁移批次已列入37；逐类/组件/HTTP方法的最终归属清单由37的S0在实施前建立。本文目录示例与本轮静态库存均不冒称已完成全量归属映射。
