# 公告简易编辑器与发布后修订设计

> 2026-10-15用户采纳，2026-10-16按澄清落地：正文写作页替代旧纯表单，发布设置为辅助。本文只讨论公告编辑与发布后修订；图片加载正常的既有用户结果保留，新增能力另行复验。

## 1. 改造前的能力与缺口

当前是纯文本正文＋独立图片列表，不是富文本。管理端只有草稿/已撤回公告显示“编辑”；已发布公告须先“下线”（撤回），编辑保存变成草稿，再发布。前后端都执行此限制，不是仅按钮漏显示。

因此，**已有撤回后编辑功能，但没有直接修订已发布公告，也没有段落居中、正文插图和图片缩放。**

## 2. 推荐交互

- 草稿仍使用“编辑”；已发布增加“修订公告”，直接加载当前正文，不先把居民正在看的公告下线。
- 工具栏只做：撤销/重做、正文/二级标题、加粗、项目列表、左对齐/居中/右对齐、插入本地图片、图片宽度调整。图片宽度提供25%/50%/75%/100%，可用滑块拖动宽度、保持图片比例，最终限制不超正文容器。
- 插图必须经受控上传，成功后插到光标处；可修改说明/替换/移除，不提供公网URL输入。上传中或失败不允许把未保存的图片当作发布成功。
- 编辑区旁可切换预览；**“实时”指本地即时预览，不是每敲一个字就改居民看到的正文。**管理员点击“保存并更新”后，整版原子生效，居民下次获取内容看到新版；取消编辑不影响已发布版。
- 本次直接修订只改标题/正文/图片。发布对象、有效期等投放规则保留原有独立流程，避免修字顺手改变谁能看。每次保存显示修订时间和版本。

## 3. 为什么不只加一个HTML输入框

比较后推荐成熟编辑器的最小功能组合，而非自己用contenteditable拼一整套编辑器，也不引入重型在线文档协同系统。

建议用Tiptap的Vue适配和基础扩展，懒加载到公告编辑页；官方资料支持对齐、图片节点及结构化JSON输出。图片扩展**不负责服务端上传**，仍接本项目上传/授权，不误以为装库就完成文件管理。不引入付费协作、云端文档或AI功能；具体依赖版本在批准实施时核对并锁定。

- [Tiptap官方：输出JSON/HTML](https://tiptap.dev/docs/guides/output-json-html)
- [Tiptap官方：TextAlign](https://tiptap.dev/docs/editor/extensions/functionality/textalign)
- [Tiptap官方：Image及缩放](https://tiptap.dev/docs/editor/extensions/nodes/image)

## 4. 保存、权限与历史

- 服务端校验受限正文结构：只接收允许的段落、文字样式、对齐、列表和本项目图片引用；拒绝脚本、事件、iframe、任意CSS、外链图片和Base64大图。前端不能原样v-html渲染用户提交的HTML。
- 富文本结构为正文事实来源，同时由后端派生纯文本摘要供列表/搜索使用，不维护两份可各自编辑的正文。管理/居民/游客复用同一只读展示规则。
- 保存修订版本及编辑人/时间，旧版只读保留；并发编辑须比较版本，拒绝旧表单覆盖新修订。原发布对象和社区权限不放宽。
- 公告阅读回执应明确所读版本：总阅读人数仍按账号去重，本次修订阅读单独区分；不能把看过旧版伪装成已读新版。保存修订默认不重复群发原发布通知，不增加一堆重复未读提醒。
- 历史纯文本及已上传图片原样可读，打开编辑时转换为受限段落/图片；未保存不批量改旧公告，不丢原文字/图片顺序。

## 5. 已采纳边界与复验

推荐的是**已发布可修订、保存后生效、保留版本**；不是把所有已发布字段无限开放，也不是后台输入即时推送正文。

R24/R27～28及30接口/数据库/UI已沿已采纳方案同步，工程与验证归50中控ca。验收只核：居中/插图/缩放保存后跨端一致；已发布修订前旧版仍可见；取消不变；历史可读；无权限/并发覆盖/恶意内容拒绝；无图不造图、移除不残留、修订不重复广播。

实施采用Tiptap 3.32.0的Vue适配、StarterKit最小配置和TextAlign；平台图片节点自定义受限字段，不引入任意HTML或外图。最终交付为标题＋文稿区＋折叠发布设置，不保留旧textarea和独立图片表单。V42保存正文/修订及所读版本，发布与浏览计数仅更新自身字段，避免旧对象回写覆盖新版正文。
