# 三端会话界面基础方案（供审阅）

依据：用户2026-10-16提出三端会话统一布局，2026-10-17要求先确认功能与布局，再使用mockup-to-page绘制设计稿。本文只说明相关前端设计，不授权实施，不替代30包契约；执行状态仅在本阶段中控维护。

## 1. 改哪里，不改哪里

**推荐：共用一套会话界面，按身份和关联业务显示功能。** 不做三套独立聊天，也不把本系统改成完整社交软件。仅分别美化现有三端会保留入口割裂，因此不推荐。

| 端 | 目前实际情况 | 本次拟调整 |
|---|---|---|
| 居民 | 消息中心内看会话列表，点击后跳独立详情页 | 在同一页面选会话、看消息、办理已有会话业务 |
| 服务人员 | 消息中心只有通知；从工单详情、带看工作台进入聊天 | 补本人参与的会话列表，保留原业务入口 |
| 管理端 | 已有左列表、右聊天，但无搜索且只取前50条 | 整理布局、搜索、筛选、完整加载及业务定位 |

- 统一的是**租约群聊、看房群聊、工单群聊、直通会话**。反馈会话仍在反馈详情中，继续共用消息列表、输入框和图片能力；本次不迁移其业务数据。
- 复用现有`ConversationChat`、`ChatMessageList`、`ChatComposer`及会话权限，不重建聊天机制。
- 系统通知与聊天分开：通知继续在消息中心/铃铛查看；三端提供一致的“消息会话”入口，原消息中心的会话入口进入同一页面，不保留两套列表。

## 2. 布局：左侧找会话，右侧处理当前会话

保留三端原有站点导航/管理侧栏，下面只是内容区布局，不是视觉设计稿：

```text
┌─会话列表：约280～320px─┬─当前会话：占剩余宽度───────────┐
│ 消息会话      发起入口 │ 名称 / 类型 / 状态          ⋯ │
│ 搜索会话              │ 社区、房屋或关联业务定位       │
│ 全部  未读      筛选  ├───────────────────────────────┤
│ 名称      时间  未读数│ 消息历史：文字 / 图片 / 协议   │
│ 业务类型、末条摘要    │                               │
│ ……独立滚动、继续加载  │ 有新消息时提示 / 回到底部      │
│                      ├───────────────────────────────┤
│                      │ 图片  ＋业务功能              │
│                      │ 输入消息                 发送 │
└──────────────────────┴───────────────────────────────┘
```

- 列表和消息区各自滚动，输入区固定在聊天区底部；不让消息把整页无限撑高。
- 成员/关联业务详情用临时抽屉或现有业务详情页，不常驻第三栏。
- 窄桌面放不下双栏时切为“列表 ↔ 聊天”，保留选中对象、草稿和阅读位置；不压缩成两条窄栏。本次不新增移动端适配范围。

## 3. 第一版所需前端功能

| 区域 | 推荐保留/补齐的功能 |
|---|---|
| 会话列表 | 名称、业务类型、末条摘要、时间、未读数；关闭会话标“已关闭”。图片摘要显示“[图片]”，协议显示“[租赁协议]”，不展示原始附件地址。按最近消息排序，无消息时用创建时间；继续加载不止50条 |
| 搜索与筛选 | 搜索会话名称、直通对象姓名、关联业务编号；范围是全部本人有权会话，不是当前已加载页。默认“全部”，支持“未读”；类型放筛选菜单，不堆成两排标签。不检索消息正文 |
| 聊天内容 | 文字、图片、系统消息、已有协议消息卡片；显示发送人/角色与必要时间分隔；图片点击预览。有未读时定位首条未读并提供“回到最新”，无未读时定位最新消息；向上继续加载更早消息 |
| 输入区 | 沿用文字最多500字、Enter发送/Shift+Enter换行和现有图片限制；保留明确“发送”按钮。图片入口直接可见，业务动作收入“＋”，不混入成员菜单 |
| 会话顶部⋯ | 查看成员、打开关联业务详情。直通会话显示实际对象；不提供无意义的“关联工单/租约”按钮。不会因查看详情自动改变业务状态 |
| 发起入口 | 居民显示“联系社区管理员”，管理端显示“发起直通会话”，沿用现有社区/居民归属校验及重复打开既有会话的规则；服务人员不显示任意建群入口 |

**标识取真实业务数据**：工单号、租约标识及房屋四段业务编号使用项目已有口径，不拿数据库自增ID伪装业务编号。无关联房屋的会话不硬放房号；不把所有直通都渲染成无法区分的“社区直通会话”。直通仍是居民与对应社区管理方的会话，不改成与某一管理员的私人单聊；居民侧标社区管理方，管理侧标具体居民及社区。

## 4. 三端在群里分别能做什么

| 会话 | 居民端 | 管理端 | 服务人员端 |
|---|---|---|---|
| 租约群聊 | 在现有条件下预约本租约房源看房；查看/同意租赁协议；打开租约详情 | 按原权限发出/查看协议；打开租约详情 | 不新增租约参与或协议权限 |
| 看房群聊 | 查看对应预约详情并在原页面操作 | 查看对应预约、按原权限安排/处理 | 仅本人参与的带看会话，打开带看详情处理 |
| 工单群聊 | 查看对应工单，按原工单流程操作 | 打开对应工单，按原调度/审核权限处理 | 仅本人参与的工单会话，打开工单详情处理 |
| 直通会话 | 联系本社区管理员 | 按原社区权限联系对应居民 | 不开放 |

租约群已有预约/协议功能从输入区“＋”进入；工单和看房先保留“去对应业务处理”，不把整张调度/审核表单塞进聊天窗口。管理员发出协议即表达管理方意愿，居民确认一次，不再加“确认承租”等重复步骤。动作同时受角色、参与者身份和实时业务状态约束；关闭会话只读，不因切换页面复活。

## 5. 必须统一的交互规则

1. **未读不乱跳**：沿用后端已读游标；会话在前台实际可见、消息渲染后，仅按实际阅读位置推进游标，不能按已加载的最新消息一次读完；成功后更新角标。只点列表、后台页签或加载失败不清零；本人发言不增加本人未读。0不显示，超过99显示99+；铃铛通知与聊天未读不能互相清零。
2. **读完不突然消失**：在“未读”筛选中，当前选中会话读完后本次仍保留，角标归零；重新切筛选/搜索时才重新过滤，不能把右侧正在输入的会话关掉。
3. **看历史不被打断**：位于底部才跟随新消息；上翻时保留位置、提示新消息数量，点击再回到底部。加载旧消息不跳动；新消息可调整左侧排序，但不切换当前会话。
4. **切群保留输入**：各会话草稿、阅读位置按账号与会话隔离，在当前登录期间切换保留；退出登录清理，不承诺跨设备同步。发送失败保留文字/待重试图片，发送中防重复点击；结果不明先核对消息，不盲目重发。
5. **实时与异常可解释**：推送或兜底更新列表、摘要、未读和当前消息，不依赖刷新整页；断线显示重连提示。区分“暂无会话”“搜索无结果”“加载失败可重试”“已关闭只读”。切群后迟到响应不能覆盖新会话，旧账号内容不能残留。

## 6. 哪些不是单改前端就能完成

| 核对结果 | 为上述功能需要的最小支持 |
|---|---|
| 列表已有分页和类型筛选，但当前按会话ID倒序，缺关键词/未读条件 | 后端在本人参与者范围内完成全量搜索、未读筛选、最近消息稳定排序及分页；不能用前50条本地过滤冒充 |
| 消息接口当前返回全部消息，尚无历史分页 | 补分批历史加载及首条未读定位所需信息，与实时补读、已读游标保持一致；不能只加“加载更多”的假按钮 |
| 列表已有title/communityId/relatedId，但缺直接可用的对象姓名、社区/房屋定位等信息 | 补必要的结构化展示/搜索信息，明确无对应信息时的空值；不逐行拼大量请求、不解析标题猜业务 |

这里仅列缺口，不预定新接口或迁移。方案获确认后再按流程补20/30对应局部契约。只列本人参与会话，**超管不自动读取全部群**；反馈不并入四类群，业务权限和已读语义不放宽。

**第一版不做**：群内全文搜索、置顶/免打扰、任意拉人/退出/删除业务群、撤回、语音视频、文件系统和新增支付入口。不绘制没有对应能力的按钮。

**审阅后下一步**：确认本稿的功能范围和双栏布局后，才按mockup-to-page进行视觉探索及设计稿；展示共享骨架、三端菜单差异和空/失败/只读/窄窗等关键状态。设计稿仍需单独确认，之后才进入工程实施与相关链路定向验证，不重跑已通过的其他手测。
