# 本轮修复定向回归手测

> 本轮只用这一份做修复复验，不重跑整本核心链。现有R-02相册、R-03及沙箱首期已获用户确认，不重复付款或重测已确认部分；R-01/R-09和其他项目只补尚未确认的结果，下一期租金错误另记DEF-205。AI不操作交易，用户可自行检查沙箱，结果只记录用户明确反馈，不代填未报告项。

## 1. 入口与准备

## 2. 既有三项：沿用已确认结果，只补新增部分

### R-01 社区删除：先看影响，再明确确认（对应HT-02）

**角色/入口：**超管 → 社区管理 → 临时社区 → 删除。前置：临时社区至少含一套房屋和一条有效居住关系；不要求创建支付或退款记录。

1. 点击删除，检查影响预览是否列出真实房屋、有效关系、租约/财务等计数；没有的项目应为0，不得省略风险说明。
2. 取消；刷新并确认社区、房屋和关系仍在。
3. 再次删除，进入最终确认；先输入错误社区名称，应不能成功删除。
4. 核对名称及影响后输入准确名称，执行最终确认；确认社区及关联资料已删除，居民账号仍保留。

**预期：**预览按社区分组显示六格实际影响，有效关系/进行中租约醒目；账号保留、不自动退款在关键位置说明。取消/继续核对/永久删除层级清楚，较低桌面分辨率下正文可滚动、操作按钮可达。不是只点一次确认就删除，也不是因存在有效关系一律禁止超管删除；未最终确认不改变数据，不自动发起退款。

### R-02 房屋相册：真实上传，多个入口同一份数据（对应HT-04）

**角色/入口：**管理员 → 社区管理的单套房屋操作，或“租住与房源 → 房源管理” → **管理房屋图片**。前置：本社区一套尚未上传图片、可用于挂牌的测试房屋；不要清空其他房屋原有图片来凑前置。

1. 未上传图片时查看管理卡片；若已有挂牌，再检查公开入口。应为空态，不应出现伪装成实拍的默认房屋图。
2. 一次选择两张实拍并上传，应逐张显示结果；选择类型、说明和顺序后保存。再单独上传平面图并设置其类型；已有说明未保存时先确认保存，不应悄悄丢失。失败仅重试对应图片；超过10张总容量应整批拒绝，不先上传一半。
3. 关闭重开并刷新；从另一管理入口查看同一房屋，应读取同一份图片、类型、说明与顺序。
4. 挂牌后在游客房源列表/详情查看；封面优先使用实拍，平面图可查看。未挂牌时已经上传的图片不应丢失。
5. 移除本次上传的图片并刷新，管理端和公开详情应恢复真实空态；过程中不改动居住关系或租约。

**预期：**只从本地上传，不需要填写图片URL；上传后关联到房屋，不是另为每次挂牌维护一份副本。失败有提示，不能把本地预览当成已保存。

### R-03 协议与付款安排：12个月合同不等于一次付12个月（对应HT-06）

**角色/入口：**居民提交出租房源入住申请 → 管理员“租住与房源 → 入住申请”审核 → 租约详情/协议 → 居民查看协议。

**前置：**存在可用协议模板；缺少时由有权限的管理员在“租住与房源 → 协议模板”准备测试模板。

**测试数据：**月租1000元、押金2000元；计划起租日取今天或未来合法日期，合同总月数12、首付月数3、后续缴租周期1。可先在测试挂牌配置相应金额，不改旧租约历史。

1. 审核时核对“租约开始”默认今天；将总月数/首付/周期分别设为12/3/1，结束日期应自动计算，而非让两端各填一份。
2. 核对首期为 **1000×3＋2000＝5000元**，不是3000元，也不是按12个月一次收取。只改首付月数时，不应跟着修改合同总期或后续周期。
3. 管理员打开租约详情，点击“同意并发出协议”；发出即代表管理方同意，不再要求管理员重复确认另一遍。
4. 居民打开对应协议正文，点击“同意协议”；管理员和居民刷新后均应显示**待支付首期费用**或同义的待支付文案，不应继续只称待签约。
5. 不进行支付；核对租约尚未正式生效、没有新建正式租客居住关系，挂牌仍被申请临时占用，不应重新供其他人申请。

**日期核对例：**若起租日为2026-10-15，12个月合同的含止日为2027-10-14，首期3个月覆盖至2027-01-14。其他起租日按原起租日加日历月、结束显示减一天，不能固定按30天算。

**R-03本项止于交易前，不要求生成支付订单。**渠道是否启用由超管配置，不应再把暂缓测试写死成产品停用。用户自行试沙箱请用下方可选入口。原合同内普通交租不延长合同；新流程为居民申请延长租期、管理方批准即延长；不新增租约/押金，批准不等于租金已缴。新增功能按R-11复验，旧成功单和有效待支付单保留。

**R-03-B 隔日补核（可稍后记录，不必守到半夜）：**另留一条起租日为当天且首期未付的测试申请/租约，记下编号；次日00:05后定时任务运行，再查看对应申请与租约应自动驳回，未生效流程结束、占用释放；若有跨日仍有效的首期订单，须等该单实际系统截止后的扫描，不应提前驳回。同一房屋无其他阻止条件且来源挂牌仍有效时，应恢复可见/可申请。不要改系统时间、回填昨天或改历史数据；本项未经历自然跨日就留空，不影响先完成其他复验。

## 3. 此前现场与本轮增量：只补尚未确认的部分

### R-04 在线操作不被无故退出（对应HT-01）

**操作：**各端重新登录，随其他用例保持页面前台操作、切页和发送消息；结束后主动退出，再刷新或返回受保护页面。

**预期：**前台有效会话不无故掉线，主动退出后不能恢复登录。新登录及成功续期为36小时；临近到期的续期时序已有工程回归，本次不用专门等36小时，也不能仅凭短时操作就认定整个到期边界均已人工验证。

### R-05 工单服务类别可见且可选（对应HT-07）

**操作：**管理员确认本社区有启用类别；居民在本社区创建服务申请，打开类别列表、选中并提交一条“回归”工单，供R-09复用。

**预期：**类别来自当前社区并可选择，不再空白；未配置和加载失败有不同提示，不伪造选项。工单详情显示实际提交类别，不要求重走整条评价/终审流程。

### R-06 公告无图不加图，有图可编辑和移除（对应HT-08）

**操作：**管理员新建测试公告，正文应是文稿编辑页而非旧文本表单。写两段正文，试加粗、居中、列表；插入本地图片，调整为50%并预览，发布后由居民查看。点击已发布公告“修订正文”，改标题/文字、移除图片，先取消验证公开内容不变；再次编辑并显式保存修订，居民重新打开应显示新版。打开版本记录，核对旧版仍在。

**预期：**正文排版与图片大小跨端一致、无图不补图；修订不先下线，不改变投放/有效期、不重复群发。未保存离开需提醒；两窗口同时修订，旧版本不覆盖新版。既有“图片加载正常”的结果沿用，编辑器与直接修订单独填结果。

### R-07 反馈图片是双向消息，匿名不露居民身份（对应HT-09）

**操作：**居民提交一条匿名测试反馈；居民与管理员各发一张图片消息。双方实时查看、点击预览、刷新回读，并核对反馈列表、详情和居民消息气泡。

**预期：**对方都能看见对应图片，刷新不丢失；不是只有上传方可见的附件。匿名反馈不暴露居民真实姓名、用户名或手机号；管理员自己的回复身份无需匿名，图片本身也不要带个人信息。

### R-08 连续预约：占3额度，但只有1条预约（对应HT-10）

**前置：**本社区可预约资源有三个相邻、未满的半小时时段；先记管理端当天占用额度Q、预约条数N。

**操作：**居民一次预约连续90分钟；管理员刷新对应日期/时段，随后居民取消该预约，管理员再次刷新。

**预期：**提交后额度为Q＋3、预约条数为N＋1；取消后释放这3个额度。若专用空资源为12小时、24段且每段100容量，应显示**3/2400额度、1条预约**，不能显示1/2400。已有预约时只核对增量，不假定初始为0。

### R-09 共用群聊基础功能与业务菜单（对应HT-11、HT-05）

**操作：**复用R-03租约群、R-05工单群；工单群缺人员时由管理员分配`staff1`。两端各发文字和图片，预览后刷新；打开租约群功能菜单，检查预约看房入口及协议消息，已有看房群则顺手同测基础聊天，不为本项重建完整看房链。

**预期：**文字/图片双方可见且不串群，刷新有历史。对方发新消息后打开群聊阅读，再刷新会话中心，旧消息不得重新计未读；自己发消息不增加本人的未读，对方新消息仍正常计入。协议消息可打开对应正文，角色菜单不越权；从租约群预约看房能定位该租约来源房源，不只是跳回公开列表、再让居民寻找已被占用的挂牌。已有关闭会话只读，不为测此分支强行关闭正在使用的流程。

**顺手记录一项体验观察：**管理员有权限内待处理事项时，侧栏/租住子Tab应有待办红点；处理完成后刷新应更新，不把居民待付款当成管理员待办。这里只记录体验，不改原HT-12结果，不作为50阶段的需求满足性判据。

### R-10 单套挂牌配置与列表补读

**操作：**管理员在“租住与房源→房源管理”选一套未挂牌房屋，单套挂牌打开“同时配置可预约看房时段”，选默认或自定义后保存；查看该房源实际可预约时段。管理员停留在入住申请Tab，另一账号新提交申请；不刷新浏览器，等待列表补读（不超过30秒），或切Tab返回。保留一个社区筛选后重复观察。

**预期：**挂牌与时段一并保存，非法时段不留下半份挂牌；列表读取新记录，保留筛选，不重置正在编辑的表单。看房时段在已有专用入口维护，编辑既有挂牌不会自动重复生成。

### R-11 租期延长与自选缴租（新流程，报价可不交易）

**前置：**一条已生效租约。居民“合同与租期→申请延长租期”，填3个月与理由；管理员租约详情查看后批准。核对批准前后合同止期及申请历史；批准后仍由“缴纳租金”交租，不存在“续租首笔”新入口。

**预期：**待审不改止期，批准只延长一次，不另建关系、不再收押金，也不把批准当成已付款。缴租月数1起，最大是后端返回的所有确认期限内真实未缴月数；12个月只缴过1个月时可选1～11，批准延3个月后余14。改月数重新显示金额及覆盖区间，缴租本身不延长合同。

**已有待支付单时：**先继续原单，月数/金额/覆盖仍以原单为准，不能为了改月数重复扣款。正常测试库当前两笔RENT待支付订单必须保留；是否继续由用户决定，AI不关单、不伪造结算。DEF-205仍待用户渠道复验，离线报价通过不代表收银台错误已修复。

### R-12 公共资源多星期快捷模板

**操作：**管理员公共资源时段配置，选“工作日”并设置同一起止时间保存；再次相同提交；再选周一/周三并设置部分重叠时间提交。

**预期：**工作日一次生成5条周模板；完全相同只显示跳过，不复活停用条目；任一部分重叠时整批零新增并提示星期/冲突时间。工作日/周末/全周/清空快捷键及手选可组合，保存后保留选择。这里是每周循环，不是选择具体年月日。

### 可选：用户自行检查沙箱入口（SB-01）

超管进入「系统管理 → 全局配置 → 支付宝渠道配置」，确认环境为**沙箱**、配置完整且渠道已启用；不需要重新填写已保存私钥。若自行调整开关，点击保存后才生效。居民打开一条合法的待首付租约，支付渠道应不再错误显示“未配置”。

若你愿意，可自行从项目入口生成新沙箱订单并访问收银台，不复用旧签名链接；记录准确页面、时间及返回信息即可。访问收银台不等于付款成功，更不等于退款通过。本项可跳过，不要求启用正式环境，AI不会代为发起支付、查单或退款。

**新订单期限补核（仅在你本来就要试沙箱时顺带检查，不要求再付一次首期）：**新首期/租金单的付款截止为首次发起后15分钟，系统订单到期为15分30秒，页面两项均显示到秒；继续有效原单不应重新计时。旧单保持原截止，不按新时长改写；后台每5分钟扫描，状态可能晚于截止更新。此参数核查不能代替DEF-205收银台错误的复验。
