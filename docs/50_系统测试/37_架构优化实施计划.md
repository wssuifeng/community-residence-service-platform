# 架构优化实施计划

2026-10-18 · 依据用户确认的后端三级结构，以及[35架构评估](35_三端与公共模块架构评估.md)、[36结构与归属规则](36_前后端项目结构与归属规则.md)

> 本文保留实施计划与难点分析；2026-10-18用户已授权执行，S0～S5及O1～O9的实际结果见[cv实施证据](evidence/cv-architecture-implementation-20261018/README.md)，最终结构与迁移索引见36。任务状态只在[50中控cu及其后续批次](_中控.md)维护。30/40的相关结构约定已依用户授权同步，原验收历史保留。

**目标：** 先完成方便维护的前后端结构整理，再逐项改善已经发现的职责、加载和同步问题。

**架构：** 仍为一个Spring Boot应用、一个Vue应用。后端一级`admin/resident/staff/common`，二级业务或技术模块，业务模块三级`controller/service/mapper`等；前端采用相同前两级，三级使用`views/components/composables/api/types/store`。共享规则、实体、登录状态与聊天引擎各自唯一维护。

**技术约束：** 沿用Java 17、Spring Boot 4.0.6、MyBatis-Plus 3.5.16及当前Vue 3/TypeScript/Vite，版本以仓库锁文件为准；此次不升级框架，不拆Maven工程或前端应用，不新增数据库迁移。

## 1. 难处与处理方法

**主要难度是拆清端专属职责，同时保持原有业务规则、权限及事务行为。** 直接按文件夹搬迁可以完成一部分整理，但不能完成混合入口和前端依赖的调整。

规划时的静态规模为464个生产Java文件、43个Controller、144个Vue文件、93个非测试TS文件，仅表示迁移前的整理范围。规划时业务代码与35评估基线`f58282c`一致；本轮规划起点为`3c2f314`。声明清单、引用位置及采集方法见[cu静态证据](evidence/cu-structure-plan-20261018/structure-analysis.json)。

| 难点 | 当前证据与实际影响 | 处理方法 |
|---|---|---|
| 混合Controller不能整类判端 | `WorkOrderController`同时有居民提交/确认、管理派单/终审、服务人员接单/完工；会话也有端专属与共享方法 | 按HTTP方法逐项归属；共享契约只留一个入口，端专属入口分别迁移 |
| 共享规则不能复制三套 | 工单状态、租约流转、房源占用与同住依赖跨端使用 | 实体、公共写规则和持久化在`common/业务模块`；只有真实端差异才创建端Service/Mapper |
| 包迁移影响运行装配 | 现有60个`@Mapper`，未见显式`@MapperScan`或资源目录Mapper XML；51个Java文件有import之外的项目全限定名命中 | 连同注解SQL、结果类型、全限定名、扫描、Bean名和测试一起核对；不能只替换import。静态命中不等于运行依赖已完整证明 |
| 拆Service可能改变事务 | 社区删除跨多表，租约/工单修改有事务、锁和通知；部分WS发送在事务提交前 | 纯移包保持方法与事务；职责调整另提交，核对代理调用、外层回滚、锁与幂等；提交后投递见O3 |
| 权限与包名不等价 | 管理员依赖社区范围，居民/服务人员依赖本人/参与者检查；会话还隔离身份空间 | 比较角色、社区、本人、参与者四类约束；公共Controller仍按原规则鉴权 |
| 前端共享层反向引用端 | `ConversationBusinessActions.vue`直接导入居民`HousingReservationView.vue` | 提取共享预约表单与数据逻辑，居民路由页和会话弹窗分别组合，不用改路径掩盖依赖 |
| 路由和共享状态存在装配关系 | 根路由汇总四类入口，user Store负责通知初始化/清理；permission Store导入三端路由但尚未找到调用 | 路由由根入口装配；保留单份认证/通知/聊天状态；未使用代码先确认再删除，不能机械搬到公共层造成反向引用 |
| 部分建议会改变读取或呈现行为 | 工作台拼多次查询、租约逐条读支付历史、刷新广播范围宽；性能改善尚无实测结论 | 放在结构之后单独改动、单独验证；性能措施由测量决定，不承诺移目录即可提速 |

**风险最高的部分：** 混合入口拆分、跨域事务与删除、身份权限、租约金额与状态摘要。**较容易的部分：** 已有单一职责文件的移包、同步导入、保留现有组件的就近归组。当前未证明Spring循环依赖、请求风暴、Redis旧类型缓存或聊天内存泄漏，不以这些假设扩大改造。

## 2. 实施顺序与批次

| 批次 | 任务 | 交付边界 | 验证后才继续 |

后端结构是第一交付目标。O编号用于对应工作项，具体先后以本表分组为准。每组达到可构建、可审阅的边界后形成独立提交；前端和后续行为优化不夹进后端移包提交。不用本计划要求用户重新测试已经通过的整本手册。

## 3. 结构治理任务

以下路径均相对项目根目录。S1之后，后端原业务路径中的类由`common/同名业务模块`接管；后续任务均使用迁移后的路径。全量逐文件清单由S0产出，本轮证据只是当前库存与代表性难点，不能当成已完成的最终归属表。

### S0 · 建立完整清单与兼容基线

**文件与产物：** 读取`backend/src/main/java/com/community/residence/`、`backend/src/test/`、`frontend/src/`及构建配置；在实施批次对应的新证据目录补`backend-ownership.csv`、`frontend-ownership.csv`、`http-contract.json`、`route-contract.json`和`test-baseline.md`；本轮cu库存保留为规划依据，不用后续结果覆盖。

1. 每个Java/Vue/TS生产文件记录原路径、目标路径、中文职责、公共/端归属与引用者；混合Controller逐方法记录HTTP方法、路径、角色表达式、数据范围检查和DTO/VO。待拆文件记录一对多去向，不能为四个一级目录凑空壳。
2. 核对完全限定名、反射/序列化、注解SQL、扫描、`@Bean`名称、切面和测试夹具；区分源码引用与真实Bean依赖。Redis只核对实际读写和类型策略，不预设存在旧类名缓存，不清空Redis。
3. 导出真实HTTP映射及前端路由/名称/角色/重定向/懒加载基线，保留分页、JSON字段、错误响应和WS目的地/载荷约定；测试装配使用替身，不连接支付渠道。仅靠注解正则不作为运行映射验收。
4. 先审查现有测试是否使用正常库或外部渠道，再记录安全可重复的测试基线、失败项及原因。性能基线只采受影响页面的请求数、响应/渲染耗时，不在迁移前启动全站压测。
5. 实施授权后，按既有冻结保护流程同步`docs/30_系统设计/架构设计.md`相关结构约定、前端相关设计段落、40实施说明与`AGENTS.md`，留决策记录；不改系统定义或新增需求。当前仅列此步骤，不擅改冻结文档。

**验收与提交：** 清单覆盖全部库存文件，所有原HTTP入口都有唯一去向，分类理由和需拆分位置明确；先提交`docs(architecture): record migration ownership and compatibility baseline`。

### S1 · 后端公共业务与技术代码迁移

**范围：** `backend/src/main/java/com/community/residence/`现有业务模块，以及根级`config/filter/interceptor/log/schedule/common`；相应测试同步迁移。

**关键归属：** 业务实体/Mapper/共享Service移至`common/<业务模块>/`；认证业务归`common/auth`，上下文/过滤器/数据权限归`common/security`，统一响应/异常归`common/web`，上传归`common/upload`，配置/留痕/任务各归`common/config`、`common/log`、`common/schedule`。启动类留根包。`ConfigController/SysConfigService/SysConfigMapper/SysConfig`属于系统配置，归`admin/auth`入口与`common/auth`规则/存储，不继续借居民目录承载。

1. 依S0映射作机械移包，业务模块间交叉引用作为同一可编译迁移集合处理；更新package/import、代码内全限定名、相关SQL结果类型及测试引用。
2. 当前Controller先随所属业务整体迁入`common/<业务模块>/controller`以保留全部原入口，作为S2之前的短期过渡；S2必须清走端独有入口。不能并存旧类和新类同时注册，也不发布“只有目录、尚不能编译”的提交。
3. 保持类名/方法体/事务注解/锁键/缓存键/配置项不变；技术模块不凑业务层。支付包只作引用迁移，渠道开关、凭据来源、密钥文件位置与交易逻辑不变。

**验收：** `backend/mvnw.cmd -f backend/pom.xml -DskipTests package`成功；原Mapper均可装配、SQL类型解析通过[2]，原映射无丢失/重复；运行S0选出的受影响单元测试及装配检查。既有注解留痕应继续生效，不凭移包推断切面失效。

**提交：** `refactor(backend): relocate shared modules without behavior changes`；此提交只含移包与必要引用修正。

### S2 · 按业务模块拆分三端入口及真实端专属处理

**首个完整模块：** 将原`WorkOrderController`拆为`admin/workorder/controller/AdminWorkOrderController.java`、`resident/workorder/controller/ResidentWorkOrderController.java`、`staff/workorder/controller/StaffWorkOrderController.java`与`common/workorder/controller/WorkOrderQueryController.java`；原`WorkOrderService`仍在`common/workorder/service`唯一维护状态流转。

1. 居民提交/修改/确认/退回/取消归居民入口，管理受理/派单/终审/驳回/建群归管理入口，服务人员接单/处理/完工归服务人员入口；详情/列表/时间线等同一契约只保留一个公共handler。附件按原授权规则逐方法归属，不另起三套存储。
2. 端Controller可直接调用公共Service完成既有单域操作；只有真实端专属协调或查询才设端Service/Mapper。新增Controller使用含端/职责前缀的类名；同步Bean名称、注入、注解和接口说明，保持原HTTP方法与URL。
3. 工单验证后，依次按模块处理社区/居民、房源/看房、租约/协议/支付、公告/反馈/预约/评价、统计/账号/会话/消息中心。每模块按S0方法清单拆分；不能因`admin`包名省略社区范围，不能因`common`包名放行未登录访问。
4. 会话发送/已读与多端相同消息中心契约保留公共入口；管理建群、居民预约等专属操作归端。登录注册和公开房源浏览归公共认证/公开入口，保留游客只读边界。

**验证：** 新增`backend/src/test/java/com/community/residence/common/web/ControllerMappingCompatibilityTest.java`，比较S0映射、请求/响应约定与角色限制；原有`WorkOrderAttachmentAccessTest`、`WorkOrderStateMachineFixTest`、`ConversationParticipantIdentitySpaceTest`等按模块迁移后运行。必须验证跨社区、非本人、非参与者拒绝，同数字ID不同身份空间仍隔离。映射检查不能只断言URL存在。

**提交：** 每个完整业务模块一笔，如`refactor(backend): separate work order portal entry points`；金融相关模块与普通模块分别提交，仍只做结构变更。

## 4. 结构之后的职责与行为优化

以下路径为实施后的目标位置；不要求一次完成。每项先增加能体现原风险的定向用例，再修改实现，运行对应测试后提交；已有测试直接复用，不为移文件编写重复断言。

### O1 · 三端工单详情加载一致性（A1）

**文件：** `frontend/src/common/workorder/composables/useWorkOrderDetail.ts`、`common/workorder/components/`详情只读区块、三端`workorder/views/WorkOrderDetailView.vue`及同模块测试。

- 主详情、时间线、附件分别维护结果/加载/错误；主详情成功即可展示，辅助请求失败局部重试；动作按端继续组合。避免提取成把全部旧逻辑再包装一层的巨大组件。
- 监听工单ID与身份变化，重置旧数据，用请求版本防止旧响应覆盖新工单；这是对路由实例复用风险的处理，当前没有把它冒称已复现缺陷。[3]
- 验证三端正常详情、辅助接口单独失败、快速切换ID、路由复用、旧响应晚到及退出清理；新增共享composable测试，保留原三端动作测试。
