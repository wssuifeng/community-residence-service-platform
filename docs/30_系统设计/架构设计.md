## 1. 总体架构（实现 R44/R45/R48~R50/N2/N4/N5/N9/N10）

前后端分离单体（单部署实例 · 单机可部署，N9）。总体架构图：
[总体架构图.html](assets/01_总体架构/总体架构图.html)
（源文件 [总体架构.architecture.json](assets/01_总体架构/总体架构.architecture.json)，
archify 交付 9/9 检查通过，SHA-256 见交付回执）。

```
浏览器（五类角色）──HTTPS──→ frontend Vue3 SPA
                              │ REST /api（Axios）＋ WebSocket 订阅
                              ▼
backend 单体（Spring Boot 4）
  ├─ 统一接入与安全层：Spring Security 过滤链 + JWT
  ├─ 业务模块层：Controller → Service → Mapper（对齐 C1~C12）
  ├─ 消息通知服务：WebSocket(STOMP) 实时推送
  └─ 横切支撑：定时任务 + AOP 切面（留痕）
        │                    │
        ▼                    ▼
     MySQL（业务库）      Redis（令牌黑名单/会话）
```

要点与需求映射：

- **无状态水平服务**：业务请求不依赖服务器会话（JWT 无状态认证，N2 并发
  不劣化的基础）；Redis 仅承载登出令牌黑名单与长连接会话注册表；
- **单进程内分层**：Controller（协议适配）→ Service（业务与状态机）→
  Mapper（数据访问）三层，禁止跨层调用（Controller 不得直连 Mapper）；
- **多实例留待未来**：单实例即可满足 N2（50 并发）；架构上不做分布式
  假设，避免为非目标（多租户 SaaS）提前付费。

## 3. 认证与授权骨架（实现 R43~R46/N4/N5）

### 3.1 认证（JWT）

- 登录签发 Access Token（短效，默认 2h）+ Refresh Token（长效，默认 7 天），jjwt 0.12.6；
- **登出/注销**：令牌加入黑名单（**DB 双写 + Redis 缓存**），N4「登出后令牌失效」的落地方案：
  - **权威来源**：数据库表 `auth_token_blacklist`（jti + user_id + expire_time + reason）
  - **性能缓存**：Redis（key: `token:blacklist:${jti}`，TTL: 令牌剩余有效期）
  - **降级策略**：Redis 不可用时，降级查 DB 验证黑名单（登出仍可成功，黑名单仍可生效，只是查询变慢）
  - **定时清理**：每日凌晨 3:00 清理 DB 中已过期的黑名单记录（减轻 DB 压力）
- 密码 BCrypt 存储（N4）。

**黑名单双写实现**：
```java
@Transactional
public void logout(String token) {
    String jti = jwtUtil.extractJti(token);
    Date expireTime = jwtUtil.extractExpiration(token);
    
    // 1. 写入 DB（权威来源，失败回滚）
    TokenBlacklist blacklist = new TokenBlacklist();
    blacklist.setJti(jti);
    blacklist.setExpireTime(expireTime);
    blacklist.setReason("LOGOUT");
    blacklistMapper.insert(blacklist);
    
    // 2. 写入 Redis（缓存，失败不影响登出）
    try {
        long ttl = expireTime.getTime() - System.currentTimeMillis();
        redisTemplate.opsForValue().set("token:blacklist:" + jti, "1", ttl, TimeUnit.MILLISECONDS);
    } catch (RedisConnectionException e) {
        log.warn("Redis 不可用，黑名单已写入 DB，登出成功但缓存失效");
    }
}

// 黑名单校验（含降级逻辑）
public boolean isBlacklisted(String jti) {
    try {
        // 优先查 Redis
        Boolean cached = redisTemplate.hasKey("token:blacklist:" + jti);
        if (cached != null) return cached;
        
        // Redis 未命中，查 DB 并回种
        TokenBlacklist blacklist = blacklistMapper.selectByJtiAndNotExpired(jti);
        if (blacklist != null) {
            try {
                long ttl = blacklist.getExpireTime().getTime() - System.currentTimeMillis();
                redisTemplate.opsForValue().set("token:blacklist:" + jti, "1", ttl, TimeUnit.MILLISECONDS);
            } catch (Exception ignored) {}
            return true;
        }
        return false;
        
    } catch (RedisConnectionException e) {
        log.warn("Redis 不可用，降级查 DB 黑名单：jti={}", jti);
        return blacklistMapper.selectByJtiAndNotExpired(jti) != null;
    }
}
```

### 3.2 两层权限模型（N5 的设计落点）

权限校验分两层，任一层不通过即拒绝并记录（越权 100% 记日志，R44/R47）：

```
第一层 · 功能级（Spring Security 注解，方法级）
  @PreAuthorize 角色断言：游客(公开接口免鉴权)/居民/服务人员/社区管理员/超管
  全局级操作（社区新建停用、全局配置、全系统广播、管理员账号管理）
  → 仅 SUPER_ADMIN 断言；社区管理员调用即 100% 拒绝

第二层 · 数据级（社区过滤切面）
  社区管理员请求 → 从 Redis 读取绑定社区集合（未命中则查库回种），
  通过 MyBatis-Plus 拦截器强制注入过滤条件 community_id IN (...)
  业务表挂 community_id（数据库设计详述）；超管不注入过滤
  公开信息子集（R12）：无有效居住关系账号 → 公开白名单路由 + 后端二次校验
```

**权限数据存储策略**：
- JWT Claims 仅存储 `userId`、`role`、`username`（精简体积，避免绑定社区
  列表导致令牌膨胀）；
- 社区绑定关系存储：
  - **权威来源**：数据库表 `sys_admin_community`（admin_id + community_id）
  - **性能缓存**：Redis（key: `user:${userId}:communities`，value: Set<String>，
    TTL: 2h 与 Access Token 同步）
- 每次请求时从 Redis 读取绑定社区列表（缓存未命中则查库并回种），
  注入 SQL 过滤条件；

**绑定关系变更处理**：
1. 更新数据库表 `sys_admin_community`；
2. 删除 Redis 缓存 `user:${userId}:communities`（下次请求自动回种新数据）；
3. 吊销该管理员全部有效令牌（查询 `auth_token` 表获取所有 jti，
   批量写入黑名单，确保旧权限范围立即失效）。

## 3.3 缓存设计（实现 N2/N4 性能基础）

### 3.3.1 Redis 职责划分

| 用途 | Key 模式 | TTL | 更新策略 |
|------|---------|-----|---------|
| JWT 黑名单 | `token:blacklist:${jti}` | 令牌剩余有效期 | 登出/注销时写入，自然过期删除 |
| 用户绑定社区缓存 | `user:${userId}:communities` | 与 Access Token 同步（默认 2h） | 绑定变更时主动清理 + 令牌吊销 |
| WebSocket 会话注册 | `ws:session:${userId}` | 连接断开时删除 | 连接建立写入，心跳续期 |
| 通知全局序号 | `notification:seq` | 永久 | `INCR` 原子递增，业务表同步写入 |
| 社区基础信息 | `community:${id}` | 1h + 随机偏移（±10min） | Cache-Aside：读缓存未命中查库回种；写操作主动失效 |
| 公告列表（社区维度） | `notice:list:${communityId}:${page}:${size}` | 10min + 随机偏移（±2min） | 新增/修改/下线时主动失效（模糊匹配 `notice:list:${communityId}:*`） |
| 房源浏览统计计数 | `housing:view:${housingId}` | 5min | 定时批量回写数据库（减少写压力）；回写成功后删除 key |
| 布隆过滤器（防穿透） | `bloom:community:exists` | 永久 | 启动时加载全部社区 ID；新增社区时同步添加；每日凌晨 2:00 重建 |

### 3.3.2 缓存一致性保证

**策略分级**：
- **强一致**（黑名单、绑定社区）：写操作同步更新缓存 + 数据库，失败回滚；
- **最终一致**（社区信息、公告）：Cache-Aside 模式，写操作删除缓存，下次读回种；
- **允许短暂不一致**（浏览统计）：异步批量回写，缓存丢失可接受。

**缓存穿透防护**：
- Redisson 布隆过滤器前置（社区 ID、房源 ID），不存在的 ID 直接拦截；
  ```java
  // 启动时初始化
  RBloomFilter<String> communityFilter = redisson.getBloomFilter("bloom:community:exists");
  communityFilter.tryInit(100000L, 0.01); // 预期 10 万社区，误判率 1%
  List<String> ids = communityMapper.selectAllIds();
  ids.forEach(communityFilter::add);
  
  // 查询前校验
  if (!communityFilter.contains(communityId)) {
      throw new ResourceNotFoundException("社区不存在");
  }
  ```
- 空值缓存（TTL 1min），防止恶意查询不存在的资源：
  ```java
  Community community = getFromCache(id);
  if (community == null) {
      community = communityMapper.selectById(id);
      if (community == null) {
          // 缓存空对象，防止穿透
          redisTemplate.opsForValue().set("community:" + id, "NULL", 1, TimeUnit.MINUTES);
          return null;
      }
      redisTemplate.opsForValue().set("community:" + id, community, 1, TimeUnit.HOURS);
  }
  return "NULL".equals(community) ? null : community;
  ```

**缓存击穿防护**（热点数据）：
- 分布式锁（Redis `SETNX`）+ 双重检查，只有一个请求回源加载：
  ```java
  String lockKey = "lock:community:" + id;
  try {
      if (redisTemplate.opsForValue().setIfAbsent(lockKey, "1", 10, TimeUnit.SECONDS)) {
          // 获得锁，回源加载
          Community community = communityMapper.selectById(id);
          redisTemplate.opsForValue().set("community:" + id, community, 1, TimeUnit.HOURS);
          return community;
      } else {
          // 未获得锁，短暂等待后重试缓存
          Thread.sleep(50);
          return getFromCache(id); // 递归重试
      }
  } finally {
      redisTemplate.delete(lockKey);
  }
  ```
- 热点数据 TTL 增加随机偏移（±10%），避免同时过期：
  ```java
  long ttl = 3600 + ThreadLocalRandom.current().nextInt(-360, 360); // 1h ± 6min
  redisTemplate.opsForValue().set(key, value, ttl, TimeUnit.SECONDS);
  ```

**缓存雪崩防护**：
- 所有缓存 TTL 增加随机偏移（已体现在职责划分表中）；
- Redis 持久化开启（AOF + RDB 混合模式），重启后快速恢复；
- 启动时预热核心数据（社区列表、有效公告），避免冷启动雪崩；
- 降级开关：Redis 不可用时自动降级为仅数据库查询（AOP 切面捕获
  `RedisConnectionException`，记录告警，透传请求到数据库）。

### 3.3.3 缓存更新时机与预热策略

**缓存更新时机**：

| 业务场景 | 更新策略 | 实现位置 |
|---------|---------|---------|
| 社区管理员绑定变更 | 清理社区列表缓存 + 吊销令牌（批量写入黑名单） | `auth` 模块 AOP 切面 |
| 社区信息修改 | 删除 `community:${id}` | `community` Service 写方法后置处理 |
| 公告发布/修改/下线 | 模糊删除 `notice:list:${communityId}:*`（Lua 脚本批量删除） | `notice` Service 写方法后置处理 |
| 房源浏览 | 递增 Redis 计数器（`INCR housing:view:${id}`），定时任务每 5 分钟批量刷库 | `housing` Service + `schedule` 模块统一调度 |
| 社区新增/删除 | 新增：同步添加到布隆过滤器；删除：标记为已删除（软删除），次日重建布隆过滤器 | `community` Service + 定时任务 |

**缓存预热策略**（启动时执行，避免冷启动雪崩）：

**预热优先级原则**（用户复核确认）：
- **高优先级**：高频读且变更少的数据（社区基础信息、布隆过滤器）
- **中优先级**：高频读但变更频繁的数据（有效公告首页列表）
- **低优先级**：访问频率不确定的数据（房源详情、用户信息）
- **具体预热数据清单留待测试阶段压测确认**（测试不同预热策略对启动时间与缓存命中率的影响）

```java
@Component
public class CacheWarmupRunner implements ApplicationRunner {
    @Override
    public void run(ApplicationArguments args) {
        log.info("开始缓存预热...");
        
        // 1. 预热社区基础信息（高优先级，假设社区数量 < 100）
        List<Community> communities = communityMapper.selectList(
            Wrappers.<Community>lambdaQuery().eq(Community::getStatus, "ACTIVE")
        );
        communities.forEach(c -> {
            long ttl = 3600 + ThreadLocalRandom.current().nextInt(-360, 360);
            redisTemplate.opsForValue().set("community:" + c.getId(), c, ttl, TimeUnit.SECONDS);
        });
        
        // 2. 预热布隆过滤器（高优先级，社区 ID）
        RBloomFilter<String> communityFilter = redisson.getBloomFilter("bloom:community:exists");
        communityFilter.tryInit(100000L, 0.01);
        communities.forEach(c -> communityFilter.add(c.getId()));
        
        // 3. 预热有效公告首页列表（中优先级，仅首页前 10 条）
        // 测试阶段根据访问日志确认是否预热、预热多少条
        if (shouldPreloadNotices()) { // 配置开关
            communities.forEach(c -> {
                List<Notice> notices = noticeMapper.selectPage(
                    new Page<>(1, 10),
                    Wrappers.<Notice>lambdaQuery()
                        .eq(Notice::getCommunityId, c.getId())
                        .eq(Notice::getStatus, "PUBLISHED")
                        .orderByDesc(Notice::getPublishTime)
                ).getRecords();
                long ttl = 600 + ThreadLocalRandom.current().nextInt(-120, 120);
                redisTemplate.opsForValue().set("notice:list:" + c.getId() + ":1:10", notices, ttl, TimeUnit.SECONDS);
            });
        }
        
        log.info("缓存预热完成：社区 {} 个，公告缓存 {} 个", communities.size(), shouldPreloadNotices() ? communities.size() : 0);
    }
    
    private boolean shouldPreloadNotices() {
        return environment.getProperty("cache.warmup.notices.enabled", Boolean.class, false);
    }
}
```

## 4. 实时通信设计（实现 R29/R30/R48~R51/N3）

- **选型：Spring WebSocket + STOMP 子协议**。理由（决策日志 09-06 留痕）：
  满足 N3（≤3 秒在线送达）与 E11 双向场景（反馈会话双方收发）；SSE 仅
  单向推送无法承载 C6 会话，不满足全部需求，排除；
- 用户级订阅隔离：STOMP 用户目的地（`/user/queue/notifications`），
  天然按账号隔离，服务人员只收被派工单、居民只收本人通知（R48 覆盖）；
- **上线补拉**（R50）：通知表使用 Redis 全局序号（`INCR notification:seq`）
  保证严格单调递增，登录/重连时携带本地最大序号增量拉取——补拉不依赖
  长连接，掉线不丢（E11）；序号生成与通知记录插入在同一事务内完成；
- 渠道分级（R51）：站内必达；短信/微信服务号为**可插拔模拟通道**（接口
  + 空实现，触发即写留痕记录），不依赖真实第三方（N9）。

### 4.1 长连接鉴权与降级策略（Redis 雪崩场景）

**核心理念**：保大头（正常用户），牺牲长尾（异常流量）；优先核心消息通道可用，权限变更允许短暂延迟。

#### 4.1.1 降级鉴权策略

**正常情况**（Redis 可用）：
- 连接建立（CONNECT/握手）时，校验 JWT 令牌（Redis 黑名单 + 用户状态）
- 鉴权通过后建立会话，后续消息收发直接走长连接，不再频繁鉴权

**降级情况**（Redis 不可用）：
- 连接建立时，通过 **DB 一次鉴权**（黑名单降级查 DB，用户状态查 DB）
- 鉴权通过后建立会话，后续业务请求直接走长连接，不再频繁鉴权
- **DB 鉴权压力**：50 并发用户，会话生命周期 30min，DB 鉴权 QPS = 50 / 1800 ≈ 0.028，完全可控

#### 4.1.2 会话生命周期与重连豁免

**会话生命周期**：10-30 分钟（可配置），到期后服务端主动断连，客户端重连时重新鉴权。

**短时重连豁免**（防止网络抖动导致 DB 压力飙升）：
```java
// 会话断开时缓存用户状态（5 分钟有效）
public void onDisconnect(String sessionId, Long userId) {
    try {
        redisTemplate.opsForValue().set(
            "session:reconnect:" + userId, 
            sessionId, 
            5, 
            TimeUnit.MINUTES
        );
    } catch (RedisConnectionException e) {
        // Redis 不可用时不缓存，降级为每次重连都鉴权
    }
}

// 重连时检查豁免（5 分钟内重连免鉴权）
public boolean canReconnectWithoutAuth(Long userId, String oldSessionId) {
    try {
        String cachedSessionId = redisTemplate.opsForValue().get("session:reconnect:" + userId);
        return oldSessionId.equals(cachedSessionId);
    } catch (RedisConnectionException e) {
        return false; // Redis 不可用时不豁免，走 DB 鉴权
    }
}
```

#### 4.1.3 权限变更处理（主动踢人）

**场景**：用户在会话期内被封禁/解绑社区/角色变更，需立即生效（R47）。

**实现**：
- 维护本地映射 `userId -> sessionId`（单实例）
- 权限变更时主动踢人（发送 KICK 消息 + 服务端关闭连接）
- 用户被迫重连，重新鉴权获取新权限

```java
// 本地映射（单实例）
private static final ConcurrentMap<Long, String> USER_SESSION_MAP = new ConcurrentHashMap<>();

// 权限变更时踢人
public void kickUser(Long userId, String reason) {
    String sessionId = USER_SESSION_MAP.get(userId);
    if (sessionId != null) {
        simpMessagingTemplate.convertAndSendToUser(
            sessionId, 
            "/queue/kick", 
            new KickMessage(reason)
        );
        // 服务端主动关闭连接
        WebSocketSession session = sessionRegistry.getSession(sessionId);
        if (session != null) {
            session.close(CloseStatus.POLICY_VIOLATION);
        }
        USER_SESSION_MAP.remove(userId);
        log.info("踢出用户：userId={}, reason={}", userId, reason);
    }
}

// 多实例扩展（未来）：通过 Redis Pub/Sub 广播踢人指令
public void kickUserCluster(Long userId, String reason) {
    redisTemplate.convertAndSend("channel:kick", new KickCommand(userId, reason));
}
```

#### 4.1.4 频控与防雪崩

**鉴权失败处理分级**：
- **认证失败**（密码错误、用户不存在）：允许 5 次/5 分钟，超过则拉黑 5 分钟（传统频控）
- **鉴权失败**（令牌伪造、过期令牌反复使用）：**一次即拉黑 1 小时**（异常流量，从源头阻断）

**拉黑实现**（本地 + Redis 双层）：
```java
// 本地拉黑缓存（避免 Redis 不可用时拉黑失效）
private static final LoadingCache<String, Long> LOCAL_BLACKLIST = Caffeine.newBuilder()
    .expireAfterWrite(1, TimeUnit.HOURS)
    .maximumSize(10000)
    .build(key -> null);

public void blacklistIpOrUser(String key, String reason, Duration duration) {
    long expireTime = System.currentTimeMillis() + duration.toMillis();
    
    // 1. 本地拉黑（立即生效）
    LOCAL_BLACKLIST.put(key, expireTime);
    
    // 2. Redis 拉黑（集群同步）
    try {
        redisTemplate.opsForValue().set("blacklist:" + key, reason, duration);
    } catch (RedisConnectionException e) {
        log.warn("Redis 不可用，仅本地拉黑：key={}", key);
    }
    
    // 3. DB 审计日志
    blacklistLogMapper.insert(new BlacklistLog(key, reason, new Date(expireTime)));
}
```

## 4b. 通知生成机制（实现 R48）

- 业务事件 → `messaging` 模块统一入口 `NotificationPublisher`（Spring
  应用事件解耦：各模块发布领域事件，监听器生成通知），通知记录携带

## 5. 定时任务与自动判定（实现 R14/R15/R26）

单实例内 Spring `@Scheduled`（无需引入调度中间件，N9 单机约束）：

| 任务 | 频率 | 逻辑 | 幂等保证 |
|------|------|------|---------|
| 租期判定扫描 | 每日 01:00 | 扫描已生效租住 → 按止期+N 天判定「即将到期/已到期」（R14，非人工流转）；分页扫描（每批 500 条） | Redisson 分布式锁（`lease:scan:lock`，TTL 30min，看门狗自动续期）；状态只前进不回退 |
| 到期提醒 | 判定扫描后触发 | 同一租住记录同一状态只提醒一次（提醒去重表 `lease_reminder`，唯一键 `lease_id + status`），管理员可手动重发（插入前删除旧记录） | 数据库唯一约束；失败重试（@Retryable，最多 3 次，指数退避） |
| 公告下线 | 每小时 | 失效时间已过的公告批量下线（R26）；详情访问兜底校验（下线前窗口期 ≤1 小时）；同步清理缓存 `notice:list:*` | WHERE 条件包含状态判断，避免重复更新；分布式锁防止并发执行 |
| 浏览统计回写 | 每 5 分钟 | Redis Pipeline 批量读取 `housing:view:*` 计数器，累加到数据库 `view_count` 字段，回写成功后删除 Redis key | 数据库更新使用 `UPDATE ... SET view_count = view_count + ?` 保证原子性；失败时 Redis key 保留，下次重试 |
| 布隆过滤器重建 | 每日 02:00 | 从数据库全量加载社区/房源 ID，重建布隆过滤器（处理删除场景） | 使用临时 key 构建，完成后原子替换（`RENAME bloom:temp bloom:community:exists`） |

**任务执行监控**：
```java
@Component
public class ScheduledTaskMonitor {
    @Around("@annotation(org.springframework.scheduling.annotation.Scheduled)")
    public Object monitor(ProceedingJoinPoint pjp) throws Throwable {
        String taskName = pjp.getSignature().getName();
        long startTime = System.currentTimeMillis();
        
        TaskExecutionLog log = new TaskExecutionLog();
        log.setTaskName(taskName);
        log.setStartTime(new Date(startTime));
        
        try {
            Object result = pjp.proceed();
            long duration = System.currentTimeMillis() - startTime;
            log.setEndTime(new Date());
            log.setDuration(duration);
            log.setStatus("SUCCESS");
            
            // 超过预期 2 倍时间告警
            if (duration > getExpectedDuration(taskName) * 2) {
                log.setAlertLevel("WARN");
                log.setAlertMessage("任务执行超时：预期 " + getExpectedDuration(taskName) + "ms，实际 " + duration + "ms");
            }
            
            taskLogMapper.insert(log);
            return result;
            
        } catch (Exception e) {
            log.setEndTime(new Date());
            log.setStatus("FAILED");
            log.setErrorMessage(e.getMessage());
            log.setAlertLevel("ERROR");
            taskLogMapper.insert(log);
            
            // 失败 3 次后人工介入标记
            if (getRecentFailureCount(taskName) >= 3) {
                alertService.notifyAdmin("定时任务连续失败：" + taskName);
            }
            
            throw e;
        }
    }
}
```

## 8b. 性能关键路径与指标（实现 N2）

**目标并发**：50 并发用户（N2），关键接口响应时间目标：

| 接口 | 目标响应时间 | 性能瓶颈点 | 优化措施 |
|------|-------------|-----------|---------|
| POST /api/auth/login | < 500ms | BCrypt 密码校验（CPU 密集） | 使用默认强度 10（平衡安全与性能）；JWT 签发缓存公钥；失败次数限流（5 次/5 分钟） |
| POST /api/workorder | < 1s | 状态机流转 + 通知生成（2 次数据库写入 + 1 次事件发布） | 通知推送异步化（事务提交后）；数据库连接池 20 个（HikariCP 默认）；索引优化（user_id + status） |
| GET /api/notice/list | < 300ms | 社区维度分页查询 | Redis 缓存列表（TTL 10min + 随机偏移）；分页参数合理性校验（max pageSize=100）；数据库复合索引（community_id + status + publish_time） |
| WebSocket 推送 | < 3s（N3） | 在线用户数 × 消息大小 | 消息体压缩（JSON 精简，移除冗余字段）；批量推送使用 STOMP 广播而非逐个发送；心跳间隔 30s |
| GET /api/statistics/dashboard | < 2s | 多维度聚合查询（C9 运营看板） | 按日/周/月预聚合结果缓存（Redis，TTL 1h）；慢 SQL 监控（Druid，阈值 1s）；异步刷新缓存 |

**数据库连接池配置**（HikariCP）：
```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 20        # 最大连接数（公式：核心线程数 × 平均SQL时间 / 平均响应时间 × 2）
      minimum-idle: 5              # 最小空闲连接
      connection-timeout: 30000    # 连接超时 30s
      idle-timeout: 600000         # 空闲连接存活 10min
      max-lifetime: 1800000        # 连接最大生命周期 30min
      connection-test-query: SELECT 1  # 连接测试查询
```

**性能监控埋点**：
- 所有 Controller 方法 AOP 记录耗时（超过目标 2 倍记录 WARN 日志）；
  ```java
  @Around("@RestController")
  public Object monitor(ProceedingJoinPoint pjp) {
      long start = System.currentTimeMillis();
      Object result = pjp.proceed();
      long duration = System.currentTimeMillis() - start;
      
      if (duration > getThreshold(pjp.getSignature().getName()) * 2) {
          log.warn("接口响应慢：{} 耗时 {}ms", pjp.getSignature(), duration);
      }
      return result;
  }
  ```
- Druid 监控慢 SQL（阈值 1s）+ SQL 防火墙（禁止 `SELECT *`、未加 WHERE 的 UPDATE/DELETE）；
- Redis 连接池监控（Lettuce 默认，最大连接数 8，等待队列长度告警阈值 50）；
- JVM 监控（堆内存使用率、GC 频率与耗时，告警阈值：Full GC > 5 次/小时）。

## 9. 异常处理与降级策略

### 9.1 外部依赖降级

| 依赖 | 降级策略 | 用户体感 | 实现方式 |
|------|---------|---------|---------|
| Redis 不可用 | **黑名单降级查 DB**（登出仍可成功，黑名单仍可生效）；业务缓存降级查库（响应变慢但功能可用） | 响应变慢（缓存失效），但功能完全可用 | `@Around("@Cacheable")` 捕获异常调用原方法；黑名单校验见 §3.1 双写逻辑 |
| MySQL 连接池耗尽 | HikariCP 默认等待 30s 超时；超时返回 503 + 明确错误信息 | 提示"系统繁忙，请稍后重试" | 全局异常处理捕获 `SQLTimeoutException` → 503 |
| WebSocket 连接失败 | 前端自动降级为轮询模式（每 10s 调用 `/api/notifications/pull` 增量拉取） | 通知延迟增加（10s 内送达，仍满足 N3） | 前端 WebSocket onerror 回调触发轮询；后端补拉接口按 seq 返回增量 |
| 布隆过滤器未初始化 | 跳过布隆校验，直接查库（记录 WARN 日志） | 性能轻微下降（增加穿透查询） | 启动时异步初始化布隆过滤器，初始化前查询直接透传 |

**降级开关配置**（application.yml）：
```yaml
resilience:
  redis:
    enabled: true                # Redis 总开关，false 时全局降级
    circuit-breaker:
      failure-threshold: 5       # 连续失败 5 次触发熔断
      wait-duration: 60s         # 熔断后等待 60s 再尝试恢复
  cache:
    bloom-filter-enabled: true   # 布隆过滤器开关，紧急情况可关闭
```

**Redis 雪崩降级关键点**（详见 §3.1 黑名单双写、§4.1 长连接降级鉴权）：
- **黑名单双写**：DB 为权威来源，Redis 为缓存，降级查 DB 保证登出必定生效
- **长连接鉴权**：建立时一次 DB 鉴权，会话期免检（30min），DB 压力从秒级降为分钟级
- **短时重连豁免**：5 分钟内重连免鉴权，防止网络抖动冲击 DB
- **鉴权失败拉黑**：本地 + Redis 双层拉黑，一次鉴权失败即拉黑 1 小时（保护 DB）

### 9.2 统一异常处理

`@RestControllerAdvice` 全局捕获：

| 异常类型 | HTTP 状态码 | 错误码 | 返回示例 | 日志级别 |
|---------|------------|-------|---------|---------|
| `IllegalArgumentException` | 400 | `INVALID_PARAM` | `{"code": "INVALID_PARAM", "message": "预约时段不在可预约范围", "timestamp": 1693900800}` | WARN |
| `UnauthorizedException` | 401 | `UNAUTHORIZED` | `{"code": "UNAUTHORIZED", "message": "令牌已失效"}` | WARN |
| `ForbiddenException` | 403 | `FORBIDDEN` | `{"code": "FORBIDDEN", "message": "无权访问该社区数据"}` | ERROR（记录越权尝试） |
| `ResourceNotFoundException` | 404 | `NOT_FOUND` | `{"code": "NOT_FOUND", "message": "工单不存在"}` | INFO |
| `BusinessException` | 200 | 业务错误码 | `{"code": "WORKORDER_INVALID_TRANSITION", "message": "当前状态不允许此操作", "data": null}` | WARN |
| `DuplicateKeyException` | 409 | `DUPLICATE_RESOURCE` | `{"code": "DUPLICATE_RESOURCE", "message": "资源已存在"}` | WARN |
| `SQLTimeoutException` | 503 | `SERVICE_UNAVAILABLE` | `{"code": "SERVICE_UNAVAILABLE", "message": "系统繁忙，请稍后重试"}` | ERROR |
| `Exception`（兜底） | 500 | `INTERNAL_ERROR` | `{"code": "INTERNAL_ERROR", "message": "系统内部错误", "traceId": "abc123"}` | ERROR（含堆栈） |

**统一响应格式**：
```java
@Data
public class ApiResponse<T> {
    private String code;         // 错误码或 "SUCCESS"
    private String message;      // 用户友好提示
    private T data;              // 业务数据
    private Long timestamp;      // 时间戳
    private String traceId;      // 链路追踪 ID（生产环境）
}
```

**安全原则**：
- 生产环境异常堆栈不返回给前端（仅记录日志 + traceId 供排查）；
- 数据库约束违反（如唯一键冲突）转换为业务错误（避免泄露表结构）：
  ```java
  catch (DuplicateKeyException e) {
      String msg = e.getMessage();
      if (msg.contains("uk_user_phone")) {
          throw new BusinessException("PHONE_ALREADY_EXISTS", "该手机号已注册");
      }
      throw new BusinessException("DUPLICATE_RESOURCE", "资源已存在");
  }
  ```
- 敏感字段脱敏（密码永不记录明文，身份证号/手机号中间脱敏）；
- 越权尝试 100% 记录日志（含 userId、requestURI、IP）。

## 11. 架构扩展性预留

虽然当前为单实例架构（N9），但以下设计为未来多实例扩展预留了接口：

| 扩展点 | 当前实现 | 多实例扩展方案 |
|-------|---------|---------------|
| WebSocket 推送 | 本地 `SimpMessagingTemplate` | 通过 Redis Pub/Sub 广播，每个实例订阅后推送本地连接用户 |
| 定时任务调度 | `@Scheduled` + Redisson 分布式锁 | 引入 XXL-Job 统一调度中心（任务数 > 10 时） |
| 会话状态 | Redis 存储（已支持跨实例共享） | 无需改动 |
| 缓存一致性 | 本地缓存 + Redis | 无需改动（已是分布式缓存） |
| 用户权限信息 | Redis 缓存 | 无需改动（已是分布式缓存） |

**负载均衡接入点**（多实例时）：
```
                          Nginx (负载均衡)
                               │
                 ┌─────────────┼─────────────┐
                 ▼             ▼             ▼
            实例 1         实例 2         实例 3
                 │             │             │
                 └─────────────┴─────────────┘
                               │
                    ┌──────────┼──────────┐
                    ▼          ▼          ▼
                 MySQL       Redis    (共享)
```

**会话亲和性**（WebSocket）：Nginx 配置 `ip_hash` 或 `sticky session`，
确保同一用户的 HTTP 请求与 WebSocket 连接路由到同一实例（降级轮询时无此要求）。
