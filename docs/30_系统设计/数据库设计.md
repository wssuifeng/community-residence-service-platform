## 1. 概念模型（实体关系）

### 1.1 核心实体（53 张业务表）

> **表数口径（2026-09-22 主会话裁决，定稿）**：本节与全文口径为 **53 张业务表**
> （逐迁移枚举 `CREATE TABLE` 亦为 53）——
> **53 张业务表**（库内另有 Flyway 历史表 `flyway_schema_history`，故
> `information_schema` 计数为 **54**）；50 阶段实测记的 **54** 即该
> `information_schema` 计数（含 Flyway 历史表），**与本节 53 张业务表不冲突**。
> **本轮 V24 / V25 / V26 均不新建表 ⇒ 本清单不变**。

按 C1~C12 业务模块分组，每个实体对应一张数据库表：

**C1 社区基础信息管理（7 张表）**
- 社区 `community` — 多社区架构的顶层实体；V18 增 `auto_approve_residence`
  （入住申请自动通过开关）与 `default_lease_months`（自动通过默认租期月数，R62 补）
- 楼栋 `building` → 社区（N:1）
- 单元 `unit` → 楼栋（N:1）
- 房屋 `house` → 单元（N:1），含状态枚举
- 房屋状态历史 `house_status_history` → 房屋（N:1），状态变更留痕
- 公共资源 `public_resource` → 社区（N:1）
- 可预约时段 `resource_timeslot` → 公共资源（N:1）

**C2 居民与居住关系管理（4 张表）**
- 居民 `resident` — 跨社区账号体系
- 入住申请 `residence_application` → 居民 + 社区 + 房屋（N:1）；V20 status 取值加
  `WITHDRAWN`（申请人撤回，R66）
- 居住关系 `residence_relation` → 居民 + 社区 + 房屋（M:N 关联表）
- 全局配置 `sys_config` — 注册开关等全局级配置

**C3 租住管理（8 张表）**
- 租住记录 `lease_record` → 居民（租客）+ 社区 + 房屋（N:1）；V18 增列 `agreement_status`
  （协议签约状态进度视图列，R64）；V20 增列 `tenant_confirm_at` / `tenant_confirm_by`
  （承租确认留痕，R67）与 `conversation_id`（租约群聊，R68），status 取值加 `TO_SIGN`
- 到期提醒去重 `lease_reminder` → 租住记录（N:1），唯一约束防重复提醒
- 押金退还记录 `lease_deposit_refund` → 租住记录（N:1，弱关联退租申请），
  **V22 设计（R72）**：`out_request_no` 幂等键唯一防重复退款，**非资金账户**（无余额/计息）
- 租约续约支付单 `lease_payment` → 租住记录 + 居民（N:1），在线支付流水（V15 R61；
  V20 增 `payment_type` 区分首期 / 续期，R71）
- 租约属性变更历史 `lease_change_log` → 租住记录（N:1），字段级前后值 + 操作人快照（V18，R64/R65 管理端租住属性管理）
- 协议模板 `agreement_template` → 社区（N:1，可空=全局通用模板），正文与附件（V18，R64）
- 租约协议 `lease_agreement` → 租住记录 + 社区（N:1），正文快照 + 双方确认留痕（V18，R64）
- 租约退租申请 `lease_move_out_application` → 租住记录 + 居民 + 社区 + 房屋（N:1），
  居民自助退租申请与审核留痕（**V20 新表**，R70）

**C4 服务申请与工单管理（8 张表）**
- 服务类别 `service_category` → 社区（N:1）
- 工单 `work_order` → 居民 + 社区 + 服务类别（N:1）
- 工单附件 `work_order_attachment` → 工单（N:1）
- 工单处理记录 `work_order_process` → 工单（N:1），时间线展示
- 工单派单关系 `work_order_assignment` → 工单 + 服务人员（N:1）
- 人员常驻社区 `staff_community` → 服务人员 + 社区（M:N 关联表，V19，R65）
- 人员擅长类别 `staff_service_category` → 服务人员 + 服务类别（M:N 关联表，V19，R65）
- 人员排班 `staff_schedule` → 服务人员 + 社区（N:1），一人一社区一天一条（V19，R65）

**C5 公告广播管理（3 张表）**
- 公告 `notice` — 可跨社区广播
- 公告目标范围 `notice_target` → 公告（N:1），定向发布
- 公告查看记录 `notice_view_record` → 公告 + 用户（M:N 关联表）

**C6 居民反馈管理（3 张表）**
- 反馈单 `feedback` → 居民 + 社区（N:1）
- 反馈附件 `feedback_attachment` → 反馈单（N:1）
- 反馈会话消息 `feedback_message` → 反馈单（N:1），自引用 parent_id

**C7 公共资源预约管理（2 张表）**
- 资源预约 `resource_reservation` → 用户 + 公共资源 + 社区（N:1）
- 违约处置记录 `violation_record` → 用户（N:1）

**C8 服务评价管理（2 张表）**
- 工单评价 `work_order_evaluation` → 工单 + 居民 + 社区（1:1）
- 不满意跟进 `unsatisfied_followup` → 评价（1:1）

**C9 社区运营统计（1 张表，可选）**
- 统计快照 `statistics_snapshot` → 社区（N:1），预聚合优化

**C10 用户与权限管理（5 张表）**
- 系统用户 `sys_user` — 管理员/服务人员账号体系
- 管理员-社区绑定 `sys_admin_community` → 管理员 + 社区（M:N 关联表）
- JWT令牌黑名单 `auth_token_blacklist` — DB 双写降级方案
- 操作日志 `sys_operation_log` — 关键变更留痕
- 拉黑审计日志 `sys_blacklist_log` — 频控与拉黑记录

## 2. 逻辑模型（表结构设计）

### 2.1 命名规范

- **表名**：小写 + 下划线，单数形式（`resident` 而非 `residents`）
- **字段名**：小写 + 下划线，避免保留字（如 `order` → `work_order`）
- **主键**：统一命名为 `id`（BIGINT UNSIGNED AUTO_INCREMENT）
- **外键**：`关联表名_id`（如 `community_id`、`resident_id`）
- **时间戳**：`created_at` / `updated_at` / `deleted_at`
- **软删除**：`is_deleted` (TINYINT) + `deleted_at` (DATETIME)

### 2.2 字段类型约定

| 用途 | 类型 | 说明 |
|------|------|------|
| 主键 | BIGINT UNSIGNED AUTO_INCREMENT | 统一主键类型 |
| 外键 | BIGINT UNSIGNED | 统一外键类型，必加索引 |
| 状态枚举 | VARCHAR(20) | 灵活性优先，代码层控制 |
| 短文本 | VARCHAR(长度) | 标题/名称/编号 |
| 长文本 | TEXT | 内容/描述/备注 |
| 金额 | DECIMAL(10, 2) | 租金/价格 |
| 布尔 | TINYINT(1) | 0/1 |
| 日期 | DATE | 业务日期（租期起止） |
| 时间 | TIME | 时段（08:00:00） |
| 日期时间 | DATETIME | 时间戳，默认 CURRENT_TIMESTAMP |
| JSON | JSON | 扩展字段/操作内容 |

## 3. 表结构明细（按模块）

### 3.1 C1 社区基础信息管理

#### 3.1.1 community（社区）

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | BIGINT UNSIGNED | PRIMARY KEY AUTO_INCREMENT | 社区ID |
| name | VARCHAR(100) | NOT NULL | 社区名称 |
| address | VARCHAR(255) | NOT NULL | 社区地址 |
| responsible_admin_id | BIGINT UNSIGNED | NULL，FK → sys_user(id) | 社区责任人，应用层验证role=ADMIN；姓名电话由账号派生（V31） |

| updated_at | DATETIME | DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP | 更新时间 |

**索引**：

- INDEX idx_status (status)

**约束**：
- status 枚举：'ACTIVE'（运行中）、'INACTIVE'（已停用）

  `PENDING → REJECTED`（审核驳回）、`TO_SIGN → REJECTED`（申请撤回 / 驳回）
- **审核通过 ≠ 租约生效**：通过后租约 `status='TO_SIGN'`，`house.status` **保持 VACANT**
  （V20 起取消「通过即置 OCCUPIED」口径）
- **R67 修正（2026-10-11）**：旧 tenant_confirm_at/by 只读保留历史，不再作为流程/协议前置且不新写入；无需删除列或改旧 Flyway。有效确认在 lease_agreement：发出写 admin_confirm_name/time、PARTIAL；居民针对快照同意写 tenant_confirm_name/time、SIGNED。历史已生效不回退，无管理方留痕的旧未完成协议撤回重发。


- "即将到期/已到期"通过 end_date 计算，不是状态字段（架构设计 §6.2）
- `agreement_status` 仅表达协议确认进度，**不再承担"是否生效"语义**（生效由 `status` 表达）
- **押金状态（V22 新增，R72）**：`deposit_status` 取值与流转——
  `UNPAID`（默认；未缴）→（首期费用支付成功，押金部分入账，R71）→ `PAID`（已缴）→
  （管理端发起原路退款）→ `REFUNDING`（退还中）→（渠道退款成功）→ `REFUNDED`（已退还）；
  结算抵扣时置 `OFFSET`（**处置金额与说明必须在该租约的 `lease_deposit_refund` 留痕**）；
  退款失败时由 `REFUNDING` 回落到 `PAID`（**可重试，失败原因写 `lease_deposit_refund.fail_reason`**）
- **押金状态存量回填（v1.5 补记，2026-09-22，V25 已执行）**：V22 仅给出列默认值
  `'UNPAID'`，**未回填存量**——存量中「首期费用已支付成功」的租约其押金实缴其实已完成
  （成功首期单金额 = 首月租金 + 押金），状态却仍是 `UNPAID`，会使 R72 押金退还第一步即被门禁挡住。
  **V25 幂等回填口径**：`deposit_status='UNPAID'` 且该租约存在
  `payment_type='FIRST'` 且 `status='SUCCESS'` 且 **`amount > monthly_rent`**（押金部分 > 0）
  的支付单 ⇒ 置 `PAID`；**`PAID` / `REFUNDING` / `REFUNDED` / `OFFSET` 一律不动**
  （幂等，已进入退还流程的租约不被回退）。**实测：开发库租约 4/6 回填为 `PAID`**；
  **只改数据、不改结构、不建表**（见 §9 第 19 条）
- **押金硬约束（库级 + 应用层，源自定义 v1.6 §3 边界声明，R72）**：
  ①**退款金额不得超过该租约实缴押金**（实缴 = 该租约首期支付单中的押金部分之和，
  由 R73 的金额构成拆分字段支撑；应用层校验，超限拒绝）；
  ②**必须原渠道原路退回**（`lease_deposit_refund.channel` 必须与实缴支付单的渠道一致，
  跨渠道退款拒绝）；③**库内不得出现任何押金资金账户 / 余额 / 计息字段**——
  平台不托管押金资金（`lease_record.deposit` 为登记金额、`lease_deposit_refund` 为
  退款指令与结果留痕，两者皆非资金账户），**架构核查项，任何后续迁移不得引入**

#### 3.3.8 lease_deposit_refund（押金退还记录 · **V22 新表**）

> **设计口径（R72，定义 v1.6）**：**追加型留痕表**——每次发起押金退还写一条新记录，
> 不覆盖历史（重试失败后再发起即再写一条，`out_request_no` 幂等键防止同一请求重复建单）。
> 本表只承载**退款指令与渠道结果**，**不是资金账户**（无余额、无计息字段）。

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | BIGINT UNSIGNED | PRIMARY KEY AUTO_INCREMENT | 记录ID |
| lease_id | BIGINT UNSIGNED | NOT NULL | 租住记录ID（`lease_record.id`） |
| move_out_application_id | BIGINT UNSIGNED | NULL | 关联退租申请（`lease_move_out_application.id`，非退租场景可空；**弱关联不设外键**，口径同 `viewing_appointment.lease_id`） |
| amount | DECIMAL(10,2) | NOT NULL | 本次退还金额（**≤ 该租约实缴押金**，应用层校验） |
| channel | VARCHAR(20) | NOT NULL | 退款渠道：`ALIPAY` / `WECHAT`（**必须与原支付渠道一致**，跨渠道拒绝） |
| out_request_no | VARCHAR(64) | NOT NULL | **商户退款请求号（幂等键）**——同一 `out_request_no` 重复提交**幂等返回既有结果**，不重复退款 |
| channel_refund_no | VARCHAR(64) | NULL | 渠道退款单号（渠道返回后回写；`SUCCESS` 时非空） |
| status | VARCHAR(20) | NOT NULL DEFAULT 'PENDING' | 退款状态：`PENDING`处理中 / `SUCCESS`已退还 / `FAILED`失败 |
| fail_reason | VARCHAR(500) | NULL | 失败原因（渠道返回或异常摘要；`FAILED` 时必填） |
| operator_id | BIGINT UNSIGNED | NOT NULL | 发起人（`sys_user.id`，社区管理员 / 超管） |
| created_at | DATETIME | NOT NULL DEFAULT CURRENT_TIMESTAMP | 发起时间 |
| refunded_at | DATETIME | NULL | 退款完成时间（`SUCCESS` 时写） |

**索引**：
- PRIMARY KEY (id)
- UNIQUE KEY uk_deposit_out_request_no (out_request_no)（**幂等键**）
- INDEX idx_deposit_lease (lease_id, created_at)（租约维度倒序查询退还记录）

**外键**：
- FOREIGN KEY (lease_id) REFERENCES lease_record(id)
- `move_out_application_id` **不设外键**（弱关联：退租申请可能被清理或历史缺失，
  与 `viewing_appointment.lease_id` / `lease_record.conversation_id` 同口径）

**约束**：
- **幂等**：`out_request_no` 唯一；重复提交同号请求**返回既有记录**（不新建、不重复退款）
- **金额上限**：`amount ≤ 该租约实缴押金`（实缴押金 = 该租约**成功**的
  `lease_payment`（`payment_type='FIRST'`）中的押金部分；应用层校验，超限拒绝）
- **原渠道**：`channel` 必须与该租约实缴支付单的 `channel` 一致

**与其它表的关系**：
- `lease_record` → `lease_deposit_refund`（1:N，同一租约可多次发起/重试，追加留痕）
- `lease_move_out_application` → `lease_deposit_refund`（1:N，弱关联，退租结算是主要发起场景）
- **不得新增押金资金账户 / 余额 / 计息类字段或表**（定义 v1.6 §3 边界；架构核查项）

**级联删除（DEF-066 纪律）**：本表**不带 `community_id`**，但经 `lease_id` 关联租约——
社区级联删除时**必须在物理删除 `lease_record` 之前**清理本表（与 `lease_agreement` /
`lease_change_log` 同段），否则 FK 违约。详见 §9「级联删除清单纪律」条。

> **V21 增量（P0 缺陷 DEF-067，2026-09-21 批次 g · `V21__notification_owner_identity.sql`，已执行）**：
> **身份口径**——`(owner_type, user_id)` 二元组才是**完整收件人**：`USER` 指
> `sys_user.id`（员工 / 管理员主体），`RESIDENT` 指 `resident.id`（居民主体）；
> 列表 / 未读 / 增量拉取 / 已读 / WebSocket 推送**一律按该二元组收口**。
> **根因**——系统内 `resident` 与 `sys_user` 是**两套互不相同的身份空间**，主键各自自增、
> **id 可撞号**（`resident 1 = resident1` 与 `sys_user 1 = superadmin`）；而 `notification.user_id`
> 为**单列无外键**，写入侧居民调用传 `resident.id`、管理侧调用传 `sys_user.id`，读取侧仅按
> `user_id` 过滤 ⇒ **撞号即双向串收**（超管/管理员可读到居民口径通知、居民亦可读到员工通知，
> 属**越权可读**；实测 `notification id=17 (user_id=1)` 为居民口径「首期费用支付成功」，
> 却出现在超管通知中心）。
> **服务层收口**——只提供 `createForUser` / `createForResident` 两个**显式入口**
> （`NotificationService`，无「默认 USER」的隐式重载，避免新调用点漏标），常量类
> `common/constant/NotificationOwnerType`；`owner_type` 由登录主体角色推导（`ofRole`：
> `RESIDENT` → `RESIDENT`，其余角色 → `USER`），**应用层不得依赖列默认值隐式落库**。
> **WebSocket 主体名分离**——点对点推送主体名带身份空间前缀（`common/context/IdentityPrincipal`：
> 居民 `R:{residentId}` / 员工 `U:{sysUserId}`），居民与员工**永不落到同一 destination**；
> 在线判定同步按 `(ownerType, userId)`。
> **表数不变（仍 52）**——本迁移仅加列 + 加索引 + 存量回填，明细见 §9 变更记录第 15 条。

- 未读口径：`unread = COUNT(conversation_message.id > last_read_message_id)`；
  标记已读仅前移（防回退把旧消息变未读）
- **身份口径（V24 已执行）**：`(owner_type, user_id)` 二元组才是**完整参与者身份**
  ——应用层判定 / 展示 / 未读 / WS 订阅全部按二元组收口；**仅按 `user_id` 判定即越权**
  （DEF-098：`superadmin`(sys_user.id=1) 与 `resident1`(resident.id=1) 撞号可读他人会话）

### 4.2 外键约束策略

**约束行为**：
- `ON DELETE RESTRICT`（默认）：防止误删被引用数据
- `ON UPDATE CASCADE`：主键更新时级联更新外键

**例外情况**：
- 日志表不设外键约束（性能优先，避免锁等待）
- 跨模块引用使用应用层控制

### 4.3 字符集与排序规则

```sql
CREATE DATABASE community_residence_service
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;
```

- **utf8mb4**：支持完整 Unicode（含 emoji）
- **utf8mb4_unicode_ci**：不区分大小写，多语言排序准确

### 4.4 分区表设计（可选优化）

**操作日志按月分区**（保留 ≥4年，N6）：

```sql
CREATE TABLE sys_operation_log (
  ...
) PARTITION BY RANGE (YEAR(created_at) * 100 + MONTH(created_at)) (
  PARTITION p202601 VALUES LESS THAN (202602),
  PARTITION p202602 VALUES LESS THAN (202603),
  ...
  PARTITION p203012 VALUES LESS THAN (203101),
  PARTITION pmax VALUES LESS THAN MAXVALUE
);
```

**任务日志按周分区**（保留 1年）：

```sql
CREATE TABLE sys_task_log (
  ...
) PARTITION BY RANGE (TO_DAYS(created_at)) (
  PARTITION p20260101 VALUES LESS THAN (TO_DAYS('2026-01-08')),
  ...
);
```

**说明**：
- 分区表提升大数据量下的查询和删除性能
- 自动删除旧分区（`ALTER TABLE ... DROP PARTITION`）
