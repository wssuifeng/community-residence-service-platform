# 架构设计改进建议

> 针对架构设计的深度优化方向，供后续阶段参考。

## 1. 权限模型优化方向

### 1.1 当前方案
社区管理员每次请求从 JWT 提取社区 ID 列表，MyBatis-Plus 拦截器注入 `community_id IN (...)`。

### 1.2 潜在问题
- 管理员绑定 10+ 社区时，SQL `IN` 子句较长，索引效率下降
- JWT Claims 包含社区 ID 列表，令牌体积膨胀（每个社区 ID ~36 字节 UUID）
- 社区绑定变更后的令牌吊销机制未详细说明

### 1.3 优化建议（多实例扩展时考虑）

**方案 A：权限信息 Redis 缓存**
```
登录时：
1. JWT Claims 只存 userId + role（不存社区 ID 列表）
2. 社区绑定关系写入 Redis（key: user:${userId}:communities, value: Set<communityId>, TTL: 2h）

请求时：
1. 从 JWT 提取 userId
2. 从 Redis 读取绑定社区列表（未命中则查库回种）
3. MyBatis-Plus 拦截器注入过滤条件

绑定变更时：
1. 删除 Redis 缓存 user:${userId}:communities
2. 将该用户所有有效令牌的 jti 加入黑名单（查 auth_token 表获取 jti 列表）
```

**方案 B：按社区分散查询（适用于绑定社区很多的极端情况）**
```
不在 SQL 中用 IN，改为：
1. 应用层循环查询每个社区的数据
2. 合并结果集并分页
3. 适用场景：单次查询结果集小，但绑定社区多（如跨区域巡检员绑定 50+ 社区）
```

**推荐**：当前 N2（50 并发）目标下，现有方案已足够；多实例扩展时优先采用方案 A。

## 2. 实时通信扩展性

### 2.1 当前方案
单实例 Spring WebSocket + STOMP，会话注册表在内存。

### 2.2 多实例扩展挑战
- WebSocket 长连接固定在某个实例，用户 A 连接实例 1、用户 B 连接实例 2
- 工单派给用户 B，实例 1 处理请求，如何推送到实例 2 的连接？

### 2.3 扩展方案（留待未来）

**Redis Pub/Sub 广播**
```
单实例时（当前）：
NotificationPublisher → 直接调用 SimpMessagingTemplate.convertAndSendToUser()

多实例时：
NotificationPublisher → 发布到 Redis Channel（topic: notification:broadcast）
每个实例订阅 → 收到消息后调用本地 SimpMessagingTemplate
                → 如果用户连接在本实例，推送成功；否则静默跳过
```

**架构预留口**：
- 通知推送逻辑抽象为接口 `NotificationPusher`
- 当前实现 `LocalNotificationPusher`（直接调用 SimpMessagingTemplate）
- 未来扩展 `RedisNotificationPusher`（发布到 Redis Pub/Sub）

## 3. 缓存预热策略

### 3.1 冷启动问题
系统重启后 Redis 缓存全空，首批请求全部穿透到数据库（缓存击穿）。

### 3.2 预热策略

**启动时预热**（适用于热点数据量小的场景）：
```java
@PostConstruct
public void warmupCache() {
    // 预热所有社区基础信息（假设社区数量 < 100）
    List<Community> communities = communityMapper.selectList(null);
    communities.forEach(c -> redisTemplate.opsForValue()
        .set("community:" + c.getId(), c, 1, TimeUnit.HOURS));
    
    // 预热有效公告（按社区）
    // ...
}
```

**渐进式预热**（适用于数据量大的场景）：
```
1. 启动时不全量加载
2. 第一次缓存未命中时，加布隆过滤器锁（SETNX）
3. 只有获得锁的请求回源，其他请求短暂等待（自旋 100ms）后重试缓存
```

**推荐**：当前场景社区数量有限，采用启动时预热；未来数据量增大时改为渐进式。

## 4. 定时任务分布式调度

### 4.1 当前方案
单实例 `@Scheduled` + Redis 分布式锁（SETNX）。

### 4.2 多实例扩展挑战
- 多个实例同时执行定时任务，依赖 Redis 锁互斥
- 锁持有者宕机，锁 TTL 到期前任务无法执行（最多延迟 10 分钟）

### 4.3 生产级方案（留待 70 阶段）

**方案 A：使用 Redisson 分布式锁**
```java
RLock lock = redisson.getLock("task:lease:scan");
try {
    if (lock.tryLock(0, 10, TimeUnit.MINUTES)) {
        // 执行任务
    }
} finally {
    lock.unlock();
}
```
- 看门狗机制：锁自动续期，避免任务执行时间超过 TTL
- 锁释放：任务完成或异常时自动释放

**方案 B：引入 XXL-Job / ElasticJob**
- 统一调度中心，可视化管理
- 适用场景：任务种类多、需要动态调整 cron、需要执行日志查询
- 当前场景：任务仅 4 个，暂不需要

**推荐**：多实例部署时升级为 Redisson 分布式锁；任务数量增加到 10+ 时考虑 XXL-Job。

## 5. 数据库连接池调优

### 5.1 当前配置
Druid 默认连接池大小 20（隐式配置）。

### 5.2 调优公式

**推荐连接池大小**：
```
连接数 = (核心线程数 × 平均 SQL 执行时间) / 平均请求响应时间

示例（N2 目标：50 并发）：
- Tomcat 默认线程池 200
- 平均 SQL 执行时间 50ms
- 目标响应时间 500ms
- 连接数 = (50 × 50ms) / 500ms = 5

实际配置：5 × 2（安全系数）= 10~20 已足够
```

### 5.3 监控指标
- 连接池活跃连接数峰值（Druid 监控页）
- 连接等待超时次数（应为 0）
- 数据库 `show processlist` 长时间运行的查询

**推荐**：初期保持 20，压测后根据监控数据调整。

## 6. 布隆过滤器实现细节

### 6.1 使用场景
缓存穿透防护：拦截不存在的社区 ID、房源 ID 查询。

### 6.2 实现方案

**Redisson 布隆过滤器**（推荐）：
```java
RBloomFilter<String> bloomFilter = redisson.getBloomFilter("community:exists");
bloomFilter.tryInit(100000L, 0.01); // 预期元素 10 万，误判率 1%

// 启动时加载所有社区 ID
List<String> communityIds = communityMapper.selectAllIds();
communityIds.forEach(bloomFilter::add);

// 查询前校验
if (!bloomFilter.contains(communityId)) {
    throw new ResourceNotFoundException("社区不存在");
}
```

**Guava 布隆过滤器**（单实例可用）：
```java
BloomFilter<String> bloomFilter = BloomFilter.create(
    Funnels.stringFunnel(Charset.defaultCharset()),
    100000,
    0.01
);
```

**维护策略**：
- 新增社区时同步添加到布隆过滤器
- 删除社区时布隆过滤器不支持删除（只能重建，或允许误判）
- 重建频率：每天凌晨 2:00（定时任务）

## 7. API 幂等性设计

### 7.1 需要幂等的场景
- 工单提交（用户重复点击提交按钮）
- 支付类操作（未来扩展预约押金场景）

### 7.2 幂等实现方案

**方案 A：前端防重令牌**
```
1. 前端打开提交表单时，调用 /api/idempotent/token 获取一次性令牌
2. 提交时携带令牌（Header: X-Idempotent-Token）
3. 后端校验令牌（Redis SETNX），已存在则拒绝
4. 处理完成后删除令牌（或 TTL 5 分钟自动过期）
```

**方案 B：业务唯一键**
```
工单表增加唯一约束（user_id + submit_time + title_hash）
重复提交触发唯一键冲突，捕获后返回"请勿重复提交"
```

**推荐**：方案 A 用户体验更好（返回"操作已提交，请勿重复点击"），方案 B 作为数据库层兜底。

## 8. 日志分级与脱敏

### 8.1 日志分级策略
```
ERROR：系统错误（数据库连接失败、Redis 不可用、未捕获异常）
WARN： 业务异常（登录失败、权限不足、状态机非法流转）
INFO： 关键业务节点（用户登录成功、工单状态流转、通知推送）
DEBUG：开发调试信息（SQL 执行、缓存命中率、方法入参出参）
```

### 8.2 敏感信息脱敏
```java
// 密码：永不记录明文
log.info("User login: username={}, password=***", username);

// 身份证号：中间 10 位脱敏
String maskedIdCard = idCard.replaceAll("(\\d{4})\\d{10}(\\d{4})", "$1**********$2");

// 手机号：中间 4 位脱敏
String maskedPhone = phone.replaceAll("(\\d{3})\\d{4}(\\d{4})", "$1****$2");
```

### 8.3 日志归档策略
```xml
<!-- logback-spring.xml -->
<rollingPolicy class="ch.qos.logback.core.rolling.TimeBasedRollingPolicy">
    <fileNamePattern>logs/app.%d{yyyy-MM-dd}.log</fileNamePattern>
    <maxHistory>30</maxHistory> <!-- 保留 30 天 -->
    <totalSizeCap>10GB</totalSizeCap> <!-- 总大小上限 -->
</rollingPolicy>
```

## 9. 总结

以上改进建议分为三个优先级：

**P0（当前阶段必须考虑）**：
- 已在架构设计中补充：缓存设计、异常处理、性能指标、降级策略

**P1（多实例扩展时必须实施）**：
- 权限信息 Redis 缓存
- 实时通信 Redis Pub/Sub 广播
- Redisson 分布式锁升级

**P2（生产优化方向）**：
- 缓存预热策略
- 数据库连接池调优
- 布隆过滤器防穿透
- API 幂等性设计
- 日志分级与脱敏

**建议**：当前架构设计已满足毕设需求（N2/50 并发），P1/P2 优化留待实际压测发现瓶颈后按需实施。
