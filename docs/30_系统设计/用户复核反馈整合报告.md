## 2. 重大方案调整详解

### 2.1 Redis 雪崩降级方案（反馈 4 + 5）

**原方案问题**：Redis 不可用时黑名单校验失败拒绝 → 缓存崩溃 = 全系统不可用（过于严格）

**新方案核心理念**：保大头（正常用户），牺牲长尾（异常流量）

**六大策略调整**：

#### 策略 1：黑名单 DB 双写 ✅ 已实施
- **变更**：黑名单数据 DB 双写（权威来源 + Redis 缓存）
- **降级逻辑**：Redis 不可用时降级查 DB，登出仍可成功，黑名单仍可生效
- **实现位置**：§3.1 补充完整代码示例（登出双写 + 黑名单校验含降级）

#### 策略 2：长连接降级鉴权 ✅ 已实施
- **变更**：连接建立时一次 DB 鉴权，会话期（30min）免检，后续消息直接走长连接
- **性能分析**：DB 鉴权 QPS = 50 并发 / 1800 秒 ≈ 0.028（完全可控）
- **实现位置**：§4.1 新增章节"长连接鉴权与降级策略"

#### 策略 3：短时重连豁免 ✅ 已实施
- **变更**：5 分钟内重连免鉴权（防止网络抖动冲击 DB）
- **降级容错**：Redis 不可用时豁免失效，每次重连走 DB 鉴权（权衡可用性 > 性能）
- **实现位置**：§4.1.2 补充完整代码示例

#### 策略 4：权限变更主动踢人 ✅ 已实施
- **变更**：维护本地映射 userId -> sessionId，权限变更时主动踢人强制重连
- **扩展性**：单实例本地映射，多实例通过 Redis Pub/Sub 广播
- **实现位置**：§4.1.3 补充完整代码示例

#### 策略 5：鉴权失败分级拉黑 ✅ 已实施
- **变更**：认证失败（密码错误）5 次/5 分钟拉黑 5 分钟；鉴权失败（令牌伪造）一次拉黑 1 小时
- **双层拉黑**：本地缓存（Caffeine）+ Redis，Redis 不可用时仅本地拉黑生效
- **实现位置**：§4.1.4 补充完整代码示例

#### 策略 6：会话生命周期 ✅ 已实施
- **变更**：10-30 分钟到期强制重连（配置项）
- **设计理念**：将缓存同步压力从秒级降为分钟级
- **实现位置**：§4.1.2

### 2.2 缓存预热策略调整（反馈 2）

**原方案**：无区别加载社区、布隆、公告所有数据

**新方案**：
- **优先级分级**：高优先级（社区、布隆）→ 中优先级（公告首页）→ 低优先级（具体数据留测试阶段确认）
- **配置开关**：`cache.warmup.notices.enabled` 控制是否预热公告
- **测试阶段验证**：压测不同预热策略对启动时间与缓存命中率的影响

**实施位置**：§3.3.3 代码示例增加优先级说明与配置开关

## 3. 方案审核结果

已产出 **《Redis 雪崩降级方案审核报告》**，审核结论：

- **总分**：47/50（优秀）
- **发现的"坑"**：5 个（误伤正常用户、网络抖动 DB 压力、集群会话映射、会话劫持、DB 表膨胀）
- **修正建议**：全部已补充到架构设计文档

**关键优化点**：
1. ✅ 拉黑分级（认证失败 5 次 vs 鉴权失败 1 次）
2. ✅ 短时重连豁免（5 分钟内免鉴权）
3. ✅ 定时清理过期黑名单（每日凌晨 3:00）
4. ✅ 本地 + Redis 双层拉黑（防止 Redis 不可用时拉黑失效）
5. ✅ DB 黑名单表设计（jti + expire_time + reason）
