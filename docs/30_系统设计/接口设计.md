## 1. 接口设计原则

### 1.1 RESTful 规范

- **资源命名**：复数名词，小写 + 连字符（`/work-orders` 而非 `/workOrder`）
- **层级关系**：体现资源层级（`/communities/{id}/buildings`）
- **HTTP 方法映射**：
  - GET：查询资源
  - POST：创建资源（非幂等）
  - PUT：全量更新资源（幂等）
  - PATCH：部分更新资源 / 状态操作（幂等）
  - DELETE：删除资源（幂等）
- **状态操作**：使用 PATCH + 动作（`/work-orders/{id}/assign`）
- **幂等性保证**：PUT/DELETE 幂等，POST 非幂等

### 1.2 接口版本化

- **URL 版本**：`/api/v1/` 前缀（毕设无版本变更需求，调试方便，答辩演示清晰）
- **版本升级策略**：新版本通过 `/api/v2/` 提供，旧版本保持兼容

### 1.3 命名规范

| 资源类型 | URL 模式 | 示例 |
|---------|---------|------|
| 列表查询 | GET /resources | GET /api/v1/work-orders |
| 详情查询 | GET /resources/{id} | GET /api/v1/work-orders/123 |
| 创建资源 | POST /resources | POST /api/v1/work-orders |
| 更新资源 | PUT /resources/{id} | PUT /api/v1/work-orders/123 |
| 部分更新 | PATCH /resources/{id} | PATCH /api/v1/work-orders/123 |
| 删除资源 | DELETE /resources/{id} | DELETE /api/v1/work-orders/123 |
| 状态操作 | PATCH /resources/{id}/{action} | PATCH /api/v1/work-orders/123/assign |
| 子资源列表 | GET /resources/{id}/sub-resources | GET /api/v1/communities/1/buildings |

## 2. 统一响应格式

### 2.1 成功响应

```json
{
  "code": 200,
  "message": "success",
  "data": {},
  "timestamp": "2026-09-06T15:30:00"
}
```

**字段说明**：
- `code`：业务状态码（200 成功，其他为业务错误码）
- `message`：响应消息（成功时为 "success"，失败时为具体错误信息）
- `data`：响应数据（可为 null、对象、数组）
- `timestamp`：响应时间戳（ISO 8601 格式）

### 2.2 分页响应

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "records": [],
    "total": 100,
    "page": 1,
    "size": 20,
    "pages": 5
  },
  "timestamp": "2026-09-06T15:30:00"
}
```

**字段说明**：
- `records`：当前页数据列表
- `total`：总记录数
- `page`：当前页码（从 1 开始）
- `size`：每页大小
- `pages`：总页数

### 2.3 错误响应

```json
{
  "code": 5301,
  "message": "工单不存在",
  "data": null,
  "timestamp": "2026-09-06T15:30:00"
}
```

## 3. 统一异常处理

### 3.1 异常类型映射

| 异常类型 | HTTP 状态码 | 业务状态码 | 说明 | 示例 |
|---------|-----------|-----------|------|------|
| 参数校验异常 | 400 | 400 | 请求参数不合法 | 字段必填、长度超限、格式错误 |
| 未认证异常 | 401 | 401 | 未登录或令牌失效 | JWT 过期、未携带 Token |
| 无权限异常 | 403 | 403 | 无权限访问 | 角色不匹配、数据级权限拒绝 |
| 资源不存在异常 | 404 | 404 | 资源不存在 | 工单/社区/居民不存在 |
| 业务异常 | 200 | 5xxx | 业务逻辑错误 | 工单状态流转非法、预约冲突 |
| 系统异常 | 500 | 500 | 服务器内部错误 | 数据库连接失败、未知异常 |

### 3.2 业务错误码规划

| 错误码范围 | 业务模块 | 示例 |
|-----------|---------|------|
| 5001~5099 | 通用业务错误 | 5001-操作失败, 5002-数据已存在, 5003-数据不存在 |
| 5101~5199 | 社区管理错误 | 5101-社区已停用, 5102-楼栋被引用无法删除 |
| 5201~5299 | 居民管理错误 | 5201-账号已冻结, 5202-入住申请已审核 |
| 5301~5399 | 工单管理错误 | 5301-工单不存在, 5302-工单状态流转非法 |
| 5401~5499 | 预约管理错误 | 5401-预约时段冲突, 5402-预约已取消 |
| 5501~5599 | 评价管理错误 | 5501-工单未完成不可评价, 5502-已评价不可重复 |
| 5901~5999 | 支付管理错误（R61） | 5901-该支付渠道未配置, 5902-发起支付失败, 5903-渠道支付金额与应付金额不一致 |

## 4. 分页/排序/过滤规范

### 4.1 分页参数

**请求参数**（Query String）：
- `page`：页码（从 1 开始，默认 1）
- `size`：每页大小（默认 20，最大 100）

**示例**：
```
GET /api/v1/work-orders?page=1&size=20
```

**参数校验**：
- `page` ≥ 1
- `1 ≤ size ≤ 100`

### 4.2 排序参数

**请求参数**（Query String）：
- `sortBy`：排序字段（可选，默认 `createdAt`）
- `sortOrder`：排序方向（ASC/DESC，默认 DESC）

**示例**：
```
GET /api/v1/work-orders?page=1&size=20&sortBy=createdAt&sortOrder=DESC
```

**可排序字段**：
- `createdAt`：创建时间
- `updatedAt`：更新时间
- `status`：状态
- 其他业务字段（根据具体接口）

### 4.3 过滤参数

**通用过滤参数**（Query String）：
- `status`：状态过滤（枚举值）
- `startTime` / `endTime`：时间范围过滤（ISO 8601 格式）
- `keyword`：关键词搜索（模糊匹配标题/描述）
- `communityId`：社区过滤（社区管理员自动注入绑定社区列表）

**示例**：
```
GET /api/v1/work-orders?status=IN_PROGRESS&startTime=2026-09-01T00:00:00&endTime=2026-09-30T23:59:59&keyword=维修
```

## 7. 权限标注规则

### 7.1 五角色定义

| 角色代码 | 角色名称 | 权限范围 |
|---------|---------|---------|
| GUEST | 游客 | 公开信息查询、房源浏览、看房预约 |
| RESIDENT | 居民 | 个人信息管理、工单提交、反馈提交、资源预约、服务评价 |
| STAFF | 服务人员 | 工单处理、反馈回复 |
| ADMIN | 社区管理员 | 社区内数据管理（限绑定社区），不可操作全局配置 |
| SUPER_ADMIN | 超级管理员 | 全局管理（社区创建/停用、全局配置、管理员管理） |

### 7.2 权限注解示例

```java
// 单角色权限
@PreAuthorize("hasRole('RESIDENT')")
@PostMapping("/api/v1/work-orders")
public Result<WorkOrderVO> createWorkOrder(@RequestBody @Valid WorkOrderCreateDTO dto)

// 多角色权限（OR）
@PreAuthorize("hasAnyRole('ADMIN', 'SUPER_ADMIN')")
@GetMapping("/api/v1/work-orders")
public Result<PageResult<WorkOrderVO>> listWorkOrders(@RequestParam Map<String, Object> params)

// 超级管理员专属
@PreAuthorize("hasRole('SUPER_ADMIN')")
@PostMapping("/api/v1/communities")
public Result<CommunityVO> createCommunity(@RequestBody @Valid CommunityCreateDTO dto)

// 公开接口（无需权限）
@GetMapping("/api/v1/housings")
public Result<PageResult<HousingVO>> listHousings(@RequestParam Map<String, Object> params)
```

### 7.3 数据级权限规则

| 角色 | 数据级权限 | 实现方式 |
|------|-----------|---------|
| 超级管理员 | 无过滤 | MyBatis-Plus 拦截器不注入条件 |
| 社区管理员 | 限绑定社区 | 自动注入 `WHERE community_id IN (绑定社区列表)` |
| 居民 | 限个人数据 | 查询个人数据时注入 `WHERE resident_id = 当前用户ID` |
| 服务人员 | 限派单工单 | 查询工单时注入 `WHERE assignee_id = 当前用户ID` |

**MyBatis-Plus 拦截器示例**：
```java
@Component
public class DataScopeInterceptor extends JsqlParserSupport implements InnerInterceptor {
    @Override
    public void beforeQuery(Executor executor, MappedStatement ms, Object parameter, 
                           RowBounds rowBounds, ResultHandler resultHandler, BoundSql boundSql) {
        // 获取当前用户角色与绑定社区
        UserContext user = SecurityContextHolder.getUser();
        
        if (user.getRole() == Role.ADMIN) {
            // 社区管理员：注入社区过滤
            injectCommunityFilter(boundSql, user.getBoundCommunityIds());
        } else if (user.getRole() == Role.RESIDENT) {
            // 居民：注入个人数据过滤（根据具体表判断）
            injectResidentFilter(boundSql, user.getUserId());
        } else if (user.getRole() == Role.STAFF) {
            // 服务人员：注入派单过滤（仅工单表）
            injectStaffFilter(boundSql, user.getUserId());
        }
        // SUPER_ADMIN：不注入任何过滤
    }
}
```

## 8. 参数校验规范

### 8.1 常用校验注解

| 注解 | 用途 | 示例 |
|------|------|------|
| @NotNull | 非空校验 | @NotNull(message = "社区ID不能为空") |
| @NotBlank | 非空白校验（字符串） | @NotBlank(message = "标题不能为空") |

```java
public @interface ValidStatus {

    Class<?>[] groups() default {};

    Class<? extends Enum<?>> enumClass();
}

// 使用
```


##### 9.1.1.6 社区级联删除（仅超管）

**接口**：`DELETE /api/v1/communities/{id}`

**权限**：SUPER_ADMIN

**路径参数**：
- `id`：社区ID

**响应**：`ApiResponse<Void>`（成功 `data` 为 null）

**业务规则**（R1 / R6 v1.2，50 阶段步骤 1b 交付）：
- **级联语义**：删除社区时其下级结构与关联业务数据一并物理删除——结构链（楼栋 / 单元 / 房屋 / 公共资源 / 房源及时段与看房预约）、工单链（工单 / 处理记录 / 附件 / 派单关系 / 评价 / 跟进）、公告链（公告 / 目标 / 查看记录）、反馈链（反馈 / 消息 / 附件）、预约链（预约 / 违约记录）、租住链（租约 / 提醒 / **变更历史 / 租约协议**）、服务类别与人员绑定（常驻社区 / 排班）、统计快照与通知；
- **账号体系不删**：`sys_user` / `resident` 为跨社区共享账号（resident 无 `community_id` 列，社区归属经 `residence_relation` 表达），仅解除 `sys_admin_community` 绑定行；
- 结构表（building / unit / house / public_resource）带 `@TableLogic` 软删除，级联须走物理删除以解除 FK 引用；
- 删除顺序一律**子表在前、父表在后**（FK 约束要求），关键顺序：人员擅长类别先于服务类别、租约协议与变更历史先于租约；
- **新增表须同步本清单**（DEF-066 经验，2026-09-21 制度化，见数据库设计 §9 变更记录）；
- 不存在 / 已删返回 404；删除动作写操作日志。

> 批量形态见 §9.16.1（`POST /api/v1/communities/batch-delete`，逐社区独立事务 + 部分成功语义）。

### 9.13 租约续约支付（C3 扩展 · R61，v1.4）

> 支付渠道：支付宝（电脑网站支付 alipay.trade.page.pay）与微信（Native 扫码 v3）双渠道，
> 凭据门控——渠道凭据（payment.alipay.\* / payment.wechat.\*）未配置时该渠道禁用并明示
> （GET /payment/channels 返回 enabled=false），不报错不阻断。
> 本地无公网回调：支付结果以**后端主动查单**（支付宝 alipay.trade.query /
> 微信 GET /v3/pay/transactions/out-trade-no/{no}）+ 前端轮询 GET /payment/orders/{no}
> 替代异步 notify；公网部署时按官方文档补 notify 回调控制器（代码预留接入注释，
> 见 PaymentController 类注释）。
> 支付单状态机：`PENDING → SUCCESS / CLOSED`（终态）；成功落账 = 回写支付单 +
> 租约 end_date 顺延 months 个月 + 通知居民与社区管理员（同一事务，幂等不重复延展）。

#### 9.15.1 按社区批量挂牌

**接口**：`POST /api/v1/housings/batch-generate`

**权限**：ADMIN/SUPER_ADMIN（ADMIN 限绑定社区，越权 404 不暴露存在性）

**请求体**：`{communityId, monthlyRent, deposit?, rentType?, buildingIds?, unitIds?, houseIds?, titleSuffix?, createTimeslots?, timeslotMode?, timeslots?}`
```json
{
  "communityId": 1,
  "monthlyRent": 3500.00,
  "deposit": 7000.00,
  "rentType": "RENT",
  "buildingIds": [11, 12],
  "titleSuffix": "特价",
  "createTimeslots": true,
  "timeslotMode": "DEFAULT"
}
```

**同时建立可预约看房时段**：
- `createTimeslots`：Boolean，可空，**未传视为 true（默认勾选）**；显式 `false` 时本次不建任何时段
- `timeslotMode`：`DEFAULT` / `CUSTOM`，可空默认 `DEFAULT`，其它值 400
- `timeslots`：`[{dayOfWeek(1-7), startTime, endTime}]`，`timeslotMode=CUSTOM` 且建时段时**必填非空**（示例 `[{"dayOfWeek":1,"startTime":"09:00","endTime":"12:00"}]`）；`dayOfWeek` 1~7、`startTime<endTime`、时间格式 `HH:mm[:ss]`，越界一律 400 参数错误（校验在建房源之前，失败不落任何数据）
- `DEFAULT` 口径：周一~周五（`dayOfWeek` 1~5）各两段 **09:00-12:00** 与 **14:00-18:00**（共 10 条/房源）
- 建时段范围：**仅本次新建房源**（`is_available=1`）；已有在架房源被跳过的房屋**不建时段**，其既有时段配置不受影响
- 幂等：同房源 + 同 `dayOfWeek` + 同起止时间已存在则跳过（重复执行不堆叠时段）

**业务规则**：为社区内**无在架房源**（非 OFFLINE）的房屋批量生成 AVAILABLE 房源（标题「{楼栋}{单元}{房号}·精装房源[·后缀]」）；已有房源房屋跳过（幂等）。**响应**：`{created, skipped, timeslotsCreated}`（`timeslotsCreated` = 本次新建时段条数，`createTimeslots=false` 时为 0）。

**业务规则**：管理端社区结构内直接管理房屋房源挂牌（R62 一体化）。

#### 9.15.3 房屋管理分页列表（带图卡片）

**接口**：`GET /api/v1/communities/houses-manage`

**权限**：ADMIN/SUPER_ADMIN；ADMIN 数据范围限绑定社区（house 表含 community_id，由数据级权限拦截器在 SQL 层注入 `community_id IN (绑定社区)`，传入未绑定社区 ID 返回空页）

**查询参数**：`communityId?`（空=全部管辖社区）、`buildingId?`、`unitId?`、`keyword?`（房号模糊）、`listing?`（`all` 全部 / `listed` 已挂牌 / `unlisted` 未挂牌，默认 `all`，其它值拒绝）、`page`（默认 1）、`size`（默认 20，上限 100）

**业务规则**

- 房屋为主线、挂牌为可选子对象：房屋可未挂牌（`housing` 为 null），与 §9.15.2 一体化树同口径
- `listing=listed/unlisted` 按 house 是否存在 housing 记录判定（EXISTS / NOT EXISTS 子查询随分页下推到 SQL，`total` 保持全集口径，非页内内存过滤）
- `coverImage` 取 `housing.images` 逗号串首个非空项（`/uploads/xxx.png` 相对路径原样返回），无图为 null
- 同一房屋存在多条房源记录时取 id 最大者（最新一条）

- 归属名称与挂牌摘要按主键集合批量装配（各一条查询），不做逐行查询

#### 9.16.3 结构链一次性批量生成（楼栋 → 单元 → 房屋）

**接口**：`POST /api/v1/structures/batch-generate`

**权限**：ADMIN / SUPER_ADMIN（ADMIN 限绑定社区，越权按数据级权限口径拒绝）

**请求体**：`StructureBatchGenerateDTO`

```json
{
  "communityId": 1,
  "buildingNamePrefix": "C",
  "buildingStartNo": 10,
  "buildingEndNo": 12,
  "buildingNameSuffix": "号楼",
  "unitCountPerBuilding": 2,
  "unitNameSuffix": "单元",
  "floorsPerUnit": 6,
  "housesPerFloor": 4,
  "houseNumberPrefix": "",
  "houseNumberWidth": 2,
  "skipItems": "4, 04, 2:1",
  "houseStatus": "VACANT",
  "area": 89.50,
  "roomCount": 3,
  "description": "结构批量生成",
  "dryRun": false
}
```

**字段说明**

- `buildingNamePrefix` / `buildingStartNo` / `buildingEndNo` / `buildingNameSuffix`：楼栋名 = 前缀 + 序号 + 后缀（默认后缀「号楼」）
- `unitCountPerBuilding`：每栋单元数（默认 0 = 不生成单元）；`unitNamePrefix` / `unitNameSuffix`（默认后缀「单元」）
- `floorsPerUnit`：每单元楼层数（默认 0 = 不生成房屋）；`housesPerFloor`：每层房号数
- `houseNumberPrefix`：房号前缀（如 `A-`）；`houseNumberWidth`：序号补零宽度（默认 2）
- `skipItems`：跳过项字符串（语法见下）
- `houseStatus`：房屋状态，可空默认 `VACANT`（可选 `VACANT` / `OCCUPIED` / `RESERVED` / `MAINTENANCE`）
- `area` / `roomCount` / `description`：生成房屋的统一属性（生成房屋时 `area` 必填）
- `dryRun`：`true` 时**零写入**，仅返回预计生成清单与计数

**房号生成口径（权威）**：`房号 = houseNumberPrefix + 楼层 + 补零(序号, houseNumberWidth)`；补零宽度默认 2（与前端结构总览门牌号规则一致）。

**跳过语法（权威口径，与前端结构总览一致）**

| 写法 | 含义 |
|------|------|
| `4` | 第 4 层**整层** |
| `04` / `*:4` | **所有楼层**的 4 号 |
| `4:1`（全角冒号 `4：1` 亦可） | 第 4 层的 1 号 |
| `104` | 基础门牌号（1 层 4 号） |
| `A-101` | 完整房号**精确匹配** |

- 多片段分隔符：逗号 / 顿号 / 空格
- **非法片段忽略且不阻断**（不影响其余片段的排除效果）
- 被排除的房屋计入 `skippedCount`，不计入失败

**上限**：楼栋 ≤ 60 / 单元总数 ≤ 600 / 房屋总数 ≤ 5000，**超限返回参数错误（INVALID_PARAM）**，不落任何数据。

**响应**：`StructureBatchGenerateResultVO`

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "dryRun": false,
    "buildingsCreated": 3,
    "unitsCreated": 6,
    "housesCreated": 64,
    "previewBuildings": ["C10号楼", "C11号楼"],
    "previewUnits": ["C10号楼-1单元"],
    "previewHouses": ["C10号楼-1单元-101"],
    "skippedCount": 8,
    "dedupedCount": 0,
    "failures": []
  },
  "timestamp": "2026-09-21T10:00:00"
}
```

**业务规则**：
- 逐层级先校验后落库：楼栋 / 单元重名（批内或库内已存在）**逐条跳过并记 failures**，不阻断其余分支
- 房屋落库复用单单元批量创建的逐行校验 / 去重 / 失败反馈链路（同单元撞号计入 `dedupedCount`）
- 楼栋 `floors` 落值为生成网格的楼层数（仅建楼栋不建房屋时按最小 1 落库，可在楼栋编辑中按实际维护）
- `dryRun=true` 时三类计数为**预计值**，`preview*` 为预览清单

**接口**：`POST /api/v1/lease-agreements/{id}/confirm`

**权限**：RESIDENT / ADMIN / SUPER_ADMIN

**请求体**：`{confirmName?, remark?}`（`confirmName` 缺省取当前账号姓名）

**业务规则**：
- **按当前身份落位**：居民落居民方（`tenantConfirmName` / `tenantConfirmTime`），管理方落管理方（`adminConfirmName` / `adminConfirmTime`）；居民仅可确认本人租约的协议
- 单方确认 → `PARTIAL`，同步回写租约 `agreement_status = PARTIAL`
- **两方均确认 → `SIGNED`**，同步回写租约 `agreement_status = SIGNED`，并记录协议签约变更留痕
- **已确认方重复确认不覆盖首次留痕**（确认人姓名与确认时间保持首次值）
- 已撤回（`CANCELLED`）协议不可确认；确认非法状态返回状态流转错误

#### 9.17.9 协议撤回（仅管理方）

**接口**：`POST /api/v1/lease-agreements/{id}/cancel?reason=`

**权限**：ADMIN / SUPER_ADMIN

**业务规则**：仅管理方可撤回；**仅 `PENDING` / `PARTIAL` 可撤回**（`SIGNED` 已生效不可撤回，`CANCELLED` 幂等返回成功）；`reason` 必填（落在 `cancel_reason`）；撤回后租约 `agreement_status` 回落 `NONE`。

**LeaseVO 增字段**：`agreementStatus`（租约签约状态，见本节状态口径）、`contractUrl`（契约附件地址；`lease_record.contract_url`）。

### 9.18 服务人员绑定、排班与工单调度（C4 扩展 · R65，v1.6）

#### 9.18.3 服务人员能力详情 / 保存（全量覆盖式）

**接口**：`GET /api/v1/staff-capabilities/{staffId}`、`PUT /api/v1/staff-capabilities/{staffId}`

**权限**：ADMIN / SUPER_ADMIN

**请求体**：`{communityIds?: [Long], categoryIds?: [Long]}`

**业务规则**：
- **全量覆盖式**保存：请求中的集合即为该人员最终绑定集；**空数组 = 清空该维度**；字段不传 = 该维度不变
- 绑定目标校验：communityId 需在 ADMIN 绑定社区范围内（越权拒绝）；categoryId 需存在
- 服务人员账号本身的创建 / 启停 / 社区绑定仍归超管（R46 v1.2），本节只维护**调度属性**，不触碰账号状态

#### 9.18.4 排班查询

**接口**：`GET /api/v1/staff-schedules?communityId=&startDate=&endDate=&staffId=`

**权限**：ADMIN / SUPER_ADMIN

**请求参数**：`startDate` / `endDate` **必填**（`yyyy-MM-dd`），跨度 ≤ 62 天（超限 400）；`communityId` / `staffId` 可选。

**响应**：`List<StaffScheduleVO>`，字段：`id, staffId, staffName, communityId, communityName, workDate, shiftType, shiftLabel, startTime, endTime, remark`。

#### 9.18.5 排班批量保存

**接口**：`PUT /api/v1/staff-schedules/batch`

**权限**：ADMIN / SUPER_ADMIN

**请求体**：`BatchSaveScheduleDTO`

```json
{
  "communityId": 1,
  "staffIds": [11, 12],
  "dates": ["2026-09-22", "2026-09-23"],
  "shiftType": "MORNING",
  "startTime": "08:00",
  "endTime": "12:00",
  "remark": ""
}
```

**响应**：`BatchSaveScheduleResultVO{saved: 4}`

**业务规则**：
- 一人一社区一天一条：同「人员 + 社区 + 日期」**覆盖**（`uk_staff_schedule` 兜底），不堆叠
- `shiftType` ∈ `MORNING`（早班 08:00-12:00）/ `AFTERNOON`（午班 12:00-18:00）/ `EVENING`（晚班 18:00-22:00）/ `FULL`（全天 08:00-18:00）/ `REST`（休息）；其它值 400
- `startTime` / `endTime` 缺省取班次默认值并落库为快照；**自定义时间须 开始早于结束**（否则 400）；`REST` 忽略并置空时间列
- `REST` 行同样落库（**用于区分「明确休息」与「未排班」**）
- `communityId` 校验社区存在 + 数据级权限（ADMIN 限绑定社区）；`staffIds` 须为启用的服务人员账号

#### 9.18.6 排班删除

**接口**：`DELETE /api/v1/staff-schedules/{id}`、`DELETE /api/v1/staff-schedules?communityId=&staffIds=&startDate=&endDate=`

**权限**：ADMIN / SUPER_ADMIN

**请求参数**（批量）：`communityId` 必填；`staffIds` 逗号分隔（**可空 = 全部人员**）；`startDate` / `endDate` 必填。

**响应**：单删 `data: null`；批量删 `BatchSaveScheduleResultVO{saved: n}`（`saved` 为清除的记录数）。

#### 9.18.7 工单列表调度参数与调度标记

**接口**：`GET /api/v1/work-orders`（在 §9.4.2 既有参数基础上**新增**）

**新增请求参数**：
- `assigneeId`：按处理人筛选（可选）
- `sort`：`DEFAULT` | `WAIT_DESC`（等待时长降序）| `PRIORITY`（紧急优先）；**`DEFAULT` 与不传完全等价**，保持原 `ORDER BY id DESC`

**WorkOrderVO 新增字段**

| 字段 | 说明 |
|------|------|
| `dispatchFlag` | 调度标记：`OVERDUE` / `URGENT` / `NEW` / `NORMAL` |
| `waitedMinutes` | 等待时长（分钟）：自**当前状态进入时间**起算，无进入记录时以提交时间起算 |
| `assigneeShiftLabel` | 处理人当日班次标签（早班/午班/晚班/全天/休息；空=当日未排班） |
| `assigneeActiveOrders` | 处理人当前未完结工单数 |

**调度标记阈值（权威）**

| 标记 | 判定条件 |
|------|---------|
| `OVERDUE` | 待受理 / 待派单 > 30 分钟；已派单 > 120 分钟未接单；处理中 > 1440 分钟 |
| `URGENT` | 未完结且 `priority=URGENT` |
| `NEW` | 创建时长 ≤ 120 分钟 |
| `NORMAL` | 其余 |

判定优先级：**`OVERDUE` → `URGENT` → `NEW` → `NORMAL`**（命中即返回，不再向下判定）。

#### 9.18.8 可派单服务人员（档位推荐）

**接口**：`GET /api/v1/work-orders/assignable-staff`（在 §9.4.2 既有端点基础上**新增参数**）

**新增请求参数**：`categoryId`（工单服务类别，可选；传入后按该类别判定「擅长」档位）

**StaffOptionVO 新增字段**

| 字段 | 说明 |
|------|------|

| `matchedCommunity` | 是否常驻当前社区（`staff_community` 绑定） |
| `matchedCategory` | 是否擅长当前工单类别（`staff_service_category` 绑定） |
| `communityNames` | 常驻社区名称（逗号拼接） |
| `todayShiftLabel` | 今日班次标签（空=当日未排班） |
| `activeOrderCount` | 当前未完结工单数 |

**推荐档位（权威）**

| 档位 | 条件 |
|------|------|
| 1 | 常驻本社区**且**擅长该类别 |
| 2 | 常驻本社区 |
| 3 | 擅长该类别 |
| 4 | 其他 |

同档内按**在手工单数升序**，再按人员 ID 升序（稳定次序）。档位随参数变化：
不传 `categoryId` 时「擅长」不成立（无档位 1/3）；未显式传 `communityId` 且 ADMIN 为多社区绑定时「常驻本社区」不成立（无档位 1/2）。

### 11.2 接口设计特点

1. **RESTful 规范**：统一使用 REST 风格，URL 资源命名清晰，HTTP 方法语义明确
2. **统一响应格式**：`{ code, message, data, timestamp }` 格式一致，前端易于解析
3. **统一异常处理**：业务错误码分段规划（5xxx），HTTP 状态码与业务状态码分离
4. **分页规范统一**：`page` + `size` 参数，`records` + `total` + `page` + `size` + `pages` 响应
5. **权限控制完善**：五角色 @PreAuthorize 注解 + 数据级 MyBatis-Plus 拦截器
6. **状态机完整**：工单 10 状态、租住 5 状态、预约 6 状态、反馈 3 状态全部覆盖
7. **实时通信支持**：WebSocket + STOMP 协议，通知推送 + 反馈会话
8. **文件上传规范**：通用上传接口 + 专用附件关联接口，图片/文档分类限制
9. **参数校验严格**：@Valid + JSR-303 注解，正则/长度/范围全面校验
10. **需求覆盖完整**：R1~R65 功能需求 100% 映射到接口（R1~R57 为 v1.0 基线，
    R58~R65 为增量，映射见 §10.13）

### 11.3 接口设计亮点

1. **数据级权限自动注入**：社区管理员绑定社区自动过滤，居民/服务人员自动限制个人数据
2. **状态流转校验严格**：每个状态操作接口都有前置状态校验，非法流转返回 5xxx 错误码
3. **幂等性保证**：PUT/DELETE 幂等，POST 非幂等，PATCH 部分更新幂等
4. **缓存策略清晰**：Redis 黑名单/权限缓存/通知序号/社区信息，TTL 与更新策略明确
5. **定时任务支持**：租期判定/到期提醒/公告下线/浏览统计回写，定时任务覆盖全流程
6. **通知推送完善**：业务事件 → Spring Event → 通知生成 → WebSocket 推送 → 增量补拉，全链路设计
7. **违约处置完整**：资源预约/看房预约违约 → 违约计数 → 超限冻结账号，闭环管理
8. **工单时间线**：完整记录工单状态流转历史，操作人 + 操作时间 + 备注，可溯源
9. **游客支持**：看房预约支持游客（resident_id 为 null），手机号 + 预约编号验证
10. **不满意跟进**：评分 < 4 自动创建跟进记录，管理员添加跟进措施，服务质量闭环
