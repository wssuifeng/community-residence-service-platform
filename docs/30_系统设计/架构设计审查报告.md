**修复**：新增 §3.3 缓存设计章节，明确：

## 3. 逻辑错误与风险（3 项）

### 3.1 权限模型性能风险 📝 已记录优化方案

**问题**：社区管理员每次请求都从 JWT 提取社区 ID 列表并注入 SQL `IN (...)`，存在：
- 管理员绑定的社区列表较长时 SQL 性能问题
- 社区绑定变更后的令牌吊销逻辑未详述（"同步吊销该管理员全部令牌"如何实现？）

**风险评估**：中等。单管理员绑定社区数通常 < 10，IN 性能可接受；但令牌吊销机制确实模糊。

**优化建议**（已补充到 §3 建议部分）：
- JWT Claims 中只存社区 ID 数量（避免 JWT 过大）
- 权限信息缓存到 Redis（key: `user:${userId}:perms`，TTL 与 Access Token 同步）
- 社区绑定变更时清理缓存 + 吊销令牌（将旧令牌 jti 加入黑名单）

**处理**：当前设计可满足 N2（50 并发）需求，优化方案记录为未来扩展方向；令牌吊销逻辑在「接口设计」阶段细化具体实现。

---

### 3.2 通知序号方案的并发问题 ✅ 已修复

**问题**：原设计"通知表单调递增序号（数据库设计详述）"，如果使用数据库自增 ID 作为序号，在高并发下可能出现"序号空洞"（事务回滚导致 ID 不连续），客户端会漏拉通知。

**影响**：高。补拉机制失效，离线用户重连后漏收通知。

**修复**：§4 更新为 Redis 计数器方案（`INCR notification:seq`），保证严格单调递增无空洞；通知表增加 `seq` 字段（非主键）。决策日志已记录。

---

### 3.3 定时任务幂等性不足 ✅ 已修复

**问题**：提到了提醒去重表，但未说明：
- 定时任务本身的分布式锁（虽然当前单实例，但架构设计应前瞻）
- 任务执行失败重试机制
- 扫描的批次大小与分页策略

**修复**：§5 改表，补充：
