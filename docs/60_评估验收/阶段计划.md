# 60 · 评估验收 · 阶段计划

编制日期：2026-10-19。依据用户本轮要求，将质量评估与需求验收共同纳入第六阶段。
任务执行状态只在[_中控](_中控.md)维护；本文件规定范围、顺序、方法和完成条件，不表示专项已经执行。

## 1. 目标与职责

- **质量评估**：从体验、结构、效率和风险分析系统质量，给出证据、影响和改进建议。
- **需求验收**：对照20包当前需求及已批准修订，逐条判断R1～R75、N1～N10以及E1～E12/E10b是否达成。
- 两条工作线共用证据；质量建议不自动成为新增验收门槛，已经明确的需求缺失也不能降为一般优化。
- 50包的设计符合性测试结论作为输入；本阶段补充核对证据缺口，不重开50阶段或整册重跑。
- 本轮交付是完整阶段计划；实际评估、整改与最终验收分别记录，不由计划建账推导通过结论。

### 2.3 执行边界

- 金融沿用户已确认可用的结果。AI不执行支付、主动查单、退款或渠道配置写入；只采用既有用户确认和适用的非交易证据，不扩写为所有异常分支均已实测。

- 冻结的10～50阶段包保持只读。整改若要求改变既有定义或设计，先记录差距和影响，再按既有决策流程办理；新增范围只记录，不直接实施。

## 6. 差距处理与整改控制

1. **核实登记**：各维度发现汇入同一份差距清单，一个事实一个G编号；记录来源任务和R/N/E、复现或核对证据。G-001～G-003继续待核实，不预判为已确认缺陷。
2. **分类与排序**：核实后按缺陷/不足/超纲分类；缺陷优先，其余按影响与成本排序。权限、数据破坏和核心流程阻断的影响单列，不以外观评分抵消。
3. **限定批次**：每批写清G编号、目标行为、改动范围、上游依据、依赖、成本、验证方式和停止条件。普通既定范围内缺陷按已授权收尾方向修复；新增功能、主观方案取舍或冻结定义/设计变化先交用户裁决，不借“评估”扩大实施范围。
4. **修改与复验**：只处理批内条目；验证原问题、受影响相邻入口及相关需求/质量维度。按实际影响选择检查，不机械重跑全项目，也不以单测总量代替结论。
5. **回写与提交**：证据 → 差距清单/逐条台账/报告 → 中控任务 → 必要决策和总控入口。完整任务按项目规则本地提交；推送沿用户后续明确授权办理。
6. **后续去向**：本版不处理的不足列明理由、残余影响及用户裁决；超纲建议只记录并链接全局灵感留存处，不转成自动开发任务。
