# 60 · 评估验收 · 阶段计划

编制日期：2026-10-19；同日按用户裁决确定“先验收、再评估”，并参考验收、页面检查、性能诊断及结论核验类技能优化方法。验收项目是否按需求实现，评估项目质量。
任务执行状态只在[_中控](_中控.md)维护；本文件规定范围、顺序、方法和完成条件，不表示专项已经执行。按工作分组细化的步骤、文件与交付见[实施计划](实施计划.md)，实际进展从中控和报告读取。

## 1. 目标与职责

- **先做需求验收**：验收项目是否按需求实现；对照20包当前需求及已批准修订，逐条判断R1～R75、N1～N10以及E1～E12/E10b是否达成，处理需求差距并复验，形成需求验收结论。
- **再做质量评估**：需求验收通过后，以验收版本为基线，评估项目质量；从体验、结构、效率和风险给出证据、影响及改进建议。
- 两部分严格按先后顺序执行，共用适用证据；质量建议不自动成为新增验收门槛，已明确的需求缺失不能降为一般优化。
- N1～N10中现有的性能、并发、安全等要求仍在需求验收时核对；后续对应质量评估分析质量表现、风险与改进空间，不把既有需求推迟到评估阶段才判断。
- 50包的设计符合性测试结论作为输入；本阶段补充核对证据缺口，不重开50阶段或整册重跑。
- 整体计划与[细化实施计划](实施计划.md)用于组织执行；实际验收、评估、整改与最终结论分别留证，不由计划建账推导通过结论。

### 4.1 先建立可核对的需求判据与覆盖清单（60-01）

- 以原需求正文、后续批准修订和现行角色权限为准，将每条R/N及每段E流程的完整标准展开为可逐项核对的记录。可以在R40等条目下编号子项，但子项仅作核对索引，不增加需求数量或改变标准；存在冲突先登记依据及待裁决内容。
- 覆盖清单记录“R/N/E及原标准位置 → 角色与社区/本人/参与者范围 → 页面/操作/接口 → 适用证据与版本 → 尚缺内容”。同一需求涉及多个入口时分别列明，不能由一个页面可打开推导全部达成。
- 先核对正常成功路径，再核对原需求要求的拒绝、边界、撤回/取消、重复操作与恢复分支；适用性以原标准为准，不能套用仅成功路径的技能而遗漏要求。金融部分引用用户确认，不补做交易。
- 每条以“前置条件 → 操作 → 预期结果 → 实际结果”记录；静态代码、单元测试、合成页面、真实HTTP/浏览器和用户确认注明证据类型。接口满足不能单独证明页面入口可用，截图不能单独证明后端权限或数据一致性。

### 4.2 复用证据与补足缺口

| 证据情形 | 处理方式 |
|---|---|
| 需求、相关代码/配置、环境与数据条件仍适用 | 保留原日期和原路径，说明与当前版本的关系，直接引用可证明的子判据 |
| 仅部分入口、分支、角色或规模适用 | 明列已证明与尚未证明的部分；只对缺口补充核对，不扩写原结论 |
| 当前版本或条件已变化，或者只有口头推断 | 先确定影响范围，再安排受影响检查；无法证明时写“证据不足” |
| 金融已有用户确认 | 原样记录确认对象、日期、范围及限制；不要求AI重放交易或补造渠道异常证据 |

没有代码改动不能单独证明历史性能数据仍适用，仍需核对数据规模、配置、运行条件与原测量方法；未执行的操作不得写成当前实测。

### 4.3 逐条结论与数量统计

- **通过**：全部适用原判据达成，证据能够对应到当前待验版本；**未通过**：有证据确认违反原判据，关联G编号；**证据不足**：现有材料不能支撑判断，保留缺口及核实动作。待验收只表示尚未开始判定。
- 同条需求的部分标准通过、部分未通过或证据不足时，整体结论按未满足的情况记录，并保留子项结果，不能折算为整条通过。
- 不适用仅限原需求本身带条件且本项目当前范围确实不触发，或已有用户明确裁决；记录依据，不能为绕过难测要求而自行排除。出现范围变更仍走冻结变更流程。
- 分别报告75条R、10条N、13个流程对象的结论数量；子项核对数量与有证据对象数量单列。证据覆盖和需求通过是两件事，不将建账数量、断言数量或材料存在率写成需求通过率。无需百分比时直接给各类数量和缺口。

### 5.1 统一证据要求

- 每份记录包含任务编号、日期、源码/构建/运行版本、检查对象、角色、视口或负载、数据条件、方法、实际观察和结论边界。
- 历史证据注明原路径及与当前版本的关系；不得把新计划日期当成原测试执行日期。变更影响范围不清或证据缺失时，保留核实动作。
- 截图、接口记录、SQL结果、性能摘要等自产证据保存在本包evidence中，按任务和批次归组。正文只链接必要摘要，不入库凭据、真实敏感数据或生成型大文件。
- 同一事实可以支持质量评估和需求验收，但两类结论分别填写。静态代码检查、合成页面、真实运行和用户确认分别注明。
- 报告不使用一个综合分数掩盖严重问题；先列确认的缺陷、主要不足、证据缺口，再给维度评价和建议。

### 5.3 页面、交互与架构评估的覆盖方法

- 前端先建立“页面/角色 × 1440/1024/768 × 适用页面状态”的索引。加载、空数据、长文本/较多数据、失败、无权限，以及表单校验、提交中、成功/失败等状态按页面能力选择；未检查写明，不假设每页拥有所有状态。
- 交互沿居民、服务人员、小区管理员、超管的实际任务及未登录公开浏览流程走查：识别入口、完成操作、确认结果、出错后继续操作；检查键盘顺序、可见焦点、对话框进入与返回、控件名称和错误说明。专家走查不冒充用户研究，也不把审美偏好直接列为缺陷。
- 截图说明视口、缩放和页面条件；交互记录绑定DOM/网络及实际结果。使用项目现有工具和独立浏览器会话，页面等待以目标内容就绪为准；不照搬与实时连接、轮询不相容的等待条件。
- 架构评估选择跨端共享业务、权限、通知和关键写入等代表调用链，解释规则由谁维护、调用方需要理解什么、一次规则修改会影响哪些入口、能否定向验证。评价依据是实际职责、约束和修改影响，不能以目录整齐、类数量或文件长短替代。

### 5.4 性能、安全、并发及恢复的检查条件

| 对象 | 先记录的条件与范围 | 分析方法与结论限制 |
|---|---|---|
| 前端性能（60-04.4） | 生产构建、页面与操作、浏览器/设备、网络、数据量、冷/热缓存、测量次数与工具能力 | 分别观察进入页面与操作反馈，关联请求链、脚本/图片、渲染与布局变化；重复测量并保留波动，说明等待后端还是前端处理。接口P95不能代替页面性能；工具不可采集的指标保留缺口 |
| 后端性能（60-05.2） | 接口、读写比例、并发、数据规模、持续时间、配置及相关历史证据 | 同时看耗时分布、吞吐、错误、SQL/索引、连接与锁等待；有依据才归因。优化前后保持可比条件，实测收益与估计收益分别写，不因发现某写法就判性能缺陷 |
| 安全性（60-05.3） | 身份、操作与目标数据范围；HTTP/实时订阅、上传等实际入口；采用资料的版本与条目 | 先验证访问者可做什么，再检查拒绝及留痕；前端隐藏按钮不能证明后端授权。后端依据适用OWASP与Spring官方资料，不能用不支持Java的技能冒充完整安全审计；依赖告警需核对本项目可受影响条件 |
| 并发（60-05.4） | 共享业务对象、竞争的全部已知入口/任务、锁键/获取顺序/释放、行锁、事务读写/提交/回滚及外部调用 | 接续50矩阵，按“竞争如何发生 → 应维持什么业务结果 → 现有约束如何保证 → 证据能证明多少”分析；优先核对跨入口、重复与重试、提交后通知。负载能力和正确性分别作结论，未覆盖入口不得外推 |
| 恢复与数据（60-06.1/.2） | 故障前、期间、恢复后的请求与数据状态；原Redis故障证据的版本/条件 | 核对响应耗时、失败语义、恢复后继续使用、重复执行和关联状态；区分立即一致与已明确的补偿过程。仅对缺口隔离补测，不从一次恢复推出全部故障安全 |

动态检查执行前先确认现有工具能采集什么；工具不足时保留已完成的源码/网络等分析及能力限制，不能把未测写成达标。新增工具、依赖或运行配置不由技能自动授权。外部性能指标或通用体验建议仅作分析参考，不改变N1～N10等既定验收要求。

### 5.5 每项评估的统一交付

每项用一份可追溯记录回答：检查范围与抽样理由、现有表现及优点、问题事实或尚未复现风险、对谁有什么影响、建议与预计改动/验证成本、证据及限制。结论回到该维度的具体问题，必要时写“证据不足”，不强制凑分或预设必须重构。报告只汇总主要结论，详细记录按任务链接；同一事实跨维度引用同一G编号。

技能检索、原文来源、适用与未采用内容见[技能参考与计划优化说明](技能参考与计划优化说明.md)。本节是将适用方法写入本项目计划，未安装新技能，也不表示已运行相应专项。

## 6. 差距处理与整改控制

1. **核实登记**：先登记需求验收发现，验收通过后再登记质量评估发现；两部分汇入同一份差距清单，一个事实一个G编号；记录来源任务和R/N/E、复现或核对证据。逐项采用核实后的证据和分类，不将旧候选口径当作最终结论。
2. **分类与排序**：核实后按缺陷/不足/超纲分类；缺陷优先，其余按影响与成本排序。权限、数据破坏和核心流程阻断的影响单列，不以外观评分抵消。
3. **限定批次**：需求验收整改归60-03，质量评估后的整改归60-07；每批写清来源、G编号、目标行为、改动范围、上游依据、依赖、成本、验证方式和停止条件。普通既定范围内缺陷按已授权收尾方向修复；新增功能、主观方案取舍或冻结定义/设计变化先交用户裁决，不借“评估”扩大实施范围。
4. **修改与复验**：只处理批内条目；验证原问题、受影响相邻入口及相关需求/质量维度。按实际影响选择检查，不机械重跑全项目，也不以单测总量代替结论。
5. **回写与提交**：证据 → 差距清单/逐条台账/报告 → 中控任务 → 必要决策和总控入口。完整任务按项目规则本地提交；推送沿用户后续明确授权办理。
6. **后续去向**：本版不处理的不足列明理由、残余影响及用户裁决；超纲建议只记录并链接全局灵感留存处，不转成自动开发任务。

## 7. 阶段完成条件与审阅

- 先形成需求验收通过结论并记录验收版本，再开展11项质量评估；质量评估均有可追溯结论、覆盖范围、证据和未覆盖说明；不能仅有检查清单。主观视觉/交互意见与客观缺陷分别陈述。
- 75条R、10条N、13个流程对象全部有验收结论和适用版本；C1～C12核心业务按当前需求判据达成，金融采用用户确认并保持原证据边界。
- 本阶段确认的缺陷清零；影响最终结论的待核实项和证据缺口已经核实或获得明确裁决，不能静默跳过。
- 每个差距具备分类、影响、成本、排序、批次/去向及复验记录；本版保留的不足和超纲项供用户确认，不用总体评分代替逐项处置。
- 最终报告分开给出质量评估意见和需求验收结论，注明当前交付版本、主要限制、整改结果与70接收材料。
- 需求验收结论在质量评估前独立形成；用户审阅综合报告后形成整个60阶段完成记录，再按既有阶段流程处理总控和中控。计划编制、自动检查通过均不等于阶段完成。
