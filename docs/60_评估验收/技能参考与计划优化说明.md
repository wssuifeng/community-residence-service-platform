## 2. 采用的方法与计划落点

| 参考内容 | 本项目具体改进 | 对应产物 |
|---|---|---|
| 验收场景须有可信输入、前置条件、操作和明确结果 | R/N/E下展开原需求全部判据与角色/数据范围，补适用的拒绝及边界分支；子项只作核对索引，不增加需求 | [阶段计划§4](阶段计划.md#4-需求验收任务明细)、[台账填写格式](需求逐条验收台账.md#11-逐条记录格式) |
| 结论必须对应实际可证明的范围 | 分开记录通过、未通过、证据不足；核对历史证据的版本/配置/规模，区分证据覆盖与需求通过；金融沿用户确认 | 阶段计划§3/4、台账及报告需求结论记录 |
| 先观察真实页面与用户任务 | 建立页面/角色/视口/状态索引，记录任务路径、键盘焦点、表单反馈和失败恢复；合成页面与真实运行分别说明 | 阶段计划§5.3、60-04.1～.3 |
| 性能分析从实测到请求依赖再到原因 | 记录构建、设备/网络、数据量、缓存、重复次数与工具能力；接口与页面分别评估，优化前后条件可比，估计和实测分别写 | 阶段计划§5.4、60-04.4与60-05.2 |
| 以实际职责和约束判断结构质量 | 看代表调用链的规则归属、依赖方向和一次规则变更的影响；不按目录、文件长短给架构结论 | 阶段计划§5.3、60-05.1与60-06.3 |
| 检查要有适用范围与限制 | 并发关联共享对象、全部已知竞争入口、锁、事务和提交/回滚；安全采用适用官方资料；工具缺口不能写成已测 | 阶段计划§5.4、60-05.3/.4与60-06.1/.2 |
| 证据先于完成结论 | 整改绑定前后版本和原失败判据，复验受影响入口；质量整改影响需求时更新验收结论；用户报告先列结论和决策事项 | [差距清单](差距清单.md)、[综合报告](评估验收报告.md)、阶段计划§6/7 |

每项质量评估还统一交付现有表现及优点、问题事实或风险、影响、建议与成本、证据和限制，不强制合成一个总分。主观建议、确认问题和未覆盖内容分别陈述。

## 3. 保留的边界

- 七组工作、75条R、10条N、13个流程对象和11项质量评估保留；本轮只优化执行方法、证据与记录格式，不填实际通过结论。
- 先完成需求验收及整改复验，形成需求验收通过结论后再执行质量评估。N1～N10原有性能、安全、并发要求在需求验收时先核对。
- Spring Boot验收技能仅提供成功路径场景方法，不替代拒绝、越权、异常等现行需求标准；不自动增加Cucumber、Testcontainers等依赖或要求重写现有测试。
- UI规范只选适用方法，不把桌面/平板扩展为完整移动端，不以第三方风格偏好替代需求。关联[界面规范原文](https://github.com/vercel-labs/web-interface-guidelines/blob/main/command.md)含框架和场景假设，按项目能力筛选。
- 性能测量采用实际可用工具；执行时记录官方定义与工具版本。后端安全沿项目现有OWASP依据及适用Spring官方资料，不将语言不符的技能当作完整审计。
- 不重新安装现有技能，不运行新业务测试，不操作金融、正常服务或用户浏览器；只做文档检查。本地第三方原文缓存排除入库，正文仅保留来源和自产分析。
