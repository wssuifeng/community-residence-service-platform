# 核心业务流程三端联动手测用例（E1~E13 + E10b）

> **本文件是什么**：**跨端交替操作**的完整业务闭环手测用例集——一条业务从居民端发起，
> 经管理端审核 / 派单、服务人员端执行，再回到居民端确认，**验的是「编码是否符合 30 系统设计」**。
> **与 `12_用户手测清单.md` 的分工（先读这条再决定用哪个）**：**单点核对用 12 号**
> （U-01~U-34，逐条验某个页面 / 某个接口 / 某条规则按设计做对了没有）；
> **完整闭环用 13 号**（本文件，跨端交替操作的端到端链路）。
>
> **阶段职责边界（2026-09-21 用户裁决，必须遵守）**：本文件**只判「编码是否符合 30 系统设计」**
> （**设计符合性**——设计写「已到期不得支付首期」，就验它是否真的拒绝；设计写「越权 100% 拒绝」，
> 就验是否真被拒）。**「功能是否满足 20 需求 / 好不好用」由 `60_评估验收` 判定，
> 不在本文件作为通过 / 不通过判据**；执行中观察到需求满足性 / 体验类现象，
> **只记录**并标注「**需求满足性 → 60 评估验收**」，**不判通过与否**。
>
> **执行中若发现「文档如此写、实现非如此」** → 按 `docs/50_系统测试/08_缺陷跟踪与回归.md`
> 登记 **DEF**（附端点 / 状态 / 错误码 / 日志），并在本文 **§1.3 记录表**填「**不通过 + 缺陷号**」。
>
> **权威依据（纪律 8）**：`docs/20_需求分析/需求规格说明.md`（端到端流程 **E1~E12 + E10b**；
> 当前 **v1.17**，需求 **R1~R75**）+ `docs/30_系统设计/接口设计.md`（**v1.7**）+
> `docs/30_系统设计/UI设计.md`（**v1.5**）+ `docs/30_系统设计/架构设计.md` §6（六大状态机）。
> **状态名 / 错误码 / 端点路径一律以 20 / 30 包当前版本为准**；不确定处标「**待核**」，不猜。

| 4 | 管理端 · `admin1` | 「居民」→ **批量导入**：下载 CSV 模板 → 改成 3 行（2 行合法 + 1 行故意重复手机号）→ 上传 | **部分成功语义**：逐行结果反馈，`2 成功 1 失败` 且失败行**标明失败原因**；成功行生效 |
| 5 | 居民端 · 新账号 | 「租住与房源 → 房源信息」选一处**空置**房屋 → 「申请租住 / 入住申请」：填关系类型（产权人 / 承租人 / 共同居住人等）、居住起止、备注 → 提交 | 提交成功、状态「**待审核**」（`PENDING`）；**房屋非空置时被拒**（`HOUSE_NOT_VACANT(5205)`）；**同一居民同一房屋已有待审核申请时被拒**（`APPLICATION_PENDING_EXISTS(5206)`） |
| 6 | 管理端 · `admin1` | 「租住与房源 → **入住申请**」（Hub 默认 Tab）查看该申请（申请人 / 身份 / 目标房屋 / 申请时间 / 状态 / 操作） | 待审申请可见；历史行（已通过 / 已驳回 / 已撤回）在历史筛选中可见 |
| 7 | 居民端 · 新账号 | 对该**待审核**申请点「**撤回申请**」→ 二次确认 | 状态 → **`WITHDRAWN` 已撤回**；管理端同一行的状态同步为「已撤回」；**对已通过 / 已驳回的申请再撤回被拒**（`APPLICATION_NOT_WITHDRAWABLE(5605)`） |
| 8 | 管理端 · `admin1` | 另起一条待审申请 → 审核**驳回**（理由必填） | 状态 → **`REJECTED` 已驳回**、驳回理由可见、申请人收到通知；**已审核的申请再次审核被拒**（`APPLICATION_ALREADY_REVIEWED(5202)`） |
| 9 | 管理端 · `admin1` | 再起一条待审申请 → 审核**通过**（按设计填租期起止 / 月租 / 押金） | 状态 → **`APPROVED` 已通过**；非租客按原规则建立关系；TENANT只建TO_SIGN租约与会话，无正式关系/不置已入住，接CF-E3-C/D |
| 10 | 管理端 · `admin1` | 「居民 → 居住关系」页选该居民 → 查看居住关系行 | 非租客或FIRST成功后的TENANT出现「居民｜房屋｜入住日期｜-｜居住中｜搬出登记」；未付TENANT无正式关系；居住关系台账**按房屋查当前与历史居住人员**、**按居民查全部居住历史**双向一致 |
| 11 | 居民端 · 该居民 | 用已通过审核的账号登录，打开原私有功能 | 居住关系生效后**居民端业务功能入口开放**（待办 / 报修 / 反馈 / 预约等可用） |
| 12 | 管理端 · `admin1` | 对该居住关系点「**搬出登记**」（填搬出日期与原因）→ 提交 | 居住关系**终止并记搬出时间**、状态不再为「居住中」；历史关系仍可查；**该居民失去对应房屋的居民端功能入口** |
| 13 | 管理端 · `admin1` | 对**非在住**居住关系再办搬出 | 被拒（`RELATION_NOT_ACTIVE(5207)`「居住关系不在住，不可办理迁出」）；全流程写操作日志 |

**通过判据**：入住申请 **4 态**（待审核 / 已通过 / 已驳回 / **已撤回**）流转可达且只有设计允许的流转成功；
注册方式开关（全局级）生效且社区管理员越权被拒；代建与 CSV 批量导入**部分成功语义**正确；
OWNER/FAMILY及管理员登记关系维持原规则；TENANT须协议SIGNED且FIRST成功才正式关系与私有权限联动；搬出登记终止关系并记搬出时间、历史保留；
非法流转与越权 **100% 被拒**并留痕。

**跨端衔接点**：居民提交申请 → **管理端「入住申请」待办 + 通知**；
管理端审核通过 → **居民端申请状态 + 待签约租约 + 自动建租约群聊**（接 **CF-E3-A**，详见 §4 速查表第 1~2 行）；
**入住申请行的会话入口按真关联 `conversationId` 渲染**（本轮新增交互）：**有群**才出现「进入租约会话」；**无群不出现该入口**（另有「咨询社区管理员」居民侧直通会话兜底，与租约会话不是同一入口，见 **CF-E3-B** 第 11 步）；
**申请行「查看我的租约」按 `residence_application.lease_id`（V26 强关联）深链**，`lease_id` 为 NULL 时给中性兜底「暂无关联租约」+ 去租约列表，**不出错指死链**；
搬出归档是 **CF-E3-F** 的终态口径。

> **备注（观察项）**：社区开启 `auto_approve_residence`（R62 补）时，提交入住申请即由系统自动审批、
> 无需人工审核——此路径的覆盖情况按 `50_系统测试/_中控.md` 批次 e 口径记录；
> 「审核体验 / 提示文案是否好用」属 **需求满足性 → 60 评估验收**，本文件只记录现象。

### CF-E3-A 租住申请与审核通过（→ 待签约）（E3 段 A · C3 · R66）

**流程目标**：居民提交租住申请 → 管理端审核通过 → 租约落「**待签约**（`TO_SIGN`）」
——**审核通过 ≠ 租约生效，房屋不置已入住**。
**涉及端与角色**：居民（提交申请 + 待审核阶段可撤回）+ 社区管理员 `admin1`（审核通过 / 驳回）。

| # | 端 · 账号 | 操作 | 预期 |
|---|-----------|------|------|
| 1 | 居民端 · 居民账号 | 「租住与房源 → 房源信息」选一处**空置**房屋 → 「**申请租住**」：填关系类型与备注 → 提交 | 提交成功、状态「**待审核**」（`PENDING`）；申请可在居民端「入住申请」列表看到；**待审核阶段可撤回** |
| 2 | 居民端 · 同上 | （附验）对待审核申请点「撤回」 | 状态 → **`WITHDRAWN` 已撤回**、**不产生租约**、房屋状态不变；对已通过 / 已驳回的申请再撤回被拒（`APPLICATION_NOT_WITHDRAWABLE(5605)`） |
| 3 | 管理端 · `admin1` | 「租住与房源 → 入住申请」找到该申请 → 点「**通过**」→ 核对来源挂牌/申请时价格，月租押金默认预填，可调整并留痕，填写租期 → 确认通过 | 申请状态 → **`APPROVED` 已通过**；toast说明只生成待签约租约，首期成功后正式入住；**同事务生成租约与会话，不建正式租客关系** |
| 4 | 管理端 · `admin1` | 「租住与房源 → 租约管理」切到「**待签约**」分组，查看该租约行 | 租约状态 = **「待签约」（`TO_SIGN`）**——**不是「已生效」**；不再显示独立承租确认；协议 = 「未发起协议」；租期 / 月租 / 押金与第 3 步填写值一致 |
| 5 | 管理端 · `admin1` | 「社区管理」/「租住与房源 → 房源管理」核对目标房屋状态 | 房屋仍为「**空置**」——**审核通过后房屋不置已入住**（设计硬口径，DEF-070 断言口径） |
| 6 | 居民端 · 该居民 | 「租住与房源 → 我的租约」查看租约卡片 | 卡片显示「**待签约**」与「查看协议」入口（未发出时等待管理方）；租期 / 月租 / 押金与登记值一致（金额取种子实际值即可做等值断言） |
| 7 | 管理端 · `admin1` | 驳回分支：另取一条待审申请点「**驳回**」（理由必填） | 状态 → **`REJECTED` 已驳回**、理由可见、申请人收到通知；**不产生租约** |
| 8 | 管理端 · `admin1` | 越权 / 边界：对**非绑定社区**的申请执行审核 | 被拒或无数据（社区级数据权限过滤）；越权记录入日志 |

**通过判据**：审核通过后租约状态为 **`TO_SIGN` 待签约**（**不是 `ACTIVE`**）且**房屋不置已入住**；
申请 4 态流转与撤回口径正确（撤回不产生租约，非法撤回 5605）；驳回不动租约、须填理由；
审核通过 → 只建待签约租约，不提前正式租客关系 + 自动建租约群聊（接 **CF-E3-B**）；
数据级权限（社区级）在审核动作上生效。

**跨端衔接点**：居民提交申请 → **管理端「入住申请」待办 + 通知**；
管理端审核通过 → **居民端出现「待签约」租约卡片与协议入口（无独立承租动作）**，同时**自动建 `LEASE_GROUP` 租约群聊**（接 CF-E3-B）。

### CF-E3-B 租约群聊与看房 / 带看分配（E3 · C3/C11/C12 · R59 / R63 / R68 / R69）

**流程目标**：租住申请**审核通过**时自动创建 `LEASE_GROUP` 租约群聊；
群内可发起**看房预约**（复用 R54/R55/R60 契约与冲突校验），管理端**分配带看人**后带看人入群并形成带看沟通会话。
**涉及端与角色**：居民（群内发起看房预约与沟通）+ 社区管理员 `admin1`（分配带看人）+ 服务人员 `staff1` / `staff2`（带看人）。

| # | 端 · 账号 | 操作 | 预期 |
|---|-----------|------|------|
| 1 | 管理端 · `admin1` | 审核通过一条租住申请后，打开「**消息会话**」列表 | 出现「**租约沟通·<房屋位置>**｜租约群聊｜进行中」；`conversation.type=LEASE_GROUP`、`related_id=租约 ID`、`status=ACTIVE` |
| 2 | 管理端 · `admin1` | 打开该会话详情 / 消息列表 | 群聊**立即可见、可打开、可发送**；默认参与者 = **申请居民 + 该社区全部启用状态的社区管理员**（R68 口径）；页面不展示成员名单时以成员接口口径核对 |
| 3 | 管理端 · `admin1` | 重复触发审核动作 / 重新进入该租约详情 | **同一租约不重复建群**（幂等）——会话列表中该租约仍只有 1 个 `LEASE_GROUP` 群 |
| 4 | 居民端 · 该居民 | 「消息中心 → 沟通会话」找到该租约群聊并发一条消息 | 消息即时可见；管理端在线时**无需刷新即收到**（WS ≤3s，断连走轮询兜底）；**非参与者不可见**（越权拒绝） |
| 5 | 居民端 · 该居民 | 在群内点「**预约看房**」：选房源与可约时段（可多段连续，单次上限按 `sys_config` 默认 120 分钟）→ 提交 | 群内发起的预约与房源页发起**同构**（同表、同状态机、同冲突校验）；提交成功状态「**待确认**」；**时段外请求不被受理**；**同一房源同一时段重叠预约被拦**；**非连续多段选择被禁止** |
| 6 | 管理端 · `admin1` | 对该看房预约点「**分配带看人**」：候选按档位排序（① 常驻本社区且擅长该类别 → ② 常驻本社区 → ③ 擅长该类别 → ④ 其他，同档按在手工单数升序）→ 选 `staff1` | 分配成功；**状态「待确认」→「已预约」**；**带看人自动入群**（群成员三方：居民 + 社区管理员 + 带看人）；**带看人与居民均收到通知**；被分配对象须为启用状态账号（否则 `VIEWING_ASSIGNEE_INVALID(5805)`） |
| 7 | 服务人员端 · `staff1` | 「**我的带看**」工作台查看待办，打开预约详情 | 待办可见；**预约详情内预约居民与带看人会话沟通可用**；带看会话消息**仅会话参与者可读写**（越权 100% 拒绝） |
| 8 | 服务人员端 · `staff1` | 在带看沟通会话内发一条消息 | 居民端可实时收到；消息实时推送 + 轮询兜底生效；带看记录可留痕 |
| 9 | 管理端 · `admin1` | 打开「租住与房源 → 租约管理」该租约详情，查「关联看房」 | 该看房预约**带租约标识**并可在租约详情查到（**R69 双向关联**）；未分配带看人的预约可查看详情但无会话对象 |
| 10 | 管理端 · `admin1` | 越权核查：用 `admin2`（社区 2）打开该会话 / 该预约 | 被拒或无数据（社区级数据权限）；**非本租约参与者发起预约被拒** |
| 11 | 居民端 · 该居民 | **会话入口渲染口径核查（本轮新增交互）**：「我的租约」租约卡与「入住申请」列表逐行核对会话入口 | 入口**按真关联 `conversationId` 渲染**：`conversationId` 非空（**有群**）才渲染「进入租约会话 / 租约沟通」入口，点击直达该会话；**无群（`conversationId` 为空）则租约会话入口不出现**；**不得**按 `houseId` 反查 / 猜群（不再走「同居民 + 同社区 + 同房屋取最新租约」的弱关联）。**注**：入住申请列表在无群时另有一个**居民侧直通会话**兜底入口（「咨询社区管理员」，`POST /conversations/direct`，居民仅本人），与「租约会话」入口**不是同一个东西**，不得混判 |
| 12 | 管理端 · `admin1` | **管理端开启会话两个入口核查（本轮新增交互）**：①「会话中心 → 开启会话」按**居民**发起直通会话；②在**租约详情 / 会话中心**按**租约**建 / 取租约群 | ① `POST /api/v1/conversations/direct`：**管理端（ADMIN / SUPER_ADMIN）可用**，`residentId` **可选**（指定会话对象居民）；**幂等**（重复发起返回同一条）；**未指定居民 → 参数错误 `400`（`INVALID_PARAM`）**、**跨社区 → 403**、**居民传他人 → 403**；② `POST /api/v1/conversations/lease-groups {leaseId}`：按租约建 / 取 `LEASE_GROUP`（已存在返回既有会话，**幂等**），并**回写 `lease_record.conversation_id`**。**待核（设计回写待办）**：`30_系统设计/接口设计.md` §9.14.3 当前仅记请求体 `{communityId}`（**未记 `residentId`**），`POST /conversations/lease-groups` **尚未入档**——二者为本轮实现口径（DEF-076）；**设计回写完成前本步只记录现象**，不据此判不通过 |

**通过判据**：**审核通过即建 `LEASE_GROUP` 群聊**且成员正确、**同租约不重复建群**；
群内发起预约与房源页发起**契约与冲突校验一致**（时段外、重叠、非连续、超时长均被拦）；
**分配带看人后状态「已预约」+ 带看人入群 + 双方收到通知**；带看沟通**仅参与者可读写**（越权 100% 拒绝）；
看房预约与租约**双向关联**可回溯；
**居民端会话入口按真关联 `conversationId` 渲染**（**有群才出现**租约会话入口，无群不出现、**不按 `houseId` 反查**）；
**管理端两个开启会话入口可用且幂等**（`direct` 未指定居民 **400** / 跨社区与居民传他人 **403**；`lease-groups` **回写 `conversation_id`**）。

**跨端衔接点**：管理端审核通过 → **居民端出现租约群聊**；
管理端分配带看人 → **服务人员端「我的带看」待办 + 带看人入群**（§4 速查表第 3 行）；
带看是**可选的沟通手段**，不构成协议发出或居民同意的前置；居民只需对管理方已发出的具体协议正文同意一次（接 **CF-E3-C**）。
管理端按租约建 / 取群（`POST /conversations/lease-groups`）→ **居民端租约卡出现会话入口**（§4 速查表新增行）；
本节的带看分配口径与 **CF-E12** 第 4~5 步同构（同一机制两处入口）。

> **备注**：租约群聊的**生命周期**（申请取消 / 驳回 / 撤回或租约归档时关闭会话：`status=CLOSED` + `closed_at`，
> 发消息被拒 `CONVERSATION_CLOSED(5604)`，历史只读）在 **CF-E3-F** 中做端到端收口断言。

### CF-E3-C 协议意愿单一入口：管理方发出 → 居民同意正文 → 待首期

依据：30 系统设计 §6.2/§6.7、接口 §9.17.6/§9.17.8/§9.19.3/§9.19.5、UI 设计协议面板（2026-10-11 用户裁决，取代 DEF-078 旧意愿复用方案）。本节仅判设计符合性，体验只记录。

| 步骤 | 端 / 角色 | 操作 | 设计符合性核查 |
|------|-----------|------|----------------|
| 1 | 管理端管理员 | 审核通过入住申请 | 租约 TO_SIGN、房屋 VACANT；自动建租约群聊。申请已经表达基础意愿，不再要求确认承租 |
| 2 | 居民 | 查看“我的租约”和租约群聊 | 没有“确认承租/承约”按钮或承租徽标；看房、群聊不构成协议发出门槛 |

**跨端衔接点**：本用例是**其它所有用例的前置**（先确认权限骨架正确，再看业务流转）。

### CF-E10b 超管搭建组织与社区级授权（E10b · C10）

**流程目标**：超管新建社区 → 创建社区管理员账号 → 绑定管辖社区 → 社区管理员在授权范围内开展工作。
**涉及端与角色**：超管 + 社区管理员。

| # | 端 · 账号 | 操作 | 预期 |
|---|-----------|------|------|
| 1 | 管理端 · `superadmin` | 「系统 → 系统用户」新建社区管理员账号 `admin2`（初始密码） | 创建成功；账号列表可见且角色为社区管理员 |
| 2 | 管理端 · `superadmin` | 将 `admin2` **绑定**到 `联调测试社区` | 绑定成功；该账号的数据范围 = 该社区 |
| 3 | 管理端 · `admin2` | 登录并执行本社区内工作：代建居民账号（含 CSV 批量导入）、发布限本社区的公告、派单 | 均可用且范围限本社区；**导入为部分成功语义**（逐行结果反馈，如 2 成功 1 失败并标明失败原因） |
| 4 | 管理端 · `admin2` | 尝试越权：新建社区 / 停止其他社区 / 修改全局配置 | 全部被拒并记录 |
| 5 | 管理端 · `superadmin` | 停用（或解绑）`admin2` 后，用该账号登录 / 操作 | 停用后不可登录或操作被拒；历史数据留痕不受影响 |

**通过判据**：账号创建 → 社区绑定 → 范围内的功能可用、范围外的操作被拒；停用即时生效。
**跨端衔接点**：本用例产出的 `admin2` 可替代 `admin1` 执行 CF-E2/E3/E5 等管理侧步骤（**建议保留 `admin1` 作对照**）。

### CF-E11 通知三端可见性与收件人身份隔离（E11 · C11，含 DEF-067）

**流程目标**：业务事件触发通知 → 在线长连接 ≤3s 推送 / 离线入库并上线补拉 → 已读；**且居民口径与管理口径通知互不串号**。
**涉及端与角色**：居民 + 社区管理员 + 服务人员 + 超管。

| # | 端 · 账号 | 操作 | 预期 |
|---|-----------|------|------|
| 1 | 居民端 · `resident1` | 触发一个居民口径通知（如提交工单、支付首期）后，**保持页面在线** | 通知在 ≤3s 内出现在铃铛 / 消息中心（WS 推送）；未读角标 +1 |
| 2 | 居民端 · `resident1` | **关闭页面（模拟离线）** → 由管理端触发一条面向该居民的通知 → 重新登录 | 上线后通过**补拉**看到离线期间的通知，**不丢失、不重复** |
| 3 | 居民端 · `resident1` | 点开通知 / 标记已读 | 已读状态生效、角标减少；通知文案与跳转正确（租约类通知应跳到「我的租约」对应租约） |
| 4 | **居民 vs 管理撞号验证（DEF-067）** | 先让 `resident1` 产生一条居民口径通知（如"首期费用支付成功"）；**另开隐身窗口**用 `superadmin` 打开消息中心，查看该时间段通知 | **超管的通知中心不得出现该居民口径通知**（`resident` 与 `sys_user` 是两套身份空间，id 会撞号，读取按 `(owner_type, user_id)` 收口） |
| 5 | （反向验证） | 让管理侧产生一条**管理员口径**通知（如"社区租约首期费用到账"）；回到 `resident1` 通知中心核对 | 居民端**不得出现**该管理员口径通知；管理侧（`admin1` / `test_admin2`）各自只看到发给自己管理员身份的通知 |
| 6 | 服务人员端 · `staff1` | 触发一条面向服务人员的通知（如被派单） | 服务人员端只看到自己的通知；不出现居民 / 管理员口径通知 |
| 7 | 管理端 · `admin1` | 查看「通知渠道分级」与站内通知落点 | 站内必达；勾选渠道按勾选留痕（同 CF-E5 第 4 步） |
| 8 | 三端 | 同时在线的两端互相发消息（如群聊 / 反馈会话） | 三端会话与通知的可见范围与参与者一致，非参与者不可见 |

**通过判据**：①在线实时 ≤3s、离线补拉不丢不重；②已读与跳转正确；
③**居民口径与管理口径通知双向不可见**（DEF-067 修复点）；④渠道留痕与勾选一致。
**跨端衔接点**：任一端的业务动作 → 对端通知中心 / 待办 / 群聊的变化；**必须用"撞号账号对"（`resident1` 与 `superadmin`）双向验证**，这是本用例最关键的观察点。

### CF-E12 房源上架 → 看房预约 → 带看 → 完成 / 违约（E12 · C12）

**流程目标**：管理端上架房源 → 游客筛选浏览 → 注册并登录居民账号 → 居民预约看房（冲突校验）→ 管理方确认并分配带看 → 线下带看 → 完成 / 违约处置。
**涉及端与角色**：社区管理员 + 游客 + 居民 + 服务人员。

| # | 端 · 账号 | 操作 | 预期 |
|---|-----------|------|------|
| 1 | 管理端 · `admin1` | 「租住与房源 → 房源管理」新增房源：关联 **CF-E1 的房屋**、标题、描述、月租 / 押金、租售类型（出租）、户型、图片、地图位置 → 上架 | 房源状态 **`AVAILABLE`**；也可用「按社区批量挂牌」为无房源房屋批量生成（默认月租 / 押金取挂牌值） |
| 2 | 游客端（未登录） | `/guest` → 房源列表：按租售类型 / 户型 / 社区筛选 → 打开房源详情 | 列表与筛选结果准确；详情含位置地图、图片、租金 / 押金；**出售类房源只提供展示与线下看房预约**（系统内无交易 / 网签 / 资金记录） |
| 3 | 游客端（未登录） | 打开房源详情，查看可预约时段，点击「登录 / 注册后预约看房」 | 游客只读浏览；跳转 `/auth/login?redirect=/resident/housings/:id/reserve`；不调用预约创建接口；详情不出现游客姓名、游客人数或短信验证码字段 |
| 4 | 居民端 · 注册账号 `resident1` | 登录后回跳预约页，选择可预约时段并提交（联系电话可选） | 提交成功、状态 **「待确认」**；`user_id` 绑定当前居民；**时段外 / 同一房源同一时段重叠预约被拦**；不需要短信验证码 |
| 5 | 管理端 · `admin1` | 「看房预约」找到该预约 → **确认**（并分配带看人 `staff1`） | 状态 **「已预约」**；居民收到站内通知；`staff1` 端出现带看待办（同 CF-E3-B 的分配口径） |
| 6 | 服务人员端 · `staff1` | 「我的带看」查看并执行线下带看；可与会话方沟通 | 待办可见；带看会话消息可用；带看记录可留痕 |
| 7 | 管理端 · `admin1` | 登记**完成** | 状态 **「已完成」**；带看量 / 浏览量计入统计（接 CF-E9） |
| 8 | 管理端 · `admin1` | 另取一条居民预约登记**违约**（未到场）并处置（冻结账号 / 限制预约） | 状态 **「已违约」**；处置留痕；被处置账号后续预约受限 |
| 9 | 管理端 · `admin1` | 下架该房源（`OFFLINE`） | 游客端列表不再显示；已产生的预约历史仍可查 |

**通过判据**：状态机「待确认→已预约→已完成 + 已取消 / 已违约」可达；
**同一房源同一时段重叠预约 100% 被拦**；游客只读浏览、居民账号预约且数据级权限符合设计（全社区开放 + 社区筛选）；
违约处置留痕并影响后续预约。

### CF-E13 出租全链总览（当前口径：2026-10-12）

挂牌与房源展示 → 注册并登录的居民预约看房（可选）→ 入住申请 → 审核通过 → TO_SIGN + 租约群聊 → **管理方同意并发出具体协议 → 居民在正文处同意一次 → SIGNED / TO_SIGN / VACANT（继续临时保留）** → 首期成功 → ACTIVE / 正式租客关系 / OCCUPIED → 续约 → 退租申请与审核 → 押金原路退还 → 归档。

- 审核通过不生效；入住申请已经表达基础意愿，无独立承租确认；管理方发出即管理方同意，不重复签署。
- 居民必须确认具体协议快照；旧承租时间不得代写确认。协议撤回重发后必须对新版本重新同意。
- 管理端不能直接把待签约记录置已生效。确认重试只读，撤回/同意串行化；历史已生效不自动回退。
- CF-E3-C 是协议段逐步用例；首期、续约、押金按 CF-E3-D/E/F。当前沙箱外部接入阻塞已暂缓，**不得把支付冻结写成已完成交易，也不跑真实渠道**。
- 入住申请按 lease_id、租约群按 conversationId 真关联；生命周期、通知 owner_type 隔离与支付类型 FIRST/RENEWAL 维持既有设计。
- 每步仅判断 30 系统设计符合性。需求满足性与入口体验类观察留给 60 评估验收。

## 6. 核心业务链路连续性只读观察项（2026-09-27，未实施）

> 本节不新增 CF 用例，也不改变设计符合性结论。执行时把现象写在对应 CF 行备注；
> 「需求满足性 / 易用性」只记录并转 60 评估验收；只有文档设计与实现不一致才登记 DEF。

### 6.1 租住闭环连续性

1. **申请到租约的强关联**：管理端审核通过后，居民端申请行、租约卡、租约详情和租约会话是否始终指向同一个 `leaseId` / `conversationId`；同一房屋存在多条租约时不得靠猜测反查。
2. **管理方发出到居民入口**：管理员发出即管理方同意，居民可查看具体协议并自主决定是否同意；没有独立承租动作、管理方重复同意或代居民确认。刷新或重新登录后状态仍一致。
3. **协议确认到生效**：管理方同意并发出、居民正文同意、`SIGNED`、FIRST成功后租约 `ACTIVE`、房屋已入住是否按设计顺序发生；避免出现重复确认、跳级生效或局部成功局部失败后页面误导。
4. **首期费用支付可恢复**：首期入口是否持续显示正确状态；支付宝页面关闭、支付单 `PENDING` / `CLOSED` / `SUCCESS` 后重新进入，是否能续接、重试或明确告知不可操作原因。
5. **退租到押金退还再到归档**：退租申请、审核、房态、居住关系、押金状态、退款流水、租约时间线和群聊关闭是否跨端同步；部分退款失败时不得误显示为已全部退还。
6. **通知与深链**：租约、退租、押金、协议相关通知点击后是否落到正确租约/申请；不同身份空间不会串收，也不会出现通知成功但页面找不到目标对象。

### 6.2 工单闭环连续性

1. **受理前后群聊边界**：未受理工单不应提前出现临时群聊；管理端受理后才建立 `WORK_ORDER_GROUP`，居民、受理管理员和服务人员看到的会话状态应一致。
2. **派单与服务人员入群**：派单后服务人员待办、通知、群成员和工单详情是否同时更新；改派、重复派单、刷新后不得出现旧人员仍可操作的假状态。
3. **按钮与状态机一致**：居民、服务人员、管理员各端每个状态下可执行按钮是否与 30 系统设计一致，尤其是接单、开始处理、提交结果、居民确认、管理员终审与退回。
4. **终审与会话回收**：管理员终审结束后工单关闭、群聊只读、历史可查、发送消息被拒的结果是否一致；评价入口不得指向已不可评价的状态。
5. **失败恢复与通知收件人**：网络失败、刷新失败、重复点击、通知延迟时，页面是否给出当前状态和重试入口；通知对象必须是正确的居民、服务人员或管理方，不能只依赖相同数字 ID 猜测身份空间。
