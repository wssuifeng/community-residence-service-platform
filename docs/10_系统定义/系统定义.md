## 1. 目标用户（具体群体，非虚构个人）

**小区管理者**：具有明确服务管理方的居住小区管理方人员——物业公司管理人员、
长租公寓 / 公租房（保障性租赁住房）运营人员、单位或园区宿舍管理员、
社区服务中心工作人员。关键特征：

- **痛点**：房屋、住户、入住搬出、报修、公告、资源预约等信息散落在纸质台账、
  Excel、电话和微信群中——更新不及时、居住关系不清、服务过程不可追溯、
  资源预约易冲突、服务质量缺乏统计依据；
- **规模与部署条件**：单个居住小区数百至数千户；管理方可能同时受托管理
  多个小区，故**一个部署实例支持一个或多个小区**（多小区数据隔离、
  按小区授权）；系统不含物联网 / 心跳类高频数据，业务负载稳定，
  单机 / 单服务器部署即可运行；
- **适用形态**：商品房小区、长租公寓、公租房、宿舍等均适用——系统不按产权
  类型分别建设，通过居住关系统一建模；
- **获客展示诉求**：管理方需要面向潜在租户 / 购房者的窗口——房源信息展示、
  看房预约入口与联系入口，减少重复的线下咨询电话；看房预约须由注册并登录的居民账号发起，未登录访问仅可浏览公开房源与可预约时段。居民账号可在建立有效居住关系前创建；是否可访问居住私有数据仍按有效关系及具体业务规则判定。**挂牌房源分出租与出售两类：
  出租房源走本系统完整的租住管理闭环（v1.5，见 C3）；出售房源仅提供信息展示
  与线下看房预约入口，房屋买卖交易本身不介入（v1.5，见 §3 非目标）。**

系统的直接使用角色（均服务于上述管理者的管理目标）：

| 角色 | 构成 | 职责边界 |
|------|------|---------|
| 居民 | 业主、租客、共同居住人、宿舍入住人员及尚未建立有效居住关系的居民账号等 | 按有效居住关系与具体业务规则查看本人居住信息；提交有权办理的服务申请 / 反馈 / 资源预约，参与反馈会话沟通，确认服务结果并评价 |
| 服务人员 | 维修、保洁、客服等小区服务执行人员 | 接收并处理分配到本人的工单，更新进度，填写处理记录并上传处理结果 |
| 小区管理员 | 小区管理方人员 | 管理**所绑定小区**的基础信息 / 居住关系 / 工单 / 公告（广播范围限绑定小区）/ 反馈 / 资源 / 房源 / 本小区**居民账号** / 本小区统计；按v1.11管理授权范围内服务人员业务资料、派单与排班；系统账号高权限仍按定义限制 |
| 超级管理员 | 平台运营方人员 | **全局级操作**：小区新建与停用、全局配置（注册方式开关等）、全系统广播、小区管理员账号创建与全局小区绑定分配、全局统计与操作日志，以及小区管理员可执行的业务 |

未登录公开访问不是账号角色，只能访问明确公开的信息与接口。居民账号即使尚未建立有效居住关系，仍属于居民身份；账号身份本身不授予居住私有数据权限。

## 2. 核心业务功能（系统的存在理由）

| 编号 | 核心功能 | 验收判据（可度量的完成标准） |
|------|---------|------------------------------|
| C1 | 小区基础信息管理：多小区列表，小区 / 楼栋 / 单元 / 房屋层级信息，房屋状态（业主自住 / 租客居住 / 空置 / 维护中 / 停用；正式居住由有效主关系驱动，临时占用独立），公共资源信息（是否开放预约、开放时段由资源配置决定） | 多小区数据隔离，管理端可切换小区操作；层级结构均支持增删改查；已被下级节点或业务数据引用的**楼栋 / 单元 / 房屋 / 资源**禁止删除、只可停用；**小区可由超级管理员级联删除**（下级结构与关联业务数据一并删除、二次确认、全量留痕，v1.2 变更）；房屋状态变更留有记录 |
| C2 | 居民与居住关系管理：居民档案，房屋与居民的关系（产权人 / 承租人 / 共同居住人等），入住与搬出登记审核。居民账号可在有效居住关系建立前创建；未登录访问及无有效居住关系的居民账号仅可访问公开信息子集（公告、房源等，子集范围由管理方配置），不可见居住私有数据 | 两种注册方式均可用且可由后台开关切换；非租赁入住与搬出经管理员审核后生效，租赁关系须协议确认且首期费用支付成功才生效（**小区可配置入住申请自动通过，v1.5，见 C3 判据**）；无有效居住关系的账号不具备居民端居住私有业务权限；任一房屋可查当前及历史居住人员列表 |
| C3 | 租住管理：租客入住申请、租期起止维护、到期提醒、搬出与历史记录、**租期延长申请审核与合同内自主按月缴租（v1.10）**、**租赁协议在线确认（v1.5）**、**押金状态与在线退还（v1.6）**——出租业务在本系统内形成完整闭环：房源挂牌 → 展示 → 看房预约 → 入住申请 → 审核（或小区级自动通过）→ 租赁协议双方确认 → 首期费用支付成功 → 租约与正式租客居住关系生效 → 正常缴租／租期延长申请与审核 → 退租申请与审核 → **押金原路退还** → 归档（维护小区内部居住关系，**不做房屋买卖交易**）。其中"即将到期 / 已到期"由租期止期自动判定，非人工流转 | 租住状态机「待审核→已生效→即将到期→已到期→已搬出→已归档」各状态可达且每次流转留痕；到期提醒按管理员配置的天数触发；**居民提交具体月数的租期延长申请，经管理方审核通过即延长同一租约；普通缴租可按1至已确认租期内剩余未缴月数支付且记录可查，不延长租期、不重复收押金（v1.10）**；**租赁协议正文以发起时的快照留存、双方各自确认留痕、双方确认后租约签约状态同步回写（v1.5，效力边界见 §3 说明）**；**小区可配置入住申请自动通过，自动通过时租期按小区配置月数推导、租金与押金取房源挂牌值（v1.5）**；**押金具状态（未缴 → 已缴 → 退还中 → 已退还 / 已抵扣）且退还经支付渠道原路退回、结果与失败原因留痕可查；平台不托管押金资金（v1.6，边界见 §3 说明）** |
| C4 | 服务申请与工单管理（报修渠道，异步处理）：居民提交需要派人处理的服务事项（室内维修、公共设施报修、公共区域卫生、水电管道、电梯楼道、安全隐患上报），可附图片佐证，统一生成工单，受理→派单→接单→处理→居民确认→关闭全过程管理；处理结果为图片与文字组合。**服务人员可绑定常驻小区与擅长服务类别，并按排班表体现每日班次，作为派单推荐的依据（v1.5）** | 工单状态机「待受理→待派单→已派单→已接单→处理中→待确认→已完成 / 已取消 / 已驳回→已关闭」全流转覆盖；每次流转记录操作人、时间与备注；居民提交与服务人员处理结果均支持图片（多张）+ 文字上传；**派单候选按「常驻本小区且擅长该类别」优先排序，排班与在手工单数可查（v1.5）** |
| C5 | 公告广播管理：公告发布 / 分类 / 置顶 / 有效期，定向发布（可选定一个或多个小区及楼栋范围）；公告查看记录（已读回执）；广播渠道分级——站内通知必达，短信 / 微信服务号渠道由管理员按信息重要性勾选 | 过期公告自动从居民端列表下线；置顶公告排在列表最前；已读记录可统计（已读人数 / 目标人数）；勾选的站外渠道按管理员选择触达 |
| C6 | 居民反馈管理（反馈渠道，会话式）：意见 / 建议 / 投诉等需要答复处理的事项，提交后由管理员受理，受理后建立**会话**——居民与管理方可实时沟通（长连接），办结后归档留痕。与 C4 的边界：需要派人处理的走工单（异步），需要答复沟通的走反馈（会话） | 每条反馈的提交、受理、会话消息、办结全程留痕可查；会话期间消息实时送达（长连接在线时秒级到达）；会话记录归档后不可篡改 |
| C7 | 公共资源预约管理：活动室 / 会议室 / 停车位等资源的预约、审核、冲突校验、违约记录 | 同一资源同一时间段的重叠预约在测试用例集内 100% 被拦截；预约状态机「待审核→已预约→已取消 / 已完成 / 已违约 / 已拒绝」全状态可达 |
| C8 | 服务评价管理：居民对已完成工单的评价（满意度等级 + 文字），不满意评价的处理 | 每个已完成工单可提交一次评价；可按服务人员和服务类别统计满意度 |
| C9 | 运营统计：房屋状态分布、居民与入住搬出量、工单量 / 完成率 / 处理时长、服务人员工作量、满意度、预约量、房源浏览与看房预约量 | 各统计报表数值与库内明细数据核对一致（抽样核对 100% 相符） |
| C10 | 用户与权限管理：四类账号角色（居民 / 服务人员 / 小区管理员 / 超级管理员），登录认证、基于角色的权限校验与**全局级 / 小区级两层权限**（全局级操作仅超级管理员可执行：小区新建停用删除、全局配置、全系统广播、管理员账号与通用小区绑定分配；小区管理员限绑定小区范围，设置本小区责任人时可触发仅该责任人账号的本小区自动授权，不能分配其他小区）、多小区数据授权、操作日志（保留 2 年，到期自动清理并通知运营者，v1.2 变更）。未登录公开访问不属于账号角色，只能访问公开白名单 | 各账号角色登录后仅能访问其权限范围与授权小区内的功能与数据；匿名请求访问未公开接口、无有效居住关系居民账号访问居住私有数据，以及越权访问（含小区管理员越全局级）均100%被拒绝并记录；关键数据变更（新增 / 修改 / 删除 / 状态流转）均写入操作日志（操作人 / 时间 / 对象 / 内容）；日志到期清理产生超管通知与任务日志（清理对运营者透明） |
| C11 | 消息与通知中心：统一管理各业务触发的通知（工单进度、审核结果、租期到期、公告广播、**反馈会话新消息**、看房预约确认等）；站内通道采用长连接实时推送，前端建立连接时**主动补拉**离线期间增量，避免上线丢消息；管理员按信息重要性勾选广播渠道（站内必达；短信 / 微信服务号为可插拔适配通道）。**多方会话：看房预约自动建群（预约居民 + 该小区管理员，分配带看人后带看人入群），居民可发起与所在小区管理员的直通会话（v1.5）** | 在线用户实时收到通知（秒级）；离线用户重新上线后补拉不丢失（测试用例覆盖"离线期间产生通知→上线可见"）；广播渠道勾选后按所选渠道触发（本版本模拟通道留痕可查）；**群聊与直通会话消息实时互通，越权访问 100% 被拒绝（v1.5）** |

## 3. 非目标（本版本明确不做的）

| 项 | 排除理由 |
|----|---------|
| 资金收付：**押金资金池 / 托管、线下垫付**、物业费 / 水电费缴纳、资金归集与分账 | 【v1.4 收窄】租住续约的在线支付已纳入范围（C3，居民经支付宝 / 微信渠道自主支付续租费用，见 R61）；【**v1.6 再收窄**】**押金在线退还已纳入范围**（C3，押金状态与退还记录 + 经支付渠道**原路退款**，v1.6，见 R72 与下方边界声明）——本项排除仅剩**押金资金池 / 托管（平台代为归集、保管、计息、垫付押金资金）**、**线下垫付**与物业 / 水电等生活缴费：前者需资金存管资质与合规条件，后者无对应业务闭环（约束本版本，不承诺永久） |
| 房产交易环节：房屋买卖交易、网签备案、资金监管、过户登记、税费代扣、中介佣金撮合 | 【v1.5 收窄】原表述中的「在线签约、电子合同」已移出本排除项——**租赁协议在线确认属 C3 租住管理范围**（v1.5，见 C3 与 R64）。本项排除限于**房屋买卖交易环节本身**：出售房源可展示与预约线下看房（C12），但网签备案、资金监管、过户登记、税费代扣须对接不动产登记与银行资金监管系统，中介佣金撮合属居间服务，均超出纯软件系统边界，不介入 |
| 智能硬件：门禁、人脸识别、摄像头监控、车牌识别、电梯 / 停车场设备接入 | 无硬件部署条件，超出纯软件系统边界 |

| 多租户 SaaS、跨城市统一运营 | 本系统是单一管理方组织的自营多小区（C1），非对外售卖的 SaaS 平台 |
| 移动 App 与微信小程序客户端 | 本版本以 Vue Web 端优先交付；后端按 RESTful API + JWT 设计天然支持多端接入，App / 小程序列入后续版本候选（灵感留存处 P-006） |

| 居民信用评分 | 无权威数据来源，评分易失真且涉及个人信息合规 |
| 实时定位与导航服务 | C12 的地图仅用于房源位置静态展示与定位标注，不提供 GPS 追踪、路线导航等实时位置服务 |

规则：非目标是本版本宪法，约束本版本，**不承诺永久**——大版本跃迁制定新定义时
可重新评估进入。

> **关于「租赁协议在线确认」的效力边界（v1.5 声明）**：C3 的租赁协议在线确认
> 为**平台内确认留痕**（协议正文快照 + 双方确认人 / 时间 / 身份），**不含**
> CA 数字证书、可信时间戳与第三方电子签服务，**不主张《中华人民共和国电子
> 签名法》第 13~14 条规定的可靠电子签名效力**，属电子签约的工程实现简化。
> 该能力**在范围内**（与上表「房产交易环节」排除项无关，排除项仅指买卖交易
> 环节）。详见 `20_需求分析/需求规格说明.md` R64 与决策日志 2026-09-21。

> **关于「押金在线退还」的边界（v1.6 声明，依据用户 2026-09-21 裁决）**：
> C3 的押金退还为**平台内状态记录 + 支付渠道原路退款**——押金具状态
> （未缴 → 已缴 → 退还中 → 已退还 / 已抵扣），退租等结算场景由管理端发起
> 退还，平台调用支付渠道退款接口并将**渠道结果与失败原因留痕**。
> **平台不托管押金资金、不计息、不为押金垫付**：资金自始由支付渠道收付，
> 平台只发起反向指令与记录结果；因此本能力**不构成资金存管或"押金池"业务**，
> 与 §3 非目标中仍保留的「押金资金池 / 托管、线下垫付」不冲突。
> 关联需求见 `20_需求分析/需求规格说明.md` R72；决策依据见决策日志
> 2026-09-21「押金支持在线退还（定义变更 v1.5 → v1.6）」条目。
