## 1. 目标用户（具体群体，非虚构个人）

**社区管理者**：具有明确服务管理方的居住社区的管理方人员——物业公司管理人员、
长租公寓 / 公租房（保障性租赁住房）运营人员、单位或园区宿舍管理员、
社区服务中心工作人员。关键特征：

- **痛点**：房屋、住户、入住搬出、报修、公告、资源预约等信息散落在纸质台账、
  Excel、电话和微信群中——更新不及时、居住关系不清、服务过程不可追溯、
  资源预约易冲突、服务质量缺乏统计依据；
- **规模与部署条件**：单个居住社区数百至数千户；管理方可能同时受托管理
  多个社区，故**一个部署实例支持一个或多个社区**（多社区数据隔离、
  按社区授权）；系统不含物联网 / 心跳类高频数据，业务负载稳定，
  单机 / 单服务器部署即可运行；
- **社区形态**：商品房小区、长租公寓、公租房、宿舍等均适用——系统不按产权
  类型分别建设，通过居住关系统一建模；
- **获客展示诉求**：管理方需要面向潜在租户 / 购房者的窗口——房源信息展示、
  看房预约与联系入口，减少重复的线下咨询电话。

系统的直接使用角色（均服务于上述管理者的管理目标）：

| 角色 | 构成 | 职责边界 |
|------|------|---------|
| 居民 | 业主、租客、共同居住人、宿舍入住人员等 | 查看居住信息与公告，提交服务申请 / 反馈 / 资源预约，参与反馈会话沟通，确认服务结果并评价 |
| 服务人员 | 维修、保洁、客服等社区服务执行人员 | 接收并处理分配到本人的工单，更新进度，填写处理记录并上传处理结果 |
| 社区管理员 | 社区管理方人员 | 管理**所绑定社区**的基础信息 / 居住关系 / 工单 / 公告（广播范围限绑定社区）/ 反馈 / 资源 / 房源 / 本社区**居民账号** / 本社区统计；**服务人员账号由超级管理员统一管理（创建 / 启停 / 绑定），社区管理员对服务人员的控制经业务机制实现（派单选择、服务类别配置等），无权直接启停 / 封禁服务人员账号（v1.3）** |
| 超级管理员 | 平台运营方人员 | **全局级操作**：社区新建与停用、全局配置（注册方式开关等）、全系统广播、社区管理员账号创建与社区绑定分配、全局统计与操作日志、社区管理员可做的一切 |
| 游客 | 未建立居住关系的访问者（潜在租户 / 购房者） | 浏览公开信息（公告、房源），预约看房，获取联系入口；不涉及居住私有数据 |

## 2. 核心业务功能（系统的存在理由）

| 编号 | 核心功能 | 验收判据（可度量的完成标准） |
|------|---------|------------------------------|
| C1 | 社区基础信息管理：多社区列表，社区 / 楼栋 / 单元 / 房屋层级信息，房屋状态（自住 / 出租 / 空置 / 维修中 / 停用），公共资源信息（是否开放预约、开放时段由资源配置决定） | 多社区数据隔离，管理端可切换社区操作；层级结构均支持增删改查；已被下级节点或业务数据引用的**楼栋 / 单元 / 房屋 / 资源**禁止删除、只可停用；**社区可由超级管理员级联删除**（下级结构与关联业务数据一并删除、二次确认、全量留痕，v1.2 变更）；房屋状态变更留有记录 |
| C2 | 居民与居住关系管理：居民档案，房屋与居民的关系（产权人 / 承租人 / 共同居住人等），入住与搬出登记审核。注册方式由后台配置：①管理员录入居民并代建账号；②居民自助注册 + 入住申请审核，两种方式并存。游客与未建立居住关系的账号仅可访问公开信息子集（公告、房源等，子集范围由管理方配置），不可见居住私有数据 | 两种注册方式均可用且可由后台开关切换；入住、搬出均经管理员审核后生效；无有效居住关系的账号不具备居民端私有业务功能入口；任一房屋可查当前及历史居住人员列表 |
| C3 | 租住管理：租客入住申请、租期起止维护、到期提醒、搬出与历史记录（仅维护社区内部居住关系，不做交易撮合）。其中"即将到期 / 已到期"由租期止期自动判定，非人工流转 | 租住状态机「待审核→已生效→即将到期→已到期→已搬出→已归档」各状态可达且每次流转留痕；到期提醒按管理员配置的天数触发 |
| C4 | 服务申请与工单管理（报修渠道，异步处理）：居民提交需要派人处理的服务事项（室内维修、公共设施报修、公共区域卫生、水电管道、电梯楼道、安全隐患上报），可附图片佐证，统一生成工单，受理→派单→接单→处理→居民确认→关闭全过程管理；处理结果为图片与文字组合 | 工单状态机「待受理→待派单→已派单→已接单→处理中→待确认→已完成 / 已取消 / 已驳回→已关闭」全流转覆盖；每次流转记录操作人、时间与备注；居民提交与服务人员处理结果均支持图片（多张）+ 文字上传 |
| C5 | 公告广播管理：公告发布 / 分类 / 置顶 / 有效期，定向发布（可选定一个或多个社区及楼栋范围）；公告查看记录（已读回执）；广播渠道分级——站内通知必达，短信 / 微信服务号渠道由管理员按信息重要性勾选 | 过期公告自动从居民端列表下线；置顶公告排在列表最前；已读记录可统计（已读人数 / 目标人数）；勾选的站外渠道按管理员选择触达 |
| C6 | 居民反馈管理（反馈渠道，会话式）：意见 / 建议 / 投诉等需要答复处理的事项，提交后由管理员受理，受理后建立**会话**——居民与管理方可实时沟通（长连接），办结后归档留痕。与 C4 的边界：需要派人处理的走工单（异步），需要答复沟通的走反馈（会话） | 每条反馈的提交、受理、会话消息、办结全程留痕可查；会话期间消息实时送达（长连接在线时秒级到达）；会话记录归档后不可篡改 |
| C7 | 公共资源预约管理：活动室 / 会议室 / 停车位等资源的预约、审核、冲突校验、违约记录 | 同一资源同一时间段的重叠预约在测试用例集内 100% 被拦截；预约状态机「待审核→已预约→已取消 / 已完成 / 已违约 / 已拒绝」全状态可达 |
| C8 | 服务评价管理：居民对已完成工单的评价（满意度等级 + 文字），不满意评价的处理 | 每个已完成工单可提交一次评价；可按服务人员和服务类别统计满意度 |
| C9 | 运营统计：房屋状态分布、居民与入住搬出量、工单量 / 完成率 / 处理时长、服务人员工作量、满意度、预约量、房源浏览与看房预约量 | 各统计报表数值与库内明细数据核对一致（抽样核对 100% 相符） |
| C10 | 用户与权限管理：五角色（游客 / 居民 / 服务人员 / 社区管理员 / 超级管理员）账号管理、登录认证、基于角色的权限校验与**全局级 / 社区级两层权限**（全局级操作仅超级管理员可执行：社区新建停用删除、全局配置、全系统广播、管理员账号与社区绑定；社区管理员限绑定社区范围）、多社区数据授权、操作日志（保留 2 年，到期自动清理并通知运营者，v1.2 变更） | 各角色登录后仅能访问其权限范围与授权社区内的功能与数据，越权访问（含社区管理员越全局级）100% 被拒绝并记录；关键数据变更（新增 / 修改 / 删除 / 状态流转）均写入操作日志（操作人 / 时间 / 对象 / 内容）；日志到期清理产生超管通知与任务日志（清理对运营者透明） |
| C11 | 消息与通知中心：统一管理各业务触发的通知（工单进度、审核结果、租期到期、公告广播、**反馈会话新消息**、看房预约确认等）；站内通道采用长连接实时推送，前端建立连接时**主动补拉**离线期间增量，避免上线丢消息；管理员按信息重要性勾选广播渠道（站内必达；短信 / 微信服务号为可插拔适配通道） | 在线用户实时收到通知（秒级）；离线用户重新上线后补拉不丢失（测试用例覆盖"离线期间产生通知→上线可见"）；广播渠道勾选后按所选渠道触发（本版本模拟通道留痕可查） |
| C12 | 房源展示与看房预约：管理方在后台维护**本系统在管社区**的房源信息（关联 C1 房屋：位置地图、户型、面积、朝向楼层、租金 / 售价、图片），面向游客与居民展示，可按条件筛选；游客 / 居民可预约看房（须注册账号，所选时段须落在后台配置的可预约时段内→管理方确认→线下带看，复用 C7 冲突校验，确认结果经站内通知触达，后续可经平台沟通或房源联系信息接洽）。房源信息发布遵循《住房租赁条例》（国务院令第812号）真实性要求：地址、面积、租金等信息真实、准确、完整 | 房源 CRUD 与条件筛选可用；后台可配置可预约时段，时段外的预约请求不被受理；看房预约状态机「待确认→已预约→已完成 / 已取消 / 已违约」全状态可达；同一房源同一时段重叠预约 100% 被拦截；已违约由管理方处置（冻结账号 / 限制预约等）并留痕；带看量 / 浏览量纳入统计 |

规则：数量不设人为上限；每条必须挂可度量的判据，禁止"体验良好"类不可测表述。
**具体的测量方法属于 50_系统测试阶段的职责**；50 阶段依据本表度量标准设计
实际测量方法与用例。

## 3. 非目标（本版本明确不做的）

| 项 | 排除理由 |
|----|---------|
| 资金收付：在线收租、押金托管、物业费 / 水电费缴纳 | 不接入真实支付渠道，规避资金安全与合规负担（约束本版本，不承诺永久） |
| 房产交易环节：在线签约、电子合同、押金 / 租金收付、中介佣金撮合 | 系统只做房源信息**展示**与看房**预约**（C12），不介入交易撮合与资金环节；交易在线下完成 |
| 智能硬件：门禁、人脸识别、摄像头监控、车牌识别、电梯 / 停车场设备接入 | 无硬件部署条件，超出纯软件系统边界 |
| 通用即时聊天：居民之间的自由社交沟通 | 沟通场景仅限"居民 ↔ 管理方"且依托业务产生（反馈会话 C6 / 工单 C4），不做居民间点对点聊天 |
| 生活增值服务：社区团购、外卖跑腿、医疗诊断、紧急救援、征信查询 | 非居住管理核心，属社会化专业服务 |
| 多租户 SaaS、跨城市统一运营 | 本系统是单一管理方组织的自营多社区（C1），非对外售卖的 SaaS 平台 |
| 移动 App 与微信小程序客户端 | 本版本以 Vue Web 端优先交付；后端按 RESTful API + JWT 设计天然支持多端接入，App / 小程序列入后续版本候选（灵感留存处 P-006） |
| 真实第三方消息通道对接 | 短信 / 微信服务号提供可插拔适配接口与模拟通道（C11），本版本不强制对接付费商业服务——学校要求不依赖第三方商业接口；真实对接列入后续版本 |
| 居民信用评分 | 无权威数据来源，评分易失真且涉及个人信息合规 |
| 实时定位与导航服务 | C12 的地图仅用于房源位置静态展示与定位标注，不提供 GPS 追踪、路线导航等实时位置服务 |

规则：非目标是本版本宪法，约束本版本，**不承诺永久**——大版本跃迁制定新定义时
可重新评估进入。
