## 一、C4 工单链（郭景2025 / 郑若鹢2021 / 吴嘉炜2024 / 蒋晟2021）

**链路对症**：用户反馈的核心业务链问题中，工单链的关注点是处理闭环完整性与
派单质量。本组文献给出的最有价值设计（按文献论证强度）：

### 1. 确认不通过的回退循环 + 状态门控字段编辑（郭景2025，§1.1/§2.1/§2.4）

- **回退循环**：工程师处理完 → 工单转"待验证"（对本课题即 C4 的"待确认"）；
  提交人确认**不通过**则"填写反馈意见后回退原工程师重新处理"，通过才归档。
  处理结果与预期不符时有明确的回流路径，而不是只能关闭重开。
- **状态门控字段编辑**："仅'未提交'状态可编辑，提交后自动锁定"，归档后表单
  全只读——防止流转中数据被篡改导致留痕失真。可推广为**各状态机的字段级
  可编辑矩阵**（本课题 C3/C4/C7/C12 四个状态机均适用）。
- 附带：**人读工单号**（"TKT+年份后两位+5 位流水"）便于群聊/电话口头引用
  追溯；**逐状态测试用例表**（每级流转后"状态更新且意见完整记录""分配后
  收到提醒"逐条验证）可直接作 C4 十状态机回归清单模板。

### 2. 定向通知 + 通知与主流程异步解耦（郑若鹢2021，§4.1/§5.2）

- **按类别路由的定向通知**：报修类型经 topic 交换器只通知对应类别处理人
  ——映射到本课题：新工单/派单通知应只推给"**绑定该服务类别 + 常驻该社区**"
  的在班人员（R65 的 staff_community / staff_service_category / staff_schedule
  三表数据已齐，缺的只是通知过滤逻辑），而非广播给全体服务人员。
- **通知异步化**：提交报修"写库 + 入队即返回"，短信/邮件由监听端异步消费。
  本课题无 MQ，可用 **Spring 事件 + @Async** 等效承接，避免 WS 推送与通知
  落库拖慢工单提交主接口。
- **主单与处理单两表分离**（§3.3）：故障主单 repair_details 与处理单
  repair_handle 分表——印证本课题 work_order / work_order_process /
  work_order_assignment 分表留痕路线正确。

### 3. 双维度评价 + 评价汇总反哺派单（郑若鹢2021 §3.3 + 蒋晟2021 §2.1.1）

- 郑若鹢评价表含"**处理过程评分**"与"**维修服务评分**"两分项 + 文字意见
  ——C8 可由单一满意度扩为过程/结果双评分，不满意跟进的定位更准。
- 蒋晟"宿管评级后系统排名"思路迁移：C8 评价聚合分可作为 **C4 派单四档候选
  推荐的排序权重**之一（与郭景"分单计入当前负荷"建议互补——四档推荐可补
  "在班且未完结工单数"权重），使评价与调度形成闭环而非孤立填分。

### 4. 居民侧状态透明（蒋晟2021，§2.1.2）

宿管核对后"学生能看到报修是否审核成功"，维修完成后宿管对该报修"回复"——
印证居民端应实时可见工单全状态与处理人留言（本课题已有基础，P-008 中
"服务人员工单分页完整性"等观察项可对照补强）。

### 5. 附件内容查重（吴嘉炜2024，§5.2 的改进版）

上传前查重思路可取，但其按文件名匹配不可靠——改进为**内容哈希（MD5/SHA-1）
判重**，用于工单/反馈附件防重复上传。

## 二、C7 公共资源预约链 + C12 看房预约链（王以伍2023 / 王小豹2025 / 丁福江2023）

**链路对症**：预约冲突链是已知薄弱点（R60 连续时段合并、并发唯一约束已做），
文献的增量价值集中在**冲突链下游**（到场确认、违约处置）与**上游**（源头减量）。

### 1. 超时自动判违约 + 违约溯源（王小豹2025，§1.2.2/§2.3）★ 对症

- "规定时间内没有签到或签退的，系统自动判断为违规"——**定时任务扫描超时
  未到场预约 → 自动置"已违约"并释放时段**，消除僵尸预约永久占用资源。
  与本课题四个定时任务 + Redisson 锁的既有设施零成本衔接，C7 / C12 两条
  预约链通用（看房预约"已违约"支线同理）。
- "违规信息表数据来源于预约表，两表建立外键关系"——违约记录必须挂到
  **具体预约单**，处置与申诉有据。本课题 violation_record 已有，对照检查
  是否与预约单一一可溯。

### 2. 默认责任人下放 + 预约前状态可见（王以伍2023，§2.2.2/§2.2.3）

- 每资源预设**默认审批人/责任人**，预约提交直达责任人——映射 C12：带看人
  可设默认分配（现 R59 带看人分配为管理员手动指派，可加"默认带看人"配置，
  减少待确认积压）。
- "进入实验室后查看所需仪器耗材的状态（可否预约）"——**提交前明示可约性**
  （本课题 C7 已有可约时段接口，C12 看房可对照检查游客端是否在提交前展示
  可约性），从源头减少无效预约流入待确认队列。
- 其连续时段 started_at/ended_at 模型无并发防重，弱于本课题既有"栅格 +
  数据库唯一约束"，仅作印证不作参考。

### 3. 审批流三做法（丁福江2023，§3.1.2/§3.2）

- **业务-流程双轨分离**（businessKey 关联）：审批状态与业务数据解耦——
  其载体 Activiti 对单体过重（本课题手写状态机已够），只取思想。
- **自动审批节点留痕**："自动审批"意见写入审批记录——对应本课题 V18 社区
  自动审批（auto_approve_residence）**是否留"自动通过"意见记录**，可对照查漏。
- ⚠ **驳回退回重提**："驳回后申请单退回申请人修改或删除"——**与本课题已
  冻结的状态机冲突**（入住申请/资源预约的"已驳回"为终态）。仅记录，若要
  改须走需求裁决 + 冻结文档变更流程。

## 三、C3 租住链 + C12 房源（胡龙2025 / 薛元杰2024 / 何斌斌2025 / 杨玉2025 / 闫俊甫2025）

**链路对症**：R61~R72 支付/协议/退租/押金链是最新扩展，规则完备性是关注点。

### 1. 通知附带行动入口（预警-服务联动）（胡龙2025，§四(五)）★ 对症

识别风险时"自动向房东、租客及运营方发送预警通知，**并附带整改建议或服务
支持链接**"——纯软件即可复刻的链路贯通手法：**到期提醒通知带续约支付入口、
违约通知带退租申请入口、协议待确认通知带确认面板直达链接**，修复"通知到了
但用户不知道下一步做什么"的断点（正对 P-008"通知同步状态反馈"关注点）。
其"找房-看房-签约-入住-退租全流程一网通办"目标与本课题出租完整闭环同构，
可作论文绪论的行业实践佐证。

### 2. 违约-押金结算规则矩阵（薛元杰2024，§3.2 表2）

按违约方与情形给资金归属的**确定性规则**：租客提前解约→保证金与押金归房东；
房东提前解约→押金归租客；到期→押金归租客、保证金归房东。本课题押金链
（R72 原路退款）有流程无明文情形矩阵——退租审核（R70）可落一张
"退租原因 × 押金处置"规则表，且无需引入区块链（该文的链/IPFS 均在边界外，
但其"以留痕替代信任"思想已由本课题操作日志/变更历史覆盖）。

### 3. 一键退租 + 角色分视图统计（何斌斌2025，§3/§5.3.2/§5.3.3）

- 针对纸质签批繁琐实现"一键退租"——印证居民自助退租（R70）的流程极简路径。
- "管理员查看所有车辆费用统计、驾驶员只能看所驾驶车辆、可选时间段"——
  **统计口径 × 数据权限 × 时间段**三维组合，C9 租约/支付统计可对照
  （本课题看板已有社区筛选，可加"按角色可见范围"与时间段维度）。

### 4. 反面印证（杨玉2025，§5）

作者自陈两点未做到：**未实现具体支付功能**；"缺乏对复杂问题的多级处理流程，
当一个投诉或维修任务需要多个部门协作处理时，系统无法有效支持"——反向印证
本课题真实支付双渠道（R61）+ 多方会话（R63）的设计必要性，论文综述/展望
可直接引用作同类系统短板对照。

### 5. 既有设计印证（闫俊甫2025）

统一响应封装 R\<T\>、Redis 缓存、容器化后台布局 + 动态菜单——与本课题
ApiResponse / Redis / 权限菜单基本重合，作论文例证即可，无增量。

## 四、C10 权限链（卢万有2025 / 何立富2025 / 申正阳2024 / 陈海锋2024 / 雷云祥2022 / 王勇2024 / 魏郧华2025）

**链路对症**：本课题 JWT + Redis 黑名单 + MyBatis-Plus 数据权限拦截器路线已定，
文献增量价值在**令牌失效盲区**与**权限热更新**两个工程细节。

### 1. JWTVersion 登录版本号（卢万有2025，§3.3）★ 对症

用户表加 JWTVersion 字段，每次登录自增写入 Claims；鉴权时**"JWT 中版本号
低于实际版本号即失效"**——一次性解决"改角色、禁用账号、踢下线后**旧令牌
仍带旧权限**"的盲区。本课题 Redis 黑名单只覆盖主动登出；版本号机制（机制
与语言无关，实现成本极低）把其余失效场景统一收敛。另"鉴权前按 Claim 查库
校验用户是否被禁用"（§3.3.1）可一并对照。

### 2. 权限缓存 + 变动即时刷新（何立富2025，§3.2.2）

首次解析令牌后把"用户角色对应的权限列表"存 Redis 并设过期，鉴权先查缓存；
**"当用户权限发生变动时，必须及时更新缓存"**——角色调整即时生效，消除
"令牌未过期但权限已变"的越权窗口。附：URI 动态鉴权 hasPermission 按
request URI 比对（含 RESTful 路径参数遇 `{` 截断、查询串处理细节），可作
功能级权限统一入口的补强参照。

### 3. IP 与 JWT 绑定 + 令牌加密存储（申正阳2024，§2.1/§2.2）

登录时把客户端 IP 写入 Payload，每次调用校验"Payload 中 IP 与连接 IP 一致，
不一致则为伪造客户端"——令牌被截获后异机不可用。⚠ 移动网络 IP 漂移会误伤，
须做成可配置开关。鉴权结果内存缓存（位图）面向海量权限场景，五角色单体不适用。

### 4. 接口级权限表 + 前端双校验（陈海锋2024，§2.1~2.3）

- 核心洞察：前后端分离下被保护对象从页面变成**接口**（"通过接口可以访问到
  页面看不到的资源"）——api_info 接口资源表 + 角色-接口多对多。
- 前端"动态路由 + 路由守卫双校验"（守卫先校验 token 再校验页面权限）——
  对照本课题 permission store + v-permission 指令查漏补缺。

### 5. RefreshToken 静默刷新（雷云祥2022，§2.3/3.5）

短有效期 + "剩余有效期小于总时长 1/2 时"客户端携 RefreshToken 静默换新
——缓解短有效期与频繁掉线的矛盾。单体场景价值中等，记录备选。
（其"URL 树压缩入 Token"防 Token 膨胀的做法同文备查。）

### 6. 权限树非递归构建 + 按钮指令删 DOM（王勇2024，§2.1~2.3）

pid 分组 Map + 栈遍历建树（非递归，注意"最小 pid 不一定是 0"）；按钮权限
"system:user:add"式编码，前端全局指令无权限时**删除标签元素而非仅隐藏**
——对照本课题 v-permission 实现是隐藏还是移除 DOM。菜单三分类型（目录/
菜单/按钮）与 component 字段驱动动态加载同构，可对照核对完备性。

### 7. 长会话持续权限验证（魏郧华2025，§3）

后台线程心跳持续验证权限"直到用户退出"——对本课题 **WebSocket 长连接期间
权限被撤销**的即时生效有启发（可在 WS 心跳/订阅校验中复查状态），但原文
技术陈旧仅取思路。

## 五、C11 通知链与并发控制（徐智勇2024 / 王栋柱2024 / 王龙军2023 / 蒋凌燕2024）

**链路对症**：P-008 关注点"通知同步状态反馈、失败恢复、离线不丢"三条全在本组。

### 1. 离线消息补发闭环（徐智勇2024，§2.2 表1/§2.3 表2/§3.3）★ 对症

- "若连接不存在，则将需推送的消息存入**离线消息数据库**"（含 client_id/msg/
  send_time/**status** 字段）；客户端重连时"将离线消息**按时间顺序补发**"。
- 一条设计同时命中三个关注点：**离线不丢**（本课题 notification 落库 +
  unread/pull 已有基础，可加**推送结果状态字段**）、**失败恢复**（重连触发
  补发）、**状态反馈**（status 可查可统计）。
- 心跳 + 连接健康监测：服务端失测心跳即关连接；LastMsgTime/LastHeartTime
  双时间戳清理不活跃连接——推送可恢复的前提是先感知断连，**决定轮询兜底
  的启动时机**。
- 独立推送服务架构（雪花连接标识、中国剩余定理加密）对单体过重，不采用。

### 2. Redis 分布式锁三要素（王栋柱2024，§2.1/§2.2）——既有做法的原理依据

SETNX 原子获取 + UUID 持有者经 **Lua 脚本比对后才能释放**（防误删他人锁）
+ **expiration/3 周期看门狗续期** + 过期自愈防死锁。本课题 Redisson 已内置
全部语义，本文价值是**论文/答辩的原理级依据**；其"确保同一任务多节点仅执行
一次"正对四个定时任务防重入，"资源竞争控制"对预约并发与防重复提交。

### 3. 连接表去重更新（王龙军2023，§2.3）

@OnOpen 时"同 readerId 已存在则**先 remove 再 put**"——同用户重连以新
session 替换旧连接，消除旧连接残留导致的推送失败。本课题 utils/websocket.ts
+ store/notification.ts 可对照检查断线重连时是否清理旧连接。其"实时数据走
WS、非实时走 HTTP 双通道协同"与本课题 WS 主推 + 30s 轮询兜底架构同构，
是论文双保障架构的直接文献支撑。

### 4. 推送选型论证（蒋凌燕2024，§3.1/§3.3/§6）

综述性文献：短轮询"结构简单易实现，但实时性较差且服务器负载较大"适合
"客户端数量少、消息频率低"——**30s 短轮询作兜底（而非长轮询）的合理性依据**；
WS 清单"心跳包检查连接状态；连接断开时自动重连"可作前端 websocket.ts 的
对照核查项。论文选型章节直接可用。

## 六、技术栈与同类系统对照（论文素材为主）

### 1. 与本课题栈几乎完全同构的工程细节（时业茂2023，§3.2/§3.4）

MyBatis-Plus 分页拦截器注册（MybatisPlusInterceptor + PaginationInnerInterceptor）
+ Lambda 动态条件（`lqw.like(条件!=null, ...)` 非空才拼接）+ 统一响应模型 R
——论文第 2/5 章"分页与动态查询实现"的直接文献依据；其"Controller=Spring MVC、
Service=Spring、DAO=MyBatis-Plus"分层归位表述可作技术章骨架。

### 2. 同域系统功能与表设计对照（张艳军等2025，§1.2/§1.3）★ 对照价值最高
