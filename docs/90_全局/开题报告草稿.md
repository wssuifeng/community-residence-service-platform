## 一、选题的目的和意义

### 1.1 选题目的

城市居住小区类型多样，商品房小区、长租公寓、公共租赁住房、单位与园区宿舍等均由相应的物业企业、运营单位或后勤部门实施管理。不同类型小区的管理主体不同，但面临的问题高度相似。

**信息分散的现状**：目前多数小区的管理方仍以纸质台账、电子表格、电话和微信群等分散方式记录房屋信息、居住人员、报修申请和公共资源使用情况，存在信息更新滞后、居住关系不清晰、服务处理过程不可追溯、资源预约冲突频发、服务质量缺乏数据支撑等问题。

**问题的共同根源**：信息分散在多个渠道，缺少一套贯穿居住关系全过程的统一记录，导致同一事实在不同环节重复录入、口径不一，出现争议时也难以回溯。

**本课题的目标**：设计并实现一个面向小区管理者的小区居住服务管理系统，基于 Spring Boot 与 Vue 前后端分离架构，将小区房屋、居民居住关系、服务工单、公告反馈、公共资源预约及运营统计纳入统一管理，以规范小区日常服务流程、提高管理效率，并通过完整的设计与实现过程锻炼综合运用软件工程方法解决实际问题的能力。

### 1.2 选题意义

**信息集中化**：将分散的小区管理信息集中化、结构化，通过入住审核、搬出登记和租期维护保证居住关系数据准确可查。

**服务事项闭环**：将报修、隐患上报等事项统一为工单流程，处理全程留痕，居民可实时查看进度，管理方可以量化考核服务质量。

**预约冲突前置拦截**：通过公共资源预约的时间冲突校验避免资源重复占用，把冲突从事后协调提前到提交时拦截。

**运营决策支撑**：通过统计报表为管理方提供运营决策依据，使服务质量与服务力量配置具备数据支撑。

**理论与训练意义**：完整实践需求分析、系统设计、数据库设计、前后端编码、系统测试的软件工程全流程，掌握 Spring Boot、Vue 3、MySQL、Redis 等主流开发技术，提高独立分析问题与解决问题的能力。

## 二、主要研究内容

### 2.1 设计目标

**空间层级管理**：面向具有明确服务管理方的居住小区的管理者，设计并实现支持单／多小区管理的 Web 系统，在空间维度上支持小区、楼栋、单元、房屋四级层级信息管理。

**居住关系管理**：采用审核式管理，支持产权人、承租人与共同居住人等关系的登记与变更，注册方式（管理员代建或自助注册加入住审核）由后台配置，入住、搬出与租期变更均需全过程登记留痕。

**服务事项分流**：报修类事项走工单渠道全过程异步跟踪，意见建议与投诉类事项走反馈渠道并以会话形式实时沟通。

**公告与预约**：提供公告定向广播（含已读统计）与消息通知中心，站内长连接实时推送，短信与微信服务号渠道可插拔；支持公共资源预约与时间冲突校验；面向潜在租户与购房者提供房源信息展示与看房预约。

**评价与统计**：提供服务评价与运营统计，为管理方考核服务质量提供数据依据。

**角色与权限**：设置居民、服务人员、小区管理员、超级管理员四类角色，权限分全局级（仅超级管理员）与小区级（小区管理员限所绑定小区）两层，多小区数据按小区维度隔离授权，关键操作留操作日志。

### 2.2 设计方案

#### 2.2.1 系统分析

**未建立居住关系的居民**：仅可浏览公开公告与房源、查看可预约时段、获取联系入口，可发起看房预约，但不具备居住私有业务功能入口。

**居民侧**：覆盖查看居住信息与公告、提交服务申请与反馈、预约公共资源、参与反馈会话、确认与评价服务。

**服务人员侧**：聚焦工单的接收、处理与进度反馈，并可上传图片与文字处理结果。

**小区管理员**：面向所绑定的小区，负责基础信息维护、居住关系审核、工单派发、公告广播与反馈会话、资源配置、房源维护、通知渠道管理、本小区统计与居民账号管理。

**超级管理员**：面向全局，负责小区的新建与停用、全局配置、小区管理员账号创建与小区绑定、全局统计与操作日志。两级权限的分界是本系统权限设计的核心约束之一。

**双渠道业务**：报修类事项走工单渠道，以异步流转的方式全过程跟踪；答复类事项走反馈渠道，以会话形式进行实时沟通。两条渠道共用同一套通知与留痕机制，但在状态模型与处理角色上彼此独立。

**状态模型与边界**：对租住、工单、公共资源预约、看房预约四类业务分别建立状态模型，明确状态全集与合法流转。系统边界明确排除在线支付、房产交易环节与智能硬件接入等非管理核心功能。

#### 2.2.2 系统设计

**前端**：以 Vue 3.5 与 TypeScript 构建居民端、服务人员工作台与管理员后台三个入口，基于 Vite 构建、Pinia 管理状态、Axios 调用接口、ECharts 绘制统计图表。各端共用同一套请求封装与类型定义，仅在路由、布局与页面组织上按角色区分，既保证交互风格一致，又避免同一业务逻辑在前端重复实现。

**后端**：以 Spring Boot 4.0.6 提供 RESTful API，集成 Spring Security 与 JWT（jjwt）实现认证与基于角色的授权。多小区数据由 MyBatis-Plus 数据权限拦截器按小区维度统一过滤，业务代码中不重复编写可见范围判断。

**实时通信**：采用 WebSocket（SockJS + STOMP）承载反馈会话与消息通知推送，推送失败时由 HTTP 轮询增量补拉兜底，保证离线期间产生的消息不丢失。

**数据持久层**：采用 MySQL 9.x 存储业务数据，Redis 7 用于缓存与分布式锁（Redisson），ORM 采用 MyBatis-Plus 3.5.16，表结构以迁移脚本为唯一事实来源，避免设计与实现出现两套口径。

**接口契约**：由 Springdoc 从代码注解生成，作为前后端联调的唯一依据。

**数据库设计**：覆盖小区、楼栋、单元、房屋、居民、居住关系、租住记录、服务类别、工单及处理记录、公告及查看记录、反馈会话、公共资源、预约、房源、看房预约、评价、通知与操作日志等核心表，绘制 E-R 图并遵循第三范式。

**状态机约束**：对租住、工单、公共资源预约与看房预约四类业务分别设计状态机流转约束，明确状态全集、合法流转路径与越权流转的拒绝方式。

#### 2.2.3 系统实现

**分层职责**：后端按架构设计的分层契约组织为控制器层、服务层与数据访问层。控制器层只做参数校验与响应封装，业务规则集中在服务层，数据访问层由 ORM 框架承担且不承载业务判断。

**共享与隔离**：跨模块共用的实体、状态流转定义与通用存储集中在共享域内唯一维护，各端入口只负责本端的协调与查询，端与端之间不直接调用，公共层也不反向依赖端层，以此保证同一业务规则在多个入口下只有一份实现。

**实现顺序**：先落地身份认证与权限，再依次实现小区基础信息、居住关系与租住、工单、公告与反馈会话、公共资源预约、房源与看房预约、消息通知中心，最后实现评价与统计。

**单域推进**：每个业务域按「实体—状态机—接口—页面」的顺序推进，前一域的状态与权限约束稳定后再进入下一域，避免因上游规则变动导致返工。

**主线一·认证与授权**：请求经统一的过滤器链完成身份解析，功能级权限按接口表达式判定，数据级权限由持久层拦截器按小区维度统一注入过滤条件，业务代码中不出现分散的可见范围判断。

**主线二·状态流转**：租住、工单、公共资源预约与看房预约四类业务各自维护状态全集与合法流转表，状态变更统一走状态机校验并同步写入处理记录，非法流转在提交前即被拒绝。

**主线三·并发与一致性**：预约类业务以时段记录加唯一约束表达占用，并发提交由数据库约束兜底、分布式锁降低无效重试；定时任务以防重入锁保证单实例执行，并以执行日志留痕。

**主线四·通知与留痕**：站内通知以长连接推送为主、增量补拉兜底，保证离线期间产生的消息不丢失；关键数据变更与协议确认均写入留痕记录，与业务数据在同一事务内提交。

**定时任务**：承担租期状态自动判定、租期到期提醒、公告到期自动下线与浏览统计回写四类周期工作，任务之间互不阻塞，单次执行结果记入执行日志以便追溯。

**接口契约落地**：接口文档工具从代码注解生成契约并作为前后端联调的唯一依据，前端各端按契约封装请求层与类型定义，减少联调阶段的语义偏差。

#### 2.2.4 系统测试

**用例来源**：以需求条目为唯一来源，每一条功能需求与非功能需求都对应可执行的测试项，测试项再细化为具体用例，形成「需求—测试项—用例—执行结果—缺陷」的完整追溯链，任何一条需求都能回答「由哪些用例验证、结果如何」。

**冒烟前置**：测试进入全面执行前先设冒烟环节，冒烟不通过则打回修改，不进入后续轮次，避免在基础功能不可用的状态下消耗测试资源。

**功能与权限测试**：功能测试按业务域组织，覆盖正常流程、边界条件与异常输入；权限测试采用否定用例，针对四类角色的越权访问与跨小区数据访问设计用例，要求越权请求全部被拒绝并留下记录。

**异常与非功能测试**：异常流程测试针对状态机的非法流转、重复提交与并发冲突构造场景；非功能测试覆盖接口响应时间、并发处理能力与长连接在弱网和断线重连下的表现。

**专项一·时间冲突**：以重叠、相邻、跨天等时段组合验证唯一约束与合并提交的正确性，要求重叠预约全部被拦截。

**专项二·数据隔离**：以同一角色跨小区访问为场景，验证数据级权限的过滤是否在所有查询路径上生效。

**专项三·离线补偿**：以「离线期间产生通知—重新上线—补拉可见」为主线，验证消息不丢失且顺序正确。

**缺陷闭环**：每个缺陷记录复现条件、影响范围与等级，修复后必须在同一轮次内完成针对性回归，回归不通过不计入修复完成。

**出口判定**：以用例执行率、缺陷收敛情况与专项测试结果共同判定，测试结论与遗留问题一并写入测试报告，作为验收依据。

### 2.3 关键技术

本课题的关键技术集中在权限、并发、实时通信与可视化四个方面，具体如下：

（1）基于 JWT 的无状态登录与接口级权限校验，配合功能权限与多小区数据权限两层控制；

（2）基于 Redis 与 Redisson 的分布式锁，用于预约并发控制与定时任务防重入；

（3）公共资源与看房预约的时间冲突检测，复用同一校验逻辑，重叠预约全部拦截；

（4）租期到期状态的日期自动判定与到期提醒，以去重表保证同一租约不重复提醒；

（5）WebSocket（SockJS + STOMP）实时会话与通知推送，结合增量游标补拉保证离线消息不丢失；

（6）基于 MyBatis-Plus 数据权限拦截器实现小区级数据隔离；

（7）操作日志切面、附件上传与 ECharts 统计可视化。

### 2.4 拟采取的研究方法、技术路线

**研究方法**：文献调查法、原型法与软件工程规范化方法相结合。通过文献调查明确小区居住服务管理的业务构成与前后端分离架构下的通用设计模式；通过原型法验证预约冲突、工单流转等关键交互。

**阶段主线**：按「需求分析—系统设计—编码实现—测试验证—部署运行」推进，每一阶段产出对应文档，包括需求规格、设计文档与测试报告，保证开发过程可追溯、结论可复核。

**文档契约**：文档同时作为阶段之间的交付契约，下游阶段只依据上游文档推导任务，避免需求在设计或实现过程中被隐式改写。

**技术路线**：Java 17 与 Spring Boot 4.0.6 构成后端主体（Spring MVC、Spring Security、MyBatis-Plus、JWT、Redis、Redisson），Vue 3.5 与 TypeScript 构成前端主体（Vite、Pinia、Axios、ECharts），MySQL 9.x 作为数据库；前后端通过 RESTful API 交互，Maven 管理依赖，Flyway 迁移脚本作为表结构唯一事实来源。
