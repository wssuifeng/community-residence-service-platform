**课题名称：基于 Spring Boot 的社区居住服务管理系统设计与实现**

## 1 引言

城市居住社区的日常管理涉及房屋与配套设施台账、居住人员关系、报修与服务事项
处理、公共资源使用安排、公告通知与居民诉求等多类信息。多数管理方长期以纸质
台账、电子表格、电话与即时通讯群组分散记录，信息更新滞后、居住关系难以追溯、
服务处理过程不可复盘、资源预约冲突频发等问题普遍存在。把这类业务收敛到统一的
信息系统，在智慧社区建设背景下已成为明确需求，随之而来的是软件工程层面的问题：
如何在一个系统中同时承载多条业务链、如何约束各条链的状态流转、如何在多社区
场景下保证数据边界。

为确定研究切入点，本文对国内外相关文献作综述。检索以中国知网（CNKI）期刊库与
学位论文库为主渠道，以「社区／物业／居住管理 + 管理系统」「Spring Boot／Vue +
管理系统」「JWT／RBAC／权限控制」「Redis／分布式锁」「WebSocket／消息推送」
「预约系统／工单管理／租赁管理」等主题词组合检索，时间窗限定为 2021—2025 年；
外文文献经 Crossref 逐条核实 DOI。纳入本综述的文献共 43 篇，其中中文 39 篇、
外文 4 篇，年度分布为 2021 年 5 篇、2022 年 5 篇、2023 年 6 篇、2024 年 13 篇、
2025 年 14 篇。

需要说明检索与阅读的实际条件：中文期刊全文可获取并逐篇阅读的有 32 篇；学位论文
在数据库中多为 CAJ/KDH 封装或打印扫描件，未取得可检索文本层，只能依据题录与
摘要，共 7 篇；外文文献未取得全文与摘要，仅确认其真实存在与出版信息，共 4 篇。
这一条件限制决定了本文的论证强度：凡涉及具体设计细节的判断，均以全文可读的

## 2 社区居住服务管理信息化的研究现状

### 2.1 面向社区与物业的综合管理系统

综合类系统是数量最多的一类，其共同目标是把管理方分散的事务集中到同一平台上。
在业务构成上，这类系统的功能谱系高度相似：以房屋、居民、车位等基础信息登记为
底座，叠加报修、投诉、公告等事务处理，再视需要配置费用管理。张艳军等以居民
信息为核心构建平台，功能覆盖居民信息增删改查、房屋管理、车位管理、物业费用
管理、设备报修与留言管理[1]；闫俊甫等实现的小区物业系统在此之上增加了物业
人员管理与统计报表[2]；杨玉等按小区、房产、设备、业主、服务、车位组织模块[3]；
吴嘉炜等把重心放在社区服务侧，以志愿活动报名、留言交流与社区新闻发布为主要
业务[4]；李乐健等面向移动端，将人员出入管理、物资需求管理与打卡签到作为主要
功能[5]。以社区管理为题的研究亦有学位论文涉及，付昌昌围绕小区楼宇与住户信息
组织公告与投诉建议等物业事项[6]，包添文以社区管理系统为题[7]，二者均属摘要级
证据，本文只据其题名与摘要说明该方向已有系统性实践。

从设计方法看，这类系统普遍采用表现层、业务逻辑层、数据层三层结构[1]，技术
选型集中于 Spring Boot 与 Vue，组件库多取 Element UI 一类成熟方案[2]。值得
注意的是数据建模的粒度：有研究明确采用「每个模块对应一张数据表、表之间通过
外键关系关联」的扁平设计[1]，未引入状态机、时段约束或字段级变更留痕。这一
取舍在功能规模有限时是合理的，但当业务需要在同一条记录上表达多阶段流转、
并对流转过程追责时，扁平结构会显得不足。

更直接的对照来自作者自陈的局限。杨玉等在结语中承认系统未实现具体支付功能，
并指出投诉与维修管理缺少对复杂问题的多级处理流程，当任务需要多个部门协作时
支持有限[3]。这两点恰好对应本课题需要正面处理的问题：涉及资金与协议的环节
如何在系统内表达，以及跨角色的服务事项如何在一个流程内闭环。

### 2.2 面向单一业务链的专题系统

与综合类系统相对，专题研究把单条业务链做得更细，其设计经验对本课题的模块
设计更具参考价值。

工单类系统的做法最为成熟。郑若鹢的后勤报修系统覆盖报修提交、管理方审核、
短信派工、维修处理与服务反馈，并单列统计分析模块，按普通用户、维修人员、
后勤管理人员、系统管理员四类角色分权[8]。郭景等实现的 IT 工单系统给出更细的
状态字典——未提交、已提交待审核、问题已处理待验证、已归档，并规定用户确认
问题未解决时工单自动回退至原工程师重新处理，同时把「提交后编辑功能自动锁定」
作为防止流转中数据被改写的措施[9]。曹陈涵的研究面向运维工单的自动化管理[10]，
属摘要级证据。三者的共性在于「状态字典 + 处理留痕 + 审核节点」的组合，差异
在于回退路径与编辑权限的处理粒度。

预约类系统的核心议题是时间冲突与履约约束。王以伍等在实验室与仪器耗材预约
平台上预先设定各实验室的默认预约责任人与审批权限，使用方进入实验室后可查看
仪器的「可否预约」状态，再选择时段提交，由责任人审核[11]；其预约表以
开始时间与结束时间两个字段表达占用区间。陆向艳等的机房预约系统按管理员、
教师、学生三类角色分配权限，教师负责审核预约与发布公告，并按机房划分管理
范围[12]。王小豹等的座位预约系统把约束推到履约环节：管理员可签到签退，系统
设定定时任务，在规定时间内未签到或未签退的预约由系统自动判定为违规，且违规
信息表的数据来源于预约信息表并建立外键关系，以保证违规记录可回溯到具体预约
单据[13]。这一点提示预约系统的完整性不只取决于提交时的冲突校验，还取决于
到期未履约的处理。

租赁与居住关系类研究相对分散。何斌斌等面向制造企业的租赁车辆管理，以调度
模块与统计报表模块为核心，并针对纸质签批的退租流程实现一键退租[14]。胡龙等
从治安治理角度构建租住业态管理方案，以实人核验、数据共享与风险预警为主线，
提出「一端申报、一网通办」，并指出风险预警通知应附带整改建议或服务支持链接，
使处置与服务衔接[15]。薛元杰等则把房屋信息上链与智能合约执行租赁合同作为
技术路线[16]，其去中心化存证思路与本课题的纯软件边界不同，但「以留痕替代
信任」的问题意识值得注意。国际上亦有面向共享租赁的平台设计与应用研究[17]，
以及以 Spring Boot 与 Vue 实现合同全生命周期管理的研究[18]。
住宿登记方向，蒋晟等实现的宿舍管理系统覆盖入住与寝室交换、卫生与日常评级、
报修管理，并明确学生可查看报修信息是否审核成功[19]，其实质是把审核结果对
申请方透明化。

审批流程的实现方式存在明显分歧。丁福江等在访客管理系统中引入工作流引擎，
以业务主键关联流程实例与业务数据，使审批状态与业务数据解耦，并在自动审批
环节把「自动审批」作为处理意见写入任务完成记录；其驳回处理是把申请单退回
申请人修改或删除[20]。这一做法与「驳回即终态」的设计取向不同，选择哪一种
取决于业务是否允许申请方修正后重提。金明俐的叫号系统研究属摘要级证据[21]。
郭婷等的交互式分享平台研究[22]与国际期刊上的社区物业管理研究[23]的题名显示，
以 Spring Boot 为后端的管理类 Web 平台在国际期刊中同样存在，其业务域分别为
智慧社区物业、共享租赁、合同管理与攻略分享。需要重申的是，上述四条外文文献
均未取得全文与摘要，此处仅据题名判断研究方向，不引述其结论与技术水平。

### 2.3 现有研究的覆盖特征

把上述两类研究放在一起看，可以得到三点关于覆盖范围的认识，且这三点都限制在
本次检索与已读文献的范围内。

其一，场景粒度以「单一社区、单一组织」为主。多社区并存、并在同一部署实例内
按社区划分数据边界的系统设计，在所读文献中未见专门论述。

其二，角色模型以「管理员 + 普通用户」二元结构为主，少数研究扩展到三类
（管理员／教师／学生[12]、宿管／学生／管理员[19]、普通用户／维修人员／后勤
管理人员／系统管理员[8]）。其共同点是把服务提供方作为流程中的一个节点，
而非具有独立工作台、排班与能力标签的受派角色。

其三，业务链路彼此割裂。工单系统止于工单，预约系统止于预约，租赁研究止于
租赁，链与链之间的衔接——工单完成后的评价与不满意跟进、预约违约后的信用
处置、租赁协议与费用支付的先后约束——在所读文献中缺少贯通论述。

## 3 系统实现关键技术的研究现状

### 3.1 前后端分离架构与 Spring Boot、Vue

前后端分离是上述系统的共同架构基础。吴昌政以该架构为题作了框架层面的研究
[24]（摘要级）；刘子凡等以 Spring Boot 与 MyBatis 组合实现个人博客系统，
展示了该组合的快速开发能力[25]；时业茂等给出 Spring Boot 整合 Spring MVC 与
MyBatis-Plus 的编码方案并总结了一般性整合方法[26]；谢振华等以 Vue.js 与
Spring Boot 实现教务管理系统，实践了组件化页面与接口交互[27]；王科翔等、
胡金宇、田海晴分别在智慧学习、企业绩效考核与共享运营场景中采用同类组合
[28][29][30]；伦康等采用 Spring Boot 3 与 Vue 3 实现管理系统，并在其中引入
加权评分的位置推荐算法，以训练集、网格搜索与混淆矩阵验证效果[31]，是所读
文献中少数给出算法验证闭环的研究。

这些文献的一致结论是：Spring Boot 以约定优于配置、自动配置与内嵌容器降低
后端工程的搭建与部署成本；Vue 以组件化与响应式数据绑定改善前端开发效率；
两者经 RESTful 接口与 JSON 契约衔接后可并行开发、独立部署。差异主要在持久层
（JPA、MyBatis、MyBatis-Plus）与前端组件策略（自写组件库或成熟组件库）。
从工程组织角度看，所读文献多以「Controller—Service—Mapper」分层并据此归位
各层职责[26]，但对同一后端同时服务多类端（游客、居民、服务人员、管理员）时，
工程目录与职责如何按端划分，讨论较少。

### 3.2 认证与授权

认证授权是前后端分离系统的必要环节，其技术路线已相当收敛。申正阳等以 JWT
承载用户身份与服务权限，提出加密存储、解密使用以及 IP 与令牌绑定的安全策略，
并以图数据库存储权限关系、以位图法加速校验[32]；雷云祥等提出「集中认证、
分散鉴权」的分布式权限控制模式[33]；卢万有把 JWT 与 RBAC 结合，给出令牌签发、
请求拦截器统一携带、角色菜单动态加载的实现路径，并针对异地登录后原令牌无法
撤回的问题提出在用户表增加登录版本号、由筛选器比对版本使旧令牌失效[34]；
何立富围绕 Spring Security 的过滤器链构建权限体系，以自定义表达式按请求 URI
完成功能级鉴权，并强调用户权限变动时必须及时更新缓存，否则会出现令牌未过期
而权限已变的窗口[35]。陈海锋等指出前后端分离后受保护对象已从页面变为接口，
主张以接口资源表与角色—接口关联建模，并配合前端动态路由与路由守卫作双校验
[36]；王勇等给出权限树的树形转换、菜单动态创建与按钮级权限校验的具体实现
[37]；魏郧华把 RBAC 应用于作业管理场景，讨论了角色设计与数据安全的结合[38]。

在所读文献中，较常见的做法由四部分组成：无状态令牌承载身份、角色模型聚合权限、
框架级过滤器或表达式作统一入口、缓存与失效补偿解决性能与一致性。共同的前提
是「一个用户属于一个组织」；当同一角色在不同范围内可见不同数据时，权限维度
需要从「角色—接口」扩展到「角色—数据范围」，这一层在所读文献中讨论较少。

### 3.3 缓存与并发控制

Redis 在本类系统中承担两类职责：缓存高频读取数据与实现分布式互斥。王栋柱等
系统论述了基于 Redis 与 Lua 脚本的分布式锁设计，覆盖锁的原子获取与释放、
持有者标识比对、过期与续期、死锁检测等关键点，其目标场景是同一任务在多节点
下只被执行一次以及有限资源的并发竞争控制[39]。就社区服务场景而言，定时任务
防重入、预约名额与工单派单等环节都存在同类问题。

值得指出的是，分布式锁解决的是「同一时刻只有一个执行者」，并不能替代数据的
唯一性约束。所读文献对并发控制的讨论多集中于锁机制本身，对「数据库层唯一约束
与应用层锁」的双重保障、以及约束冲突时的事务回滚与用户提示，论述相对有限。

### 3.4 实时消息推送与离线补偿

消息推送的选型在文献中已有较为清晰的比较。蒋凌燕的系统性比较指出，短轮询
结构简单、易于实现，但实时性较差且服务器负载较大，适用于客户端数量少、消息
频率低的场景；WebSocket 在客户端与服务器之间建立长连接，是全双工通信，实时性
较好，常用于聊天、协作与实时推送系统[40]。王龙军等以 Redis 与 WebSocket 实现
图书馆数据推送，并在连接管理上明确同一用户重连时以新连接替换旧连接，同时
采用实时数据走长连接、非实时数据走 HTTP 的双通道协同[41]。徐智勇等设计的
独立推送系统把心跳检测、离线消息补发、安全加密与消息推送并列为功能需求，
明确规定连接不存在时把待推送消息存入数据库并在客户端重连后按序补发，同时
以心跳判定连接健康状态[42]。

三者合起来给出了一个可复用的组合：长连接负责实时性，落库负责不丢失，重连
补发负责失败恢复，心跳负责感知断连并决定降级时机。现有研究较少讨论的是，
长连接持续期间用户权限被撤销或账号被冻结时，订阅通道如何即时失效；以及在
推送结果需要审计时，推送状态如何回写并与补拉游标保持一致。

### 3.5 数据可视化

季玉洁等基于 ECharts 实现自然资源大数据可视化，采用 Vue 与 ECharts 组合，
以地图与图表结合的方式呈现分析结果，并借助时间轴组件在多个图表配置间切换
[43]。其价值在于图表组织方式而非具体业务：把多源指标聚合为可组合的图表单元，
并按主题切换。对本课题而言，运营统计需要同时满足「按社区筛选」「按时间范围
统计」与「按角色可见范围」三项约束，而这三项的组合在所读文献中未见系统讨论；
何斌斌等提出的「管理员看全部、使用人只看自己所驾车辆、可选时间段」的统计
口径[14]，是较接近的表述。

## 4 关键设计问题上的研究缺口

在本次检索范围与已读文献之内，可以识别出四个缺少直接可复用论述的设计问题。

**多社区层级与数据隔离。** 社区管理的数据天然分层（社区—楼栋—单元—房屋），
且管理方往往同时管理多个社区。既有权限研究以「角色—接口／菜单」为主轴
[34][35][36][37]，其隐含前提是单一组织。把社区标识作为数据维度的第二重约束，
并在查询层统一注入而非在业务代码中逐处过滤，尚未见到完整论述。

**连续时段预约与并发抢占的一致性。** 预约研究已普遍采用「时段 + 状态 + 审核」
的结构[11][12]，并以签退签到与定时任务处理履约[13]。但把相邻时段合并为一次
预约、以及在提交峰值下由数据库唯一约束兜底而非仅靠应用层检查的做法，在所读
文献中未见展开；王以伍等的预约表虽以起止时间表达区间[11]，其文中未讨论区间
重叠的判定与并发冲突的处理。

**服务闭环与评价回流。** 工单研究已把「处理—确认—回退」做成闭环[9]，并有
研究把维修量统计与人员评价作为管理支撑[8]。但评价结果如何回流到派单决策、
不满意如何触发跟进、以及异步的会话式沟通（反馈、群聊）如何与结构化的工单
流转并存，缺少系统设计层面的讨论。

**居住关系生命周期与资金、协议边界。** 租赁研究多把重点放在流程效率（一键
退租[14]）或技术路线（上链与智能合约[16]），对「入住申请—审核—协议确认—
费用支付—生效—续约—退租—押金退还—归档」这一完整生命周期中的状态约束、
以及协议确认的法律效力边界与押金资金归属规则，缺少明确论述。薛元杰等以
技术手段替代信任[16]，胡龙等把治理诉求外化为预警与联动[15]，两者都指向同一
问题域，但都未给出纯软件系统内的边界划分。

## 5 述评

综合上述文献可得到三点判断，均以本次检索范围与已读文献为限。

**技术路线已高度成熟。** Spring Boot 与 Vue 的前后端分离组合、基于 JWT 与
RBAC 的认证授权、Spring Security 过滤器链与表达式鉴权、Redis 缓存与分布式锁、
WebSocket 长连接配合落库与补拉、ECharts 组件化图表，在本类系统中都有可复用的
工程实践与文献支撑[24][26][31][34][35][39][40][42][43]。技术选型的风险主要
不在可行性，而在如何把上述机制与具体业务约束正确组合。

**业务覆盖呈现碎片化。** 综合类系统覆盖面广但深度有限，其数据模型多为扁平的
「一模块一表」[1]，且作者自陈在支付与多部门协作流程上存在短板[3]；专题类
系统在单条链上更细致，但链与链之间缺少衔接。把房屋与居住关系、服务工单、
公告与反馈、公共资源预约、房源展示与看房预约、服务评价与运营统计纳入同一
系统，并让它们共享同一套角色、权限与状态约束的研究，在已读文献中尚不多见。

**若干设计问题缺少专门论述。** 即第 4 节所列的四项：多社区数据隔离、连续时段
预约与并发一致、服务闭环与评价回流、居住关系生命周期与资金／协议边界。

据此，本课题的定位是：以成熟的 Spring Boot 与 Vue 前后端分离架构为基础，
面向游客、居民、服务人员、社区管理员与超级管理员五类角色，设计并实现一个
多社区的居住服务管理系统；以状态机约束工单、租住、资源预约与看房预约等核心
业务的流转，以功能级权限与数据级权限两级模型实现社区维度的数据隔离，以
「结构化流转 + 会话式沟通」两条路径组织服务事项，并在协议确认、押金退还等
敏感环节明确系统能力的边界。课题不追求在通用技术上提出新方法，其价值在于
面向上述四项缺口给出可运行、可验证的工程方案。

## 6 结语

国内外文献表明，社区居住服务管理的信息化在技术层面已有充分积累，在业务层面
则以单场景系统为主。本课题从业务综合性与多社区数据隔离两处切入，技术路线
与研究范围均有文献依据；同时，本综述所依据的 4 篇外文文献未取得全文，7 篇
学位论文仅有摘要，相关结论的适用边界已在正文中逐处说明，后续取得全文后
需要复核并可能修正其中关于国际研究现状的判断。
