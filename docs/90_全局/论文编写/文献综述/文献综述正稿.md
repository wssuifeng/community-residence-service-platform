**课题名称：基于SpringBoot的小区居住服务管理系统设计与实现**

## 1 引言

城市居住小区的日常管理涉及房屋与配套设施台账、居住人员关系、报修与服务事项
处理、公共资源使用安排、公告通知与居民诉求等多类信息。多数管理方长期以纸质
台账、电子表格、电话与即时通讯群组分散记录，信息更新滞后、居住关系难以追溯、
服务处理过程不可复盘、资源预约冲突频发等问题普遍存在。把这类业务收敛到统一的
信息系统，在智慧小区建设背景下已成为明确需求，随之而来的是软件工程层面的问题：
如何在一个系统中同时承载多条业务链、如何约束各条链的流转、如何在多小区场景下
保证数据边界。

为确定研究切入点，本文对国内相关文献作综述。检索以中国知网（CNKI）为主渠道，
以「小区／物业／居住管理 + 管理系统」「Spring Boot／Vue + 管理系统」
「JWT／RBAC／权限控制」「Redis／分布式锁」「WebSocket／消息推送」「预约系统／
工单管理／租赁管理」等主题词组合检索，检索时间窗设定为 2021—2025 年。纳入本
综述并实际读到全文的文献共 36 篇：中文期刊论文 33 篇、学位论文 3 篇。年度分布
为 2019 年 1 篇、2021 年 3 篇、2022 年 1 篇、2023 年 8 篇、2024 年 10 篇、
2025 年 13 篇；2021 年及以后共 35 篇，占 97.2%。唯一一篇 2019 年的学位论文
（付昌昌）因业务域与本课题最为接近，作为背景文献纳入。

需要说明阅读条件的限制，这决定了本文的论证强度：36 篇中 30 篇原件有可检索
文本层；另外 6 篇原件为扫描图像、无文本层，经逐页渲染成图后阅读（期刊 3 篇：
陆向艳 2025、王科翔 2023、季玉洁 2025；学位论文 3 篇：付昌昌 2019、
包添文 2023、曹陈涵 2023），图表与个别字词存疑处以原 PDF 为准。学位论文的

## 2 小区居住服务管理信息化的研究现状

### 2.1 面向小区与物业的综合管理系统

综合类系统是数量最多的一类，其共同目标是把管理方分散的事务集中到同一平台上。
在业务构成上，这类系统的功能谱系高度相似：以房屋、居民等基础信息登记为底座，
叠加报修、投诉、公告等事务处理，再视需要配置费用与车位管理。张艳军等以居民
信息为核心构建平台，功能覆盖居民信息增删改查、房屋管理、车位管理、物业费用
管理、设备报修与留言管理[1]；闫俊甫等实现的小区物业系统在此之上增加了物业
人员管理与统计报表[2]；杨玉等按小区、房产、设备、业主、服务、车位组织模块[3]；
吴嘉炜等把重心放在小区服务侧，以志愿活动报名、留言交流与小区新闻发布为主要
业务[4]；李乐健等面向移动端，将人员出入管理、物资需求管理与打卡签到作为主要
功能[5]。

两篇学位论文给出的综合系统设计更为完整。付昌昌把小区物业综合服务系统划分为
基础信息管理、物业服务与系统管理三大模块：基础信息管理负责小区、楼栋、住户等
基础数据，物业服务模块为居民提供通知公告、投诉建议与物业缴费，系统管理模块
负责登录、登出与个人信息维护；居民端采用微信小程序，面向系统管理员、物业管理
员与小区商家的管理端采用 Vue.js，后端为 Spring Boot 与 MyBatis[6]。包添文把
小区管理系统拆为居民、房屋、车位、缴费、小区服务、小区居民操作六个模块，其中
居民管理系统进一步分为「访问控制」与「居民信息维护」两部分——前者由管理员做
身份验证并设置不同用户权限以限制可访问的信息与功能，后者做居民信息增删改查
[7]。值得注意的是其缴费模块设置了人工核销环节：管理员核对居民已缴费后，才把
缴费状态改为「已缴费」[7]。

从设计方法看，这类系统普遍采用表现层、业务逻辑层、数据层三层结构[1]，技术
选型集中于 Spring Boot 与 Vue，组件库多取 Element UI 一类成熟方案[2]。包添文
则把架构细分为视图层、控制层、业务逻辑层与持久层四个逻辑层，并明确各层之间
只通过接口交互，以便更换数据库时只改持久层[7]。值得进一步注意的是数据建模的
粒度：有研究明确采用「每个模块对应一张数据表、表之间通过外键关系关联」的扁平
设计[1]，未引入状态机、时段约束或字段级变更留痕。这一取舍在功能规模有限时是
合理的，但当业务需要在同一条记录上表达多阶段流转、并对流转过程追责时，扁平
结构会显得不足。

更直接的对照来自作者自陈的局限。杨玉等在结语中承认系统未实现具体支付功能，
并指出投诉与维修管理缺少对复杂问题的多级处理流程，当任务需要多个部门协作时
支持有限[3]。这两点恰好对应本课题需要正面处理的问题：涉及资金与协议的环节
如何在系统内表达，以及跨角色的服务事项如何在一个流程内闭环。包添文的缴费核销
虽已落地，但仍是「线下缴费 + 线上确认」的半人工形态[7]，并不构成在线支付。

### 2.2 面向单一业务链的专题系统

与综合类系统相对，专题研究把单条业务链做得更细，其设计经验对本课题的模块
设计更具参考价值。

工单类系统的做法最为成熟。郑若鹢的后勤报修系统覆盖报修提交、管理方审核、
短信派工、维修处理与服务反馈，并单列统计分析模块，按普通用户、维修人员、
后勤管理人员、系统管理员四类角色分权[8]。郭景等实现的 IT 工单系统给出更细的
状态字典——未提交、已提交待审核、问题已处理待验证、已归档，并规定用户确认
问题未解决时工单自动回退至原工程师重新处理，同时把「提交后编辑功能自动锁定」
作为防止流转中数据被改写的措施[9]。两者的共性在于「状态字典 + 处理留痕 +
审核节点」的组合，差异在于回退路径与编辑权限的处理粒度。郭景等的方案建立在
eladmin 代码生成框架之上，其论文亦说明开发者借此将精力集中于状态流转与角色
权限等核心业务逻辑[9]。

曹陈涵的学位论文把工单研究的重心从流转推到了智能分配与根因分析：其系统先由
监控系统按阈值判定异常、生成工单，再经根因分析确定初步原因，然后按推荐序列
把工单分配给运维专家，当前专家无法解决时继续分配下一位，已解决的工单回流到
数据库用于更新后续的推荐与根因分析模型[10]。该文指出两个具有普遍性的问题：
一是传统基于历史转派关系与工单相似度生成的推荐序列，其中的专家彼此高度相似，
一旦首位专家解决不了，后续几位往往同样解决不了，导致处理时间延长；二是仅依据
工单文本判定异常节点、未利用系统节点之间的关系特征，根因分析效果受限[10]。
这两点提示，工单系统的价值不只在流转是否闭环，还在于「派给谁」这一步是否有
可解释的依据。

预约类系统的核心议题是时间冲突与履约约束。王以伍等在实验室与仪器耗材预约
平台上预先设定各实验室的默认预约责任人与审批权限，使用方进入实验室后可查看
仪器的「可否预约」状态，再选择时段提交，由责任人审核[11]；其预约表以开始时间
与结束时间两个字段表达占用区间。陆向艳等的机房预约系统按管理员、教师、学生
三类角色分配权限，教师负责审核预约与发布公告，并按机房划分管理范围[12]。
王小豹等的座位预约系统把约束推到履约环节：管理员可签到签退，系统设定定时
任务，在规定时间内未签到或未签退的预约由系统自动判定为违规，且违规信息表的
数据来源于预约信息表并建立外键关系，以保证违规记录可回溯到具体预约单据[13]。
这一点提示预约系统的完整性不只取决于提交时的冲突校验，还取决于到期未履约
的处理。

租赁与居住关系类研究相对分散。何斌斌等面向制造企业的租赁车辆管理，以调度
模块与统计报表模块为核心，并针对纸质签批的退租流程实现一键退租[14]。胡龙等
从治安治理角度构建租住业态管理方案，以实人核验、数据共享与风险预警为主线，
提出「一端申报、一网通办」，并指出风险预警通知应附带整改建议或服务支持链接，
使处置与服务衔接[15]。薛元杰等则把房屋信息上链与智能合约执行租赁合同作为
技术路线[16]，其去中心化存证思路与本课题的纯软件边界不同，但「以留痕替代
信任」的问题意识值得注意。住宿登记方向，蒋晟等实现的宿舍管理系统覆盖入住与
寝室交换、卫生与日常评级、报修管理，并明确学生可查看报修信息是否审核成功
[17]，其实质是把审核结果对申请方透明化。

审批流程的实现方式存在明显分歧。丁福江等在访客管理系统中引入工作流引擎，
以业务主键关联流程实例与业务数据，使审批状态与业务数据解耦，并在自动审批
环节把「自动审批」作为处理意见写入任务完成记录；其驳回处理是把申请单退回
申请人修改或删除[18]。这一做法与「驳回即终态」的设计取向不同，选择哪一种
取决于业务是否允许申请方修正后重提。

### 2.3 现有研究的覆盖特征

把上述两类研究放在一起看，可以得到三点关于覆盖范围的认识，且这三点都限制在
本次检索与已读文献的范围内。

其一，场景粒度以「单一小区、单一组织」为主。多小区并存、并在同一部署实例内
按小区划分数据边界的系统设计，在所读文献中未见专门论述。付昌昌与包添文的系统
虽都以「小区」为业务单位，其设计与实现均围绕单一管理方展开[6][7]。

其二，角色模型以「管理员 + 普通用户」二元结构为主，少数研究扩展到三类
（管理员／教师／学生[12]、宿管／学生／管理员[17]、普通用户／维修人员／后勤
管理人员／系统管理员[8]）。其共同点是把服务提供方作为流程中的一个节点，
而非具有独立工作台、排班与能力标签的受派角色。曹陈涵的系统虽把专家推荐作为
核心议题，其专家仍是待分配的候选人集合，未展开为具有可管理属性的组织实体[10]。

其三，业务链路彼此割裂。工单系统止于工单，预约系统止于预约，租赁研究止于
租赁，链与链之间的衔接——工单完成后的评价与不满意跟进、预约违约后的信用
处置、租赁协议与费用支付的先后约束——在所读文献中缺少贯通论述。

## 3 系统实现关键技术的研究现状

### 3.1 前后端分离架构与 Spring Boot、Vue

前后端分离是上述系统的共同架构基础。刘子凡等以 Spring Boot 与 MyBatis 组合
实现个人博客系统，展示了该组合的快速开发能力[19]；时业茂等给出 Spring Boot
整合 Spring MVC 与 MyBatis-Plus 的编码方案并总结了一般性整合方法[20]；
谢振华等以 Vue.js 与 Spring Boot 实现教务管理系统，实践了组件化页面与接口
交互[21]；王科翔等在智慧学习平台中采用同类组合[22]；伦康等采用 Spring Boot 3
与 Vue 3 实现管理系统，并在其中引入加权评分的位置推荐算法，以网格搜索优化
超参数、以决策树与混淆矩阵验证模型效果[23]，是所读文献中少数给出算法验证
闭环的研究；韦彩仁等基于 Vue 3 与 Spring Boot 实现学生信息管理系统，并在
需求分析一节给出按「角色×模块×功能项」组织的角色权限关系表[24]，把权限
落到具体功能点而非笼统的角色划分。

这些文献的一致结论是：Spring Boot 以约定优于配置、自动配置与内嵌容器降低
后端工程的搭建与部署成本；Vue 以组件化与响应式数据绑定改善前端开发效率；
两者经 RESTful 接口与 JSON 契约衔接后可并行开发、独立部署。差异主要在持久层
（JPA、MyBatis、MyBatis-Plus）与前端组件策略（自写组件库或成熟组件库）。
从工程组织角度看，所读文献多以「Controller—Service—Mapper」分层并据此归位
各层职责[20]，但对同一后端同时服务多类端（居民、服务人员、管理员）时，
工程目录与职责如何按端划分，讨论较少。Farshidi 等从方法论层面提出把架构知识
结构化为可复用的决策模型，使设计模式的选型依据可被记录与追溯[25]，这为本课题
把分层、权限与状态机的选型理由写入设计文档提供了依据。

### 3.2 认证与授权

认证授权是前后端分离系统的必要环节，其技术路线已相当收敛。申正阳等以 JWT
承载用户身份与服务权限，提出加密存储、解密使用以及 IP 与令牌绑定的安全策略，
并以图数据库存储权限关系、以位图法加速校验[26]；雷云祥等提出「集中认证、
分散鉴权」的分布式权限控制模式[27]；卢万有把 JWT 与 RBAC 结合，给出令牌签发、
请求拦截器统一携带、角色菜单动态加载的实现路径，并针对异地登录后原令牌无法
撤回的问题提出在用户表增加登录版本号、由筛选器比对版本使旧令牌失效[28]；
何立富围绕 Spring Security 的过滤器链构建权限体系，以自定义表达式按请求 URI
完成功能级鉴权，并强调用户权限变动时必须及时更新缓存，否则会出现令牌未过期
而权限已变的窗口[29]。陈海锋等指出前后端分离后受保护对象已从页面变为接口，
主张以接口资源表与角色—接口关联建模，并配合前端动态路由与路由守卫作双校验
[30]；王勇等给出权限树的树形转换、菜单动态创建与按钮级权限校验的具体实现
[31]；魏郧华把 RBAC 应用于作业管理场景，讨论了角色设计与数据安全的结合[32]。

外文研究把讨论推进到「令牌有效是否等于身份可信」这一层。Bučko 等指出 JWT
本身不携带用户历史行为信息，因而提出在令牌校验链路上叠加行为历史评分：把密码
尝试次数、IP 一致性、User-Agent 类型等因子各自赋权、累加为账户可信度，并在
每次交易后更新，实现于 .NET 与 PostgreSQL 环境[33]。该思路与本课题的会话
失效策略指向同一问题——令牌未过期并不等于当前会话可信。Uddin 等从访问控制
的动态性切入，指出现有模型是静态的、缺少动态职责分离与任务实例级的职责分离，
提出以授权工作流与任务—角色模型支持实时访问决策[34]。Butt 等在电子健康云
场景中用信任机制加权优化 RBAC 的授权决策[35]。三者共同说明：角色模型解决
「谁能做什么」，但「在什么条件下、基于多少信任」这一维度正在被单独建模。

在所读文献中，较常见的做法由四部分组成：无状态令牌承载身份、角色模型聚合
权限、框架级过滤器或表达式作统一入口、缓存与失效补偿解决性能与一致性。
共同的前提是「一个用户属于一个组织」；当同一角色在不同范围内可见不同数据时，
权限维度需要从「角色—接口」扩展到「角色—数据范围」，这一层在所读文献中
讨论较少。

### 3.3 缓存与并发控制

Redis 在本类系统中承担两类职责：缓存高频读取数据与实现分布式互斥。王栋柱等
系统论述了基于 Redis 与 Lua 脚本的分布式锁设计，覆盖锁的原子获取与释放、
持有者标识比对、过期与续期、死锁检测等关键点，其目标场景是同一任务在多节点
下只被执行一次以及有限资源的并发竞争控制[36]。就小区服务场景而言，定时任务
防重入、预约名额与工单派单等环节都存在同类问题。

值得指出的是，分布式锁解决的是「同一时刻只有一个执行者」，并不能替代数据的
外文研究从另外三个角度补足了这条链。Fan 等指出两阶段提交（2PC）虽能保证强
一致与事务执行顺序的串行化，但在高并发、事务冲突频繁的多微服务场景下扩展性
不佳，瓶颈正在于「锁在事务全过程中被持有」，其提出的 2PC* 通过减少锁持有范围
提升并发度[37]。这一分析恰好解释了本课题在单库单体架构下的取舍：既然没有跨
服务的分布式事务边界，把一致性交给数据库事务与唯一约束、把并发控制交给 Redis
互斥，比引入 2PC 更合适。Giebas 等用静态源码分析检测多线程应用中的并发错误，
把并发缺陷类型系统化[38]，为并发测试用例应当覆盖哪些缺陷类型提供了依据。
Hassan 等从数据访问路径出发验证查询缓存对响应时间的改善，并讨论缓存位置与
失效策略[39]，与本课题 Redis 缓存层的设计动机一致。

值得指出的是，分布式锁解决的是「同一时刻只有一个执行者」，并不能替代数据的
唯一性约束。所读文献对并发控制的讨论多集中于锁机制本身或分布式事务协议
[36][37]，对「数据库层唯一约束与应用层锁」的双重保障、以及约束冲突时的事务
回滚与用户提示，论述相对有限。

### 3.4 实时消息推送与离线补偿

消息推送的选型在文献中已有较为清晰的比较。蒋凌燕的系统性比较指出，短轮询
结构简单、易于实现，但实时性较差且服务器负载较大，适用于客户端数量少、消息
频率低的场景；WebSocket 在客户端与服务器之间建立长连接，是全双工通信，
实时性较好，常用于聊天、协作与实时推送系统[40]。王龙军等以 Redis 与 WebSocket
实现图书馆数据推送，并在连接管理上明确同一用户重连时以新连接替换旧连接，
同时采用实时数据走长连接、非实时数据走 HTTP 的双通道协同[41]。徐智勇等设计的
独立推送系统把心跳检测、离线消息补发、安全加密与消息推送并列为功能需求，
明确规定连接不存在时把待推送消息存入数据库并在客户端重连后按序补发，同时
以心跳判定连接健康状态[42]。

三者合起来给出了一个可复用的组合：长连接负责实时性，落库负责不丢失，重连
补发负责失败恢复，心跳负责感知断连并决定降级时机。现有研究较少讨论的是，
长连接持续期间用户权限被撤销或账号被冻结时，订阅通道如何即时失效；以及在
推送结果需要审计时，推送状态如何回写并与补拉游标保持一致。

### 3.5 数据可视化

季玉洁等基于 ECharts 实现自然资源大数据可视化，采用 Vue 与 ECharts 组合，
以地图与图表结合的方式呈现分析结果，并借助时间轴组件在多个图表配置间切换
[43]。其价值在于图表组织方式而非具体业务：把多源指标聚合为可组合的图表单元，
并按主题切换。Bach 等从设计模式角度系统归纳了仪表板的组织方式，把数据、视图
与交互三个层面的常见做法整理为模式库，并说明模式选择与使用场景的对应关系[44]，
这比单一系统的实现经验更具通用性，可支撑看板的信息层级与交互设计。对本课题
而言，运营统计还需要同时满足「按小区筛选」「按时间范围
统计」与「按角色可见范围」三项约束，而这三项的组合在所读文献中未见系统讨论；
何斌斌等提出的「管理员看全部、使用人只看自己所驾车辆、可选时间段」的统计
口径[14]，是较接近的表述。

## 4 关键设计问题上的研究缺口

在本次检索范围与已读文献之内，可以识别出四个缺少直接可复用论述的设计问题。

**多小区层级与数据隔离。** 小区管理的数据天然分层（小区—楼栋—单元—房屋），
且管理方往往同时管理多个小区。既有权限研究以「角色—接口／菜单」为主轴
[28][29][30][31]，其隐含前提是单一组织。把小区标识作为数据维度的第二重约束，
并在查询层统一注入而非在业务代码中逐处过滤，尚未见到完整论述。

**连续时段预约与并发抢占的一致性。** 预约研究已普遍采用「时段 + 状态 + 审核」
的结构[11][12]，并以签到签退与定时任务处理履约[13]。但把相邻时段合并为一次
预约、以及在提交峰值下由数据库唯一约束兜底而非仅靠应用层检查的做法，在所读
文献中未见展开；王以伍等的预约表虽以起止时间表达区间[11]，其文中未讨论区间
重叠的判定与并发冲突的处理。

**服务闭环与评价回流。** 工单研究已把「处理—确认—回退」做成闭环[9]，并有
研究把维修量统计与人员评价作为管理支撑[8]；曹陈涵进一步说明派单依据本身可以
成为研究问题[10]。但评价结果如何回流到派单决策、不满意如何触发跟进、以及
异步的会话式沟通（反馈、群聊）如何与结构化的工单流转并存，缺少系统设计层面的
讨论。

**居住关系生命周期与资金、协议边界。** 租赁研究多把重点放在流程效率（一键
退租[14]）或技术路线（上链与智能合约[16]），对「入住申请—审核—协议确认—
费用支付—生效—续约—退租—押金退还—归档」这一完整生命周期中的状态约束、
以及协议确认的法律效力边界与押金资金归属规则，缺少明确论述。包添文的缴费
核销仍依赖人工比对[7]，薛元杰等以技术手段替代信任[16]，胡龙等把治理诉求
外化为预警与联动[15]，三者都指向同一问题域，但都未给出纯软件系统内的边界划分。
外文方面，Junaid 等针对土地管理的效率低、透明度不足与易被篡改问题，用区块链
实现租约与抵押的透明化管理，其动机同样是「传统系统复杂、易错、缺乏实时校验」
[45]——这与国内研究的关切一致，但同样把结论指向引入区块链，未回答不引入
区块链时纯软件系统能把边界划到哪里。

## 5 述评

综合上述文献可得到三点判断，均以本次检索范围与已读文献为限。

**技术路线已高度成熟。** Spring Boot 与 Vue 的前后端分离组合、基于 JWT 与
RBAC 的认证授权、Spring Security 过滤器链与表达式鉴权、Redis 缓存与分布式锁、
WebSocket 长连接配合落库与补拉、ECharts 组件化图表，在本类系统中都有可复用的
工程实践与文献支撑[19][20][23][28][29][36][40][42][43]。技术选型的风险主要
不在可行性，而在如何把上述机制与具体业务约束正确组合。

**业务覆盖呈现碎片化。** 综合类系统覆盖面广但深度有限，其数据模型多为扁平的
「一模块一表」[1]，且作者自陈在支付与多部门协作流程上存在短板[3]；专题类
系统在单条链上更细致，但链与链之间缺少衔接。把房屋与居住关系、服务工单、
公告与反馈、公共资源预约、房源展示与看房预约、服务评价与运营统计纳入同一
系统，并让它们共享同一套角色、权限与状态约束的研究，在已读文献中尚不多见。

**若干设计问题缺少专门论述。** 即第 4 节所列的四项：多小区数据隔离、连续时段
预约与并发一致、服务闭环与评价回流、居住关系生命周期与资金／协议边界。

据此，本课题的定位是：以成熟的 Spring Boot 与 Vue 前后端分离架构为基础，
面向居民、服务人员、小区管理员与超级管理员四类角色，设计并实现一个
多小区的居住服务管理系统；以状态机约束工单、租住、资源预约与看房预约等核心
业务的流转，以功能级权限与数据级权限两级模型实现小区维度的数据隔离，以
「结构化流转 + 会话式沟通」两条路径组织服务事项，并在协议确认、押金退还等
敏感环节明确系统能力的边界。课题不追求在通用技术上提出新方法，其价值在于
面向上述四项缺口给出可运行、可验证的工程方案。
