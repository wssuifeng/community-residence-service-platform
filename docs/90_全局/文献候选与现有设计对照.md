## 二、按链详述

### C4 工单链

文献候选 #1（回退循环）**直接撤销**——现有实现与郭景 §2.1 的设计逐点吻合
（强制反馈意见、回原处理人、状态表允许 TO_CONFIRM↔IN_PROGRESS 循环），
且与接口设计 §9.4.2.14 一致无漂移。这项转为**论文印证**：可在论文 5 章
引"同类系统亦有此设计"。

真正的缺口按严重度：
- **#3 服务人员不接收新工单通知**：现状是"管理员派单制"——新工单只通知
  管理员（设计使然），服务人员只能被动等派单。文献"过滤后定向推送"的
  前提是"要推"，所以这条的实质是**需求问题**：要不要让在班（排班过滤）
  且匹配类别/社区的服务人员收到新工单提醒？回答了这个问题才有"过滤"可谈。
- **#4 通知同步**：create 与业务同事务，好处是通知必达一致、坏处是推送
  慢会拖主接口。可折中为"仅 WebSocket 推送与渠道留痕挪出事务"
  （@Async/事务提交后回调），不整链 MQ 化——属架构权衡，须裁决。
- **#5 评价入派单**：四档已按 recommendLevel→负荷排序，把"评价聚合分"
  加为第三键是小工程；**双分项评价**（过程分+结果分）动表结构，须裁决。

### C7/C12 预约链

- **#6 超时自动判违约是本组最对症的确认缺口**：5 个定时任务无一扫描预约
  超时，违约全靠手动——与王小豹 §2.3 的自动化做法完全空白对上。落地即
  "新增一个定时任务 + 状态置违约 + 释放时段"，设施（Redisson/状态 VIOLATED）
  全部现成；唯一要裁决的是**触发语义**（超时多久判违约？判违约前要不要
  先通知？C7 与 C12 时限是否同口径？）。
- **#7 居民侧违约透明度**：软关联已有，但居民看不到自己哪条预约被判违约、
  无申诉通道——比"补外键"更值得做的是**居民端违约明细 + 申诉入口**
  （需求扩展，须裁决）。
- **#8 带看默认分配**：确认逐单手动；做成"社区或房源维度默认带看人"配置
  可减少待确认积压（需求扩展，须裁决）。
- 文献候选 #8 前半（预约前可约性展示）**已具备**（C7/C12 双域 available-slots
  + 前端月历/置灰消费），候选该部分撤销。

### C3 租住链

- **#10 押金处置规则矩阵**：退租审核（approve）只联动状态/房态/群聊，
  不涉押金；退金独立发起、金额自由输入。文献薛元杰"违约方×情形→资金
  归属"的确定性规则可落成"退租原因 × 押金处置"规则表（须裁决——涉及
  资金边界表述，按 v1.6 定义平台不计息不垫付，规则表只决定"退多少"，
  不引入资金池，边界安全）。
- **#2 租约侧字段白名单**：租约 ACTIVE 下 startDate/endDate/monthlyRent/
  deposit/remark 全可改（R62 字段级 diff 留痕是"事后审计"，不是"事前
  门控"）——文献郭景是事前门控。两者不冲突（留痕已有），补白名单属
  加固（须裁决）。
- **#9 深链缺口**：支付/协议类通知只落列表页。修法二选一：后端这两类
  通知的 sourceId 直接放 leaseId（前端 notificationNav 已支持按租约跳），
  或前端为这两类 sourceType 加映射——**纯工程细节**。
- **#11 dashboard 时间范围**：仅社区筛选+角色门禁，无时间参数（须裁决，
  优先级低）。

### C10 权限链

文献候选 #12/#13 **双双撤销**——这是本轮对照最大的"反向发现"：文献指出的
两个盲区，本项目**已经用更强机制覆盖**：
- 旧令牌失效：TokenRevocationService 用户级吊销时间戳 ≡ JWTVersion 效果，
  且覆盖面更广（改角色/冻结/改密/社区绑解绑全吊销）。
- 权限即时生效：变更即吊销强制重登，无"令牌未过期权限已变"窗口。

保留的真缺口：
- **#17 RefreshToken——文档承诺与实现直接冲突**（架构设计.md:74 vs 单令牌
  2h 无刷新端点）。两条出路：补实现（短效+静默刷新，顺便把 #14 IP 绑定
  一起权衡）或修文档（冻结文档，走变更流程）。**必须二选一，不能悬着**。
- #14 IP 绑定：缺失，安全加固备选（注意移动网漂移误伤，须做成开关）。

### C11 通知并发链

**#15 是"机制半成品"的典型**——最值得优先看的一组：
- pull 增量机制（seq 游标）完备、channel_log 表的 SUCCESS/FAILED 语义
  在 DDL 里设计好了，但两处没接上：失败不回写（表永远只有 SUCCESS）、
  重连不触发补拉（靠 30s 轮询兜底，重连后最长 30s 空窗）。
- 修复量级：`onConnect` 回调加一次 `refreshBaseline()`（一行级）+ 推送
  catch 里回写 FAILED+error_message（小工程）。**不动状态机不动需求**，
  是 19 项里实施成本最低、对症"通知同步状态反馈/失败恢复"最直接的两条。
- #16 前端清旧连接已具备，候选撤销；后端多端在线是有意设计。
- 心跳：未显式配置，靠 stompjs 默认 10s 心跳——可接受，记录印证即可。
